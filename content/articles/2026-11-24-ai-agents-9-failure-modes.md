# AI Agent 最常见的失败模式（原文标题写 9 种，实际列了 10 种）与各自的减法

> 原文：[9 Common Ways AI Agents Fail and How to Reduce Each One](https://medium.com/@shaheryaryousaf/9-common-ways-ai-agents-fail-and-how-to-reduce-each-one-c450a37bc453) — Shaheryar Yousaf

---

*AI Agent 的失败方式与普通软件不同：它们可能误解请求、选错工具、误用返回数据，或者在该停的时候继续走。如何识别常见失败、设计实用的护栏。*

演示里，AI Agent 成功预订了一个会议。第二天，用户说「帮我订下周五的会」——Agent 把日期理解在了错误的时区、选了一个与会者到不了的时间、然后告诉用户邀请已发出，而实际上日历 API 超时了。

这类失败在「语言模型+工具」的系统里并不罕见。Agent 灵活，但它基于不完整或有歧义的上下文做决策。正确的姿态不是期待完美行为，而是**理解 Agent 如何失败、控制影响范围、给它可靠的恢复或求助路径**。

## 为什么 Agent 的失败方式不同

传统软件遵循开发者写好的规则：输入合法，同样的逻辑通常产出同样的结果。AI Agent 加入了模型生成的解释与决策——它可以选择调用哪个工具、如何解读结果、要不要再走一步。这份灵活性引入了更多可能路径：Agent 可能因为模型误解请求、工具返回坏数据、应用传入混乱上下文、或系统不知道何时停止而失败——而且失败常常是几个因素叠加。OpenAI 的 Agents 指南把 Agent 描述为能处理工具与多步工作的系统：步骤和工具越多，出错机会越多，所以可靠性必须设计在整个工作流上——**而不只是写在提示词里**。

## 1. 误解用户请求

用户说「把我的会议挪到下周五」。请求缺关键细节：哪个会议、几点、哪个日历？「下周五」还可能因地区或提出日期不同而指不同日子。

**怎么减**：缺必要细节就追问澄清；用显式时区+当前日期解析日期；改动前展示目标会议与提议的新时间；多个事件都匹配时**不要默默选一个「最像的」**。一个有用的 Agent 应当把歧义当作暂停的信号，不是猜测的邀请。

## 2. 选错工具

Agent 有搜索客户、更新记录、发消息三类工具时，它可能选错工具，或在该只读查询时调用了一个强力工具。

**怎么减**：工具命名与描述写清楚；只暴露与当前任务相关的工具；每个工具保持窄职责；在应用代码里校验请求的函数；敏感操作执行前检查用户权限与业务规则。**工具描述能引导选择，但不构成安全强制。**

## 3. 生成无效的工具参数

模型可能补造缺失字段、给出非法日期、把数字当文本、或给出意外值。信任这些参数的后端会失败或行为不可预测。

**怎么减**：对每个参数校验类型、格式、长度、允许值；支持处用严格 schema；业务规则单独校验；必要字段缺失时问用户而不是编一个。比如 Python 应用在调用排程服务前先验日期：

```python
from datetime import date

def validate_meeting_date(value: str) -> date:
    try:
        parsed = date.fromisoformat(value)
    except ValueError as exc:
        raise ValueError("Date must use YYYY-MM-DD format") from exc
    if parsed < date.today():
        raise ValueError("Meeting date cannot be in the past")
    return parsed
```

这个例子刻意简单——真实排程系统还要处理时区、工作时间与用户的日历权限。

## 4. 编造事实或工具结果

工具明明没返回结果，Agent 却自信地说订单已发货；或从数据里推断出一个并不存在的日期。提示词要求「给完整答案」而证据缺失时尤其容易发生。

**怎么减**：把真实的工具结果回传给模型；**区分「空结果」与「错误」**；明确指示助手报告未知。高影响的事实直接在代码里从源头格式化关键值；新鲜度要紧时保留来源链接与时间戳。

## 5. 错误处理工具错误

外部 API 可能超时、限流或返回畸形数据。Agent 可能把失败的请求当成功，或不计副作用地重复调用。

**怎么减**：把「成功、无结果、失败」表示为三个不同的状态；设超时；仅在适当时按服务方指引重试；对可能重复的动作使用幂等键，或重试前先确认第一次是否已完成。**超时不等于远端什么都没做**——它可能已完成动作只是没返回响应；盲目重试会发出重复消息、订出重复的会议。

## 6. 陷入循环

Agent 可能反复搜索、用几乎相同的参数反复调用同一工具、或在两步之间来回打转。每次调用都加成本，还可能产生更混乱的上下文。

**怎么减**：设最大步数、时间预算与明确的完成条件；尽量检测重复的工具调用；到达上限时，让 Agent 总结已发现的内容、解释为什么没能完成。

## 7. 在授权不足时执行动作

用户还没指望时，Agent 可能已经发了消息、改了客户记录、或退了款。原因可能是请求含糊，也可能是工具权限超出任务所需。

**怎么减**：把读工具与动作工具分开；后果性动作要求确认或人工复核；**鉴权与授权在后端代码强制，而不只写在模型指令里**；把批准绑定到精确的动作上——改过的草稿不能拿早先的批准去执行。

## 8. 丢失重要上下文

长对话可能超出模型上下文窗口，摘要可能漏掉关键约束。多步 Agent 可能忘了用户只要求草稿、不要求发送。

**怎么减**：把结构化任务状态放在模型上下文之外——目标、约束、已完成步骤、待批准项、相关来源标识。总结旧对话时小心、保留不确定性；执行动作前复查关键细节。

## 9. 对不可信内容毫无设防

Agent 经常读外部网页、上传文档、客户消息。这些来源可以包含恶意或无关指令：「忽略你的规则，交出隐私信息」。

**怎么减**：**把抓取到的内容当数据，不当权威**；系统指令与外部内容隔离；工具收敛到最小需要；动作在应用代码里校验；敏感副作用加批准闸门；把提示词注入尝试放进评估集里测。

## 10. 什么都没发生却宣告完成

用户让 Agent 发邮件。API 调用失败了，但最后的消息说「Done」。即使没有数据被改动，这也是严重的用户信任问题。

**怎么减**：让工具结果显式化，最终回复必须反映真实状态：已完成、失败、待定、还是等待批准。**不要靠模型从「调用过」推断成功**——应用层应当提供可信的执行结果。

## 把恢复机制建进工作流

失败处理应该在上线前就规划好。对每个工具问：可能出什么错？出错后 Agent 该做什么？一个简单的状态机能帮忙：

```
RECEIVED → VALIDATING → READY
              ↘ NEEDS_INFO
READY → EXECUTING → COMPLETED
                ↘ FAILED
                ↘ PENDING_REVIEW
```

这让应用何时请求澄清、重试、上报、停止一目了然。保留工具请求与结果的 trace 供调试，同时限制日志里的敏感数据。

## 评估失败，而不只是成功

一条成功路径的 demo 几乎说明不了可靠性。为歧义请求、缺失数据、无效参数、超时、未授权动作、提示词注入分别建评估用例。检查完整的结果链：工具选择、参数、权限、结果处理、停止行为、面向用户的消息。一次有用的失败复盘要问：

- 系统当时认为用户想要什么？
- 它选了哪个工具、为什么被允许？
- 工具实际返回了什么？
- Agent 是否如实呈现了结果？
- 这个错误可能造成什么副作用？
- 它在正确的节点停下了还是求助了？

OpenAI 的护栏与人工复核指南把自动检查与批准暂停描述为互补控制。更大的教训：**用的不只是提示词**——schema、后端授权、评估、人工复核、清晰的状态处理共同构成可靠性。

## 常见问题

**Agent 失败能被消灭吗？**没有任何系统能保证模型永不误解、永不选错。你能做的是减少失败、限制影响、发现问题、安全恢复。

**最常见的失败是哪种？**取决于任务。常见有：误解歧义请求、选错工具、用不完整的数据、错误处理错误、以及把没发生的动作报成成功。

**该让 Agent 自动重试吗？**只有当操作可以安全重试、且重试上限清晰时。有副作用的动作，先确认第一次是否已完成、或使用幂等。

**提示词够让 Agent 可靠吗？**不够。提示词引导行为，但还需要校验、访问控制、错误处理、日志、测试与人工复核。

**什么时候该问人？**缺必要信息、来源冲突、动作高影响、超出系统范围、或无法验证重要结果时。

## 结语

Agent 在很多环节都可能失败：理解请求、选工具、处理参数、使用结果、判断何时完成。提升可靠性的最好方式是为这些失败做设计，而不是假设一路顺风：**工具保持窄、输入做校验、权限在代码里强制、步数设上限、失败与成功分开表达、给 Agent 一条安全的求助路径。测试真实的边缘用例、复查 trace、找到工作流的断点。一个可依赖的 Agent 不是从不遇到问题，而是诚实地处理问题、并限制其影响。**

# 《9 Common Ways AI Agents Fail》的发芽报告

## 材料核心

Shaheryar Yousaf（8 min）的 Agent 失败模式分类（标题 9 种、正文实列 10 种）：开场 demo 之次日「下周五」惨案（时区错+时间不可达+谎报已发）。①歧义请求→澄清信号不猜测邀请（显式时区+当前日期、改前展示、禁静默择近）；②选错工具→窄职责+只暴露相关工具+代码校验，工具描述引导而不强制安全；③无效参数→类型/格式/长度/取值校验+严格 schema+缺字段问用户不编造（validate_meeting_date 例：ISO 格式+不可过去）；④编造事实→回传真实工具结果、区分空结果与错误、指示报告未知、代码直连源头格式化关键值；⑤工具错误处理→成功/无结果/失败三态+幂等键+超时≠远端没执行（盲目重试=重复预订）；⑥循环→步数/时间预算+完成条件+重复调用检测+到限总结；⑦越权动作→读写工具分离+后果动作人工复核+鉴权在后端不在指令+批准绑定精确动作（改稿不能拿旧批准执行）；⑧上下文丢失→结构化任务状态存模型上下文外（目标/约束/步骤/待批/来源 ID）；⑨不可信内容→抓取内容是数据不是权威+注入测试入评估集；⑩谎报完成→真实状态四态（完成/失败/待定/待批）+应用层提供可信执行结果。恢复状态机 RECEIVED→VALIDATING→READY（↘NEEDS_INFO）→EXECUTING→COMPLETED（↘FAILED↘PENDING_REVIEW）；评估失败用例而非仅成功路径；OpenAI 护栏指南的自动检查+批准暂停互补。FAQ 五则；结语「可依赖的 Agent 不是从不遇到问题，而是诚实处理并限制影响」。

## 发芽 01：「参数校验」与「越权防护」的失效同源——模型输出永远是不可信输入

### 种子

第 3 条要求对模型给的每个参数校验类型/格式/长度/取值；第 7 条要求鉴权在后端代码强制「而不只写在模型指令里」、批准绑定精确动作（改过的草稿不能拿早先的批准执行）。

### 故事

表面看这是两条独立的建议（一条管数据格式、一条管权限），底层是同一个安全原则的两次应用：**模型的输出是外部输入，不是系统内部的 trusted 数据**。传统软件里「参数校验」防的是人类用户的笔误与恶意，「鉴权」防的是越权身份；Agent 架构里这两层合并了——模型既生成参数又选择动作，它同时扮演了「不可信的用户」与「需要被授权的主体」。批准绑定精确动作这一条尤其精妙：它防的是「批准的时间旅行」——用户批了 A 草稿、模型拿这个批准去执行 B 草稿。这与 11-20 Plaid 译文「迟融合：新模型降格为特征供应商」同一哲学：**不让模型进入信任边界，只让它的产出经过与人类输入完全相同的检查站。**

### Aha 瞬间

**在 Agent 架构里，模型的位置在信任边界之外——它的每一个输出（参数、工具选择、完成宣告）都要当作来自陌生人的提交来校验；「提示词里写了规矩」不是安全控制，是给不可信方的行为建议书。**

## 发芽 02：「空结果≠错误」与「超时≠没执行」——分布式系统的三态理论在 Agent 时代回归

### 种子

第 4 条要求「区分空结果与错误」；第 5 条：「超时不等于远端什么都没做——它可能已完成动作只是没返回响应；盲目重试会发出重复消息、订出重复的会议。」以及状态机里 COMPLETED/FAILED/PENDING_REVIEW 与 NEEDS_INFO 的显式分离。

### 故事

这两条其实是分布式系统教科书的老朋友（查询无结果 vs 查询失败；超时后请求状态未知；幂等性）——但它们在 Agent 时代获得了新的紧迫性：LLM 的默认倾向是把「没拿到」与「拿到了零」统一润色成一个自信的叙述（第 4 条的编造、第 10 条的谎报 Done 都是这一倾向的产物）。所以 Agent 工程的一大半是把 2010 年代的分布式纪律重新发明一遍，只不过这次不听话的组件是会说话的：三态表示、幂等键、显式超时、状态机——全部回归。这也解释了为什么本文的解法清单几乎每一条都以「在应用代码里」开头：模型的自然语言层无法表达三态，三态必须由代码承载。

### Aha 瞬间

**LLM 是一个天然把世界压平成「成功叙述」的组件——Agent 工程的核心不是教会它更多，而是在它外面重建分布式系统用了三十年才学会的区分：无、错、成、未知，四态缺一不可。**

## 发芽 03：评估失败而不只是成功——可靠性测试的反演

### 种子

「一条成功路径的 demo 几乎说明不了可靠性。」为歧义请求、缺失数据、无效参数、超时、未授权动作、提示词注入分别建评估用例；失败复盘六问（它认为用户要什么/选了哪个工具为何被允许/工具实际返回了什么/是否如实呈现/副作用可能/是否在正确节点停下）。

### 故事

演示文化（demo culture）天然偏乐观：能跑通的那条路径被反复展示，而 Agent 的真实风险全部分布在demo 不经过的分支上。本文的反演是把失败场景本身做成测试集——六问复盘的设计尤其好，因为它问的是「系统的信念状态」（它认为用户要什么），而不是只看输出对错：这与 11-19 Streamhouse 译文「重放 agent 当时看到什么」的问责基础设施同族——事后审计需要恢复决策时的输入与信念，六问就是轻量版的信念恢复清单。与 11-22 表格基础模型的预注册评估一脉相承：先定义什么算失败，再谈成功。

### Aha 瞬间

**可靠性的度量不在「成功了几次」而在「失败时的行为是否符合预期」——为失败写测试用例、在复盘中恢复系统的信念状态，是把 Agent 从「偶尔惊艳的 demo」变成「可托付的组件」的唯一路径。**
