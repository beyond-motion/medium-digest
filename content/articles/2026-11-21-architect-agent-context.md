# 别再给 AI Agent 塞更多上下文了：开始架构它们收到的上下文

> 原文：[Stop Giving AI Agents More Context. Start Architecting the Context They Receive.](https://medium.com/@christian.sepulveda/stop-giving-ai-agents-more-context-start-architecting-the-context-they-receive-2deed868c4ad) — Christian Sepulveda

---

我们都经历过：让 AI 编码智能体实现一个功能，它开始探索仓库、读一堆文件、对架构做出假设，最后交付一个能跑的东西——或者至少看起来能跑。有时结果好得惊人；有时它无视既有约定、引入不必要的抽象、重复造已有的轮子，或者改动根本不属于原始请求的东西。

我们的常见反应是改进提示词、换模型、或者再换一个 AI IDE。但如果问题不在模型本身呢？如果我们没有给模型一个合适的工作环境呢？我认为 AI 辅助软件工程里最有趣的机会之一，不是找一个更好的模型，而是**围绕我们已有的模型构建一个更好的系统**。这就是「AI harness（智能体鞍具）」概念的意义所在。

## 什么是 AI harness

AI harness 是围绕模型的软件基础设施，决定它如何与世界交互：如何接收上下文、能用哪些工具、如何执行任务、如何处理反馈、必须遵守什么约束。想想 Cursor、Kiro、带 GitHub Copilot 的 VS Code——它们不是把你的提示词转发给 LLM 再显示回复，而是围绕模型提供完整环境：文件探索、终端访问、规划、代码生成、工具集成、智能体执行循环。这些组件全都影响最终结果。

实践上我把 harness 分两层。**内层 harness**是你所用的 AI 软件自带的基础设施——比如 Cursor 提供的理解仓库结构、读写文件、执行终端命令、规划任务、连接外部服务、管理智能体工作流的机制。同类工具能力相似但实现与工作流各异，这正是同一个模型在两个不同 AI 编码环境里产出差异明显的原因：模型重要，它运行的环境同样重要。**外层 harness**是我们在既有基础设施之上为适配自己工程需要而构建的一切：自定义指令与规则、skills 与可复用工作流、MCP 集成、护栏与校验机制、自定义工具与编排层、公司特有的约定与工程标准——让我们不必控制或替换底层 AI 软件就能定制智能体的行为。

这里有一个重要的要点：**要标准化智能体的产出，不一定要标准化它们内部的运作方式。**把外层 harness 对期望的行为与产出写得更明确，就能在不用工具、不用底层实现之间驱动一致性。这在工程师使用不同 AI 开发环境的组织里尤其有价值：我们可能无法强制统一内层，但仍能通过外层建立共同期望。

## 从简单开始：一组共同的规则

有几件事今天就能做，不需要什么秘方，也不必第一天就造一个复杂的编排平台。可以从简单得多的东西开始：一组通用规则，围绕我们期望智能体做什么——以及同样重要的、不希望它做什么——建立清晰边界。例如：

- 不经论证不引入新依赖；
- 不重新发明仓库里已有的功能；
- 遵循既有的架构模式与编码约定；
- 不改动无关文件；
- 为新功能写测试；
- 引入变更时更新相关文档；
- 在宣告任务完成前验证实现。

这些指令对有经验的工程师是常识，但对面对陌生代码库的 AI 智能体未必。目标是靠更好的上下文与更明确的期望来减少歧义和不必要的即兴发挥。当然我们可以把规则手动注入每次提示词，但那既繁琐又引入一致性问题——得指望每位工程师每次都记得带上同一套指令。我们需要让这些规则自动可用的更好方式。

## AGENTS.md：智能体指令的公共入口

一个务实的做法是 AGENTS.md——一个为编码智能体提供仓库级指令的约定，给我们一个地方描述智能体在特定代码库中应如何开展工作。我会从每个项目根目录至少放一个 AGENTS.md 开始。想法很简单：智能体接到任务后，应当在动手前先查阅项目指令。文件里可以放直接规则、引用其他指令文件、指向相关文档，或说明特定任务应使用哪些 skills。本质上它是智能体操作指令的入口。

举个例子：让智能体在既有仓库里实现新功能。没有任何项目指令时，它只能靠探索代码库、做假设来发现约定与架构。有了定义良好的 AGENTS.md，我们可以引导这个过程——指示它：实现变更前先读架构文档；找找仓库里有没有类似实现；遵循项目既有的编码与测试约定；保持 README 精炼、聚焦开发者需要的信息；把架构决策、监控要求、实现细节写进对应的专门文档；完成任务前验证变更并更新相关文档。注意：我们并没有告诉模型具体怎么实现功能——**我们建立的是帮它做出更好决策的护栏**。

还有一个重要设计决策：根 AGENTS.md 不必变成容纳组织所有规则的海量文档。它可以引用其他文件、把更具体的指令下放：

```
project/
├── AGENTS.md
├── docs/
│   ├── architecture.md
│   ├── monitoring.md
│   └── development.md
└── skills/
    ├── testing/
    ├── documentation/
    └── architecture/
```

根文件确立基线、把智能体引向相关信息。这比把同样的指令反复注入每条提示词可维护得多——AGENTS.md 成为共享指令系统的入口，而不只是又一个 Markdown 文件。

## 别把自己锁死在单一 AI 开发环境

这套做法的最大好处之一：我们不必强行统一每位工程师的 IDE 或 AI 助手。不同工具对 AGENTS.md 的支持程度不同——有的自动发现根目录与嵌套的指令文件；有的用自己的约定（CLAUDE.md、GEMINI.md），或需要额外配置才能加载共享指令。这个区别很重要：**核心工程指令应保持工具无关，只为个别工具需要处提供轻量集成或配置文件。架构应该属于项目，不属于某个 IDE。**这样工程师可以用不同工具，同时共享同一套工程期望。

## 下一步：别再暴露整个仓库的上下文

有根 AGENTS.md 给了智能体一个公共入口，但不意味着它每个任务都要消费、理解整个仓库的上下文。想一个包含多个服务的大型代码库：让智能体改支付服务时，它真的需要探索通知服务、用户管理和无关基础设施的全部细节吗？大概率不需要——它可能只需要仓库架构、文档、约定与实现细节的一小部分。

这就是可以更进一步的地方：**渐进式上下文加载**。不再只依赖一套全局指令，而是为每个服务或组件引入更小、更聚焦的指令文件、规则与 skills。比如支付服务可以有自己的 AGENTS.md，描述它的架构与主要组件、交易如何处理、测试约定、依赖与集成点、修改该服务时必须尊重的特定约束；通知服务可以有一套完全不同的指令。智能体做支付时就拿到支付专属的引导，而不是把仓库每个部分当成同等相关。

这带来两个好处：**更少的上下文噪声**——减少与任务无关的信息争夺模型注意力，帮它聚焦手头的事；**更相关的引导**——提供在目标服务内工作所需的具体知识、约束与约定。结果是一个分层的指令架构：全局指令（整个仓库通用的规则与期望）、服务级指令（每个服务相关的架构、约定、约束与文档）、任务级 skills 与规则（按工作类型提供的专门引导）。仓库结构可以长这样：

```
project/
├── AGENTS.md
├── services/
│   ├── payments/
│   │   ├── AGENTS.md
│   │   └── docs/
│   ├── notifications/
│   │   ├── AGENTS.md
│   │   └── docs/
│   └── users/
│       ├── AGENTS.md
│       └── docs/
└── skills/
    ├── testing/
    ├── documentation/
    └── architecture/
```

根文件确立全局期望，嵌套指令文件在仓库特定区域工作时提供补充引导；嵌套指令能否被发现取决于具体智能体（有的基于访问的文件自动发现，有的需要根文件显式引用）；skills 可再提供一层专门能力，发现与激活机制同样依智能体而异。重要的不是确切的目录结构，而是背后的原则：**别再把上下文当成我们「提供」给智能体的东西，开始把它当成我们「架构」、并按任务渐进暴露的东西。**

## 指令不是强制

最后一个值得区分的边界：智能体读了规则，不保证它会遵守。AGENTS.md 能引导行为、减少歧义、建立共同期望，但它不是安全边界，也不是合规保证。要更强的保证，需要额外的机制：**指令**告诉智能体该做什么；**hook 与权限**能限制或拦截某些动作；**自动化测试与 linter** 校验实现质量；**CI/CD 检查**阻止不满足要求的变更被合并。这些机制互补。我们不该指望提示词替代确定性校验，正如不该指望自动化测试替代好的工程判断。当引导与真正的校验结合，外层 harness 的威力会大得多。

## 结语：更好的上下文，更好的智能体

我们仍处在搞清如何把 AI 智能体恰当融入软件工程的早期。大量注意力放在选最好的模型、比较 IDE、找完美提示词上。那些重要，但还有一维不该忽视：**我们围绕模型构建的环境**。可以从小处开始——用 AGENTS.md 建立共享指令——再演进到按任务自适应的规则、skills、文档与校验机制的分层系统。我们不需要每个工程师用同一个 AI 工具，不一定需要控制每个智能体的内部运作，更不需要在看到价值之前先造一个复杂的编排平台。需要对提供的上下文、建立的边界、期望的产出保持刻意。因为归根结底，目标不是给 AI 智能体更多信息，而是确保它们拥有完成工作所需的**正确信息、正确约束与正确工具**。

# 《Stop Giving AI Agents More Context》的发芽报告

## 材料核心

Christian Sepulveda（9 min，gitconnected）论 AI harness 分层架构：问题常不在模型而在环境——Agent 探索仓库做假设，产出漂移；解法不是换模型/换 IDE/改提示词，是围绕已有模型建更好的系统。内层 harness=AI 工具自带基础设施（Cursor/Kiro/Copilot 的文件/终端/规划/执行循环，同模型不同环境产出不同）；外层 harness=自建层（规则/skills/MCP/护栏/约定），关键要点：标准化产出无需标准化内部运作——外层对行为与产出写明确即可跨工具一致性。落地路径：①一组通用规则起步（不乱引依赖/不造轮子/遵循约定/不动无关文件/写测试/更新文档/完成前验证）；②AGENTS.md 公共入口（根文件确立基线+引用下放，护栏式引导而非 how-to，成为共享指令系统入口而非普通 md）；③工具无关（核心指令不锁 IDE，CLAUDE.md/GEMINI.md 只是轻量集成）；④渐进式上下文加载（按服务嵌套 AGENTS.md：支付服务不需要通知服务的上下文——两层收益：少噪声+更相关引导；全局/服务/任务三层架构）；⑤指令不是强制：读了规则不保证遵守，非安全边界——hook/权限拦截、测试/linter 校验、CI/CD 门禁互补。

## 发芽 01：内层不可控，外层可规定——一致性的正确锚点

### 种子

「同一个模型在两个不同 AI 编码环境里产出差异明显」；「要标准化智能体的产出，不一定要标准化它们内部的运作方式。把外层 harness 对期望的行为与产出写得更明确，就能在不同工具、不同底层实现之间驱动一致性。」

### 故事

组织里推广 AI 编码的最大障碍常被误认为是「工具不统一」：A 用 Cursor、B 用 Copilot、C 用 Claude Code，产出风格各异。本文的解法是把一致性锚点从「控制输入侧（内层）」移到「规定输出侧（外层）」：与其强推一个 IDE，不如把「什么是完成、什么是合规」写进外层 harness——规则、护栏、校验机制对任何内层一视同仁。这是接口思维的翻版：内部实现自由，契约严格。附带的政治学收益是它把标准化从「行政命令」（人人换工具）降级为「工程约定」（人人守契约），执行成本低一个数量级。

### Aha 瞬间

**面对不可控的底层（模型、IDE、智能体内部运作），一致性不该追求于控制实现，而该追求于规定契约——「产出标准化」是比「工具标准化」更便宜也更稳固的锚点。**

## 发芽 02：渐进式上下文加载——上下文从「投喂」到「架构」

### 种子

「支付服务不需要通知服务的全部细节」；「别再把上下文当成我们提供给智能体的东西，开始把它当成我们架构、并按任务渐进暴露的东西」——按服务嵌套 AGENTS.md，全局/服务/任务三层，收益是少噪声+更相关引导。

### 故事

这与 10-17 译文（clara 的 context engineering 四招）同脉但更推进了一步：clara 讲的是「会话内」的上下文工程（offload/retrieve/isolate/reduce），本文把它落到了「仓库结构」上——上下文架构被物化为目录树：每个服务自己的 AGENTS.md+docs，根文件只做基线与路由。这其实是几十年来软件工程「信息 hides behind 接口」原则在 Agent 时代的重演：人工程师从来不需要同时加载整个 monolith 的知识，为什么要求 Agent 需要？注意力是稀缺资源，无关信息不是中性的，是竞争任务焦点的噪声。

### Aha 瞬间

**上下文管理的终局形态不是更大的上下文窗口，而是「按任务渐进暴露」的架构——知识不该被塞给智能体，该被挂在一个智能体按需走到的地方；目录树就是新的上下文 API。**

## 发芽 03：指令不是强制——引导层与执行层的分界线

### 种子

「智能体读了规则，不保证它会遵守。AGENTS.md 不是安全边界，也不是合规保证。」机制分层：指令告诉该做什么、hook/权限拦截动作、测试/linter 校验质量、CI/CD 阻止合并——互补而非替代。

### 故事

这是全文最容易被忽略却最关键的一节：许多人把「写了规则」当成「有了治理」。指令的作用域是引导（降低歧义、减少即兴），强制的作用域是确定性机制（hook、测试、门禁）。两者混淆的后果双向都有：把该写进 CI 的规则只写进 AGENTS.md，违规照样发生；把该写进 AGENTS.md 的判断写进死板的 hook，灵活性全失。与本文互证的是 11-12 译文《权重正在变成代码》的硬边界——编辑/约束只能移除障碍不能新增能力；指令同样是「移除歧义」的工具，不能凭空创造遵守的意志。

### Aha 瞬间

**Agent 治理的完整栈是四层且不可互相替代：指令负责「知道」、hook 负责「不许」、测试负责「验证」、CI 负责「守住」——任何一层被寄予另一层的期望，都会以静默的失守告终。**
