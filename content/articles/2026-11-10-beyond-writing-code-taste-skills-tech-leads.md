# 写代码之外：品味、技能与技术领袖

> 原文：[Beyond Writing Code: Taste, Skills, and Tech Leads](https://medium.com/google-cloud/beyond-writing-code-taste-skills-and-tech-leads-592049deaa5f) — Daniela Petruzalek

---

当基础模型把全世界的知识烤进了权重里，人类还剩什么？

几十年来，我们软件工程师的身份认同绑定在「写代码」这门手艺上：精通语法、背诵标准库、为亲手建起的系统自豪。有人告诉我们 AI 只会接管无聊的样板代码，每周还给我们几小时自由时间。结果却是：看着一个模型用几秒钟生成我们花多年才学会的东西，整个行业经历了一场身份危机。**如果机器能写代码，我们还往哪儿摆？**

答案是：**人类应该当灯塔。**恰恰因为模型「什么都知道」，每条路径在它眼里都同样合理。它无法有品味地对信息排序、定序、创造。这就是我们新工作的起点——像在黑暗洞穴里探洞的人，我们举着手电，指向路径，决定模型下一步该聚焦哪里。

我们的角色从写代码演进成了编排。这对很多人其实不新——甚至早在 AI 编码之前，这就是软件职业生涯的自然推进：往上走，动手机会变少，教练帽越戴越多；为团队的产出负责；不再读每一行代码、只聚焦关键部分；学会委派并消化它的利弊。**你成了一个 tech lead。**

## 每个人都被升职成了 tech lead

在传统职业路径里，这个转变是渐进的：你在战壕里从 Junior 磨到 Senior，才最终走上 lead、工程经理或架构师的位置——聚焦大局，把实现细节留给更初级的工程师。

现在每个人都有自己的虚拟编码智能体团队，**所以连最初级的工程师也需要学会做一个好的 tech lead**——不是引导人类，而是引导智能体。

「引导它做什么？」才是最重要的问题。我们仍在构建程序，只是描述程序的方式变了。

我这辈子读过少数几本我认为常青的书，其中一本是《Structure and Interpretation of Computer Programs》（SICP）。为什么这本书现在依然相关？因为它对「程序是什么、我们工程师如何念咒语造出它们」的描述：

> 「计算过程是栖居在计算机中的抽象存在。它们演化时，操纵着另一类称为数据的抽象东西。过程的演化由一种称为程序的模式规则引导。人们创造程序来引导过程。实际上，我们是在用咒语召唤计算机的精灵。」
>
> 「……我们用来召唤过程的程序，就像巫师的咒语——由神秘深奥的编程语言中的符号表达式精心构成，规定我们要过程执行的任务。」
>
> —— Harold Abelson 与 Gerald Jay Sussman，《Structure and Interpretation of Computer Programs》（1985）

**我们仍从事召唤过程以指挥计算机的行当。改变的只是 crafting 咒语的语言。**现在我们用平实的英语而不是神秘的符号表达式写咒语；编排 agent、确保它们走在正确的轨道上，成了工作中最重要的部分——这意味着更少的写、多得多的读。你写的规格（prompt）也比以往任何时候都多。如果你在 AI 之前当过 tech lead，这一切听起来就像日常。

怎么做好？旧世界里，好的 tech lead 与经理会花大量时间辅导团队，让他们发展出自己用职业岁月（和战伤）换来的批判性思维与品味——把流程、行为、技术的知识逐渐转移下去。我上次那次吹毛求疵的 code review？因为多年前我自己对细节的疏忽搞崩过生产环境。

在今天，除了向导师与自己的战伤学习，**我们还要仔细观察 agent 的行为、从它们的错误中学习。因为这些错误以令人目眩的速度累积，agent 提供了终极压缩的反馈循环：你可以在一个下午看完几十种微妙的失败模式、竞态条件与幻觉模式——以传统发布周期十倍的速度建立架构判断力。**

本质上，我们现在的行当是编排信息的流动，确保 agent 总是拥有构建我们期望结果的最优环境。而以我们看到的演进速度，今天的最优明天大概率不再最优——所以我们需要不断打磨工具与流程。「软件从未如此一次性」：我们的咒语需要变得快速而精确，因为明天我们就需要新的咒语。

## 把信息结构化到模型可以据此行动

> 「资深软件工程师有能力组织程序，使得他们可以有理有据地确信：产生的过程将执行预期的任务。他们能预先想象系统的行为。他们知道如何结构化程序，使未预料到的问题不至于导致灾难性后果；问题出现时，他们能调试。设计良好的计算系统，如同设计良好的汽车或核反应堆，是以模块化方式设计的——部件可以分别构建、替换与调试。」
>
> —— 同上，SICP（1985）

把上面这段话里的「程序」换成「agent」，整个框架依然成立。我们需要学会结构化 agentic 编码过程，使它们产出设计良好的计算系统。

给 agent 灌注知识最重要的方式之一是 **Agent Skills**。模型的行为与人类非常相似（这不该意外——它们训练在我们生产的数据上），所以我们曾用来提升团队生产力与产出质量的同一套技术，可以直接应用于 agent。这为「用自己的战伤与行业最佳实践来创造影响模型行为的技能」提供了沃土。

其中一个技术是：**把复杂任务拆成更小的块。**这是敏捷流程的基石，如今可以经由 spec-driven development、实现计划与 subagent 的构造应用于 agentic 编码。

我 personally 把 subagent 当作我在设计的信息流的积木。这在很多意义上类似传统程序里处理并发，也在隔离上下文上扮演关键角色——毕竟，「attention is all they need」。把任务切成正交的、可被各 subagent 独立处理的单元，你就在确保 agent 宝贵的注意力只聚焦在那个单独任务上，从而提升质量与任务遵循度。

无论你是手工编织工作流、还是为后人构建技能，我发现这些点特别有用：

- **协调者角色**：让主会话保持空闲——协调者总是把执行委派给 subagent、尽快释放主会话。这样 subagent 工作时你仍能与主会话交互、实时发送评论引导方向。
- **任务正交性**：把任务切成正交单元，最小化相互依赖与冲突。先理解并尊重顺序依赖；然后就可以放心并行，确信 subagent 不会互相覆盖工作或做出不兼容的假设。
- **复刻已被验证的工作流**：与辅导和带教一样，对人类团队与经典软件工程有效的模式，对 agent 也有效。持续重读文献——新旧模式都可以教给 agent。

过去几个月我在逐步构建自己的技能目录。**因为技能会随着模型与 agent harness 的演进而腐烂，这不是「点火就忘」的事。**我不断演化它们——以至于我决定给技能加一个「新鲜度评分」，提醒我哪些正在过时，好让我要么给它们新生命、要么从目录里修剪掉。

我日常积极使用的一些技能示例：

- **double-diamond**：基于敏捷双钻方法论的产品开发工作流，强制「先发现后实现」。
- **parallel**：多用途 fan-out / map-reduce 模式，把任务拆成多线程、最后对账结果。
- **uno-reverse**：对抗式评审——反制模型的过度自信与过度工程倾向。
- **less-is-more**：一种设计哲学，告诉模型一次只做一件事并做好，而不是造臃肿应用。
- **intercom**：教我的 agent 在相关项目上互相交谈的技能。
- **show-me-the-money**：挖掘对话历史，找回「我和模型讨论过却完全忘了实现」的功能。
- **abstract**：用哲学原理把示例与情境泛化为知识。

## Agentic 代码里的破窗

> 「计算过程，在正确工作的计算机里，精确而准确地执行程序。因此，如同巫师的学徒，新手程序员必须学会理解并预期自己召唤的后果。程序里即使很小的错误（通常称为 bug 或 glitch）也可能产生复杂而未预期的后果。……现实世界的编程，需要的是细心、专业与智慧。」
>
> —— 同上，SICP（1985）

如果我们不预期召唤的后果，一个未被引导的 agent 会以比我们意识到的更快的速度复制微小的结构缺陷。这个问题不新——人写代码的时代它一直在发生，只是过程慢得多而不太被注意。有人试图阻止它，总是被叫作吹毛求疵的 code reviewer：被少数人爱、被多数人恨。

心理学里，这个现象叫**破窗理论**，基于一场 1969 年的实验：研究者把一辆弃车停在高尚社区一周，无事发生；第二周，一位研究者抡起大锤砸破一扇窗——**几个小时内，车被拆得精光。**

碎玻璃是扳机。它发出「没人在乎」的信号，于是集体停止在乎。多年来我一直主张同样的事发生在代码里：一旦代码里出现一扇破窗（错别字、坏命名、糟糕的测试、错误的抽象），它触发我们的心理系统停止在乎，问题随时间升级——小瑕疵滚成大灾难。

**在 agentic 世界，问题被放大：既有代码会在生成新代码时偏置模型。**如果既有代码是坏的，除非被正确指示，agent 只会放大它的问题——因为那被视为「可接受的标准」。

Code review 是工程工作里最不光鲜的部分，以至于很多工程师根本不认为它是工作的一部分。事实上它是最重要的部分之一。

这不意味着评审每一行代码。没人喜欢评审几千行 AI 生成的代码，我也一样。**品味不在于查语法或抓机械性 bug——那是确定性工具的活。**正如我在《How to Do Code Reviews in the Agentic Era》里写的：如果编译器、linter 或自动化测试能抓住的问题，人不应该看它。

**用 AI 打 AI、用自动化打自动化**：用确定性门禁消灭机械噪音，把评审时间聚焦在关键的架构边界上，其余抽样。因为今天的周期时间比「手工匠编码」快了几个数量级，抽样意味着即使当下漏掉一个问题，你很快会有下一次机会抓住它。把评审导向真正关键的部分，相信流程抓住其余。

## 被承诺的自由时间实际去了哪里

我们构建软件比以往任何时候都快。移除了实现瓶颈后，那些曾经躺在货架上直到被更紧急事务取代的想法，突然都变得可行了。我们可以连续快速地写原型，在它们沦为弃置项目之前就知道什么行得通、什么不行。

**但更快不替代构建心智模型的需要。**我们的核心工作是结构化上下文、约束与反馈循环，让 agent 建出我们真正想要的东西。如果说有什么变化，是我们的工作变得更难了：技术知识已成商品，**品味与批判性判断依然稀缺。**

归根结底，我们仍是召唤计算机精灵的巫师。只是我们的咒语，又跨过了一个抽象层级。

# 《Beyond Writing Code》的发芽报告

## 材料核心

以 SICP 的三段引文为骨架回答「模型什么都知道之后人类剩什么」：咒语（程序）语言从符号表达式换成平实英语，召唤精灵的行当未变——角色从写代码演进为编排。核心论点链：模型什么都知道所以每条路同样合理→人类当灯塔定方向；人人升职 tech lead（引导 agent）；agent 是十倍速压缩的反馈循环（一个下午看几十种失败模式养出架构品味）；subagent 是正交切分的注意力隔离积木；技能会腐烂需要 freshness score；破窗理论（1969 实验车）在 agentic 世界被放大——坏代码偏置模型生成更坏代码；code review 的品味在架构边界，机械错误交给确定性工具，其余抽样。

## 发芽 01：咒语的抽象层级——SICP 框架的第四十年迁移

### 种子

1985 年 SICP 说「我们用咒语召唤计算机的精灵」——咒语是神秘符号表达式；2026 年同一句话成立，咒语换成了平实英语的 prompt。作者把「程序→agent」的替换测试在第二段引文上：模块化、可分别构建/替换/调试——全部成立。

### 故事

这个迁移的工程含义被原文精确圈定：写下咒语不再是贵的部分，「编排 agent 确保它们在正轨」才是；写规格多于写实现；「软件从未如此一次性」——咒语必须快而精确，因为明天就要新的。而技能目录的 freshness score 是对「咒语腐烂」的直接工程回应：过时的咒语不只无效，还会把旧世界的假设注入新模型。

### Aha 瞬间

**抽象层级上移不改变行当的本质（结构化信息以召唤过程），只改变咒语的材质与腐烂速度**——SICP 四十年后仍是 agent 时代最好的工程教科书，因为它的对象从来不是语法，是「过程」本身。

## 发芽 02：agent 是十倍速的品味培养皿——把失败模式当课程

### 种子

传统上架构品味来自多年的战伤积累；原文的发现是：agent 的错误以惊人速度累积，这反过来使它成为「终极压缩的反馈循环」——一个下午看几十种微妙失败模式、竞态与幻觉。

### 故事

正面应用是学习加速（观察 agent 的失败模式十倍速建立判断力）；反面应用是破窗理论（1969 实验车：砸窗后几小时被拆光）——既有代码偏置模型生成新代码，坏窗不修，agent 会把「可接受标准」放大。对策是评审策略的重定位：确定性工具（编译器/linter/测试）消灭机械噪音，人聚焦架构边界，其余抽样——周期时间快了几个数量级，抽样意味着漏掉的问题很快有第二次被抓住的机会。

### Aha 瞬间

**agent 时代品味的新鲜度来自「失败密度」而非「年限密度」——但前提是你在观察并修复，而不是在加速制造破窗。**评审从逐行审查变成「确定性工具打机械、人打架构、抽样兜底」的三层防空体系。

## 发芽 03：技能目录的管理学——给 prompt 上版本与保质期

### 种子

作者把团队管理的技术直接迁移到 agent：double-diamond（先发现后实现）、parallel（fan-out/map-reduce）、uno-reverse（对抗评审反制过度自信）、less-is-more（一次一件事）、show-me-the-money（挖对话史找回忘实现的功能）——并且给每个技能加了「新鲜度评分」。

### 故事

三条编排纪律同样来自团队管理：协调者只委派保持主会话空闲（人实时引导）、任务正交化（防 subagent 互相覆盖/假设冲突）、复刻已被验证的人类工作流。这套东西的深层逻辑是「模型训练在人类数据上，所以对人类有效的管理对模型同样有效」——但也正因如此，技能会腐烂：模型与 harness 一演进，旧咒语就成了注入旧假设的隐患，必须像产品一样评分、更新、修剪。

### Aha 瞬间

**管理 agent 的最佳教材是你带团队的经验——但要给每一页教材加保质期。**「freshness score」这个动作把 prompt 从「一次性咒语」变成了有生命周期的知识资产，这是 prompt 工程从手艺走向体系化管理的标志。
