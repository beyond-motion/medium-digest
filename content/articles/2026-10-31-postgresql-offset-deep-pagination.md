# 资深工程师加了索引，PostgreSQL 还是要 12 秒

> 原文：[Our Senior Engineer Added an Index. PostgreSQL Still Took 12 Seconds](https://medium.com/@devrimkodlama/our-senior-engineer-added-an-index-postgresql-still-took-12-seconds-8107104544bf) — Production Systems | Prodrescue By Devrim

---

查询从一张 4000 万行的表里返回 20 行。索引工作得完美无缺。不幸的是，PostgreSQL 在一丝不苟地执行我们要求它做的事。

客服后台慢得令人痛苦：打开最新订单只要 80 毫秒，但翻到更早的页面可能要十二秒。资深工程师已经加了索引、查过执行计划、确认 PostgreSQL 用上了它——数据库表现堪称完美，只要没人想看星期二之前的数据。又一次投诉之后，工程经理走过来：「上周不是优化过了吗？」「优化了，PostgreSQL 在用索引。」「那第 8000 页为什么要十二秒？」

工程师打开 SQL，盯着其中一行，笑出了声——那种意识到 bug 在生产环境里躺了三年、还熬过了六轮代码评审的笑。那一行是 `OFFSET 160000`。

## 看起来毫无害处的查询

服务用 Spring Boot + Spring Data JPA + PostgreSQL，orders 表约 4000 万行，客服后台每页显示 20 条订单：

```sql
SELECT id, customer_id, total_amount, created_at
FROM orders
WHERE tenant_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 160000;
```

团队早已建好了合适的索引 `(tenant_id, created_at DESC, id DESC)`，PostgreSQL 能高效找到该租户的订单并按请求顺序读取。但索引没法让前 16 万条匹配行凭空消失——PostgreSQL 仍然要走完这些条目，才能返回用户要的那 20 行。PostgreSQL 官方文档明确警告大偏移量可能低效，因为被跳过的行依然要计算。工程师优化了穿过数据库的路线，却从没质疑应用为什么要坚持走完 16 万条记录再去取 20 条。

## EXPLAIN ANALYZE 的输出让人难堪

在代表性测试环境里对比第一页与第 8000 页，深页计划里出现了这样的内容（示意计时）：

```
Limit
  actual time=11842..11844
  rows=20
-> Index Scan using idx_orders_tenant_created
     actual rows=160020
     Buffers: shared hit=21890 read=3240
Execution Time: 11844 ms
```

索引扫描产出了 160,020 行，Limit 节点把前 160,000 行丢弃、返回 20 行。为一个只显示 20 条订单的屏幕，这是一笔惊人的工作量。十二秒的具体数值取决于测试环境的存储、缓存状态与行访问成本——这种规模的偏移量并不天然等于十二秒；但执行器不得不访问的行数，把低效的本质摆得清清楚楚。**数据库没有无视索引，它在忠实执行一个昂贵的分页策略。**

## 修复：别数页了，记住位置

解法是用 keyset 分页（也叫游标分页）替换深偏移分页：不再让 PostgreSQL 跳过 16 万行，而是让应用记住上一页最后一条订单的排序值。假设当前页末行是 `created_at = 2026-10-21 14:32:08`、`id = 9182741`，下一页查询变成：

```sql
SELECT id, customer_id, total_amount, created_at
FROM orders
WHERE tenant_id = 42
  AND (created_at, id) < (
      TIMESTAMP '2026-10-21 14:32:08',
      9182741
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

配上合适的复合 B-tree 索引，PostgreSQL 可以直接 seek 到游标位置读取后续匹配记录，不必处理之前的每一页。`id` 之所以在场，是因为多条订单可能共享同一时间戳——稳定唯一的平局裁定字段防止 created_at 相同的记录被意外跳过。本例中索引本来就存在，无需重建；真实生产系统上加索引前应先盘点现有索引、测量写入开销。查询模式与索引顺序是配合工作的，PostgreSQL 多列索引文档解释了前导等值条件与后续索引列为什么重要。

## 分页教程从不提的那部分

游标分页带来一个 API 设计决策：偏移分页下前端可以直接请求第 8000 页；游标分页下通常只能从已知位置向前或向后导航。对活动流、交易历史、审计日志和无限滚动，这个取舍往往值得；对必须跳转到任意页码的报表，需求可能需要别的方案。

还有并发写入的问题：有人翻列表时新订单可能插进来。基于确定性排序的游标能避免偏移漂移带来的一些重复与遗漏，但不会自动在不同 HTTP 请求之间造出一致性快照——业务若要求固定的历史视图，API 需要显式的快照或截止策略。用户改筛选条件时，游标必须绑定那些条件。**把一个租户或一种搜索条件的游标复用到另一个上，是制造诡异结果、甚至危险授权漏洞的绝佳方式。** 这个方案需要的思考，比「用时髦的 SQL 操作符替换 OFFSET」多一点。

## 生产环境里变了什么

示意基准里第一页本来就快，深页改善巨大——数据库不再需要走完数千行无关数据。更重要的改善出现在并发之下：此前多个客服同时开深页会同时触发昂贵的索引扫描和不必要的堆访问；改造后每个请求做的工作量都接近它实际返回的行数。团队还干脆不再给订单历史端点暴露任意页码——UI 改提供下一页游标、日期筛选和按单直接搜索。工程经理起初对改前端不太情愿，直到发现另一种选择是向客服解释「十二秒的等待在技术上完全符合 SQL 规范」，态度才热情起来。

## 藏在这个 bug 里的资深工程师面试题

如果面试官问怎么优化一条慢的 PostgreSQL 分页查询，加索引是合理的起点。但有经验的工程师应该去看执行计划，对比扫描行数与返回行数，判断是不是分页策略本身在制造不必要的工作。Staff 级工程师还该考虑 API 契约：产品真的需要随机页访问吗？用户能用游标导航吗？请求之间插入记录会发生什么，系统如何保住租户隔离？这些决策对数据库负载的影响，远在最初那条查询被优化之后仍在持续。**数据库索引很强大，但它补偿不了应用发给它的每一条昂贵指令。**

## 教训

资深工程师没建一个坏索引——他为一条「用户越翻越深就越贵」的查询建了个好索引。问题能存活，是因为团队的性能测试只覆盖前几页，而偏移分页在前几页表现完美。没有人量过第 8000 页，直到一位客服养成了真正干活的坏习惯。

在给 PostgreSQL 加资源或再加一个索引之前，先看看执行器被要求处理什么。有时候最快的优化，是改掉应用向数据库提的问题。如果一条查询检查了 16 万行才返回 20 行，**PostgreSQL 需要的是一声道歉，而不是又一个索引。**

# 《Our Senior Engineer Added an Index. PostgreSQL Still Took 12 Seconds》的发芽报告

## 材料核心

四千万行的 orders 表、每页 20 条的客服后台，`LIMIT 20 OFFSET 160000` 让一个「索引工作完美」的查询在第 8000 页耗时 12 秒：执行计划显示索引扫描产出 160,020 行，Limit 丢弃前 16 万行。修复是 keyset（游标）分页——记住上一页末行的排序值作为下界，配合 `(tenant_id, created_at DESC, id DESC)` 复合索引让每次请求的工作量贴近实际返回行数；连带的前端取舍（放弃任意页码，改游标+筛选+直搜）与并发陷阱（游标须绑定筛选条件与租户，否则造成授权漏洞）同样是方案的一部分。教训：性能测试只测前几页，bug 就能带着「已优化」的认证存活三年。

## 发芽 01：「优化了」不等于「优化对了问题」——验证你的问题定义

### 种子

资深工程师做的每一步都是对的：加索引、查计划、确认索引被使用。数据库的每一步也都没错：忠实执行昂贵的分页策略。加起来却是一页 12 秒。

### 故事

问题不在「查询如何走索引」，在「应用为什么要问这个问题」——没人质疑为什么取 20 条要先走完 16 万条。修复的本质不是换算子，而是改问题：从「给我第 8000 页」改成「给我这条记录之后的 20 条」。前端从页码导航换成游标+日期筛选+直搜，产品形态跟着问题一起变。工程经理的态度转变点也很诚实：另一种选择是向客服解释 12 秒符合 SQL 规范。

### Aha 瞬间

**当每个组件都「正确」而系统仍然糟糕时，该检查的是问题的提法，不是组件的参数。** 「加资源」「加索引」是在为错误的提问买单；最快的最优化有时是让应用换一个问题问数据库。

## 发芽 02：测试覆盖的盲区 = bug 的庇护所

### 种子

这个 bug 存活了三年、熬过六轮代码评审，不是因为它藏得深，而是因为所有性能测试都只测前几页——而偏移分页在前几页的表现无懈可击。

### 故事

第一页 80 毫秒，第 8000 页 12 秒。测试把全部火力对准「典型路径」，于是退化只发生在「用户翻得很深」这个尾部场景里。最后揭穿它的不是测试也不是评审，而是一位「养成了真正干活坏习惯」的客服——真实使用模式最终会走进测试从未铺过轨的区域。

### Aha 瞬间

**性能退化最爱藏在「输入规模的单调轴」的远端**——页深、时间跨度、数据量、并发数。为这条轴的远端专门设一两个探针（比如例行量一次第 N 深页面的延迟），比在前端多铺一百个典型用例更能兜住这类事故。

## 发芽 03：游标即契约——一个技术选型背后的 API 设计链

### 种子

从 OFFSET 换成游标，表面是 SQL 层的一处替换，实际牵出三层设计决策：前端能不能跳页、并发写入时视图是否一致、游标能否跨条件复用。

### 故事

游标分页取消了「第 8000 页」这个概念，换来无限流、审计日志等场景的正确性能；但它不自动提供跨请求的一致性快照（需要显式的截止策略），且游标必须与筛选条件和租户绑定——把 A 租户的游标用到 B 租户是危险的授权漏洞。索引选择上作者也给了工程纪律：先盘点现有索引、测量写入开销再动手，前导等值列与后续列的顺序要和查询模式配合。

### Aha 瞬间

**每一个「更快的实现」都在暗中重写 API 契约。** 性能优化做到 Staff 级，工作对象就从查询变成了契约：产品要不要随机访问、状态如何跨请求保持、权限边界画在哪——数据库负载只是这些决策的下游回声。
