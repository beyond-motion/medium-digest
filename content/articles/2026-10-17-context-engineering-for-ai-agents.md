# 深入上下文工程：AI 智能体的稀缺资源管理术

> 原文：[Deep dive into context engineering for AI agents](https://medium.com/code-like-a-girl/deep-dive-into-context-engineering-for-ai-agents-584bf3e578df)
> 作者：clara · 2026-05-15 · 7 min read
> 改写式翻译，保留原文结构与全部观点；署名与原文链接如上。

---

我们总是在谈更强的模型、更大的上下文窗口、更聪明的智能体。但大多数真实世界的失败并不来自模型能力——**它们来自上下文被构造、传递和维护的方式。**

这是个难题：领域变化快、技术仍在演化，很大程度上还是一门实验科学，取决于你所处的上下文（双关有意）、约束和环境。作者在构建多智能体系统的工作中浮现出一个反复出现的模式：**性能远不是「给模型多少上下文」的问题，而是把上下文塑造得多「精确」的问题。**

本文把这些经验蒸馏成可用的原则：如何把上下文当作受限资源来管理——决定装什么、排除什么、如何组织信息，让智能体长期保持连贯、高效、可靠。

> 说到底，最强的智能体不是看得最多的那些，而是在正确的时刻、以正确的形式、看到正确东西的那些。

## 术语表

### 上下文工程（context engineering）

上下文工程是「为 LLM 提供恰当的信息、工具和格式以完成任务」的艺术。好的上下文工程，就是找到**信号最高的最小 token 集**，让模型产出好结果的概率最大。

实践里它通常归结为四个动作：把信息**卸载（offload）**到外部系统，模型不必全量随身携带；按需**检索（retrieve）**而不是预先塞满；**隔离（isolate）**上下文，让一个子任务不污染另一个；必要时**缩减（reduce）**历史——但只以「智能体之后仍然需要」的方式减。

反面的常见失败模式是**上下文污染（context pollution）**：过多不必要、互相冲突或冗余的信息，把 LLM 的注意力搅浑。

### 上下文腐坏（context rot）

上下文腐坏指：随着窗口填满，LLM 性能退化——**哪怕还在标称上限之内**。模型仍有空间读更多，但推理开始发糊。你会注意到，模型「高质量表现的有效窗口」往往远小于它的技术容量。

两方面的原因。其一，模型对整个窗口没有完美记忆：开头和结尾的信息比中间的更可靠。其二，更大的窗口解决不了企业系统的问题：企业数据实际上无界且频繁更新，就算模型吞得下一切，也不代表它能对其保持连贯理解。

正如人类的工作记忆容量有限，每引入一个新 token 都在消耗模型的注意力预算。这种稀缺源于 transformer 的架构约束——每个 token 要关注其他所有 token，n 个 token 就是 n² 的交互模式；上下文越大，注意力被迫摊得越薄。

### 上下文压缩（context compaction）

压缩是 context rot 的通用解法：当模型接近窗口上限，把内容摘要化，以上一份摘要为起点重启新窗口。这对长任务尤其有用，让模型在性能不明显退化的前提下持续工作。

[近期关于 context folding 的工作](https://openreview.net/forum?id=JaLXQnA2wi)给出了另一条路——智能体主动管理自己的工作上下文：分支出去处理子任务，完成后「折叠」，收敛中间步骤、只保留结果摘要。

难点不在摘要，而在**决定什么活下来**。有些东西应当稳定近乎不可变：任务目标、硬约束。有些可以安全丢弃。挑战在于，信息的价值常常要到后来才显现。好的压缩必须保住那些**继续约束未来行动的事实**：哪些路线已经失败、哪些文件已创建、哪些假设已被推翻、哪些句柄之后还能用、哪些不确定性还没解决。否则你会得到一份人类读起来很漂亮、对智能体毫无用处的整洁摘要。

## 智能体线束（harness）

**模型不是智能体。线束才是把模型变成智能体的东西。**

所谓 harness，指模型周围决定上下文如何组装与维护的一切：prompt 序列化、工具路由、重试策略、步骤之间保留什么状态的规则，等等。

一旦用这个视角看真实的智能体系统，很多所谓的「模型失败」就变了样——作者在工作中遇到过多起，它们其实是**线束失败**：智能体「忘了」，因为没有任何东西持久化该保存的状态；它重复劳动，因为 harness 没有把先前失败的持久痕迹呈现给它；它选错工具，因为 harness 把动作空间塞爆了。

好的 harness 在某种意义上是**包着随机内核的确定性外壳**：它把上下文变得可读、稳定、可恢复，让模型把有限的推理预算花在任务上，而不是花在从一团乱麻的轨迹里重建自身状态。

## 智能体之间的通信

任务变复杂后，团队倾向于上多智能体系统。

错误在于以为「更多智能体 = 更多共享上下文」。实践中，把一份巨型共享转录塞给每个子智能体，恰恰制造了专业化的反面：每个智能体都在读所有东西、继承所有人的错误、为同一份上下文账单反复付费。

只共享一部分上下文呢？新问题出现：智能体意见不一致时，谁说了算？哪些保持本地、冲突如何调和？

出路是把通信不当作共享记忆，而当作**通过定义良好的接口进行的状态转移（state transfer）**。

对输入输出清晰的离散任务，智能体之间应该通过**产物（artefacts）**而非原始轨迹通信。比如一个网页搜索智能体不需要传递整个浏览历史，只需要交出下游智能体真正用得上的材料。中间推理、失败尝试、探索轨迹默认保持私有（除非显式需要）；向前传递的是蒸馏后的输出：提炼出的事实、经过验证的发现、约束下一步的决策。

对耦合更紧的任务——比如调试智能体的下游推理确实依赖先前的尝试——可以引入有限形式的轨迹共享。但这应该是深思熟虑且有边界的，不该是默认。

### KV cache 罚金

模型生成文本时会重复大量相同计算。KV caching 是一项推理期优化：记住前几步的关键信息而不是全部重算。

但在多智能体系统里，如果每个智能体共享同一份上下文，你会用一堆无关细节把模型搅晕，**还白白支付巨额的 KV-cache 罚金**。多个智能体协作需要通信——但不该通过共享记忆，而应通过受控的、最小化的结构化输出。

## 保持智能体的工具集小而相关

**工具选择是一个伪装成能力问题的上下文问题。**

随着智能体积累更多工具，动作空间越来越难导航：模型走错一步、绕了低效路线的概率随之上升。后果是，工具的 schema 需要比多数人以为的**鲜明得多**——每个工具的功能必须清晰、彼此重叠最小、用途一目了然、输入参数毫无歧义。

作者连自己团队都踩过的常见失败：工具集随时间越堆越臃肿，于是「该用哪个工具」的决策变得含混。

## 智能体记忆

这是一种让智能体定期把笔记持久化到上下文窗口之外、并在之后的时刻拉回窗口的技术。

最难的部分是**决定什么配得上晋升进记忆**。作者的经验法则：持久记忆应存放那些持续约束未来推理的东西——持久的偏好等；其余一切都要设很高的门槛。存太多只是绕回上下文污染——只不过这次你把它做成了持久的。

而没有修订机制的记忆是个陷阱。智能体一旦跨步骤、跨会话持久化笔记，就需要冲突解决、删除与降级机制——否则长期记忆会变成一座过时信念的垃圾填埋场。

## 总结

上下文工程仍在演化，没有唯一正确的方式，大部分仍靠经验、由我们构建的系统和身处的约束塑造。

放任不管，上下文会增长、漂移，最终被自己的重量压垮。管理得当，上下文就是「只会响应的智能体」和「能推理、能适应、在长复杂任务中保持连贯的智能体」之间的分界线。

# 《Deep dive into context engineering for AI agents》的发芽报告

## 材料核心

一篇来自多智能体系统一线的上下文工程方法论：失败多源于上下文构造而非模型能力；上下文工程 = 找「信号最高的最小 token 集」，四个动作（卸载/检索/隔离/缩减）对抗 context rot（有效窗口远小于标称容量、注意力预算被 n² 交互摊薄）；压缩的关键不是摘要而是「决定什么活下来」；模型变智能体靠 harness——「忘了/重复/选错工具」多为线束失败；多智能体通信的正解是经定义良好接口的状态转移而非共享记忆（顺带躲开 KV-cache 罚金）；工具集是小而相关的上下文问题；记忆要有晋升门槛与修订机制，否则成为过时信念的填埋场。

## 发芽 01：压缩的艺术不在删，而在预知什么还会被需要

### 种子

「挑战在于，信息的价值常常要到后来才显现」——好的压缩要保住失败过的路线、已创建的文件、被推翻的假设、还 unresolved 的不确定性。

### 故事

摘要人人会做，难的是清单上这些项有一个共同点：它们在当下看起来都是「过程废料」——失败的尝试、临时的文件、被否决的假设。但恰恰是它们约束着未来：不知道哪条路走过，就会再走一遍。所以压缩的判据不是「这条信息重不重要」，而是「这条信息会不会继续约束行动」。

### Aha 瞬间

给智能体做摘要时最危险的不是丢信息，而是产出一份「人类读起来漂亮、智能体用起来没用」的总结——评价压缩质量的标准要换成：拿这份摘要重启工作，会不会重蹈覆辙。

## 发芽 02：「模型失败」大多是线束失败的化名

### 种子

智能体「忘了」因为没东西持久化状态；「重复劳动」因为先前失败没有持久痕迹；「选错工具」因为动作空间被塞爆。

### 故事

这篇文章把归因倒了个个儿：遇到智能体犯错，先别急着怪模型——问三个线束问题：该保存的状态有地方落吗？失败的痕迹被呈现给下一轮了吗？动作空间是否已经臃肿到无法导航？好线束的定义也随之清晰：包着随机内核的确定性外壳，让模型把推理预算花在任务上而不是花在重建自身状态上。

### Aha 瞬间

归因决定改进方向：把线束失败归咎于模型，会得到「换个更大的模型」这种最贵的错误答案；先审线束，往往一行持久化代码就能消灭一类「智力问题」。

## 发芽 03：共享记忆是协作的直觉，也是它的陷阱

### 种子

把巨型共享转录塞给每个子智能体 = 人人读一切、人人继承所有人的错误、人人反复付同一份上下文账单，外加巨额 KV-cache 罚金。

### 故事

直觉上「信息共享越多协作越好」，但文中的替代方案更精确：通信 = 经定义良好接口的状态转移——搜索智能体交出提炼后的事实而非浏览历史，中间推理与失败尝试默认私有。这同时解决了两个问题：注意力污染（无关细节搅浑判断）和一致性政治（智能体意见冲突时谁说了算——接口清晰时根本没有「谁说了算」的问题）。

### Aha 瞬间

多智能体协作的正确心智模型不是「一个共享的大脑」，而是「一群各自带工作记忆的专家交换纪要」——传递的是结论与约束，不是思考过程的全程录像。
