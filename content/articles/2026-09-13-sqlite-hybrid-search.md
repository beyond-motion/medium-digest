# 我用 一个 SQLite 文件替换了 Chroma、Qdrant 和 Pinecone

> 原文：[I Replaced Chroma, Qdrant, and Pinecone With a SQLite File](https://medium.com/@ashrayadhikari/i-replaced-chroma-qdrant-and-pinecone-with-a-sqlite-file-1ae5210c85d4)

---

## 每个 RAG 教程的第一步都是装 Docker

作者的烦恼开始得很低调：每个 RAG 教程都一个模样——第一步装 Docker；第二步拉 ChromaDB 镜像；第三步在 8000 端口起服务器；第四步等它就绪；第五步写十二行连接样板代码；第六步意识到自己把一个「本地小 AI 项目」变成了分布式系统，默默合上笔记本。

他当时在做一个带本地 LLM 支持的 CLI 工具，需要它在多次运行之间「记住」东西——不是写 JSON 文件再 grep 的那种「记」，而是真正按相关性与新鲜度排序地检索记忆。选项有三个：本地跑一个向量数据库服务器（Qdrant 和 ChromaDB 都有服务器模式，但都假设有运维）；用 ChromaDB 的嵌入式 Python 库（在大语料上启动时间不可接受）；或者按本地优先工具的约束造一个精简的。Pinecone 他评估了五分钟就想起它是云服务——而他明确需要「无云」。于是他造了一个：**sqlite-hybrid-search，引擎的全部状态装在一个 SQLite 文件里。**

## 核心想法：SQLite 本来就在那里

SQLite 无处不在：每个 Python 安装自带它，每部手机里都有它，每个 Electron 应用都内嵌它。它是史上部署量最大的数据库引擎——几乎没人把它当搜索后端，因为它单独确实不是。

但 SQLite 自带 **FTS5**——一个由 BM25 排序支撑的全文搜索扩展；而 Unum Cloud 的 **usearch** 库可以在进程内构建快速的余弦相似度 HNSW 索引。把这两样用**倒数排名融合（Reciprocal Rank Fusion）**拼起来，就得到混合检索：稠密语义检索加精确关键词匹配，按排名融合，所有状态住在一个文件里：

```python
import sqlite_hybrid_search

engine = sqlite_hybrid_search.Engine("memory.sqlite3", dim=384)

engine.add(
    documents=[{"id": "home", "text": "I live in Munich, Germany."}],
    embeddings=[[...your vectors...]],
)

hits = engine.search_hybrid("Where do I live?", query_vec, top_k=5)
```

整个引擎跑在你的进程里。**它能启动，就能工作。**

## 检索到底怎么运作

引擎维护两个存储：一个 SQLite 数据库（文档、分块、元数据、时间戳、FTS5 表），和一个只存原始向量的内存 usearch HNSW 图。**SQLite 是唯一事实源；向量索引是一个可以随时重建的 sidecar（侧车）。**

这个先后顺序比听起来重要：`add_documents()` 先提交整个 SQLite 事务，然后才把向量插入 usearch 索引——绝不反过来。批量中途失败时，SQLite 事务干净回滚，图里不会留下孤儿向量。向量索引永远可以从 SQLite 重建；反过来不成立。

这引出了第一个在实践里咬到他的设计决策。最初版本每次打开引擎都从 SQLite 重建 HNSW 索引：1 千文档时 40 毫秒，无所谓；1 万时 0.7 秒，有点烦；**10 万时 14.6 秒**——CLI 工具的用户没法对这个数字视而不见。

修法是一个 `.usearch` 侧车文件：关闭时（或摄入后），HNSW 图序列化到磁盘；打开时从磁盘内存映射，而不是重建。新数字：1 千文档 0.6 毫秒、1 万 3 毫秒、10 万 40 毫秒——**规模化场景下 365 倍的提升**。兜底仍在：侧车缺失、截断或与 SQLite 不同步时，引擎检测到并透明重建。

## 检索质量的惊喜比启动时间更大

纯稠密检索（纯 HNSW 余弦相似度）在 1 千文档时 Recall@10 是满分的 1.000；到 10 万文档时掉到 **0.883**。这个差距真实且重要：大约每 9 条相关结果就漏掉 1 条——不是因为模型差，而是最近邻搜索在高维空间中会随语料增长而退化。

**BM25 没有这个问题。** 关键词匹配不随语料规模退化。混合检索——稠密与 BM25 融合——把召回拉了回来：10 万文档上 1.000 / 0.993（Recall@10 / nDCG@10），对比纯稠密的 0.883 / 0.752。

融合用的是 k=60 的倒数排名融合，公式来自 Cormack 等人的原始论文。关键洞察是：**你不能直接把余弦距离和 BM25 分数相加**——它们量纲不同、方向不同，BM25 还是无界的。分数归一化（min-max、z-score）很脆弱：对离群值敏感、逐查询漂移。所以改为按排名融合：每条结果从它出现的每个检索器那里得到 `1 / (60 + rank)`。

## 它适合谁

作者没有宣称这能替代所有向量数据库。他解决的是一个具体的约束组合：本地优先、无守护进程、无云、单文件可分发、CLI 级延迟。对这样的工具，把「分布式系统」装回一个文件，是对过度工程的一次优雅减法——而且顺带证明了：混合检索不只是「更好」，在语料变大后它是「召回是否会塌」的分水岭。

# 《I Replaced Chroma, Qdrant, and Pinecone With a SQLite File》的发芽报告

## 材料核心

作者为「本地优先、无守护进程、无云」的 CLI 工具造了一个混合检索引擎：SQLite FTS5 提供 BM25 关键词检索，usearch 在进程内构建 HNSW 向量图，倒数排名融合（k=60）把两者按名次合并，全部状态住在一个文件里。两个关键工程发现：其一，SQLite 是唯一事实源、向量索引是可重建的侧车——先提交事务再插向量，失败时无孤儿数据；打开时重建索引在 10 万文档上耗时 14.6 秒，改为序列化侧车文件后降到 40 毫秒（365 倍）。其二，纯稠密检索的 Recall@10 会随语料从 1.000 跌到 0.883，而 BM25 不随规模退化——混合检索把 nDCG@10 从 0.752 拉回 0.993。

## 发芽 01：「已经在那里」的组件是最大的依赖红利

### 种子

SQLite 无处不在——每个 Python 安装、每部手机、每个 Electron 应用——「它是史上部署量最大的数据库引擎，几乎没人把它当搜索后端」。作者的整个方案建立在这个被忽视的事实上。

### 故事

选项盘点时的排除法同样说明问题：向量数据库服务器假设有运维；嵌入式库在大语料上启动慢；云服务与「本地优先」直接冲突。最后胜出的不是新技术，而是两个已在机器上的老组件（FTS5 与 usearch）加一段融合公式——连兜底逻辑（侧车丢失就重建）都建立在「SQLite 永远在」这个不变量上。

### Aha 瞬间

评估依赖时，一个「零安装成本、人人已有」的组件，价值可能超过一个「更强但需要运维」的组件——尤其在工具要散播到陌生机器上的场景，存在性本身就是特性。

## 发芽 02：顺序即正确性——先写事实源，再写缓存

### 种子

「add_documents() 先提交整个 SQLite 事务，然后才把向量插入 usearch 索引——绝不反过来」；向量索引永远可以从 SQLite 重建，反过来不成立。

### 故事

这个先后顺序让失败有了确定性的形状：批量中途出错，事务回滚，图里没有孤儿向量；侧车文件缺失、截断或与主库不同步时，引擎能检测到并透明重建。整个系统的容错性不是靠更多检查堆出来的，而是靠「谁是事实源」这一个问题回答出来的。

### Aha 瞬间

多存储系统里最值钱的设计决策往往不是用什么存，而是「先写谁」——把可重建的一方永远排在可事实源的一方之后，失败就自动变成了可恢复事件而非数据事故。

## 发芽 03：会退化的检索和不会退化的检索要搭着用

### 种子

纯稠密检索在 1 千文档时 Recall@10 满分，10 万时掉到 0.883——「大约每 9 条相关结果漏 1 条」；而 BM25 的关键词匹配完全不随语料规模退化。

### 故事

融合方案选了排名而非分数：余弦距离与 BM25 分数量纲不同、方向不同、BM25 无界，min-max 或 z-score 归一化又对离群值敏感、逐查询漂移——所以每条结果只从每个检索器拿 `1 / (60 + rank)`。最终 10 万文档上混合检索的 nDCG@10 是 0.993 对纯稠密的 0.752。

### Aha 瞬间

两种机制各有互不重叠的失效域（语义检索败给规模、关键词检索败给措辞），正确组合方式是找一个对两者都中立的合并维度（排名）——修补短板之前，先确认短板属于谁、以及它什么时候才出现。
