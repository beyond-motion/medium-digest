# AI Agent 的六种规划模式，以及各自适合什么

> 原文：[6 Planning Patterns for AI Agents and When Each One Fits](https://medium.com/@shaheryaryousaf/6-planning-patterns-for-ai-agents-and-when-each-one-fits-809d01c09a95) — Shaheryar Yousaf

---

**一个 agent 的计划是组织工作的方式，不是它推理正确的证明。**学会拆解任务、选择工具、检查结果、知道何时停止的常见模式。

让 AI 助手「调研三款项目管理工具、比较定价、并为五人团队推荐一款」。一句话的回答听起来可能很自信，但这个任务包含好几块：识别合适的产品、找到当前定价、比较套餐、考虑团队需求、带保留意见地给出推荐。

这就是规划模式（planning patterns）能帮上忙的地方：它们给 agent 一个把目标变成可管理步骤的结构，还能让应用更容易调试——你能看到尝试过哪些步骤、用了什么信息、过程在哪里失败。

规划不会让 agent 万无一失。模型可能误解目标、跳过关键步骤、依赖糟糕的数据。开发者需要选一个匹配任务的模式，并围绕工具与输出加上检查。本指南覆盖实用的推理模式、一个调研示例、以及一个可预测计划的简单 Python 做法。

## 什么是 AI Agent 里的规划？

规划是决定「为达成目标可能需要哪些动作」的过程。agent 可能把请求分解成子任务、选择工具、收集结果、判断信息是否足够收尾。

对调研任务，一个计划可能是：

1. 从用户请求识别团队需求。
2. 找三个候选产品。
3. 访问或查询可靠来源获取当前定价。
4. 比较支持五人的套餐。
5. 总结权衡，并声明哪些内容无法核实。

这个计划有用，因为它**把最终推荐背后的工作暴露出来**；也给开发者留出校验输入、约束 agent 的机会——比如系统可以要求定价必须来自某来源并带「截至」日期。

OpenAI 的 agent 构建指南把编排描述为处理多步骤、工具使用、移交、护栏与上下文；Anthropic 的《Building Effective Agents》区分了预定义工作流与更灵活的 agent。这个区分要紧：**不是每个任务都需要模型自己发明执行序列。**

## 从任务出发，而不是从推理潮流出发

常见错误是先选一个流行模式，再把问题硬塞进去。先检查任务：

- 步骤可预测吗？
- 下一步依赖上一步返回的信息吗？
- 独立的部分能并行吗？
- 哪些错误代价最大？
- 需要人类批准结果吗？
- 系统怎么知道自己完成了？

如果步骤是固定的，**普通代码可能就是最好的规划器**。比如发票处理工作流：校验发票、取供应商记录、查必填字段、路由待审——固定顺序。模型可以帮忙从文档提取信息，但序列由应用控制。当请求变化大到固定路径很别扭、或 agent 必须依据取回的信息调整时，才用模型驱动的计划——并保持模型选项有界：定义可用工具、审批规则、清晰的停止点。

## 模式 1：固定工作流（Fixed Workflow）

按开发者选定的步骤走。强项是可重复过程：生成周报、检查申请表。

周报工作流：取最新销售数据 → 代码算总额与百分比变化 → 让模型用平实语言解释结果 → 校验必需小节存在 → 返回草稿待审。

好处是**可预测**：任务总走同一条路线时，应用能控制顺序、显式处理每种失败。代价是灵活性：用户要的任务需要不同顺序时就不方便。

## 模式 2：先计划，后执行（Plan, Then Execute）

模型先提出一系列步骤，应用（或另一次模型调用）再执行之——常带工具。适合任务多变、但仍可分解成动作清单的情形。

对软件比较任务：agent 提议收集候选、取定价、比较用户数上限、撰写推荐。**应用可以在执行前检查这个计划**——拒绝使用未经批准来源的步骤、就预算追问、要求在创建账户前确认。

计划不天然可信。它可能漏掉必要步骤，或包含应用做不到的动作。**对照白名单校验每个动作，并让工具结果对最终综合可见。**

## 模式 3：ReAct 风格的工具循环

ReAct 循环在「推理下一步」与「执行动作」之间交替：agent 观察结果、决定下一步。

```
Goal → 选择下一个动作 → 调工具 → 检查结果
     → 再选动作或给出最终答案
```

比预先规划每一步更具适应性——第一次搜索发现产品改了定价页，agent 可以调整下一个查询。但循环也可能更不可预测：可能做不必要的调用，或在证据已足够后继续搜索。

生产系统要设上限：迭代次数、工具类型、时间、成本。记录每次工具请求与结果。定义「何时问用户、何时交给人」的条件。

## 模式 4：路由与专家（Routing and Specialists）

路由器给请求分类、送往合适的工作流或专家。支持系统把计费问题路由给计费流程、技术问题路由给排障流程。

路由能让指令更清晰、减少每条路径可用的工具数。它也会分错类：**加一条「不确定」路由，测边界样例，让转人工容易。**

专家应有清晰分工。**如果两个 agent 有相同的工具和指令，拆分只会增加复杂度。**当任务真正需要不同的策略、工具或专长时才用专家。

## 模式 5：并行工作（Parallel Work）

有些任务可拆成独立子任务：一个流程收定价、另一个比协作功能、第三个查部署选项，应用再合并结果。

并行能缩短等待或提供多视角，但**不保证准确**。合并输出需要一个综合步骤来解决分歧、检查来源支撑。在同一问题上跑多份模型副本也可能只是倍增成本而不增加有效多样性。

在子任务真正独立、结果能通过清晰契约合并时用并行。保持输出结构化到应用可比较的程度。

## 模式 6：起草、评估、修订（Draft, Evaluate, Revise）

对质量能对照标准检查的任务：产出草稿→评估→修订。写作助手起草报告、检查每条断言有没有来源、修订缺口。

这个模式在**评估者有具体标准**时效果最好。「写得更好点」是模糊的；「每条定价断言必须带当前来源；至少含两个权衡；缺失数据标为未知」才容易检查。

即便是独立的评估模型也会犯错。对事实断言，用确定性检查或对照来源材料验证。设最大修订轮数与失败兜底，避免无穷批判循环。

## 一个简单 Python 例子：可预测的调研计划

入门项目里，可以用普通 Python 表示阶段，而不是让模型生成开放式计划（调研函数是占位；真实应用会接到获批数据源）：

```python
from dataclasses import dataclass

@dataclass
class Product:
    name: str
    monthly_price_per_user: float | None
    source_url: str | None

def compare_tools(team_size: int, products: list[Product]) -> list[dict]:
    if team_size < 1:
        raise ValueError("team_size must be at least 1")
    comparisons = []
    for product in products:
        total = (
            product.monthly_price_per_user * team_size
            if product.monthly_price_per_user is not None
            else None
        )
        comparisons.append({
            "name": product.name,
            "team_monthly_cost": total,
            "source_url": product.source_url,
            "price_verified": product.source_url is not None,
        })
    return comparisons
```

代码处理可重复的计算，模型帮助解释用户的 Criteria 与权衡。注意：**缺价格保持 None 而不是猜**。这是有用分工的小示例——模型管语言与灵活解释；普通代码做精确计算、执行规则。

## 让计划可观察、可测试

计划应该帮开发者理解发生了什么。按隐私政策合适的级别存储或追踪步骤：选了哪个工具、校验过的参数、结果、停止原因。**你不需要向用户暴露私有内部推理也能让系统可观察**——一条简明的动作日志就能说明「agent 查了三个官方定价页，发现一个套餐没有公开价格」。

为这些情形建测试用例：信息完整的清晰请求；应触发提问的模糊目标；缺失或冲突的工具结果；工具失败或超时；提议计划里的不支持步骤；应需审批的请求；超出步骤上限的计划。

**评估结果，而不只是计划文本**：agent 用了可靠来源吗？算对了吗？证据够了就停了吗？区分了已验证事实与假设吗？

## 常见规划错误

- **给简单任务过度规划**：一个函数调用能完成的事，长 agent 循环只增加延迟与失败机会。够用就直接调用或固定函数。
- **把计划当保证**：计划是提案。它会变、会失败、可能基于错误假设。校验动作与结果。
- **给 agent 太多选择**：巨大的工具清单让选择更难、测试面更大。只提供与当前任务相关的工具。
- **忘记停止条件**：定最大步数、时限、触发最终答案/澄清/转人的条件。
- **用模型做精确算术**：总额、日期、资格判定这类确定性规则交给代码。模型可以解释结果，但在程序能算的地方不应成为精确计算的来源。

## 常见问答

**每个 AI agent 都需要做计划吗？**不。简单 agent 可以一轮选工具作答。任务有多步骤或依赖时规划才有用——它有开销，应在改善结果时使用。

**思维链等于计划吗？**不。计划是完成任务的可执行结构。应用可以展示简明计划或动作摘要而不暴露私有内部推理。关注可观察的动作与可验证的结果。

**该用固定工作流还是模型生成的计划？**步骤可预测用固定工作流；任务多变、模型需要在有界选项中抉择时考虑模型计划。很多系统两者结合。

**怎么防止 agent 循环？**设最大工具调用数、超时、显式完成条件。尽量检测重复调用，agent 无法完成时给清晰兜底。

**多智能体能改进规划吗？**专家角色清晰或独立视角有价值时能帮上；它们也带来协调、延迟与成本。**从一个 agent 开始，工作流确实受益于分离时再拆。**

## 结语

没有哪个模式适合所有任务。固定工作流给控制力，先计划后执行支持灵活分解，工具循环适应新结果，并行与评估模式帮助独立子任务与质量检查。

**选适配任务的最简方案。**让 agent 的工具与决策有界，精确规则交给普通代码，设清晰的停止条件，评估完整的结果。**有用的计划不是看起来最精巧的那个；是可靠地帮系统抵达可验证结果的那个。**

# 《6 Planning Patterns for AI Agents》的发芽报告

## 材料核心

以「三款 PM 工具调研推荐」贯穿全篇讲六种规划模式：固定工作流（步骤固定时代码做规划器）、先计划后执行（模型提案、应用对照白名单校验后执行）、ReAct 循环（推理-行动交替，需设迭代/成本/时间上限）、路由与专家（专家须有真分工，同工具同指令的拆分只添复杂度）、并行（真正独立才并行，合并需综合步骤）、起草-评估-修订（评估者要有具体标准，「写得更好」不可检查）。方法论核心：从任务出发而非从流行模式出发（六个检查问题），普通代码是固定步骤的最好规划器，模型管语言与灵活解释、代码管精确计算与规则（缺价格保持 None 不猜）。计划是提案不是保证；可观察≠暴露内部推理（动作日志足矣）。

## 发芽 01：「从任务出发」的六个检查问题——规划模式的反潮流选型法

### 种子

常见错误是先选流行模式再硬塞问题。作者的替代：先问六问——步骤可预测吗、下一步依赖上一步吗、独立部分能并行吗、哪些错误代价最大、需要人类批准吗、系统怎么知道完成了。

### 故事

六问各自指向一个模式：可预测→固定工作流；依赖链→先计划后执行或 ReAct；独立→并行；错误代价→审批与护栏；需要批准→路由含人工路径；完成定义→停止条件。发票例子极简但锋利：模型提取信息，序列由应用控制——「代码是最好的规划器」在 agent 时代依然是默认答案。

### Aha 瞬间

**模式选型是一道检查清单题而不是品味题——问题答完，模式自动浮出；答不完问题就选模式，是在给架构物色流行色。**「不是每个任务都需要模型发明自己的执行序列」值得钉在所有 agent 项目的墙上。

## 发芽 02：计划是提案——白名单校验与「可观察≠暴露推理」

### 种子

先计划后执行模式里最容易被跳过的一句话：计划不天然可信——它可能漏掉必要步骤、或包含应用做不到的动作；要对照白名单校验每个动作。

### 故事

配套的可观察性纪律同样反直觉：存储「选了哪个工具、校验过的参数、结果、停止原因」的动作日志，就能让系统可调试（「查了三个官方定价页，发现一个套餐无公开价格」），而不必暴露私有内部推理。测试清单也按「结果」而非「计划文本」设计：用了可靠来源吗、算对了吗、证据够了就停了吗、区分已验证事实与假设了吗——评估的对象是系统行为，不是文本美感。

### Aha 瞬间

**「展示计划」与「信任计划」之间隔着白名单校验——把计划文本给用户看是 UX，把动作对照白名单跑一遍才是工程。**Chain-of-thought 不是计划，可执行、可校验、可停止的结构才是。

## 发芽 03：分工公理——模型管解释，代码管精确，「缺价格保持 None」

### 种子

Python 例子最小却最有信息量：`price_verified: source_url is not None`、缺价格保持 None 而不是猜——用模型解释权衡，用普通代码做乘法与规则执行。

### 故事

常见错误清单把它收尾成公理：用模型做精确算术、给 agent 太多工具、忘设停止条件、给简单任务过度规划。五条错误的共同反面是同一条分工公理：**凡确定性可判定的，代码做；凡需要语言与灵活解释的，模型做；两者边界处的动作（创建账户、花钱、发消息）要审批点。**这也解释了为什么「专家 agent 须有真分工」——同工具同指令的两个模型不是专家，是冗余。

### Aha 瞬间

**agent 架构的成熟度不在于用了多聪明的规划模式，而在于确定性边界画得多清楚——None 不是一个空值，是一个设计决策。**
