# 我把一个 LLM 功能上线了。模型是容易的部分。

> 原文：[I Shipped an LLM Feature to Production. The Model Was the Easy Part.](https://medium.com/@rohithraajk/i-shipped-an-llm-feature-to-production-the-model-was-the-easy-part-17fb23970a80)

---

**Demo 花了一个周末。生产花了六个月。**

这是我希望有人在我动手之前对我说的话。每个教程、每支发布视频、每条狂热的推文串，都做得好像模型在干活、你只需站在旁边显得聪明。然后你把它放到真实用户、真实规模、真金白银面前，真相来得飞快：**模型大约只占系统的百分之十。**另外百分之九十，是没人发帖炫耀的无聊工程。

以下才是真正吃掉我时间的东西。

## 你的 eval 集才是产品，模型只是个依赖

我的第一个错误，是用测 demo 的方式做测试：敲几个 prompt，眯眼看输出，说一句「看起来不错」。这套流程恰好能撑到没有任何东西变化为止。然后厂商发了新模型版本，或者有人动了系统 prompt，输出就发生了你靠肉眼盯五个例子永远抓不到的漂移。

所以我们建了一个黄金数据集：几百条真实输入与期望输出，人工复核，像代码一样做版本管理。每一次 prompt 改动、每一次模型升级、每一个配置调整，上线前都先过它。头两周感觉小题大做。然后它抓到一次回归——新模型版本开始拒绝一整类完全合法的请求——从此永久回本。

如果本文你只带走一件事，带走这个：**先建 eval 集，再建功能。**你不会上一个没有测试的后端服务，也别上一个没有 eval 的 LLM 功能。

## 延迟是功能，而模型不在乎你的 p95

没有人会等八秒的响应。现在不会，永远不会。但模型调用就是慢，而且偏偏在系统高负载时更慢——恰恰是慢最伤的时候。

我们开始把延迟当预算管理：流式输出，让用户一秒内看到东西；简单决策路由给小而快的模型，把大的留给难题；激进缓存——你会震惊于多少「独一无二」的请求其实是换了措辞的同一个问题；独立的调用并行跑，别像讲睡前故事一样把它们串起来。

这些没有一样是 AI 研究。全是后端工程。**这正是要点。**

## 在爱上架构之前，先算单位经济学

我评审过一个多 agent 管线的设计：规划 agent、研究 agent、批评 agent，彼此聊得像一家微型创业公司。优美。它也大约**每次请求 40 美分**。按我们的量，那是每月给 API 打的第二份工资。

我们用分类器加模板替换了其中大部分：**每次请求 0.2 美分。**在刁钻的边界案例上略差，在账单上好了几个数量级。

我不是说永远别用花哨的方案。我是说：**在设计评审之前、而不是账单到达之后，把每次请求成本乘上预期量。**最便宜的 token 是你从未生成的那个。

## 模型会在你脚下漂移，为它做计划

我们钉住了模型版本。我们把每件事都做对了。然后厂商还是弃用了那个版本，替换版对同样的 prompt 给出了不同的回答。不算错——确切地说是不一样。足够让下游解析在三处断掉。

**把模型当作一个不稳定的第三方 API 对待，因为它就是。**钉版本，但按「钉子保不住」来构建：结构化校验输出；prompt 放配置里，别硬编码；准备一个不需要深夜重写 prompt 的回滚方案。

同一个 prompt，换个星期二就不一样了。那不是你代码里的 bug。那是这份工作本身。

## 每个模型调用都需要一个非模型的逃生舱

超时。带退避的重试。熔断器。降级模式——模型宕机、变慢或开始幻觉时，依然给用户有用的东西。这是清单上最没光环的工作，也是最重要的。

我们某个功能的 fallback 简单到近乎寒酸：模型调用失败两次，就返回上一个已知良好的答案，附一行小提示。用户几乎没注意到。另一条路——转圈圈然后错误页——他们一定会注意到。

**如果你的功能没有优雅降级路径，你拥有的不是一个功能。你拥有一个带可用性要求的 demo。**

## 什么都记日志。凌晨三点你会需要它。

prompt、补全、token 数、延迟、模型版本、哪个 fallback 被触发了。出问题的时候——它一定会出——这就是「我们调查一下」和「我们确切知道发生了什么」之间的差别。

一个警告：prompt 里有用户数据。相应地对待你的日志：抹除 PII、设置保留策略、往第三方分析工具里灌原始 prompt 之前三思。**你需要的可观测性，不该变成你没预料到的那场隐私事故。**

## 不性感的大实话

六个月之后，我的诚实总结是：用 LLM 构建，大部分工作与 AI 无关。它关乎 eval、延迟预算、成本数学、版本管理、fallback 和日志——后端工程师实践了几十年的同一套纪律，应用在一个恰好是概率性的组件上。

此刻靠 AI 赢的团队，不是 prompt 写得最聪明的团队。是模型行为不端时，系统依然在线、依然快、依然便宜的团队。

**可靠性才是护城河。其余一切都是 demo。**

# 《I Shipped an LLM Feature to Production》的发芽报告

## 材料核心

「Demo 一个周末，生产六个月」——模型只占 LLM 系统的百分之十，其余是没人炫耀的无聊工程。作者的六课：先建 eval 集再建功能（黄金数据集像代码一样版本化）、把延迟当预算、在设计评审前算单位经济学、把模型当不稳定第三方 API 对待、每个模型调用配非模型逃生舱、什么都记日志（并抹除 PII）。

## 发芽 01：eval 集是产品，模型是依赖——依赖会漂，产品得稳

### 种子

你不会上一个没有测试的后端服务，也别上一个没有 eval 的 LLM 功能——而且 eval 要像代码一样版本化、每次变更先过它。

### 故事

文章的转折点很典型：头两周觉得黄金数据集小题大做，直到它抓到「新模型版本开始拒绝一整类合法请求」的回归——肉眼盯五个例子永远发现不了的那种漂移，从此永久回本。与之配套的态度是把模型当不稳定第三方 API：钉版本，但按钉子保不住来构建（prompt 进配置、结构化校验、随时可回滚）。

### Aha 瞬间

传统软件里「测试保护的是你的代码」，LLM 系统里 eval 保护的是「依赖的行为契约」——而契约的另一端你控制不了。这把测试的覆盖对象从内部逻辑扩展到外部依赖的漂移，是概率性组件带来的全新测试义务。

## 发芽 02：单位经济学要算在设计评审之前

### 种子

每次请求 40 美分的多 agent 管线像微型创业公司一样优美——也像第二份工资一样烧钱；分类器加模板，0.2 美分，边界案例略差、账单好了几个数量级。

### 故事

作者的规则很锋利：在设计评审之前、而不是账单到达之后，把每次请求成本乘上预期量。「最便宜的 token 是你从未生成的那个」——延展开是全链条的克制：简单决策路由给小模型、激进缓存（大量「独一无二」的请求其实是换了措辞的同一题）、独立调用并行而非串联。

### Aha 瞬间

架构美感和单位经济学是两个独立的评分项，前者容易在评审时绑架后者。给 LLM 方案定级时，先算「每次请求成本 × 预期量」，再看架构图——顺序反了，多 agent 的优雅就会在账单日变成负债。

## 发芽 03：逃生舱决定你拥有的是功能还是 demo

### 种子

如果你的功能没有优雅降级路径，你拥有的不是一个功能，是一个带可用性要求的 demo。

### 故事

文章的 fallback 寒酸到近乎天才：模型调用失败两次，就返回上一个已知良好的答案附一行提示——用户几乎没注意到；另一条路（转圈加错误页）用户一定会注意到。配套的是全量日志纪律（prompt、补全、延迟、版本、哪个 fallback 触发），外加一道隐私警告：prompt 里有用户数据，可观测性不该变成没预料到的隐私事故。

### Aha 瞬间

「失败时用户看到什么」是概率性系统设计的核心命题：模型必然会有不听话的星期二，设计的分水岭在于系统对失败的预设——是把它当成异常去展示，还是当成常态去兜底。可靠性不是不出错，是出错时的用户体验依然完整。
