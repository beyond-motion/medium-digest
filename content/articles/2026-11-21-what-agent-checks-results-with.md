# Agent 会拿什么校验自己的结果？

> 原文：[What Will the Agent Check Its Result With?](https://medium.com/@spacholski99/what-will-the-agent-check-its-result-with-f62e3c54f623) — Szymon Pacholski

---

把任务交给编码智能体之前，我会先看一件事：**这个 Agent 能拿什么校验它的结果**。当答案是「什么都拿不到」时，我会把建那个校验定为第一个任务，真正的变更放在它之后。

在我参与的一个项目里，Agent 手上有真实数据的本地快照和模拟流程的脚本：它可以试一个想法、跑起来、报告实际发生了什么。它工作在一份静态副本上，碰不到生产数据库。我们还围绕业务规则写了测试，并且在改动既有行为之前先写特征测试（characterization tests），记录系统此刻的行为。有些问题在代码里看着没问题，只有拿真数据跑起来才暴露。

下面是一个来自 AWS 的例子，把同一个想法放大到了大得多的规模；文末还列了当项目里什么都没有时，我会优先交给 Agent 的几样东西。

## 四晚监督，然后约两小时

AWS 的 Swami Sivasubramanian 在 Werner Vogels 的博客客座文（2026 年 11 月 11 日）里描述过这件事：他用智能体重建 Alf 的复制引擎——Alf 是一个基于 Paxos 的锁服务，当初的原始构建花了约四个月。他监督了 Agent 四个晚上，然后看清了一个事实：**它没有办法校验自己的结果**。一旦有了规格说明和一个测试环境，重建只花了约两小时。

这是一个人的故事，而且是由造工具的公司讲出来的，所以我把它当一个例子看待。但就我所见：当 Agent 跑不了任何能告诉它「对不对」的东西时，监督它的人就只能在每一步上手查。

## AWS Emulator：先拿真实服务校准测试

同一个思路的另一处放大是 AWS Emulator——由智能体编写并测试的、覆盖 200 多个 AWS 服务的本地副本。这些 Agent 从 AWS 公开的 API 模型（Smithy 语言写成）出发，为它们编写端到端保真测试。**先把每个测试修正到对真实 AWS 通过**，这样测试记录下的就是真实服务的行为；然后再构建模拟器，直到它通过同一个测试。哪个测试挂了，就指向模拟器的哪块缺口。

每个变更还要过一道合并闸门：自动化检查、若干做对抗性审查的安全智能体、一个通用代码审查者，以及阻止 Agent 改动不该碰代码的确定性检查。

这篇帖子对局限也很坦率：内部版本一个周末拼出来，做到健壮花了多得多的功夫；仓库里有一个 things-that-do-not-work 文件夹，列着尚未与真实 AWS 对齐的行为。

对我最有用的部分是**步骤的顺序**：测试先对真实系统校准，然后才构建应该通过它的那个东西——于是 Agent 手里永远有一个反映现实的目标。

Swami 还提到同一团队约二十年前怎么测 Alf：把服务器跑在带模拟网络的 JVM 里、注入丢包这类故障、用 TLA+ 做形式化推理——多数并发 bug 在上真实服务器之前就被消灭了。我的读法是：这类测试环境过去本身就是一大块工程，现在 Agent 可以接手去建它。

## 有参照物时才灵

AWS 的做法依赖参照物的存在：真实的云，加上每份 API 的机器可读描述。其他可用的参照还包括一个既有实现、一份 Agent 能转成检查的规格说明、或一份带已知结果的真实数据快照。什么都没有时，Agent 就没有可以逼近的目标——它写出来的代码只是「看着对」，然后由人来手查。

在我的项目里我还学到要看一件事：**校验里的期望值从哪来**。如果测试与实现共享同一个错误假设，它们会互相印证、测试照样通过。所以要永远追问期望值的来源：真实系统？源数据？还是某个人确认过的规则？

## 我会作为第一个任务交给 Agent 的东西

当 Agent 没有任何校验手段时，我会把下面之一定为第一个任务（在真正的变更之前）：

1. **对真实系统的测试**：做集成时，在测试账号或沙箱里对真实服务跑一个测试，记录它的实际响应。一旦通过，Agent 再写代码。
2. **既有代码的特征测试**：改行为之前，先记录系统今天的行为。它们可能连 bug 一起记录下来，并会在 Agent 改动不该动的东西时报警。
3. **一个小测试环境**：真实数据的本地快照，加一个端到端跑流程的脚本，让 Agent 能试一个想法、看结果。
4. **对着真物校准过的 fake**：调用真实系统太慢、太贵或太危险时，做一个与真物通过同一组测试的假件——这就是小规模的 AWS Emulator 思路。
5. **一个调端点的脚本**：改 API 时，有时一个让 Agent 每次改完就跑的简单脚本就够了。
6. **一份 Agent 能读的规格**：API 模型、schema，或一份写得能让 Agent 转成检查的业务规则清单。

我会把顺序直接告诉 Agent：先建校验、展示它对真实系统给出正确结果，然后实现变更。这些是我的建议，做到哪一步取决于项目——一次性脚本未必需要 fake 服务；对会被反复改动的代码，这个校验值得多花的功夫。

## 换模型之前，先查校验

Addy Osmani 在 claude.dev 的一篇讲选模型的文章（2026 年 11 月 9 日）里给过相近的排序：当一个模型对任务不够好时，他列的第一步是确认模型能校验自己的工作（一个测试、一次构建、一个调端点的脚本），之后是升一档 effort，然后才是换更大的模型。

我喜欢这个顺序。换更大的模型是最容易的一步，而当 Agent 分不清自己的结果对不对时，它帮不上多少忙。

## 留给工程师的部分

Swami 把有 Agent 时的工程师工作描述为：给他们自己运转的空间，同时建好决定「何为正确」的规格、测试与合并闸门。这与我给自己的分工一致：Agent 可以写很多代码、很多测试；**但判定什么算正确、期望值从哪来，永远留在运营这个项目的人手里。**

所以，在把下一个任务交给 Agent 之前，我会先问：它会拿什么校验自己的结果？如果答案是「没有」——建那个校验，就是第一个任务。

# 《What Will the Agent Check Its Result With?》的发芽报告

## 材料核心

Szymon Pacholski（5 min）：把任务交给编码 Agent 前先问「它能拿什么校验结果」，答「没有」就先建校验。作者项目：真实数据本地快照+流程模拟脚本（静态副本不碰生产库）+业务规则测试+变更前特征测试。AWS 案例（Swami Sivasubramanian @ Werner Vogels 博客 2026-11-11）：用 Agent 重建 Paxos 锁服务 Alf 的复制引擎（原始构建约四个月）——监督四晚发现 Agent 无处校验结果，给 spec+测试环境后重建约两小时。AWS Emulator：200+ 服务本地副本由 Agent 写与测，从 Smithy API 模型写端到端保真测试，**先修正测试对真实 AWS 通过（记录真实行为）再建模拟器过同一测试**，测试挂=模拟器缺口；合并闸门（自动检查+安全 Agent 对抗审查+通用审查+确定性禁改检查）；坦承局限（内部版一周末、健壮化费大功、things-that-do-not-work 文件夹）。参照物决定论：真实云+机器可读 API 描述，或既有实现/可转检查的 spec/带已知结果的数据快照；期望值来源审计——测试与实现共享同一错误假设时互相印证照样通过。首任务清单六项：真实系统测试/特征测试/小测试环境/对真物校准的 fake/调端点脚本/可读 spec。Addy Osmani 排序（2026-11-09）：模型不够好时先查自校验、再升 effort、再换大模型。分工：Agent 写代码写测试，「什么算正确」与期望值来源留在人手里。

## 发芽 01：监督四晚与两小时——校验能力是 Agent 生产率的分母

### 种子

重建一个原始构建花了四个月的 Paxos 复制引擎：监督 Agent 四个晚上，发现的不是能力不足，而是「它没有办法校验自己的结果」；给了 spec 和测试环境之后，重建只要约两小时。

### 故事

四个月 → 四晚+两小时的换算里，四晚不是浪费而是诊断期：人类监督者在这四晚里观察到的核心事实不是「Agent 写不好」，而是「写完了不知道对不对」——没有校验手段的 Agent 生产的是「看着对的代码」，每一步都要人手查，于是速度被人工审查串行化。一旦有了「反映现实的目标」，Agent 的并行试错能力才被释放。这个案例与 11-12 译文《权重正在变成代码》的「编辑/适配只能移除障碍」呼应：测试环境对 Agent 而言正是「移除不确定性障碍」的基建——它不提升模型的智力，它让已有的智力可以自我修正。

### Aha 瞬间

**给 Agent 加速的正确顺序不是更强的模型、更长的上下文，而是先补上「它知道自己对不对」的回路——没有校验分母的自主性只是一台更快产出需要人工复查的代码的机器。**

## 发芽 02：先校准测试再建被测物——AWS Emulator 的顺序论

### 种子

「测试先对真实系统校准，然后才构建应该通过它的那个东西——于是 Agent 手里永远有一个反映现实的目标。」AWS Emulator：先让每个测试对真实 AWS 通过（记录真实行为），再建模拟器过同一测试；挂掉的测试直接指向模拟器缺口。

### 故事

传统 TDD 的顺序是「先写测试再写实现」，但测试自身的正确性常被略过——测试错了，实现「正确地」满足了一个错误的规格。AWS Emulator 把「测试的正确性」也变成有参照物的实证问题：每一个测试都必须先在真实服务上验证通过，才获得作为目标的资格。这一步同时解决了 Agent 时代的一个新风险：Agent 生成的测试与 Agent 生成的实现可能共享同一个幻觉（两边都对同一个错误行为达成一致）。先对现实校准测试，等于把「现实」焊进了目标函数——被测物只能逼近真实，而不能逼近幻觉。

### Aha 瞬间

**测试不是中性的标尺，它自己也需要校准——「先让测试对现实通过，再让实现过测试」这一步顺序，是把 TDD 从自洽系统升级为与现实挂钩的系统的那一颗螺栓。**

## 发芽 03：期望值从哪来——共享假设的互相印证陷阱

### 种子

「如果测试与实现共享同一个错误假设，它们会互相印证、测试照样通过。所以要永远追问期望值的来源：真实系统？源数据？还是某个人确认过的规则？」

### 故事

这是全文最小也最锋利的一条：一切校验的形式有效性都建立在「期望值独立于实现」之上。当期望值与实现同源（同一个人写的、同一份有偏的 spec、甚至同一个 Agent 的同一套假设），绿灯只是自洽的证明，不是正确的证明。作者给出的审计动作极简：对每个校验问一句「期望值从哪来」，并要求答案是三类独立来源之一——真实系统、源数据、被确认过的规则。这条与 AWS Emulator 的顺序论同构：Emulator 是在系统级防共享假设（测试对真实服务校准），这句是在单测级防（期望值来源审计）。特征测试是它的一个特例：期望值来自「系统今天的行为」——它能防回归，但会把今天的 bug 也固化成期望，所以它只能证明「没改不该改的」，不能证明「对」。

### Aha 瞬间

**一个测试的价值不取决于它跑没跑过，取决于它的期望值与被测物是否独立——期望值的来源审计（真实系统/源数据/被确认的规则）是自动化时代最便宜也最容易被跳过的一道质检。**
