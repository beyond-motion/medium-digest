# 当 agent 写代码时，「所有权」意味着什么

> 原文：[What ownership means when agents write the code](https://medium.com/@viajesubmarino/what-ownership-means-when-agents-write-the-code-ae269f04ace5)

---

## 两个实验，一条委托光谱

Edgar Bermudez 用两个真实场景开场。一个是「远程委托」：一次长途自驾前，他准备好指令、边界与检查点，让编码 agent 在多个工作周期里自行开发软件，自己只在每次停车加油或活动腿脚时检视进度。另一个是「贴身协作」：为一个医疗推荐平台做评估系统，他用 IDE 的 ask 模式逐条人工评审架构决策与实现细节。

这两种方式如今都是他构建软件的常态。试验一段时间后，他分得清什么时候用自己的 AI-first 框架、什么时候给 IDE agent 派任务、什么时候亲自做决定只是让 AI 从旁协助——选择取决于任务与场景。他的 AI-first 框架围绕 agent 角色与显式工件组织开发：需求变成规格说明，架构工作产出设计文档，实现通过定义好的交接推进；Obsidian 里的 agent 工作流把计划、约束与决策保存在 Markdown 中，可离线检阅、跨工具与会话携带。

这些工作流给了他不同的参与方式，但也逼他追问：如果 agent 能完成越来越长的任务、评审结果、参与决定系统如何构建——开发中还有多少需要「我」？

## 委托实现、评审、乃至架构

他认为亲手敲例行实现没有多少价值——可以委托并验证结果。agent 能生成代码、跨文件修改、写测试、迭代修复。但他同时强调：任何生产力对比都必须计入准备任务、评审输出、纠正错误、维护结果的花费——这是被媒体吹捧文略去的部分。连测量一般性生产力效应都很难：METR 2026 年 2 月的跟进报告承认，选择效应使其后期估计不可靠。

手动编码他保留在学习、排查问题、或直接做小改动这些场景。同样的推理适用于代码评审与架构分析——agent 都能做，他的框架甚至已经给 agent 派了评审角色。于是「人类会评审代码」成了一个不完整的答案：评审本身可以自动化，把人挪到架构层也只是推迟问题。他需要一个随着工具进步依然成立的、人类参与的理由。这与他的旧文呼应：「决定造什么，也是在决定我愿意为什么负责。」

## 所有权需要什么

作者给出的定义：**所有权（ownership）是能解释系统为何存在、决定哪些权衡可接受、并为系统的使用承担责任**——包括在需要变更或出错时拥有响应的权力与资源。为此亲手写每一行从来不是必要条件：软件本来就依赖库、服务与他人的贡献，人可以为一个系统负责而不必是它的唯一作者。

真正的风险是：**责任被保留，而行使责任所需的理解与控制流失了。** 比如，你仍然在批准变更，但逐渐依赖 agent 对这些变更的解释；决策记录只在「其断言可对照工作与证据验证」时才有用。他用医疗场景举例：某机构用 AI 生成治疗建议，评估器（无论生物还是人工）按规则正确算出了患者风险分数——测试能证明计算正确，但「这个分数能支撑关于推荐质量的有用结论」需要另一种证据。评估标准的选择本身必须与实现一起被审视；agent 可以帮忙提出与检验标准，但「组织准备从这些标准中得出什么结论」仍需要有人有权拍板。

## 什么让人类监督有意义

这也是为什么「人在流程中的位置」说明的问题越来越少。「human in the loop」通常指在特定动作执行前审批；「human on the loop」指监督可独立推进、随时可介入的工作。两者可在同一项目共存——但**任何一种安排都不保证有效监督**。有效的监督需要：相关信息、足够的理解、评估的时间、以及叫停或转向的许可。缺了这些条件，指定责任只是让人装备不良地扛责。

冗长的审批队列会让情况更糟：如果实际预期是尽快批准每个变更，评审就沦为形式。自动化评审员能减轻负担，但它们的同意同样需要语境——如果实现者、评审者与测试都源于同一个错误假设，它们会在和谐一致中一起错过问题。真实行为的证据、独立检查、系统的预期用途，仍然不可替代。

## 风险如何随时间演变

短期，压力来自工作量：更少的直接投入能生成更多的实现与评审，也制造更多需要理解后果的变更。对工作流的要求是：自主权必须依赖清晰边界、有用证据与从错误中恢复的能力。

长期，他更担心的是**维持控制所需的知识**。他的技术判断是多年来造东西、学概念、查故障、重访旧决策攒出来的——委托越多，越要有意识地决定保留哪些形式的实践。这个担忧延伸到团队：资深工程师用多年实现经验监督 agent，而入行的新人需要发展自己判断的机会；一个剥夺这些机会的开发流程，会让未来的监督更难——初级开发者可能永远停留在不熟练。还有供应商维度：如果团队只能通过某一家供应商的 agent 理解和维护系统，对该供应商的访问就成了运营能力的一部分——可检阅的工件有帮助，但工件本身必须有足够的内容支撑交接。

更远的未来，agent 可能接管架构、评估、监控乃至故障恢复，解释系统或响应事故也可能做得比人好。到那时，作者点出对他而言极重要的一点：**「人类总会在下一个技术任务上做得更好」不能作为人类参与的论据。** 他仍然希望人与可问责的组织保有对系统目的与使用的权威——因为「它服务谁的利益、哪些后果可接受、受影响者如何申诉」这类决定超出技术表现；agent 可以提供信息，但把定夺权交给它们，是另一个关于权力与责任如何分配（和保留）的选择。

## 那么，agent 干活时，谁来问责？

作者的定义分得很清：**所有权是理解并指导系统的能力；问责（accountability）是为启用系统的决定作答的义务。** 对他而言，负责任的 AI 包括为「把一个 AI 系统投入使用」的决定负责。即便 agent 写、审、部署，这份问责也应归于授权工作的组织——包括决定 agent 何时可以不经另一次人类审批就发布变更：显式的发布条件、证据要求、升级规则，以及为系统持续使用指定的责任人。agent 的执行成功，不能替组织回答「这个决定是否负责任」。

以医疗推荐平台为例：合格领域专家应评估评估标准是否支撑预期用途；工程与运维负责技术验证、监控与恢复；领导层则须授权可接受的风险，并给团队行动所需的资源与权力。自愿性的 NIST AI 风险管理框架是个有用的参照：它要求跨团队的清晰职责，并要求高管层为 AI 开发与部署相关的风险决策负责。模型与工具供应商也有份——按 OECD 的问责原则，责任按角色与情境跨组织与个人分配，持续的风险管理以各自的行动能力为边界。

问责在部署之后仍要继续：监控、调查、以及受影响者挑战结果的途径。日志能告诉你哪个 agent 发布了变更，但你仍需要一个能解释「为什么允许这个变更」、能响应其影响、必要时能纠正或暂停系统的组织。

## 让责任可执行

这正是监管在长期的意义所在：组织可以享受更快开发的收益，而让别人承担其决策的部分后果。好的内部实践有帮助，但会在压力下弱化；可执行的义务能建立挺得过团队更替、供应商更换、业务优先级变化的预期。EU AI Act 是个具体例子：对被归类为高风险的 AI 系统，第 14 条要求与其风险、自主性和用途相称的监督措施——让人理解相关局限、识别对输出的过度依赖、能够覆盖或叫停系统；第 26 条规定被指派监督的人需要能力、培训、权威与支持。这些条款有分阶段适用时间表，且用 agent 写代码本身并不决定软件是否落入高风险类别。作者觉得最有用的是那条原则：**责任与行使责任的能力必须绑定**——指定的评审者需要支持与权威，组织必须让监督成为可能。

监管也可能设计不良：只增加签名与文书、却不提升任何人理解或质疑决策的能力，制造的是控制的表象。评判这类规则的标准是：它们是否产生可用的证据、清晰的义务、以及一条人们挑战伤害的现实路径——并且给技术变化留出改进的余地。

## 我想让自己的框架保留什么

回到他正在测试的框架：他会继续委托更多的实现与分析，并希望框架的下一版让「所有权是否在场」更容易评估。他想试的一个新增项，是为每个被委托的工作流加一份简短的**所有权记录**，追踪五件事：

1. agent 无需进一步审批即可做的变更；
2. 接受结果所需的证据；
3. 触发升级（escalation）的条件；
4. 对其使用负责、且有权改变方向的人或团队；
5. 叫停工作、限制影响、或从错误中恢复的手段。

然后检查：记录里点名的人或团队，是否真的拥有行动所需的信息、时间与访问权。这让「允许多大自主权」变成一个可以具体评估的问题。

驾驶实验与医疗评估让他站在委托光谱的两端，他打算继续并用两者——要紧的是清楚每个位置上自己得到了什么、放弃了什么。他想继续精进的专长是：何时退后、何时质疑一个决定、什么证据足以让 agent 继续。这些边界会随工具进步而移动，但他仍希望：**对系统负责的人，保有足够的理解与权威去改变它的方向。** 这就是他想让框架保留的东西。

# 《What ownership means when agents write the code》的发芽报告

## 材料核心

作者以「长途驾驶时让 agent 独立开发」与「贴身评审医疗评估系统」两个实验为引，论证当实现、评审乃至架构都可委托给 agent 时，「人类会评审代码」不再是人类参与的充分理由。他区分所有权（理解并指导系统的能力）与问责（为启用系统的决定作答的义务），指出真正的风险是责任被保留而理解流失；监督的有效性不取决于人的位置，而取决于信息、理解、时间与叫停权四条件；问责最终归属授权工作的组织，并需监管（EU AI Act 第 14/26 条）让责任与行使责任的能力绑定。落点是每个委托工作流配一份五项「所有权记录」。

## 发芽 01：评审不是立足点——找到随工具进步依然成立的理由

### 种子

「人类会评审代码」是个不完整的答案：评审可以自动化，把人挪到架构层也只是推迟问题——作者要求的是一个随工具改进依然成立的人类参与理由。

### 故事

文章的推进方式本身就是论证：实现可委托（代理生成、改文件、写测试、迭代修复），于是人退到评审；评审可委托（agent 检查一致性、建议测试、挑战实现），于是人退到架构；架构分析也开始可委托。每一次后退都让旧立足点失效，最后作者在技术能力之外找到了那个理由——对系统目的与使用的定夺权：服务谁的利益、哪些后果可接受、受影响者如何申诉，这些决定不随技术表现失效。

### Aha 瞬间

评估自己在协作链里的位置时，别用「我还能做哪一步」来回答，要用「哪一步的责任无法让渡」来回答——能力会过时，责任不会。

## 发芽 02：责任会滞留在失去理解的人手里

### 种子

所有权最锋利的风险不是失去责任，而是「保留责任的同时，失去行使责任所需的理解与控制」——你还在批准变更，但已经依赖 agent 解释这些变更意味着什么。

### 故事

文章用医疗评估器拆解了这个陷阱：测试证明评估器「按规则正确计算了风险分数」，但「分数能支撑关于推荐质量的有用结论」是另一种证据；评估标准的选择必须与实现一起被审视，而组织准备从标准中得出什么结论，仍需有人有权拍板。决策记录也救不了场——它只在断言可对照工作与证据验证时有用，否则只是理解流失的遮羞布。

### Aha 瞬间

审批本身会制造问责的错觉：签名还在流动，理解已经断流。判断自己是否仍拥有一个系统，看的不是「变更是否经我批准」，而是「我能否独立核对这些批准背后的断言」。

## 发芽 03：教练会衰减，判断必须常驻

### 种子

作者为每个委托工作流设计的「所有权记录」里，最后一项不是证据而是恢复手段：叫停工作、限制影响、从错误中恢复的具体方式——并要求事后核验被点名者真的有信息、时间与访问权去行动。

### 故事

整篇文章对「设置一次、永久生效」的方案保持怀疑：监管可能沦为签名仪式，内部实践会在压力下弱化，agent 的自主边界会随工具进步而漂移。所以他把设计重心放在一个可持续的位置——由人持有的、可以随时重新评估「允许多大自主权」的判断，以及判断失效时把系统拉回来的物理手段。

### Aha 瞬间

任何治理机制都要回答「它衰减之后靠什么」——规则会过时、上下文会稀释、约束会被绕过；真正的兜底不是更密的规则，而是有人始终保有叫停的意愿、权限与能力，并且制度记得核对这一点。
