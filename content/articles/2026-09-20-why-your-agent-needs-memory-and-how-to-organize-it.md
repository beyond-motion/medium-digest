# 为什么你的 Agent 需要记忆，以及怎么组织它

> 原文：[Why Your Agent Needs Memory, and How to Organize It](https://medium.com/generative-ai/why-your-agent-needs-memory-and-how-to-organize-it-4509a900152e)

---

## Agent 记忆不是人类记忆

我是 Volodymyr Vreshch，我在一台机器上为我的编码 agent 维护着一个个人记忆库：181 个主题文件，背后是一个 134 行的索引。里面几乎没有「知识」。

agent 本来就知道 Express 中间件怎么工作、Playwright 测试长什么样、Dockerfile 干什么用——它读过的这类东西比我一辈子读的都多。我写下的每一行都出于相反的理由：**那是我的世界与领域平均值不匹配的地方。**部署校验器会在某项检查无法运行时故意拦下发布；发布流水线的自批准闸门读的是 `.status` 而不是 `.conclusion`——这个坑让我赔了一个下午，然后变成文件里的一行。

这就是这个东西的形状：**Agent 记忆不是 agent 所知内容的副本，而是差量（delta）——剩下没人告诉它就猜不出的那部分。**下文出自运行这个库的实践，不是读了几篇讲记忆的文章。

### 为什么多数人第一步就走偏

直觉是类比推理：我会记东西，所以 agent 也该记东西。这个类比在第一步就断了。人类记忆必须同时装下平均和例外，因为人生下来是空的；而模型出厂就带着平均值，规模是任何个人都比不了的。告诉它什么是中间件不增加信息，只增加 token。

而 token 不是免费的——这恰恰是多数人搞错的地方。**不需要的上下文不是中性的，是负的。**有一项研究测量模型正确调用 API 的频率：当模型拿到它早已熟悉的 API 文档、而检索又不完美时，正确调用率掉了 **39 个百分点**（arXiv:2407.09726）。同样的文档，拿给模型不认识的冷门 API，准确率反而升了 9 个点。同样的内容，同样的管线，相反的符号。

这改写了记忆文件的定义：**它是对模型既有假设的一份 diff。**每一行重复众所周知的约定，都在和真正要紧的那一行抢注意力——房间里稀缺的东西是注意力。

> 只写下模型猜不出的东西。

拿这条标准去量真实的上下文文件，团队放进里面的大部分都会被筛掉：命名规范、「组合优于继承」、标准目录结构——那正是领域平均值，是 linter 的领地，模型本来就有。真正有分量的行通常是丑的：变通办法、走不通的路、只在此处为真的事实。

我自己的库是 181 个主题文件、3,697 行（算上索引 3,831 行），没有一行解释中间件是什么。我删掉的行，恰恰是那些漂移成「解释知名工具」的行——模型早就懂，却让每次请求都白白付费。

## 最便宜的记忆，是不需要的记忆

如果记忆承载的是差量，那么**记忆的大小取决于你偏离通用模式有多远**。用主流架构，你几乎不欠 agent 什么；自创一套模块系统，它的每条规则都变成你必须写下来、保持为真、并在每次请求付费的一行。

这不用跑基准也能感觉到：让 agent 做主流技术栈里的事，它直接开干；换一门小众语言或自研内部框架，它停下来、瞎猜、或者反问你。补上这个差距意味着你自己扛上下文——写它、版本化它、永远维护它。

我没有干净的 A/B 实验，也不假装有。本文的论文支撑机制，我的文件只支撑实践，我不拿后者冒充前者的证明。普通栈的新活很快；大型老系统里的活很慢——那里的大部分上下文从未被写下来，有时比手写还慢。

所以**架构选择如今就是记忆选择**。选无聊的、广泛使用的模式，你就不欠任何需要永远维护的东西。

> 对通用模式的每一次偏离，都是一行你要写下并永远保持为真的记录。

自建路径在未来的每一次请求上都更贵，而不只在创建它的那一次。

## 难的不是记，是保持简单

这是 why。下面是 how。在生产里杀死记忆系统的不是遗忘，是累积。

- **价值增长慢于体积。**两倍的记忆不等于两倍有用——噪音堆得比信号快。过了某个点，更大的库答得比小的时候更差，哪怕问的就是那些喂大它的问题。
- **冲突增长快于体积。**每条新事实都可能跟已有的每条事实矛盾，可能的冲突攀升远快于文件数。而矛盾的代价比缺口大得多：缺一条事实，agent 不确定——不确定没关系，它会问，或者在看得见的地方失败。一条矛盾的事实，agent 自信且错误，循环里没有任何东西报警，没人发现。
- 更糟的是，多数记忆产品看不见冲突。向量相似度看见的是「两句话聊同一话题」，看不见一句说 YES 一句说 NO。

价值走平，冲突继续爬升，过了某个规模，**你的记忆系统正在让你的 agent 变差**。记忆不会响亮地失败——它失败的方式是一边每次查询都成功、一边自信地变得更错。所以难的不是堆积——每个产品都乐意替你堆——难的是保持小而依然够用。这需要删除，删除意味着评判自己旧日的文字。

本能反应是加结构：堆乱了，就上一套分类法——层级、类别、图、形式化知识结构。这 reliably 让事情更糟。2026 年的一项评估里，有人给一个按需上下文索引加了深度，同样的模型、同样的测试框架，准确率从 **0.91 掉到 0.64**（arXiv:2607.17598v1）。百分之三十的跌幅，全靠结构买一送一。扁平在所有被测的地方都赢了层级。精致的结构修不了复杂性——它是在原有复杂性之上叠的第二种复杂性，现在你要维护两个。

所以组织记忆，与其说画一张更好的图，不如说**给每一行设一条要过的门槛，并让这个库让过关变得便宜。**

### 每个记忆单元要过的四道测试

门槛设在单元上，不在系统上。四道测试，我的库里的每个文件都要过。在团队里，这也是评审者检查的东西：

1. **简单且致密。**只放种子信息。没有为了显得完整而存在的句子。如果一行不改变 agent 将要做的事，它是装饰，装饰不免费。
2. **互不冲突。**不存在两条不能同时为真的事实。这条最需要主动维护，因为冲突积得慢、且从来不是故意的。
3. **可度量的有用。**记忆不让 agent 更聪明，它让 agent 在同等质量下更快更省——不是更好的答案，是同样的答案省掉重新发现。如果一份文件在真实任务上看不出省时省 token，它就在白吃维护成本。
4. **分了类。**核实过的事实、假设、偏好、传闻不能长得一样。我的文件把类别写在文件名里：117 个 `reference_` 文件装核实过的事实，50 个 `feedback_` 文件装长期规则，14 个 `project_` 文件装会过期的状态。打开之前就知道它在声称什么。

一项已发表的结果看着像推翻第三条，其实是反向印证它。ETH Zurich 的研究（arXiv:2602.11988）对比了仓库上下文文件与什么都不放：任务成功率没有普遍提升，推理成本增加超过百分之二十，机器写的文件甚至略低于什么都不放。用 delta 规则一读，它就不再是反例：**一份塞满平均知识的文件正是这条规则预言的东西——真实成本，零收益。**这个发现说的不是上下文文件没用，而是「只复述平均值」的文件没用——而那是大多数。

所以纪律不是写，是删：让每行致密，绝不让两行互相矛盾。Addy Osmani 今年八月从维护侧说了同一件事：agent 文件会随模型进步而腐烂，所以要定期修剪重建，而不是永远只加不删。**只增不减的记忆是一颗定时炸弹。**

然后把活下来的部分按任务切片，像你自己的记忆那样：写文档时加载的，和调试构建时加载的，不是同一份。

> 你需要的不是一份记忆，而是眼前这个任务的最小正确切片。

### 你的存储必须满足的三条要求

四道测试没说文件住哪，那是组织的另一半。我没有评选「最佳存储格式」，而是注意到：仓库里那些已经在读 markdown 的工具，除了 markdown 之外对什么都不达成一致。`AGENTS.md` 是一个已知路径上的纯 markdown 文件，被二十多个在所有其他事情上都互相竞争的工具读取；而没有任何一个记忆 API 被竞争对手实现过两次。一项对生产编码 agent 的调研发现七个 agent 在互不通气的情况下落进同一个设计：一份常驻上下文的小 markdown 文件，加一个磁盘上按需打开的大档案。没有一个伸手去拿向量搜索。

没对过基准的七家，撞上了同样三条要求：

**一、什么都不装也能搜。**人们听到「搜索」就想到语义搜索，但那甚至不是常见情形。Anthropic 自家的记忆工具只有 view、create、replace、insert、delete、rename——根本没有 query。它指望 agent 列目录、读文件。如果你的记忆只在索引建好、嵌入新鲜、厂商在线时才能工作，你就在上下文前面放了个薄弱点。**它必须在这一切都宕掉时还能工作。**

**二、改动必须有人盯着。**自更新记忆正是这个领域眼下受伤的地方。一项生产审计检查了 10,134 条自动抽取的条目，**97.8% 是垃圾**（mem0 issue #4573）。另一项研究让模型把自己的成功运行写回记忆，**四个 agent 上有四个得分低于没有记忆**（arXiv:2505.16067）。自己会写的记忆不会温和地漂移——它自信地漂移。所以记忆的每次变更都要可评审，可评审意味着你能以 diff 看见它、拒绝它、撤销它。

**三、用已经开着的工具就能养护。**记忆系统很少死于损坏，多死于疏于打理：有人写了一次，之后再没人碰，漂移到撒谎为止。一篇 2026 年研究的综述发现，一半的上下文文件在首次提交后再也没更新过；持续修订的那 6% 属于「说 agent 真的有用」的人。我自己的文件同构：重写过的还在挣饭钱，只写了一次的就是我删掉的那些。养护必须发生在你整天开着的编辑器、搜索和版本控制里。

规格到此为止。剩下的问题只有一个：哪种存储满足它。

### 为什么 git 里的 markdown 文件三条全过

诚实的框架：文件不是我的发现。「Markdown 干翻向量数据库」这个话题 Medium 上过去一年至少吵过六次，Hacker News 的帖子下面也总有那句「一大堆字就说用文本？」如果你读成了我在反对所有人，你读错了文章——这场对话缺的是为什么。三个月里三家卖记忆数据库的厂商发文炮轰文件；两家出 agent 的厂商早就选了文件。这场仗里我没有东西可卖，我有的只是一个文件夹。

系统存什么，决定下游的一切。**Mem0** 存 LLM 抽取的句子加嵌入——向量索引里的一行，你还给你的不是原文而是抽取器的转述，而且打不开。**Zep** 在图里存带类型的边，每条事实跟两个时间线，修正靠替换：旧边标记死亡，不改写。一家向量原生的记忆初创跑了多年向量档案，2026 年初把 git 仓库里的 markdown 文件树设为编码 agent 的默认存储，每次编辑一个 commit。**Anthropic** 的记忆工具就是对你自己客户端执行的 `/memories` 目录做文件操作；仍在测试的 Memory Stores API 按路径命名、用内容哈希解决并发写——**披着 HTTP 皮的 git 数据模型**。消费级助手存一份只有渲染态的摘要，截至 2026 年 9 月没有一家提供文档化的机器可读导出。

摆在一起，真正的分野不是「文件 vs 数据库」，而是**可读 vs 不可读**。文件形状之外的所有选项共享一个属性：你无法把记忆 diff 到两个时间点，你只能用开关修正它，而不是用 commit。

### 两边都在发布，两边都有道理

MatrixOrigin 今年 3 月说静态 markdown 会腐烂、不强制任何东西。五周后 Mem0 发文《你的 AI Agent 的记忆只是个文件？这就是问题所在》，论点是平面文件重复了 1970 年代前数据库时代的错误：没有语义搜索、没有时间推理、没有并发写安全、没有遗忘。6 月 Zep 发文《Markdown 不是 agent 记忆》，其中最锋利的一句真的好：「markdown 文件记录的是写了什么，不是它替换了什么、为什么替换。」与此同时，Anthropic 自家的编码 agent 把记忆存成磁盘上的纯 markdown；Windsurf 的文档悄悄叫你把想保留的东西从它的记忆库挪进版本控制里的 markdown。注意谁在卖什么。

数据库厂商有两点是对的。**向量赢在词不重叠的场景**：你问「我说的那个关于 burnout 的东西」，笔记里从没出现过 burnout 这个词——只有嵌入能补上这个缺口，而且在百万行规模上一样快。grep 找不到你叫不出名字的东西。**图赢在时间**：只有盖了起止戳的事实才能回答「上周二我相信什么，后来什么取代了它」；相似度分数对两条矛盾事实哪个是当前版本没有立场。在一个长记忆基准的时间类问题上，第三方复测图系统 63.8% 对向量系统 49.0%。文件在两项上都输。

### 证据，连同它的警告

2026 年的检索结果跟领域预期相反：用 `grep`、`find` 和文件读取在纯文件堆里搜索的 agent，击败了被测的所有关键词、嵌入和重排基线。一项 agentic-search 基准上，**去掉嵌入检索器、让 agent 直接读文件，准确率从 69% 升到 80%，成本降了近三分之一**（arXiv:2605.05242）；另一项长期记忆研究里，纯关键词搜索在它测的每个 inline 工具调用配置里都赢过语义搜索（arXiv:2605.15184）。但一旦结果以文件形式返回，排序在一半的测试对上反转——问题奖励找到字面物：一个精确日期、一个计数、一个标识符、一个报错字符串。

警告来自第一篇论文，我不打算把它埋起来：**文件堆从 10 万涨到 40 万文档，同一套方法从 80% 跌破 40%，工具调用多三倍。**grep 在一个包络里有效——是一个尺寸区间，不是定律。区间内质量和成本双赢，区间外崩盘。所以诚实的问题是你在这条包络的哪一侧，而不是哪个系统赢。我整个库 181 个文件，比麻烦开始的地板低几百倍；LinkedIn 的生产记忆系统不是，我不主张它用 markdown。

对着三条要求量一遍，markdown 文件几乎零成本地全胜：grep 是兜底，改动是 diff，在仓库里是一个可撤销的 commit，养护工具本来就在你屏幕上。还有两样白送的：矛盾可见（两条冲突的事实是两行文字，不是两个浮点数组）；存储格式即导出格式。

> 不能 grep、不能 diff、不能删掉其中一行的东西，不是你的记忆，是别人对你的缓存。

文件的代价我宁愿点名也不藏：需要海量文档上的模糊召回时，文件输给嵌入。答案是**把索引架在文件上面、随时可重建，而不是取而代之**。Basic-memory 用 SQLite 这么做，memsearch 用 Milvus，Karpathy 的 compounding-wiki 用一个索引页、零嵌入。当索引就是存储本身，你为了本可以另得的召回，交出去的是检视、diff、所有权和可移植性。

### 我实际怎么组织

原则廉价，以下是今天正在运行的系统：

- **一个分层的指针文件，不是宣言。**agent 最先读的根文件只有 21 行，是一张地图：三个顶层区域各一行，指向更深的文件。下一层，projects 文件装真正属于我的东西：哪个仓库活着、哪个死在改名里；一切对齐到的版本；要遵守的沟通规则。这类文件在我的项目树里有 28 个，全是我写的，工作走到那里才加载。
- **agent 写、我批准的库。**旁边是 auto-memory：181 个主题文件挂在一个 134 行的索引后面。会话开始只加载索引，主题文件在任务伸手时才打开。
- **收录规则。**只收模型答错的、或不可能知道的。不是我猜将来要用的规则，是闯过祸之后写下的真实失败。三个真实例子：线上 web 仓库所在的目录与旧文档写的不同，编辑前先看 git remote；部署后的清理是尽力而为，因为并发部署会抢锁；永远不用 em dash。没有一条能从代码里读出来，没有一条在任何模型的权重里。**这就是全部的录取考试。**
- **按任务分组，不按主题。**我的库按工作切：设计任务和部署任务需要不同上下文，混在一起只会互相稀释。
- **知识层是我的，不是 agent 的。**规范、决定、计划、研究住在 Obsidian vault 里——大约一千七百个 markdown 文件，我写、agent 读。分开很重要：agent 的记忆是工作留下的痕迹，vault 是我打算做的事。混在一起，这个库就会对「什么被决定了」撒谎。

### 分层是为了加载，不是为了推理

数一数层级：四层。这正是前面 0.91→0.64 那项研究反对的深度。但那项研究变的是深度，不是「有没有索引」——它的最优配置是一个扁平的按任务索引，agent 一口气读完再决定开哪个文件：对上裸导航准确率近乎翻倍，成本约一半。准确率是在索引长出分支、模型只能靠标签猜哪条藏着答案时崩掉的。

我的索引就是扁平款：恰好一层深，会话开始整读——134 行，大约一题一行，每行说出它路由到哪些文件并用一个从句概括。没有分支可猜。**它是一张我手工维护的短路由表，不是一套要模型推理的分类法。**它还被允许不完美：181 个文件里有 11 个根本没列进去。下面的每个主题文件都小、扁平、整读；一层打开是因为工作走进了那个区域，而不是因为一个查询去找。这就是渐进披露。

检验很简单：如果模型必须靠标签猜哪个分支有答案，你建的是一棵树，等着付 0.64；如果它整读索引、按名字开文件，你建的是一个加载顺序。

> 结构用来决定加载什么，不是给模型推理用的。

### 守护措施：自己会写的记忆会漂移

agent 提议，改动以 diff 出现，我接受，或者不接受。住在仓库里的文件自带历史，「它为什么信这个」有一个可读的答案——向量库和厂商记忆页根本答不了这个问题。**没人评审过的记忆，是一条带文件名的谣言。**

隔一阵我做一次无聊的巡检：删掉六月为真的行、模型此后自己学会的文件、被更好规则取代的规则。这个库缩水的频率超出人们预期。对一个人这是习惯，对一个团队这是 pull request：记忆文件住在仓库里，对它们的改动像代码一样评审，没有谁的 agent 能悄悄学会团队从未同意的东西。

这一切都是我磁盘上的纯 markdown，不需要那个帮它写出来的助手。明年出更好的，我把同一个文件夹指给它，继续。

所以整套组织方法印在一张卡片上：**你留下的每一行过四道测试，存放它的地方过三条要求，agent 和文件之间站着一个人类。**

想知道自己的位置，一次编辑就够：打开你项目的上下文文件——`CLAUDE.md`、`AGENTS.md` 或你的工具读的那份——删掉每一行模型自己就能猜到的。我删了一半。拿下一个真实任务对着剩下的跑，看有没有真的变差。然后，下次 agent 搞错一件它不可能知道的事，精确地写下一行，像代码一样评审它。这就是纪律。**它不靠加东西来扩展。**

> 模型已经知道平均值。你唯一的工作，是差量。

# 《Why Your Agent Needs Memory, and How to Organize It》的发芽报告

## 材料核心

Agent 记忆的 defining 规则是 delta：模型出厂自带领域平均值，写在记忆里的每一行都该是「模型猜不出的事实」，否则只是每次请求白付 token 的负资产。由此推出一套完整纪律：每个记忆单元过四道测试（致密、不冲突、可度量的有用、分类），存储过三条要求（零依赖可搜、改动可评审、用日常工具养护），git 里的 markdown 文件在作者 181 个文件的规模上三条全过——前提是人类站在 agent 和文件之间。

## 发芽 01：上下文不是资产，可能是负债

### 种子

不需要的上下文不是中性的，是负的——注意力是房间里稀缺的资源，每一行废话都在稀释要紧的那一行。

### 故事

文章的两组数字互为镜像：熟悉的 API 配上不完美的检索，正确调用率掉 39 个百分点；同样的文档给冷门 API，准确率升 9 个点。ETH Zurich 的研究补上第二刀：机器生成的仓库上下文文件让任务成功率无普遍提升、推理成本涨超 20%——塞满平均知识的文件正是 delta 规则预言的「真实成本、零收益」。

### Aha 瞬间

「给模型更多背景」是一种本能错觉：背景分两种，模型没有的和模型早就有的，只有前者增值。写任何上下文文件前先过一遍「模型会猜到吗」——不会写文件的人和写得烂的人之间的差别，就是会不会删。

## 发芽 02：记忆的死法是自信地变错

### 种子

缺口让 agent 不确定——不确定是安全的，它会问或在看得见的地方失败；矛盾让 agent 自信且错误——循环里没有任何东西报警。

### 故事

文章画出两条曲线：价值随库增大而走平，冲突随库增大而加速攀升，交点处没有任何警报响起。向量相似度看不见冲突——它只看见「两句话聊同一话题」，看不见一句 YES 一句 NO。让模型自己写记忆的下场：10,134 条自动抽取的条目 97.8% 是垃圾，四个 agent 全部低于没有记忆的基线。

### Aha 瞬间

这把「记忆维护」从存储问题重新定义成验证问题：记忆系统需要的不是更大的容量，而是让矛盾可见、让变更可评审、让回滚可行的机制。两条冲突的事实是两行文字时矛盾显而易见，是两个浮点数组时永远隐形——可读性本身就是正确性基础设施。

## 发芽 03：规模决定答案，没有普适赢家

### 种子

grep 在一个包络里有效：10 万文档内 80% 准确率、成本省三分之一；40 万文档时跌破 40%、工具调用多三倍。

### 故事

文章拒绝站队：文件派在检索基准上大胜（69%→80%），但数据库厂商的两点反驳成立——词不重叠时只有嵌入能补缺口，时间推理只有带时间戳的图能回答（63.8% vs 49.0%）。作者 181 个文件的库比麻烦的地板低几百倍，所以选文件；LinkedIn 规模的生产系统不是，所以不该照抄。

### Aha 瞬间

几乎所有「X 还是 Y」的架构之争，真实答案都是「先量你在这条包络的哪一侧」。文件与数据库的正确关系不是替代而是分层——索引架在文件之上、随时可重建；判断错的是把索引本身当存储，为召回交出检视、diff、所有权和可移植性。
