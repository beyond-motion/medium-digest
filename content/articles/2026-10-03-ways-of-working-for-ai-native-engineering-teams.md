# AI 原生工程团队的工作方式（一）：当交接链塌缩时

> 原文：[Ways of Working for AI-Native Engineering Teams, Part 1: When the Handoff Chain Collapses](https://medium.com/@timothyakampa/ways-of-working-for-ai-native-engineering-teams-part-1-when-the-handoff-chain-collapses-1be7e777e5c6)

---

*我作为工程领导者和顾问的大部分职业生涯，都在围绕一条交接链塑造团队：PM 把 PRD 递给 UX 设计师，UX 设计师把设计稿递给工程师，工程师把构建递给 QA。在 AI 原生团队里，这条链正在塌缩——撑住它的那些角色边界正在一起溶解。*

这是「AI 原生团队的工作方式」系列的第一篇。这个系列讨论的是：当 AI 被当作软件构建、测试、部署、记录、维护的**核心运行层**，而不是别在上面的一个功能时，工作方式到底长什么样。

## 我过去用的模板

多年来，我用同一个六区模板塑造团队的工作方式：角色与职责、敏捷方法论、我们珍视什么、我们如何度量工作、团队仪式、我们如何做决定、我们如何高效沟通。

团队向 AI 原生开发迁移时，每一个区都必须重构。本篇处理第一个也是最根本的一个——**角色与职责**——因为其他所有区都建在它上面。（第 2 到 6 篇会覆盖其余部分。）

## 我在 Terraworks AI 看到的

Terraworks AI 是我联合创办的一家 edtech 创业公司，为新兴经济体的学习者改善学习效果——在那里我最近距离地观察了 AI 原生模式的发生。让我意外的不是某个具体的 agent 或 skill，而是**团队把 agent 带进房间的方式**。

每当出现新功能或重要功能，PM、设计师和工程师/技术负责人会一起围上来（mob）。PM 打开一个 agent 会话，触发「需求收集」skill 去澄清 why、收窄范围、压测假设。其他角色不等轮次——他们就在会话里，插话、提问、给 agent 补上下文。几个小时之内，agent 和三个人类共同收敛出一个共享的设计概念。PRD 是交付物，但真正的输出是**对齐**。

设计环节同样如此。团队刻意分开——每个人和各自的 AI 设计 agent 独立草拟一个方向（这个「分头再收敛」的模式借自 Jake Knapp 的《Sprint》），然后回来用 AI 合并想法，设计师再以领域专业判断把最终版落地。

工程从那里接手：PRD、设计产物和现有代码库一起喂给 AI Agent，产出技术需求和一份技术设计文档（TDD）加架构决策记录（ADR）。

而在每一个这样的会话里，人类都在背景里多干一件事：**注意 agent 哪里没接住——缺一个 skill、一个弱 prompt、一处上下文缺口——然后当场改进它。**团队在交付的同时，建造着自己的杠杆。

这不是工作流的微调。这是另一种运行模型。链没有变得更快——它塌缩成了一个环。

## 论题：角色边界正在溶解

我在那一切底下看到的模式是：

> 在 AI 原生团队里，角色之间的边界溶解。过去以交接链流动的工作（PM → 设计 → 工程 → QA）现在以协作环流动：人类在上游共同塑形 spec，agent 在中间做实现，人类在下游验证与评审。

角色没有消失，它们围绕一个新的重心被重新分配了。有价值的人类工作——**不可验证的工作**，判断至关紧要、「完成」语义模糊的那类——聚集在环的两端。中间那些可验证的部分，越来越多地由 agent 运行。

如果你带一个工程团队，你的工作是围绕这个环重新设计团队结构与团队实践——而不是保全旧链。

下面按工作流动的顺序，逐个角色看这次再分配。

## PM/PO：从 spec 作者到群策引导者

旧模型里，PM 拥有 PRD：跟干系人和客户工作、写需求、交出去。

AI 原生团队里，PM 依然拥有 **why**——但 **what** 越来越多地在一群人（mob）的共同书写中产生。PM 最有杠杆价值的时间不再花在 Notion 里打字，而是花在主持一场 agent 与跨职能小组之间的结构化对话上。

**领导者该做什么：**雇佣并培养「能在怀疑论工程师面前跑一场与 agent 的实时对话」的 PM，而不只是会产文档的 PM；投资共享的、版本化管理的 agent skills（比如需求收集），让 mob 有一致的起跑面。

## 设计师：从 spec 消费者到多方向生成器

旧模型里，设计发生在 PRD 之后——通常走单独的 UX 研究周期：原型、用户访谈、Figma 交接。

AI 原生团队里，设计阶段压缩成「分头-收敛」：每个成员和 AI 设计 agent 探索不同方向，然后合并。设计师的贡献从「设计的唯一作者」变成「判断并精炼团队与 agent 共同生成的方向」的领域专家——用品味选出对的那条路，而不是从空白画布独自画出一个完美设计。

这个变化 downstream 还有一个更激进的苗头，我看到萌芽但还早：**AI 原生团队正在缩小、个别情况下完全移除前期的 UX 研究-原型阶段**——把想法直接发上生产，让真实用户去测，不成立就再发一版。我听过 Anthropic 谈他们内部就这样工作，我预计未来 12 个月会有更多团队跟上——但这一条是预测，不是我普遍看到的现象。

**领导者该做什么：**按新的工作形态招设计师——能与 PM、工程师和 AI agent 群策、能把多个 AI 生成的方向合并成一个连贯设计、能用品味和判断选对方向；同时**有意识地决定**你的领域（受监管的？安全攸关的？）是否属于「前期原型与研究阶段不应被压缩」的那类——并在不该压缩的地方保护它。

## 工程师：从逐行实现者到架构师与评审者

旧模型里，工程师的手艺活在实现中：写代码、组织模块、把测试跑绿。

AI 原生团队里，手艺活在**上游**的技术设计与**下游**的评审。他们和 AI 架构 agent 一起从 PRD 和现有代码产出 TDD 与 ADR；把工作拆成纵向切片的、可验证的 ticket——常常由 agent 协助拆、工程师在环里校验切法；然后把 ticket 交给一个开发 agent（自己的机器上或云端），在实现的大部分时间里可以 AFK。

当 agent 的 commit 回来，工程师的主要工作才开始。他们评审那些 agent 自己还无法验证的东西：

* **技术债**——抽象放错了位置，今天看着没事、六个月后爆炸的捷径。
* **认知债**——代码能跑，但没有任何人能把它在脑子里装下。
* **运维债**——代码能上线，但运行、观测、恢复的成本高昂。
* **产品品味**——代码正确，但「不像这个产品」：一个笨拙的交互、一句语气不对的文案、一个与用户真实所需相悖的默认值。

这里的纪律，是 Claude Code 团队经理 Fiona Fung 说的 **trust but verify**。评审这一步同时是评估 agent 表现的地方：决定哪个 skill、哪个工具、哪个 verifier 本可以抓住这个缺口——让下一个会话比上一个更锋利。

**领导者该做什么：**提拔并奖励擅长设计、分解与评审的工程师——他们现在是你团队里杠杆最高的个人贡献者；停止用代码行数或 commit 量度量工程生产力——那些度量的是 agent，不是人。

## QA：并入工程师

QA 工程师正在合并回软件工程师。我直接在一些团队里看到这件事发生。

诚实的说法是：这是对既有趋势的**加速**，不是凭空新趋势。很多小团队从来没有专职 QA——工程师自己扮演这个角色。AI 原生开发加速了合并，因为传统 QA 职能的大部分（测试生成、回归覆盖、探索性测试脚手架）正在被 AI QA agent 增强。留给人类的，与代码评审里剩下的是同一件事：**不可验证的那一层**——「这真的是我们想要的吗？这对用户真的成立吗？」——加上上游的工作：把边缘用例写下来给 agent 去追。

那份上游工作本身就是技能。AI 原生团队的软件工程师，现在需要极其擅长思考边缘用例，并把它们精确到 agent 可以照着执行的程度。

**领导者该做什么：**如果你的团队还有独立 QA 职能，**刻意规划合并**，而不是让它在人员流失中自然发生；决定现有 QA 工程师长成什么角色。招把「边缘用例枚举」当一等技能而非杂务的工程师。

## 混合形态：AI 设计与开发工程师

这一切的极限情形，是一个我已经在团队里见过的角色：**AI 设计与开发工程师**。一个人戴齐所有帽子——产品思维、设计感觉、软件开发——由一支能干的 agent 舰队重度增强。他们和不同的 agent 合作扮演不同角色，然后交付。

在我观察到的团队里，这个角色用于**内部工具和非核心功能**——单人判断足够、重装跨职能流程纯属过度的那类工作。它还（暂时）不是我安排受监管支付流或百万用户核心界面的地方。但它的存在指明了趋势的方向：随着角色边界溶解，极限情形是**一个人**带着 agent 握住完整的环。

**领导者该做什么：**承认这个混合角色存在；为它腾出位置、划定适用范围，别硬塞进现有职级阶梯。对它尚不适用的地方保持诚实——混合角色是某些工作的工具，不是高风险工作里跨职能群策的替代品。

## EM/技术负责人：从管理人，到管理人加管理 agent

如果你读到了这里，这一节说的是你的工作。

工程经理的角色从「管理人」变成「管理人类（他们自己就是 agent 舰队的管理者）+ 直接管理 AI agents」。具体三件事：

* **设计最大化 AI 杠杆的团队结构和工作流。**这是新的工作核心。团队吞吐量现在主要是「工作如何被塑形」的函数，而不是你往上面加了多少人。
* **确保团队真的在向 agent 委派。**旧模型里学出手艺的工程师会本能地伸手抓键盘。EM 的一部分工作，就是持续把他们往上游推——推进设计和评审，那里才是他们的判断如今最值钱的地方。
* **管理 agent skills 与能力。**当团队注意到 agent 在会话里没接住，经理的工作是让那些缺口变成投资：一个新 skill、一个更锋利的 verifier、一个更好的工具。团队的杠杆只在这一层复利——而且只在这一层。

**领导者该做什么：**围绕新核心重构你的 1:1 和团队评审：人们在委派吗？本周 agent 哪里没接住？我们往 agent 工具箱里加了什么？划出明确的团队时间投资 skill 和工具——不划，它就不会发生，而那份本该复利的杠杆会悄悄漏光。

## 接下来

交接链塌缩之后，「工作方式」的其余每一件都要重审：为弥合交接而存在的仪式、度量链路吞吐量的指标、优先专业分工的价值观、假设角色权属清晰的决策方式、在孤岛之间路由信息的沟通模式。

本系列第 2 到 6 篇将逐一处理。下一篇：**AI 原生团队里的敏捷方法论。**

# 《Ways of Working for AI-Native Engineering Teams, Part 1: When the Handoff Chain Collapses》的发芽报告

## 材料核心

这篇材料以一位工程领导者的第一人称，记录了「交接链」组织范式的塌缩现场：PM→设计→工程→QA 的接力，正在被一个协作环取代——人类群策共塑上游 spec（PM 开 agent 会话跑需求收集 skill，全场插话），agent 跑中间可验证的实现（工程师甚至可以 AFK），人类守下游不可验证的验证与评审。材料的骨架是一份逐角色的再分配清单：PM 从作者变引导者、设计师从唯一作者变方向裁判、工程师从逐行实现者变架构师加四种债的评审者、QA 并入工程师、EM 的新核心变成设计最大化 AI 杠杆的结构并管理 agent 工具箱的复利。贯穿其中的两条暗线：可验证性决定工作归谁（人守两端、agent 守中间），以及「团队在交付的同时当场修补 agent 的短板」——杠杆在交付中被建造。

## 发芽 01：交接链塌缩的实质，是「对齐」取代「文档」成为交付物

### 种子

材料里最容易被略过的一句：Terraworks 的需求会上，「PRD 是交付物，但真正的输出是对齐」。旧链的每个交接物（PRD、设计稿、测试用例）都是为了让下一个人理解——链条本身就是知识传递的损耗补偿。

### 故事

在 mob 会话里，PM、设计师、工程师和 agent 同处一个上下文，几小时收敛出共享设计概念——理解不再需要经过文档的往返翻译。而 agent 吸收了中间的实现，让人类得以聚集到链条原本存在的理由上：共同决定做什么、验证做成的东西是不是它。

### Aha 瞬间

链是为了在不共享上下文的人之间搬运理解而发明的；当 agent 让上下文可以实时共享、让实现不再稀缺，链就失去了存在理由——组织形态从来是信息成本的影子。

## 发芽 02：四种债——agent 时代的评审清单是人类判断的具象化

### 种子

材料给工程师的下游评审开出一张精确的清单：技术债（放错位置的抽象）、认知债（没人能在脑内装下的代码）、运维债（跑得起但养不起的代码）、产品品味（正确但「不像这个产品」的交互与文案）。前三者是既概念的延伸，第四种是新的：agent 能生成正确的代码，但「像不像我们的产品」没有任何 verifier 能测。

### 故事

配合 Fiona Fung 的「trust but verify」，评审被双重化：既验这批 commit，也验这套系统——决定哪个 skill、哪个工具、哪个 verifier 本可以抓住这个缺口，让下一个会话更锋利。评审从把关动作变成训练回路。

### Aha 瞬间

可验证的都会被自动化，不可验证的才是岗位——而「产品品味」这种最软的东西，恰恰最后从人类手里移交，因为它连「什么算对」都无法被写进测试。

## 发芽 03：杠杆只在「投资 agent 工具箱」这一层复利

### 种子

材料对 EM 的三件事里藏着一条冷峻的经济学：团队吞吐量现在是「工作如何被塑形」的函数，而非人头的函数；当团队发现 agent 没接住，缺口必须变成投资——新 skill、更锋利的 verifier、更好的工具。

### 故事

与之对照的是两个流失路径：老派工程师本能抓键盘自己写（委派不发生），以及不划出显式团队时间投 skill 和工具（「那份本该复利的杠杆会悄悄漏光」）。材料还给出一个诚实的边界样本：一人全帽的「AI 设计与开发工程师」用于内部工具和非核心功能——还不碰受监管支付流和百万用户的核心界面。

### Aha 瞬间

AI 转型不是把 agent 加进现有流程，而是把组织的一部分注意力从「完成工作」永久迁到「升级完成工作的方式」上——那层投资是唯一有复利的层，也是唯一没人盯着就会漏光的层。
