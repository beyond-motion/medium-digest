# AI Agent 的康威定律：在 AI 时代重新思考微服务

> 原文：[Conway's Law for AI Agents: Rethinking Microservices in the Age of AI](https://medium.com/devops-ai/conways-law-for-ai-agents-rethinking-microservices-in-the-age-of-ai-6025497cb0c4) — Owen Zanzal

---

作者 Owen Zanzal 最近花大量时间在大型代码库上与 AI 编码智能体协作，开始重新思考一件他以为多年前已经想清楚的事：微服务。

长期以来，他对小型工程团队的建议很简单：**从单体（monolith）开始**。保持模块化、建立好的边界、在没有真实理由之前不引入分布式系统的复杂度。他见过太多公司 all-in 微服务的结局。

但与 AI agent 的协作让他意识到，微服务可能还有另一个理由——它与扩展基础设施或工程团队关系不大，更多关乎**管理「对大型系统做改动」的复杂性与风险**。

有趣的是底层约束可能正在变化。历史上我们按「人类团队如何沟通协调」来思考软件架构；当 agent 承担越来越多的实现工作，我们需要考虑另一个约束：**一个 agent 能有效推理多少上下文。**

而更有意思的是：为这个约束划出的架构边界，不必然是永久的。

## 我们曾经对微服务有点上头

微服务在工程组织变大时格外有吸引力：多个团队各自负责大应用的不同部分时，把功能拆成可独立部署的服务很有道理——团队拥有自己的功能、按自己的节奏部署、独立扩缩。

但把微服务做好需要对架构与组织都刻意经营：服务边界必须反映真实的功能边界，组织结构必须支撑它。很多公司学到了教训——因为微服务是「现代方式」而采用，不是因为有问题需要它解决，结果往往是**分布式单体**：传统单体的全部耦合，只是现在一切通过网络通信。函数调用变成翻分布式追踪；一个进程里能调试的事务变成排查六个服务里哪个引入了问题；部署要协调、契约漂移，一个原本简单的改动需要理解半个系统。在大组织里这是蔓延的技术债；在小组织里可能是生存问题——每个服务意味着又一处部署、又一条 CI 流水线、又一套日志指标追踪、可能又一个数据库。

这些并无争议。Martin Fowler 和 James Lewis 在微服务的原始论述里就讨论过这些权衡，行业也花了足够时间学习「服务边界不对齐业务能力」会发生什么。

作者仍然在「从单体开始」阵营。但他认为 AI 编码 agent 正在改变这个权衡的一部分。

## 康威定律与可用上下文窗口

康威定律说：我们建造的系统倾向于反映建造组织的沟通结构。这是微服务对大组织有意义的原因之一。

可当大量实现工作由 AI agent 完成时呢？

**强迫函数（forcing function）开始变化。**除了围绕人类团队的沟通边界组织软件，我们还需要考虑：一个 AI agent 能有效推理多少上下文。

注意——不是模型宣传的上下文窗口。模型能接受几十万甚至上百万 token，不代表它能可靠推理那段上下文里的每一个依赖、每个历史权衡、每个无意后果。**要紧的是可用上下文窗口（usable context window）：agent 究竟能把多少相关信息理解到「足以做出改动并建立合理的正确性信心」的程度。**

在大型遗留系统里，agent 也许能读海量代码，但不代表它拥有「一切如何交互」的可靠心智模型。问题不在获取信息，而在理解哪些信息要紧、各部分如何关联、一个改动会引入什么后果。

设计良好的架构边界能帮忙：显式契约、清晰的数据所有权、有限的依赖、可独立验证——给 agent 一个更可管理的问题。

这正是微服务重新变有趣的地方：**不一定因为我们需要独立团队或独立扩缩，而是因为服务边界能造出一个大小落在 agent 有效推理能力之内的有用工作单元。**

这不意味着按 token 数定制服务大小或一个 agent 一个服务——那是相当糟糕的软件设计。相关边界不是「agent 能读多少行代码」，而是「为安全做出某个特定改动，它需要理解系统的多少」。

康威定律反映人类组织的沟通约束；**AI 驱动的架构将日益反映 AI agent 的推理约束。**这不取代康威定律——人类仍然拥有系统、做架构决策、为生产负责——但它引入了另一条约束，随着 agent 接手更多实现工作而越来越重要。

## Agent 与大代码库的真正问题

作者与 agent 协作大型代码库的一个核心观察：**「agent 能做出一个改动」与「agent 对该改动的后果有信心」之间隔着巨大鸿沟。**

现代编码 agent 导航仓库、追踪依赖、跨文件修改功能的能力惊人。但理解一段代码做什么 ≠ 理解改动它时可能发生的一切。

想象一个跑了十年的大应用：经历过多届工程团队、几次架构转向、从未彻底完成的迁移、大量「当时合理但从未记录」的决策。**隐式契约无处不在**：一个看起来可选实则必填的数据库字段；一个依赖特定状态变更顺序的后台任务；一个五年前就有客户按其行为做了集成的 API 端点。

有经验的工程师知道其中一些，因为他们待得够久、见过什么会坏。Agent 没有这段历史——除非它被捕捉在可访问的地方。Agent 可以查代码、读测试、追依赖、做合理评估。但「理解实现」与「确信改动不会有意外后果」是两回事。

这也不全是 AI 的问题——变更影响分析与未记录依赖我们处理了几十年。AI 让问题更有趣是因为：**agent 能生成大量代码，而不消耗对等的人类实现时间。**在 agent 最有效的工作流里，代码本身往往相对便宜；更难的部分是理解、审查、测试、安全部署。系统越大越复杂，越难。

问题不是 agent 不能在大代码库上工作，而是：**有信心地验证一个改动所需的可用上下文，可能远超实际被修改的代码。**这让架构边界有了新的价值——它们不只组织代码，还约束「agent 需要推理系统的多少」。

## 笔记本电脑上复刻不出生产环境

假设 agent 对数据接入与处理做了重大改动。测试全过、staging 正常。这就安全了吗？

**不一定。**

很多系统的复杂度不在业务逻辑本身，而在逻辑暴露于生产数据与生产流量时的行为。数据保真度不只是「一份相当准确的副本」，还包括数据的分布、量、到达速度、并发操作数、持续负载下的系统行为。本地处理几千条记录的管道，未必表现得像每分钟处理数百万事件的那个。组件可以单测，但有些问题只在组件于真实条件下协同工作时显形。Google 的 SRE 指南讨论的正是这个挑战，以及为什么金丝雀部署与生产测试是可靠系统的组成部分。

当然，这不是让你盲目部署未测试的代码听天由命——而是需要一种方式：**逐步暴露改动、观察行为、在假设错了时限制后果。**

还有一层：即便软件完全按设计工作，你可能发现**造错了东西**——客户的使用方式与预期不同、数据长得不一样、性能需求与估计完全两样。这些往往无法靠事前设计完全解决。

## 微服务作为「隔离不确定性」的方式

如果换个角度想微服务呢：不只是组织工程团队的手段，而是**创建更小的、可独立验证的功能单元**的手段。

设想要向现有应用引入一项实质的新能力：基本是增量式的，但需要与系统的重要部分交互——新的数据处理工作流、接入管道、或性能特征未知的东西。

你可以让 agent 直接在现有应用里实现——有时这绝对正确。但取决于改动多深，你在要求 agent 同时解决两个问题：**新功能应该怎么表现**，以及**如何把它安全地集成进一个复杂的现有系统**。这是两种不同类型的不确定性，而且都消耗 agent 的有效推理容量。

替代方案：让 agent 把功能构建成一个相对隔离的服务。给它清晰的 API 契约、定义依赖与数据所有权、确保它能被独立部署与观察。现在 agent 的问题有界了——不必重建整个遗留应用，只需专注服务内的功能与连接系统其余部分的特定契约。你可以把功能暴露给一部分客户，在真实生产流量下观察行为，随信心增长逐步扩大发布。出了问题，有更明确的排查位置，可能还有更简单的回滚路径。

这不意味着服务自动安全——如果它改共享数据库表、跨应用产生副作用、参与复杂的分布式事务，隔离可能名存实亡。也不是非微服务不可：模块化单体、feature flag、精心设计的边界能达成许多同样的目标。需要运行时隔离、独立部署、不同的扩缩特性时，独立服务才更有说服力。

但在边界有意义的地方，收益很有意思：**你隔离的不只是功能，是不确定性。**你同时让「相关上下文的量」对 agent 变得可管理——不必理解整个系统，在显式边界内工作，其余靠定义好的契约。

而值得更多注意的部分是：**一旦学到了要学的，你可能就不再需要这个微服务了。**

## 如果第一版实现就是一次性的呢？

「临时软件」我们谈了几十年，老手都知道通常的结局：临时 workaround 变成永久依赖，原型变成产品，只打算存在六个月的服务五年后还在跑。

原因很直接：历史上写软件需要大量人类工程时间。花了几个月造出某物之后，替换它意味着再花更多时间与金钱换回已有的功能。**返工常被视为失败**——增加成本、延迟交付、消耗本可建新东西的工程产能。即便人人都同意实现不理想，经济学通常偏向保留。这也是我们为什么在实现前花那么多力气把架构做对——我们清楚事后改主意很贵。

当然，「刻意一次性」的想法不新：Martin Fowler 2014 年就写过 **Sacrificial Architecture**（牺牲式架构）——以终将被替换为预期来构建系统；绞杀者无花果模式（strangler-fig pattern）是用中间架构支撑渐进演化的另一例。有趣的问题是：**AI agent 是否正在把经济学改变到足以让这个思路适用于以前不实用的场景。**

如果 agent 能大幅降低实现与重实现功能的人力，丢弃一个能跑的实现就合理得多。这不意味着返工免费——迁移生产数据、保持兼容、验证行为、迁移客户仍有真实的成本与风险，它们常常是改造成熟系统最难的部分，AI 没有让它们消失。但**编写与重构代码所需的人力，在某些工作流里可能不再是主要约束。**

如果这是真的，我们应该重新考虑花多少力气避免重实现。**返工为什么不必然是失败？为什么不可以是有意计划的一部分？**与其在理解问题之前追求完美的架构决策，不如构建一个临时实现、用它消除不确定性、然后再决定永久实现长什么样。第一版不是最终架构的失败尝试——它有别的用途。**它帮我们学习。**

## 实现变成规格

想象你用 agent 把一项新能力建成隔离服务，部署给一部分客户，在真实生产条件下观察运行，基于所学迭代。也许发现最初的数据模型不对、客户用法与预期不同、真实负载与预估完全两样。几轮迭代后，有个能跑的东西了——更重要的是，你比开始时理解问题深得多。

此时有意思的事发生了：**这个实现不再只是一段能跑的软件，它变成了「这个功能应该如何表现」的参照——由真实生产经验喂出来的。**你有 API 契约、测试、观测到的使用模式、已知边界情况、性能指标、真实的客户反馈。开始时的许多模糊之处已被消化。

作者把这称为**可执行的规格（executable specification）**——但有一个重要限定：源码本身不是完整的规格。它可能包含意外行为、未记录的假设、和恰好在你观测条件下能跑的 bug。你仍需要刻意捕捉学到的内容：保留行为契约、测试、数据语义、失败模式、运维特性、要紧的需求。

但一旦做到，你手里就有了比原设计文档有用得多的东西——**一份由真实用户在生产条件下使用过的工作实现所支撑的规格。**

现在可以做更好的架构决策了。也许你发现这个功能真的属于现有单体：把验证过的行为、契约、测试连同参考实现一起交给 agent，让它把功能集成进大应用。你不再要求 agent「一边发现功能该做什么，一边闯遗留系统的复杂度」——需求已被更好理解，许多不确定性已被消解。这也改变了上下文问题：不再要求 agent 同时推理整个遗留系统和一个定义松散的新功能，而是给它一份理解充分的行为契约，让它解决更窄的集成问题。集成风险仍在，但你把「理解功能」与「集成功能」分开了。你甚至可以让两个实现并行运行，在真实负载下比较行为，随信心建立逐步切流量。

也可能生产证据告诉你保持独立是对的架构：扩缩需求不同、数据所有权清晰、运维隔离提供真实价值。很好，**留着它。**

要紧的是：你现在是基于实际证据做决策，而不是在构建一切之前预判所有需求与权衡。

这创造了一个有用的区分：**为学习而做的架构 vs 为长期运行而做的架构。**让 agent 最容易理解、构建、验证功能的架构，不必然是未来五年维护该功能最合理的架构。而且没有理由它们必须是同一个实现。

## AI 改变经济学，但不改变复杂度

历史上反对小团队用微服务的最强论据是运维开销：四个工程师大概不想管十五个服务——十五样要构建、部署、埋点、监控、维护的东西。可当这些实现工作大部分能由 AI agent 处理时呢？

作者自己的经验：agent 能接手惊人的机械性工作——创建服务、写部署配置、接埋点、写测试、重构实现，所需人力远少于从前。这不意味着一切免费：**分布式系统仍是分布式系统。**网络调用会失败、数据一致性依然复杂、运维问题不因代码是 agent 写的而消失。仍需要有人理解架构、为生产负责。

但**写软件的成本与运营软件的成本是两回事**——第一个正在发生显著变化。还有一个成本也在变：**丢掉一个实现的成本。**历史上替换能跑的软件是艰难决定，因为意味着投入大量工程时间重建已有的东西；即便人人同意另一个架构更好，投资也很难被论证。当 agent 能拿一份验证过的规格、以显著更少的人力产出新实现时，这笔账开始不同了。

这不意味着每个功能都该建两遍，也不意味着第二个实现自动更好——但它给了我们一个以前贵到无法认真考虑的选项：**先建东西来学习，在生产中验证，然后对去留做知情的决定。**作者不知道经济盈亏平衡点在哪，怀疑因应用而异，但基于与 agent 协作的经验，那个点在移动。

有趣的问题不是 AI 写代码多快，而是：**当写代码不再是主导成本时，我们能负担得起哪些不同的做法。**其中之一可能就是：围绕 agent 能有效理解的东西设计临时的架构边界——而不觉得有义务永远保留它们。

## 不是每个改动都值得一个微服务

必须强调：作者不主张把每个新功能都变成微服务——那会是把过去十年学会避免的所有问题更快复刻一遍的好办法。

如果 agent 在做一个有现成稳定 API 契约的 UI 功能，多半没理由引入新服务：范围清晰、接口已定、行为可测而无需理解整个后端——这本来就是 agent 最有效的场景。同样，与现有业务逻辑和数据库事务紧耦合的功能，拆成服务可能引入的复杂度多于消除的。模块化单体能在没有分布式状态与网络通信复杂度的情况下提供有界上下文的多数好处。

关于上下文论证还有一点：**别把它读成「每个服务越小越好」。目标不是把整个服务塞进 agent 的上下文窗口，而是让一次改动的相关上下文可理解、可验证。**一千行代码加一打未记录依赖的服务，对 agent 可能比一万行代码加干净接口的模块更难推理。要紧的是有效推理范围，不是实现的原始大小。

作者反复回到的区分是：**需要的是代码隔离还是运行时隔离。**如果只是让 agent 更容易理解与修改应用的某部分，结构良好的模块也许够。但如果需要独立部署、在生产负载下评估、暴露给一部分客户、或限制运维爆炸半径——独立服务更有说服力。尤其当功能是增量式的、需求不确定、客户上手后实现大概率显著演化时。

还有一条纪律：**如果你建服务主要是为了学习，就把它设计成真的能被移除。**保持契约显式、慎用共享状态、明确它拥有什么数据、引入了什么依赖、确保学到的行为能在实现之外被捕捉。否则你并没有造出临时服务——你造出了又一个永久依赖，只是管它叫临时的。那样我们就回到了原点。

## 真正的转变：我们怎么看返工

比微服务更广的想法在这里。

作者职业生涯的大部分时间里，返工被当作要最小化的东西——当工程人力昂贵、实现消耗项目预算大半时这很合理。我们花时间规划、设计、评审架构，部分就是想避免项目中途发现一切要重来。

但如果 AI agent 大幅降低了实现的人力，其中一些假设值得重看：**构建某些软件的最优方式，也许包含更多刻意的返工，而不是更少。**与其花几个月预判所有需求与架构后果，不如构建一个相对隔离的实现、验证行为、捕捉所学、然后按最合理的架构去实现它。

这不意味着放弃深思熟虑的设计——恰恰相反。**工程判断转向了：识别有用的边界、理解哪些风险可隔离、决定什么证据算充分、判断实现该保留还是该替换。**

要紧的是：我们不再必然把第一个能跑的实现当作需要保护的投资。**第一实现的价值可能是它产出的信息，而不是我们保留的代码。**这个想法在软件工程里存在已久——变化在于 AI 可能让它经济地用在更广的范围。如果发生，它会改变我们对整个开发生命周期的看法：**生产不再只是完成软件的目的地，而成了我们收集证据、验证假设、精炼规格的地方——然后再决定持久的实现该长什么样。**第一版帮我们理解问题；下一版——如果需要——围绕所学构建。

## 为构建而设的架构，可能不是为运行而设的架构

上下文论证、临时实现、微服务在这里汇合。

传统康威定律下，软件架构倾向于反映相对持久的组织结构——团队有长期的所有权边界，他们建的服务常反映这些边界。但 AI agent 引入了不同的约束：**它们的有效推理上下文有限，它们能自信完成的工作范围严重依赖问题被限定的清晰程度。**

这意味着我们可能刻意创建架构边界——只因为它们让某项工作对 agent 更容易理解、实现、验证。这些边界在开发期间有真实用途，却不必然是最终系统的正确边界。一个微服务可能是「给 agent 一个可管理的实现问题+一条安全的生产发布路径」的最佳方式；功能验证之后，同样的行为也许更适合作为大应用的一部分来实现。

而且因为干活的 agent 不是拥有长期所有权结构的持久工程团队，**改变这些边界不必然要求重组负责系统的人类。**关键区分：服务边界在服务于开发过程，而不必然在定义永久系统架构。

作者不是说每次 agent 上下文耗尽就重组软件——那很荒谬。但 **agent 的可用推理上下文应该成为架构决策的输入之一**，与团队所有权、扩展性、可靠性、运维复杂度并列。问题变成：**什么边界让「理解这个系统」与「安全地改动它」成为可能？**有时这些边界是永久的；有时它们只存在到不确定性被消除为止。而且我们越来越可能有经济上的余裕去在两者之间选择。

## 作者认为这将走向哪里

他仍然认为多数小团队应该从单体开始；过早微服务仍是坏主意；他绝不认为 AI agent 消灭了分布式系统的复杂度。

但他开始相信：某些架构决策背后的经济学在变化，**AI agent 的可用上下文窗口正在成为值得围绕设计的另一条约束**——不是因为 AI 让分布式系统变简单，而是因为**实现软件的成本可能正在比「理解改动一个复杂系统的风险」的成本下降得更快。**

这创造了一个有趣的机会：用隔离的实现探索实质性的新功能，给 agent 有界的工作上下文，把这些实现暴露在真实生产条件下，用得到的证据对「什么该成为永久」做更好的决策。有时答案是这个服务留着；有时是丢掉实现、把功能挪进单体。**无论哪种，第一实现都没有浪费——它帮我们发现了我们真正需要建的东西。**

这就是与 AI 编码 agent 协作最有趣的地方：它们给我们的不只是更快建软件的可能。**它们可能改变哪些建软件的方式在经济学上本来就是合理的。**

几十年来，我们的架构决策建立在「实现昂贵、返工应最小化、系统边界常应反映维护它的组织结构」的假设上。这些假设不一定错，但 AI 引入了一个新变量：**如果一个 AI agent 的可用推理上下文，变成与工程组织沟通结构同等重要的架构约束呢？如果我们为 accommodate 它而创建的边界不必是永久的呢？**

作者认为这些问题值得探索。因为如果实现变得足够便宜，最值得优化的可能不再是「我们多快能产出代码」或「我们保留了其中多少」——而是**我们多快能消除不确定性、建立信心、并把所学变成我们敢长期运行的软件。**

这就是他重新思考微服务的原因。

（延伸阅读：Fowler & Lewis《Microservices》、Fowler《Microservice Prerequisites》《Sacrificial Architecture》《Strangler Fig Application》、Google SRE《Canarying Releases》。）

# 《Conway's Law for AI Agents》的发芽报告

## 材料核心

Owen Zanzal 在大型代码库上与 AI agent 协作后提出：康威定律之外出现了一条新的架构约束——agent 的「可用上下文窗口」（能可靠推理到足以安全改动系统的上下文量，而非模型宣传的 token 容量）。大型遗留系统的隐式契约与「笔记本复刻不了生产」的现实，使「有信心地验证改动」所需的上下文远超被修改的代码本身。解法是把微服务当作**隔离不确定性的手段**：独立服务给 agent 有界的工作单元，灰度暴露生产、验证行为，把验证过的实现变成「可执行规格」，再决定功能并入单体还是保持独立——「为学习而做的架构」与「为运行而做的架构」不必是同一实现。AI 改变的是经济学（写码与丢弃实现的人力成本骤降）而非复杂度（分布式系统仍是分布式系统），真正的转变是对返工的态度：它可以是被计划的学习步骤，第一实现的价值在于产出的信息。

## 发芽 01：可用上下文——比 token 数更诚实的架构度量

### 种子

模型能接受百万 token ≠ 能可靠推理其中每个依赖、历史权衡与无意后果。原文把有效的架构度量从「窗口大小」换成「可用上下文窗口」：agent 究竟能把多少相关信息理解到「敢做出改动并合理确信它正确」的程度。

### 故事

十年遗留系统里的隐式契约（看似可选实则必填的字段、依赖状态顺序的后台任务、被客户按行为集成五年的 API）不在代码的表层语法里——老工程师靠「待得久、见过坏」获得它们，agent 只能靠系统里被捕捉下来的部分。于是「理解实现」与「确信改动无意外后果」分裂成两种能力，验证一个改动所需的相关上下文可能远超被改的代码。好的边界（显式契约/数据所有权/有限依赖/独立验证）直接缩减后者的量。

### Aha 瞬间

**当实现者从人换成 agent，「系统有多容易被安全地改动」从组织问题变成了上下文问题——服务边界的新职能是给推理划界，而不是给团队划地盘。**评估架构时新增一个问题：这个改动需要的「信心上下文」有多大，边界能不能把它装进去。

## 发芽 02：第一实现是学习耗材——「可执行规格」的重心在限定词上

### 种子

迭代到能跑之后，实现就不再只是软件：API 契约、测试、观测到的使用模式、已知边界、性能指标、客户反馈——一份被生产喂过的「可执行规格」。但原文特意限定：源码本身不是完整规格——它可能包含意外行为、未记录假设、和恰好在你观测条件下能跑的 bug。

### 故事

工作流因此分裂成两段：先建隔离实现吸收不确定性（agent 同时解决「功能该做什么」与「如何安全集成」会双倍消耗推理容量），灰度验证后把行为契约、数据语义、失败模式刻意捕捉出来，再决定并入单体（把「理解功能」与「集成功能」分离交给两个更窄的问题）还是保持独立（扩缩/所有权/运维隔离有真实价值）。整个流程把架构决策从「预判一切」改为「基于生产证据」。代价没有消失：迁移数据、兼容、迁客户仍是成熟系统最难的部分。

### Aha 瞬间

**「代码即文档」的真正版本不是省掉文档，而是把生产验证过的行为提炼成规格——没有捕捉这一步，你留下的只是碰巧能跑的代码。**第一实现的价值是它产出的信息；不刻意保存信息的丢弃，才是浪费。

## 发芽 03：代码隔离 vs 运行时隔离——别把上下文论证读成「越小越好」

### 种子

原文的防误读清单：不是每个功能都该建服务（稳定 API 的 UI 功能本来就是 agent 最有效的场景）；不是服务越小越好（千行+一打未记录依赖可能比万行+干净接口更难推理）；要紧的是有效推理范围，不是原始大小。

### 故事

真正的决策轴是「需要代码隔离还是运行时隔离」：只为让 agent 更容易理解修改，结构良好的模块就够；需要独立部署、生产负载评估、部分客户灰度、限制运维爆炸半径，独立服务才有说服力。配套的纪律是「为学习而建的服兑必须设计成可移除」——契约显式、慎共享状态、明确数据所有权、所学行为能在实现之外捕捉；否则你造的不是临时服务，是又一个自称临时的永久依赖。

### Aha 瞬间

**任何新约束论证都会被过度推广，防误读清单本身就是设计的一部分。**「为目标服务」的架构若要能安全退役，退役路径必须在建造当天就设计好——否则每一代「临时方案」的坟场，就是下一代的遗留系统。
