# 当读者能够行动，文档就变了

> 原文：[Documentation Changes When the Reader Can Act](https://medium.com/@zyane/documentation-changes-when-the-reader-can-act-2fbd97ebab32)

---

*可读的文字仍然必要。但对 AI agent 而言，检索、权威性、新鲜度和许可也成了契约的一部分。*

## 一个更值得琢磨的文档失败

一个 AI agent 可以读懂一条清晰的指令、正确地遵循它——然后做一件错的事。

这才是我觉得比「模型能不能读 Markdown」更有意思的文档失败。它找到的那一页可能描述的是一个旧目录；可能是一篇有用的设计笔记而非现行权威；可能把部署站点的步骤解释得明明白白，却没有确立「这个 agent、在这个会话里、被允许部署任何东西」。

**文字可以完全可懂，行动仍然是错的。**

一旦仓库文档进入了执行回路，文档本身只是决策的一部分。agent 得找到正确的知识、判断它是否现行、是否具有治理力、正确解读它，然后知道该行动还是该停。这条链上任何一环薄弱，完美可读的文档都会变成糟糕的运营上下文。

**这就是读者获得行动能力时改变的东西。**

## 失败发生在问题与行动之间

人在文档之外携带着数量惊人的文档上下文。我们记得某篇架构笔记是历史性的，哪怕它读起来仍然自信；我们知道团队实际用的是哪个部署页面；我们注意得到一条命令对当前仓库来说太老了；两份文档打架时，我们知道该问谁「哪个说了算」。

agent 也能搜索、浏览、比较文件、检查历史。区别在于：**这些步骤现在长在执行路径上，而不是背景阅读里。**

路径可以这样想：

```text
Question → candidate knowledge → governing knowledge → action boundary → action or stop
（问题 → 候选知识 → 治理性知识 → 行动边界 → 行动或停止）
```

文档里的措辞在每个阶段都重要，但好措辞解决不了整条路径。

LangChain 的 OpenWiki 发布文描述了这种分离的一个具体版本：仓库 wiki 可以远大于你愿意整包塞进高频加载的 AGENTS.md 或 CLAUDE.md 的体量，于是让小的指令面把编码 agent 指向更大的知识库、按需检索相关上下文。可迁移的思想不是 OpenWiki 本身，而是**路由上下文与知识上下文的分工**：常驻加载的那一层不需要装下仓库的记忆，它需要帮 agent 找到此刻要紧的那部分。

## 找到不等于选中

语言模型读非结构化文本已经足够好，好到解析问题把更难的问题挡住了。

如果正确的段落落进了上下文窗口，普通散文可能完全够用。真正的失败也许发生在前一步：**系统选择了检索哪个段落。**

这让「可寻址性（addressability）」成为实用问题而非装饰。稳定路径给检索一个靶子；描述性标题把靶子变小；链接把关系显式化而不是留在暗示里；元数据在它解决「消费者否则每次都得自行推断的区分」时才有用。当前的 Open Knowledge Format 规范把其中一种做法形式化了：Markdown 概念文档、基于路径的身份、结构化 frontmatter、链接与索引。

这不意味着每个仓库都需要 OKF 或每页都上 YAML。一百个结构完美的文件，如果彼此边界随意，仍然可能是糟糕的知识系统；一个巨大的文件，如果相关部分易于寻址和检索，仍然可以好用。**要点不是为结构而结构，而是给系统有意义的、可供选择的单元。**

模型的读文档能力，补偿不了「从未被展示正确的那份」。

## 最佳匹配仍可能是错误的真相源

检索系统的设计目标是浮出相关材料；而运营工作还需要**真正治理该决策的材料**——两者并不自动重合。

一段历史设计探索，可能在后来的权威文档替换它之后，仍是架构问题上语义最近的匹配。一个生成的 wiki 页面可以准确描述仓库的行为，却并不因此成为修改该行为的权威。一篇 postmortem 可能恰好含 agent 需要的全部关键词，同时描述着一个已不存在的系统。

所以相关性还需要一层：**关于权威性与现时性的证据。**证据可以很朴素：canonical 资源链接、版本历史、supersession 备注、生成 versus 人工撰写的状态、与文档所描述代码或配置的有意义的更新关系、说明信息来自何处的 provenance。

这些信号没有一样单独让文档变真——新时间戳不证明正确，检索分数不创造权威。**它们给消费者的，是比语气和相似度更好的推理依据。**

这里还牵涉来源区分必须在检索中幸存：OpenWiki 仓库目前声明输出 OKF v0.1，而本文引用的上游 OKF 规范是 v0.2——后者把 provenance、信任、新鲜度、生命周期等问题显式化了。我把 v0.2 当独立的结构参照，而不是把新语义当成 OpenWiki v0.1 的特性。

**长得像的知识不自动拥有同样的权威。**行动中的 agent 需要在这种区分变成一条命令之前就知道它。

## 正确的流程不是许可

即便一条指令现行且权威，最后还有一个问题没解决。

「部署站点」可读。它下面的步骤可能准确。**这两个事实都不能告诉 agent：部署在当前情形下是否被授权。**哪个项目？哪个环境？哪个分支？什么必须先通过？这是只读会话还是可变更会话？前置条件失败意味着重试、上报还是停止？

人类团队靠社交层携带这些边界：人们知道哪些文档解释能力、哪些文档授权行动、哪些步骤需要别人的决定。agent 不会因为能解析指令就继承这层社交。

对可能驱动行动的文档，我会把重要的区分写明：

- 描述 versus 指令
- 能力 versus 许可
- 默认路径 versus 例外
- 前置条件 versus 建议
- 现行权威 versus 参考上下文
- 停止条件 versus 可选指引

这是编辑层面的综合，不是 OpenWiki 规则或 OKF 教义——它来自消费者的变化。**一旦读者能够行动，文档里的歧义就成了执行中的歧义。**

## 反向审计一个动作

仓库不需要先上一个新文档平台才能检验这个问题。

我会从一个 agent 可能被要求的真实动作开始，从它往回走。假设动作是部署：什么知识足以支撑做它？agent 如何在不知道答案的前提下找到那份知识？什么告诉它文档是现行的、它治理这个决策而不只是描述？许可边界住在哪里？**什么会让 agent 停下来？**

然后检查的是链条，而不是文档资产的全貌：agent 发现不了治理页——问题是路由或可寻址性；找到三个都像的页面分不清谁赢——问题是权威；正确的页面描述旧环境——问题是新鲜度；流程正确但会话不被允许执行——问题是行动边界。

**这也让修复变小。你不一定需要为 AI 重写每一份文档；你需要修复「有用的知识在通往行动的路上死掉」的那个点。**

相关的 Dream Atlas 文章《The Reader Changed the Documentation Contract》把同一份契约展开成更全面的仓库知识审计。作为第一步，我建议从更窄处开始：一个动作，往回走。

## 好文档必须活到行动

我不认为这需要一套只为 agent 书写的第二文档宇宙——那制造一个显然的一致性问题：**人类读真相的一个版本，agent 检索到另一个。**

材料允许时，共享知识层是更强的默认。人仍然需要清晰的散文，agent 同样受益于清晰的散文。稳定的文档边界、链接、索引、provenance 和生命周期信号可以同时帮助两者，而不必把仓库变成一台不透明的、只供机器使用的知识机。

普通的 Markdown 能做到的事出奇地多，恰恰因为它普通：人能读，agent 能解析，版本控制能 diff。结构应该加在「反复出现的歧义需要消失」的地方，而不是默认铺满一切。

对行动型读者，标准只是比「可读」更高：**文档必须在要紧时找得到、可被认出是正确的权威、对决策足够现行、并且对读者的许可止于何处保持显式。**这些性质若有一个在「仓库到行动」的途中脱落，agent 可以读懂每一句话，仍然辜负契约。

文字仍然要紧。**它只是必须活到行动为止。**

# 《Documentation Changes When the Reader Can Act》的发芽报告

## 材料核心

agent 能读懂清晰的指令、正确执行、然后做错事——当读者获得行动能力，文档的契约从可读性扩展为一条五段路径：问题 → 候选知识 → 治理性知识 → 行动边界 → 行动或停止。文章沿路径诊断四类失败（可寻址性、权威与新鲜度、行动许可），并给出最小修复法：挑一个真实动作反向审计，修复知识死在半路的那一点。

## 发芽 01：文档的新读者不是在阅读，是在执行

### 种子

人靠社交层携带文档上下文（哪篇是历史、哪个是权威、哪步要别人拍板）；agent 不因为能解析指令就继承这层社交。

### 故事

文章把人类默默补齐的推理显式化为五段路径，并指出每段有独立的死法：检索不到是路由问题、三个候选分不清胜负是权威问题、页面描述旧环境是新鲜度问题、流程正确但会话无权执行是行动边界问题。相应的修复因此变窄：不必重写全部文档，只修知识死掉的那一点。

### Aha 瞬间

「文档质量」从一个写作问题变成了一个系统工程问题：可寻址性、权威信号、新鲜度证据、许可边界是四项独立的基础设施。评审面向 agent 的文档时，别审文笔——沿着一个真实动作倒走一遍，看它死在哪一环。

## 发芽 02：相关性 ≠ 权威性——检索系统的盲区

### 种子

检索系统负责浮出相关材料，而运营工作需要的是真正治理该决策的材料——两者并不自动重合。

### 故事

文章的三个错位案例：历史设计探索可能是语义最近的匹配（后来才被权威文档替换）、生成的 wiki 页面准确描述行为却不构成修改行为的权威、postmortem 关键词齐全却描述着不存在的系统。补救朴素而有效：canonical 链接、版本历史、supersession 备注、生成 versus 人工状态——给消费者比「语气与相似度」更好的推理依据。

### Aha 瞬间

「最新的、最像的」都不等于「说了算的」——这是知识系统设计的第三种排序键。给每份文档挂上权威与生命周期的显式信号，比把检索模型调得更聪明更便宜：让治理信息可被推理，而不是让模型去猜。

## 发芽 03：别为 agent 建第二个文档宇宙

### 种子

为 agent 单独写一套文档会制造显然的一致性问题：人类读真相的一个版本，agent 检索到另一个。

### 故事

文章主张共享知识层为默认：Markdown 恰好因为它普通而强大——人能读、agent 能解析、版本控制能 diff；结构加在「反复出现的歧义需要消失」处，而非默认铺满。对行动型读者，标准只是更高：找得到、认得出权威、足够现行、许可边界显式。

### Aha 瞬间

这与「别为 AI 建第二真相源」的上下文工程原则同源：当两类读者的需求冲突时，先检查是不是表示层的问题——多数歧义可以在共享层用结构信号消解，分裂真相永远是下策，因为它把一致性的维护成本永久化了。
