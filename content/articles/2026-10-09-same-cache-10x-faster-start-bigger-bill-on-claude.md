# 同一套缓存：本地快 10 倍，Claude 账单涨 25%

> 原文：[Same cache: 10x faster start on my laptop, bigger bill on Claude](https://medium.com/@shivangb237/same-cache-10x-faster-start-on-my-laptop-bigger-bill-on-claude-f33696c07fb7)
> 作者：Shivang Bhatnagar · 2026-10-08 · 7 min read
> 改写式翻译，保留原文结构与全部数据；署名与原文链接如上。

---

## 这篇测的是什么

「faster start」指的是**首 token 时间**（time to first token）：模型开始作答前要等多久。作者在 M4 MacBook Air 上把它从 **3-4 秒**压到了约 **0.3 秒**；而在 Claude 上，同样的缓存却让账单变贵。

实验测了人们常加在 LLM 前面的四种缓存，每种一句话：

- **精确匹配**：同一个问题问过，直接返回存好的答案。
- **语义缓存**：*相似的*问题问过，返回它的存档答案。
- **检索缓存**：相似问题已经找到过支撑段落，直接复用这些段落。
- **Prompt（前缀）缓存**：服务商复用已处理过的 prompt 开头。

统一 RAG 管线（模型先查资料再作答）、两套环境：MacBook Air 上经 Ollama 跑的 **4B 本地模型**，以及 **Claude Sonnet 5.5**。答案用公开问答数据集 SQuAD 打分。所有数字均来自带日志的实测。写给谁看：任何「因为教程说加就加了」语义缓存或 prompt 缓存的人——它有没有用，取决于你缺的是**时间**还是**钱**。

## 结论先行

- ⚡ 本地机器上，两种缓存配合让模型开始作答快了约 **10 倍**（3-4 秒 → 约 0.3 秒；检索缓存 + prompt 缓存，且问题共享段落时）。
- 💸 Claude 上，prompt 缓存让账单**涨了 18-25%**——写入缓存要付钱，却几乎没读回。让 prompt 刻意重复后，只有聚类型问题被救回来：便宜了 23%；问题类型多样化时，从没赚过。
- ⚠️ 按相似度匹配的缓存可能给出错误答案：语义缓存把 Claude 成本降了 39%，但每 201 个请求里送出 4 个错误答案。

## 本地机器：问题是时间

无缓存时，中位数问题耗时 **4.7 秒**，其中首 token 就占 4.4 秒；prompt 平均 942 token、答案只有 8.8 token——模型的时间花在「读」上，不是「写」上。

Ollama 本身就会用最多 **8 GiB 内存**缓存近期 prompt（这个尺寸约 60 条）：一条重复的 885-token prompt 只需 **29 毫秒**（原本 2,770 毫秒）。

代价在于：只有 prompt 的开头可复用，到第一处差异为止。RAG prompt 以固定指令开头（约占 6%），随后是逐题变化的段落。200 个问题涉及约 190 个段落，结果只有**约 10% 的 prompt token** 被复用。

**更大的缓存不是解法，让 prompt 重复才是。** 检索缓存记住每个问题找到过哪些段落，把同样的段落按同样的顺序交给相似问题，段落块就能命中模型已读过的前缀。顺序很重要：同样的段落换个顺序就前功尽弃。

在 100 个打乱顺序、涉及 20 个段落的问题上（相似度阈值 0.65——两问题多像才共享段落，0 到 1 取值），prompt 在 1 秒内处理完的请求占比从 **19% 升到 55%**，首 token 时间中位数从 **3-4 秒降到约 0.3 秒**。六组对比：无检索缓存 2.96s / 3.89s；阈值 0.85 → 3.75s；0.75 → 3.01s；只有最宽松的 0.65 → 0.29s / 0.31s 才带来质变。

## Claude：同样一招，关于的是钱

Claude 的 prompt 缓存是显式的：你在段落后标记断点，告诉 API 之前的所有内容可复用。写入比普通输入贵 25%，读取便宜约 90%。所以只有读回足够多才划算，成本约为普通 prompt 的 `1 + 0.25×写入占比 − 0.9×读取占比` 倍。

两组 100 问的负载：聚类型（同样 20 个段落）与多样化。每百问成本（聚类型）：

- **无缓存：$0.295。**
- **缓存 + 按相关度排段落：$0.349，贵 18%**——prompt token 只有 5% 被读回。
- **再加 0.65 阈值的检索缓存：$0.228，便宜 23%**——读回率升到 45%。

多样化负载上没有任何东西重复：所有缓存方案都**贵 20-25%**。速度也没赚：写缓存让首 token 中位数慢了 20-28%，读取也救不回来——Claude 本来就 1.4 秒左右作答。

> 本地，缓存买的是时间；API 上，缓存买的是钱——而且只有 prompt 开头重复时才买得到。

## 然后我把它搬上了 AWS ☁️

为了在笔记本之外验证网关，作者把它作为容器手动部署到悉尼区的 ECS Fargate（AWS 免运维容器服务）。镜像内置搜索索引与嵌入模型、以非 root 用户运行。第一次构建 **2.79 GB**——`chown -R` 把所有已安装文件复制进了新层；改成 install 前声明 `USER` 加 `COPY --chown` 后降到 **1.62 GB**（压缩 498 MB）。

部署刻意保持最小：公共子网单任务、无负载均衡器、无 NAT 网关；密钥放 SSM Parameter Store 启动时注入、绝不进镜像；执行角色只读一个参数路径、无其他角色（网关不调 AWS API）；安全组只对作者 IP 开 8080 端口，API 另需 `x-api-key` 头。

踩过的坑：镜像仓库与登录令牌按区域区分（错区报 "no basic auth credentials"）；推送身份只够碰 ECR，建仓库/日志组被拒——这是最小权限在正常工作；ECS 会忽略 Dockerfile 的 `HEALTHCHECK`，必须写进任务定义。

实跑验证：首个请求 **2,359 ms、$0.0035**；同一问题再问，精确缓存 **0 ms、$0** 返回；无 key 得 401。（计时在容器内测量；这是测试部署而非生产：单任务、无 HTTPS，任务重建后缓存清空、计费计数器归零；测完即停机免持续计费。）

## 我会怀疑什么

Claude 最新模型拒绝 temperature 参数（控制输出可重复的设置），各次运行有波动。所以每个实验都内置一份完全相同的对照组（无缓存）：同一配置的两份副本在 25% 的答案上不一致、F1（答案与标准答案贴合度的 0-1 分）相差 0.013——比这更小的差异当噪声处理。

检索缓存有代价：借来的段落会让 F1 本地降 0.014、Claude 上降 0.02-0.03。而且聚类型负载只覆盖 20 个段落，高估了复用率。一个数据集、两个模型，就这些。

## 我的四条收获

1. 先问哪种资源稀缺：本地模型缺时间，API 缺钱。同一个缓存能帮一个、伤另一个。
2. 开 prompt 缓存前，估算 prompt token 的读回占比——低于约五分之一，就是净亏。
3. 刻意让 prompt 开头重复：固定段落顺序，或上检索缓存。然后复查准确率。
4. 每个实验里放一份完全相同的对照组，它告诉你差异多大才算数。

# 《Same cache: 10x faster start on my laptop, bigger bill on Claude》的发芽报告

## 材料核心

这是一篇少见的「同一个优化在两个环境里符号相反」的实测：同一套四层缓存（精确/语义/检索/prompt 前缀）架在同一个 RAG 管线上，本地 4B 模型把首 token 从 3-4 秒压到 0.3 秒（瓶颈是读取，缓存命中读取就赢），Claude 上却先让账单涨 18-25%（写入费 25%、读回率只有 5%），直到检索缓存把「prompt 前缀重复率」做上去才反赚 23%。作者还给了怀疑清单：对照组双跑差 0.013 F1、检索缓存本身掉 0.014-0.03 F1、单一数据集。

## 发芽 01：优化符号取决于稀缺资源，不取决于优化本身

### 种子

同一条 prompt 缓存，本地把 29 毫秒的重复计算变成「快 10 倍的开始」，在 Claude 上变成「贵 18-25% 的账单」。

### 故事

本地机器的瓶颈是读取时间：942 token 的 prompt、8.8 token 的答案，命中读取前缀就是纯赚。API 的瓶颈是计费结构：写入贵 25%、读取省 90%，读回率 5% 时公式 `1 + 0.25w − 0.9r` 算出来就是净亏。缓存没有变，变的是「什么在稀缺」——时间便宜的地方缓存买时间，钱便宜的地方缓存花时间。

### Aha 瞬间

迁移优化结论时，先问目标环境里哪个资源在计价。教程里的「最佳实践」都是在某个稀缺条件下成立的局部真理，跨环境复用前要重新验一次符号。

## 发芽 02：缓存没起作用时，要造的不是更大的缓存，而是「可复用的重复」

### 种子

200 个问题涉及 190 个段落，只有 10% 的 prompt token 天然可复用；把段落顺序固定（检索缓存），1 秒内处理完的请求从 19% 升到 55%。

### 故事

作者试过「加大缓存」——没用，因为 RAG prompt 的段落块逐题变化，命中在第一处差异就断了。真正起效的是让 prompt 的开头**刻意**一样：检索缓存把相似问题的段落按相同顺序重新递上，前缀于是能够重复。连阈值的选择都是在控制「重复的粒度」：只有 0.65 这个最宽松的阈值带来了质变。

### Aha 瞬间

很多「缓存无效」其实不是缓存的问题，是输入的熵太高。先设计输入的可重复性（固定顺序、固定前缀），缓存只是兑现这份设计——顺序都不能变，换了顺序就前功尽弃。

## 发芽 03：对照组双跑，是给「差异」定刻度的唯一办法

### 种子

同一配置的两份副本在 25% 的答案上不一致、F1 差 0.013；于是所有比这小的改进都被当作噪声。

### 故事

Claude 新模型拒绝 temperature 参数，输出天然抖动。作者的对策不是反复调参，而是在**每个**实验里都放一份完全相同的无缓存对照，用对照自身的波动幅度来标定「多大差异才算数」。检索缓存换来的 0.014-0.03 F1 损失也是这么被如实记下的——收益与代价用同一把尺子量。

### Aha 瞬间

在不可完全复现的系统里，「显著」不是一个统计学术语，而是一个你亲手测出来的刻度。没有对照组双跑，你连自己的改进是不是幻觉都无法知道。
