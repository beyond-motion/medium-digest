# Agent 评估：从 Harness 到一个你信得过的评委

> 原文：[Evals for AI Agents: From Harness to a Judge You Can Trust](https://medium.com/@amrbelal852/evals-for-ai-agents-from-harness-to-a-judge-you-can-trust-34a7d26605fe) — Amr Belal

---

*关于 Agent harness、grader 与「造一个与你的专家意见一致的 LLM 评委」——学自 Anthropic 与 Hamel Husain。*

没有 evals，你会困在一个循环里：生产环境坏了一处→打补丁→补丁悄悄弄坏另一处。demo 里光彩照人的 Agent，开始犯没人预见过的错。

## 单次 LLM 调用 vs Agent

单轮评估很直接：三样东西——提示词（含数据）、模型的回复、给回复打分的评分逻辑。

Agent 难得多：它跨多轮调用工具、改变环境状态、根据所见调整行为。所以不能只检查最终文本——**你得知道它一路做了什么、在环境里留下了什么状态。**

## 词汇表

六个词无处不在。以退款 Agent 为例：

1. **Task（任务）**：一个测试用例=输入+什么算成功。*例：客户在签收 9 天后申请退款、商品未使用；预期=批准、全额、引用政策第 1 条。*
2. **Trial（试跑）**：对任务的一次尝试。要跑多次，因为模型的输出逐次不同。*例：同一个退款请求跑 3 遍。*
3. **Grader（评分器）**：给结果某一部分打分的逻辑。一个任务可以有多个 grader。*例：检查退款金额等于商品价格。*
4. **Transcript（全程记录）**：一次 trial 的完整记录——消息、工具调用、推理、中间结果。也叫 trace 或 trajectory。*例：Agent 查了订单、读了政策、然后做了决定。*
5. **Outcome（结果状态）**：trial 结束后环境的最终状态。**不是 Agent 说它做了什么，而是实际发生了什么。***例：退款记录真的存在于数据库。*
6. **Suite（套件）**：测试相关行为的一组任务。*例：所有「逾期申请」用例。*

transcript 与 outcome 的区分是全表最要紧的一条：**Agent 可以说「我已退款」，而数据库显示什么都没发生。给 outcome 打分，读 transcript 找原因。**

## Agent harness 与 eval harness

评估「一个 Agent」时，你评估的是模型**加上**它周围的 harness（也叫 scaffold）——让 LLM 得以作为 Agent 行动的系统。我把它想成模型周围的五个部件。这就是为什么两个团队用同一个模型能得到天差地别的分数：**改 harness，就是改 Agent。**

eval harness 则是把评估端到端跑起来的基础设施：它包住 agent harness——加载任务、在干净环境里多次执行、记录一切、打分、汇总。两者容易混，因为共享一个词：**agent harness 是被测物，eval harness 是做测量的机器。**

## 三种评分器

从代码开始，代码判不了的地方加模型，用人来检查模型。

1. **代码评分器**：普通代码写的检查。快、便宜、客观、每次结果一致。弱点：对合法变体误杀，判不了开放式文本。*退款例：金额等于价格、决定属于 approve/deny/cannot_decide、引用的政策条款存在。*
2. **模型评分器（LLM judge）**：另一个 LLM 给输出打分。能处理代码判不了的细微差别与开放式答案。代价：更贵、逐次有波动、**信任它之前必须先与人核对**。*退款例：解释是否只基于订单数据与政策？*
3. **人工评分器**：人审输出。质量最高、又慢又贵，所以省着用。它的主要职责是**检查 LLM judge**。*退款例：自己标注 30 个用例，再与裁判的判定对账。*

代码评分器有一个陷阱：**它们会误杀正确答案**。期望值是「150」，Agent 写「150.00」或「$150」，严格的字符串匹配就判错。Anthropic 有个真实例子：某模型在基准上得 42%，团队修掉死板的数字匹配这类评分 bug 后——**升到 95%**。解法：让 Agent 输出结构化数据，比值，不比字符串。

## 造一个你信得过的 LLM judge

LLM judge 只有在与「知道什么算好」的人达成一致时才有用。Hamel Husain 列了 AI 团队反复犯的错：

- **指标太多**：几十个没人据以行动的分数。
- **任意量表**：没人说得清 3 分与 4 分差在哪的 1-5 分制。
- **无视领域专家**：由工程师决定「好」是什么，绕过真正懂的人。
- **未经验证的指标**：从没测过与人类一致率的裁判。

他的解法叫 **critique shadowing（评注影随）**，七步：

1. **找到首席领域专家**——他/她的判断决定产品成败。退款 Agent 的例子里，就是退款政策的 owner。
2. **建数据集**——覆盖 AI 真会遇到的、对用例重要的各类问题。
3. **拿带评注的 pass/fail 判定**——专家每个用例只答一个问题：「AI 达成预期结果了吗？」并写一句短评说明为什么。
4. **先修错**——评注指出哪里坏了；自动化之前先修。
5. **迭代造裁判**——没看过数据之前写不出好的裁判提示词。把专家评注作为提示词中的示例，然后对比裁判判定与专家判定，**迭代到两者收敛**。
6. **做错误分析**——看 AI 在哪失败，把失败归型。
7. **必要时造更专的裁判**——每类重要失败一个裁判，而不是一个裁判管一切。

第 5 步的循环是全部要点：**裁判永远不会在第一条提示词上完工；它在与专家判定收敛的那一刻完工。**

怎么判断收敛？像测分类器一样测它。专家判失败的用例里，裁判也判失败的比例（失败召回）；裁判判失败的用例里，专家同意的比例（精度）。对一个做决策的 Agent，**失败召回率最要紧：一个放坏答案过关的裁判，比没有裁判更糟。**

## pass@k 与 pass^k

Agent 的输出逐次不同，所以每个任务要跑多次。计成功有两种方式：

- **pass@k**：k 次里至少一次成功。k 越大越高。适合「一个好答案就够」的场景（比如生成供人评审的代码）。
- **pass^k**：k 次全部成功。k 越大越低。适合「一致性要紧」的场景。

差距拉开得很快：单次成功率 90% 时，pass^3 = 0.9 × 0.9 × 0.9 = **0.729**。

## 造 Agent 评估的三阶段路线图（Anthropic 版）

**阶段一：收集任务、建数据集**
1. **从你的手工测试起步**：你发布前已经在手动做的检查、用户报过的 bug。从真实失败里抽 20-50 个任务就够起步。
2. **把任务写清楚**：两位专家对每个用例应得出同一判定，且每个用例附一个参考解法，证明它可解。
3. **配平用例集**：既测「应该发生的行为」，也测「不该发生的」——比如退款 Agent 必须以 cannot_decide 拒绝的信息缺失请求，以及信息齐全、必须拍板的相似请求。

**阶段二：设计 harness 与评分器**
1. **每次 trial 都在干净、隔离的环境里跑**——上一 trial 的残留状态会让下一个因错误的理由通过或失败。
2. **精心设计 grader**：评 Agent 产出的东西，而非它走的路径——通往正确答案的路常常不止一条；多部件任务给部分分。

**阶段三：长期维护**
1. **读 transcript**：一次失败要么是真错误、要么是 grader 误杀——只有 transcript 能分辨。
2. **盯住饱和**：一个 eval 长期接近 100% 就不再提供新信息。把它挪进每次变更都跑的回归套件，写更难的题。

（Hamel 版的同一循环：记录 trace→便宜检查写成单元测试→其余跑人工与模型评估→据结果改提示词或微调→再评估。）

## 我的收获

最大的教训：**一个强裁判的起点不在裁判提示词，而在更早的地方**：

- **维度**：在测量任何东西之前，先决定对你的用例什么要紧。通用指标测量的是别人的问题。
- **评估设计与数据集**：哪些用例入选、如何配平，决定了你的 eval 能抓到什么。
- **领域专家**：他们的 pass/fail 判定与评注，是裁判对齐的 ground truth。
- **失败**：你的 Agent 实际犯的错，是更强裁判的原料。收集、归型，把每个重要类型变成一条测试。

一句话：**没看过你的数据和你的失败之前，你写不出好的裁判。**

（来源：Anthropic《Demystifying evals for AI agents》；Hamel Husain《Your AI Product Needs Evals》《Creating a LLM-as-a-Judge That Drives Business Results》。）

# 《Evals for AI Agents》的发芽报告

## 材料核心

Amr Belal（8 min）的 Agent 评估实操指南（学自 Anthropic 与 Hamel Husain）：无 evals 的循环（生产坏→补丁→补丁坏别的）。六词词汇表：Task（输入+成功判据）/Trial（多次试跑）/Grader（部分打分逻辑）/Transcript（全程记录 trace/trajectory）/Outcome（环境最终状态，非 Agent 的自述）/Suite（相关行为组）——transcript vs outcome 最要紧（Agent 说已退款而数据库什么都没有：给 outcome 打分、读 transcript 找原因）。agent harness（模型+五部件；同模型异分数：改 harness=改 Agent）≠ eval harness（做测量的机器）。三评分器：代码（快脆、误杀合法变体——「150」vs「$150」字符串陷阱；Anthropic 实例评分 bug 修复 42%→95%；解法结构化输出比值不比字符串）/LLM judge（处理细微差别但贵且波动，信任前须与人核对）/人工（最贵、职责是查裁判）。Hamel 四错（指标太多/任意量表/无视领域专家/未验证指标）+critique shadowing 七步（首席专家→数据集→带评注 pass/fail→先修错→迭代到裁判与专家收敛→错误分析→按失败类型分设专裁判）；收敛按分类器度量、失败召回最要紧（放坏答案过关的裁判比没有裁判更糟）。pass@k vs pass^k（90% 时 pass^3=0.729）。Anthropic 三阶段：真实失败抽 20-50 任务/双专家同判定+参考解法/配平正反用例→干净隔离环境+评产出不评路径+部分分→读 transcript/饱和即转回归套件+加难题。收获：强裁判起点在裁判提示词之前（维度/设计/专家/失败原料）。

## 发芽 01：transcript 与 outcome 的分离——「说了」与「发生了」的评估学分家

### 种子

「Agent 可以说『我已退款』，而数据库显示什么都没发生。给 outcome 打分，读 transcript 找原因。」以及词汇表第 5 条的强调：「不是 Agent 说它做了什么，而是实际发生了什么。」

### 故事

六词词汇表里其余四词（Task/Trial/Grader/Suite）都是经典测试概念的换装，唯 transcript/outcome 的区分是 Agent 特有的新维度：LLM 的语言能力让「宣称完成」成为一种合法的中间状态——自然语言里「我已退款」与事实之间没有强制的引用关系。这使得 Agent 评估必须把「语言层」与「世界层」拆开打分：outcome（数据库里有没有那条记录）是唯一不可伪造的评分对象，transcript 则降级为解释材料（为什么做对了/错了）。这正好接上 11-25 的 Blocker Deception（不提障碍）与本篇的谎报完成（11-24 失败模式第 10 条）——三篇共同指向同一条规则：**Agent 的自述是证词不是证据；评分的锚点必须钉在环境里。**

### Aha 瞬间

**语言模型让「说做了」与「做了」第一次成为可以完全脱钩的两件事——Agent 评估的全部纪律，就是把评分锚点从语言层（transcript 的最后一句）搬回世界层（outcome 的最终状态）。**

## 发芽 02：42% 到 95% 的评分器事故——被测物与测量仪的混淆代价

### 种子

「某模型在基准上得 42%，团队修掉死板的数字匹配这类评分 bug 后——升到 95%。」以及代码评分器的陷阱定义：「它们会误杀正确答案」——期望「150」、实际「150.00」或「$150」都判错。

### 故事

这个 Anthropic 实例是测量史的老故事（仪器偏差被记成被测物的成绩）在 Agent 时代的重演：53 分的差距里，被评估的可能根本不是模型能力而是评分器的字符串匹配哲学。它与 11-27 另一篇《The Trust Problem》的基准批判（Goodhart/污染/代理）互补：那篇讲「分数能不能代表能力」，本篇讲「分数可能连分数都不是——它是评分器 bug 的投影」。结构化输出比值不比字符串的解法，本质是把「值的等价」与「表示的等价」分开。而对评估实践的真正教训是双向审计的必要：既审被测物（模型），也审测量仪（grader）——只审其一的评估体系，读出的任何数字都不完整。

### Aha 瞬间

**评估分数是「被测物×测量仪」的乘积——42% 与 95% 之间隔着的不是模型的进步，是评分器的进步；不审计测量仪的团队，永远在为一个未知系数调整自己的产品。**

## 发芽 03：失败召回率高于精度——裁判的伦理权重不对称

### 种子

「对一个做决策的 Agent，失败召回率最要紧：一个放坏答案过关的裁判，比没有裁判更糟。」以及 critique shadowing 的收敛定义：「裁判永远不会在第一条提示词上完工；它在与专家判定收敛的那一刻完工。」

### 故事

「比没有裁判更糟」这个判词把指标选择变成了伦理选择：裁判的两种错误（误放/误杀）代价不对称——误放一个坏决策会真实地作用在世界（错退款、错提交），误杀一个好决策只损失一次机会。所以对决策型 Agent，失败召回（坏答案漏网率）的权重天然高于精度。而 critique shadowing 的精妙在流程设计：裁判的 ground truth 不是「标准答案」而是**首席专家的 pass/fail+一句为什么**——把「好」的定义从抽象规范降格为具体人的具体判断，用评注做裁判的 few-shot 示例，迭代到收敛。这与 11-21「期望值从哪来」的审计原则同源：裁判的期望值来自一个可点名的人，而不是一个无人负责的通用量表（Hamel 四错里的「任意量表」正是反面）。

### Aha 瞬间

**LLM 裁判的合法性不来自模型聪明，来自它与一个可点名的人类判断收敛——指标选型（失败召回优先）则承认了一个伦理事实：评估系统的两种错误，在人间的代价从来不对称。**
