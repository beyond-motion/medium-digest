# 你的 AI Agent 不会变好，直到它的失败变成测试用例

> 原文：[Your AI Agent Is Not Improving Until Its Failures Become Test Cases](https://medium.com/observability-applied/your-ai-agent-is-not-improving-until-its-failures-become-test-cases-0777c051fc33)

---

## 改动不是证据

有人重写了系统提示词，他盯着看的那些坏答案不再出现了，改动上线。这一连串动作里，没有任何一环能告诉任何人：**agent 是否真的变好了。**

提示词的改动成本很低，模型的改动可能很贵——但事后都难以判断：触发改动的那次交互已经消失，剩下的唯一测试是「问题看起来还在不在」，而这取决于下一个人随手试了哪些例子。

追踪（tracing）本应解决这个问题。TrueWatch Agent Monitoring 能把 agent/LLM 请求与产生它的 trace 关联起来，在集成上报了所需 span 的情况下，trace 能展示一次交互背后的 Model、Tool 与 Skill 活动——这对理解「发生了什么」真的有用。

**但它还不是测试。**一百万条 trace 是一个档案（archive）。档案告诉你「确实发生了什么」，回归套件告诉你「一次改动是否破坏了曾经正常的东西」——这是两种不同的产物，第二种不会自己长出来。TrueWatch 可以把 trace 历史关联到保存的评估用例并跑批量评估，但「哪些 trace 值得留作用例」由团队决定。

一条生产 trace 变成可复用的测试用例，必须经过：**有人复盘了这次失败，并定义了下次该检查什么。**这一步最容易被拖延，因为它花的是人的注意力。

数据集还需要持续照料。它可能始于「某人有空复盘的那几条失败」——于是过度代表了「那一周最烦人的东西」。只有新类型的失败被持续复盘并加入，覆盖面才会增长；一个停止生长的数据集，最终只在测上个季度的问题。

## 六个阶段，一个循环

1. **生产 trace**：一次真实交互出错。这是原材料，不是结论。
2. **复盘失败**：由人判断它错在哪。团队可以按 trace 查询条件创建标注队列——值得复盘的交互以队列而非搜索结果的形式到来。复盘者记录标注结果、评分、问题类型与参考答案；写下参考答案，就是在定义「好本来应该是什么样」。
3. **保存用例**：复盘过的样本存入数据集供日后评估。这一刻，失败不再是轶事。
4. **批量评估**：对着准备好的数据集跑批量评估——现在一次提示词改动要面对的是团队记录过的**每一个**失败，而不是手边最方便的那个。评估数据可导出 JSONL/CSV。
5. **发布决定**：有人读结果并拍板。评估分数的价值取决于它背后的评分表、参考答案与数据集；结果只是「关于那个数据集和评分表」的证据，不是「关于 agent 一切」的证据。TrueWatch 报告结果，不设定结果必须跨过的门槛。
6. **持续监控**：离线评估通过不等于可以省掉灰度发布与持续的生产监控。离线用例是你已经认识的失败；生产是那些你还没见过的失败出现的地方——**而它们就是下一批测试用例。**

## 团队仍然拥有的东西

一个小例子（数字是虚构的，因为没有人测过）：一个客服 agent 处理长对话。线程变长时，它的摘要开始丢掉客户最初的问题，于是后续回复答非所问。复盘者打开这些 trace，把问题类型标为「摘要截断」，写出摘要本应包含的内容——这些成了数据集。下一次提示词改动，上线前先对着它们评估。

注意工具在这里**做了什么、没做什么**：TrueWatch 提供 trace 与评估工作流；团队仍然定义成功、验收阈值与发布决定。团队拥有参考答案——因为它编码的是「产品本该做什么」。

复盘者在这里做的是**产品工作**，不是工具工作。这个缺陷必须被命名为「摘要截断」——如果叫成「模型对长线程不擅长」，就什么测试用例都产不出来。

Datadog 描述过类似的工程模式：观察 trace → 形成假设 → 离线评估 → 实验 → 继续监控。这种收敛值得注意——**它说明这个循环才是实践本身，而不是某家厂商的功能。**

## 信任一个分数之前的五个问题

在一个分数被允许用于佐证发布之前，先问：

1. **谁定义了预期行为？**没人定义，分数就没有公认的产品标准。
2. **数据集里有什么？**数一数用例数，说出它们覆盖的失败类型。
3. **数据集缺什么？**没被复盘过的失败，就是你测不到的失败。
4. **阈值是什么时候定的？**看到结果之后才选的阈值，不是阈值。
5. **发布之后生产里发生什么？**答案是「没什么」，这个循环就是开路的。

**agent 的进步，等于团队对它失败的理解的进步——并且被写了下来。**trace 只是这个循环的起点；一次孤零零的提示词改动，什么都不是的起点。

# 《Your AI Agent Is Not Improving Until Its Failures Become Test Cases》的发芽报告

## 材料核心

作者区分两种产物：trace 档案（记录确实发生了什么）与回归套件（验证改动是否破坏曾经正常的东西）——一百万条 trace 不会自动变成后者。转化需要六阶段闭环：生产 trace → 人工复盘（标注问题类型与参考答案）→ 存为用例 → 发版前批量评估 → 发布决定 → 持续监控（新失败成为下一批用例）。工具提供管线，团队仍拥有三样不可外包的东西：成功的定义、验收阈值、参考答案——因为参考答案编码的是「产品本该做什么」。复盘是产品工作而非工具工作：缺陷必须被命名为可测的类型（「摘要截断」），否则连用例都产生不了。

## 发芽 01：档案与测试之间隔着一道人的判断

### 种子

「A million traces is an archive. An archive tells you what did happen, and a regression suite tells you whether a change broke something that used to work.」——两种产物的区别不在数据量，在于有没有人先定义过「应该是什么样」。

### 故事

文章指认了转化的确切动作：复盘者写下参考答案的那一刻，就是在陈述「好本来应该长什么样」；保存用例的那一刻，失败停止成为轶事。这两个动作成本极低却最常被跳过——因为它花的是人的注意力，而工具链的其他环节（采集、存储、检索）都在自动运转。

### Aha 瞬间

可观测性系统的价值上限不由采集能力决定，而由「多少比例的异常被人类认真看过并定义过」决定——没有复盘环节的监控体系，只是用更高清的镜头拍摄无人认领的事故。

## 发芽 02：命名缺陷的方式，决定你能否测它

### 种子

「这个缺陷必须被命名为『摘要截断』——如果叫成『模型对长线程不擅长』，就什么测试用例都产不出来。」

### 故事

同一个失败现象的两种描述，产物截然不同：「摘要截断」指出了一个可检查的具体机制（长线程时摘要丢掉客户最初的问题），于是可以写出参考答案、可以批量重跑、可以验证修复；而「模型不擅长长线程」是一个不可操作的能力归因——它把问题推给一个无法修改的黑箱，顺便免除了构建用例的责任。

### Aha 瞬间

问题的命名粒度就是它的可解性上限——「模型不行」式的归因不是诊断的终点，而是放弃诊断的标志；能写成测试用例的名字，才是真正的诊断。

## 发芽 03：停止生长的数据集在测上个季度的问题

### 种子

「一个停止生长的数据集，最终只在测上个季度的问题」——数据集的覆盖面只在「新类型的失败被持续复盘并加入」时才会增长。

### 故事

文章把数据集的起点说得毫不浪漫：它可能始于「某人有空复盘的那几条失败」，于是过度代表「那一周最烦人的东西」。循环的第六步因此不是收尾而是供料：生产中没见过的失败出现，复盘后成为下一批用例——离线评估与生产监控不是两个阶段，是一个持续供血的循环。

### Aha 瞬间

测试集不是资产而是流程——它反映的是「团队对失败的理解」在某个时刻的快照；判断一个 agent 团队的健康度，不看它有多少条用例，看它的用例集最后一次新增是什么时候。
