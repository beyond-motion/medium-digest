# 编码 agent 还不是你的队友

> 原文：[Coding agents aren’t your teammates yet](https://medium.com/@james_66157/coding-agents-arent-your-teammates-yet-e61f8158de7f)

---

每个 agent 都完成了自己的任务。合并还是崩了。本文讲并行编码 agent 在哪里失去对齐、我们造了什么来修它、以及三个基准测试怎么说——**包括那些不为我们脸上贴金的结果。**

## 长话短说

- 并行编码 agent 的失败发生在**agent 之间**：对不上的代码、困在单个聊天里的决策、丢失上下文的交接。
- 隔离解决不了它。在我们跑的每个 CooperBench 任务里，两个 agent 的功能都碰了同一个文件。
- Pawsly 是一个协调层：共享决策记录、带归属者的计划、行动前检查、带上下文的代码交接、一次经过验证的合并。
- 在我们的测试里，它让 agent 达成一致、尊重决策。它**没有**让它们更正确，而且花了约 **1.5 倍**的 agent 步骤。

### 关键数字

- **3 → 9**（10 任务）：四 agent 下代码一致的比例（shared Git → Pawsly · CooperBench）
- **0 → 12**（12 项）：被尊重的既定决策（bare → Pawsly · TheAgentCompany）
- **22 → 35**（36 次）：通过各自检查的运行（bare → Pawsly · MAST）
- **6 → 6**（10 任务）：通过率——正确性未变（shared Git → Pawsly · CooperBench）
- **1.5×** agent 步骤：协调的代价（Pawsly vs shared Git · CooperBench）

我的四个 agent 各自完成任务并报告成功。然后我合并分支，整个东西塌了：一个 agent 改了 API，另一个还在按旧版构建；我在第三个会话里做的决策从未到达其他会话。我花了一整晚在本来该替我省时间的 agent 之间传话。

那一晚教会我一件事，现在我每次启动一个 agent 舰队都会想起：**合并暴露问题，但协调失败开始得早得多。**

## 漂移的 API

Agent A 在重构 auth 端点。干净利落，自己的测试全绿。Agent B 在 auth 之上建新的计费流。也是全绿，也信心满满。

问题是时间差。Agent A 周二改了一个参数名。Agent B 周一读过旧签名，之后再没看过。**两个 agent 对「它们各自最后一次看到的世界」都是正确的**——合起来的构建第一次运行就失败。

这是我反复撞上的失败模式：**分支编码了互不兼容的假设。**每套测试只把一个分支对照它所知道的世界来检查，没有任何东西检查两个分支彼此一致，直到合并——而那时每个 agent 都已经走远了。

这不是罕见意外。CooperBench 是一个公开基准：两个 agent 在同一个仓库里各建一个功能。在我们跑的十个核心任务里，两个功能**在全部十个任务里都改了同一个文件**，其中五个改了同样的行。当 agent 只能互相发消息但不能共享代码时，**10 次合并里 7 次冲突**——基准把每次冲突都记零分。

## 困在单个聊天里的决策

周中我发现限流策略错了，于是告诉做 API 网关的那个 agent 改方向。它很快改了。

另外三个 agent 按旧策略又多建了两天。决策到达了一个会话，死在了那里。我是评审时才发现的：网关代码和客户端代码对限流怎么工作讲着两个不同的故事。

跑一个 agent 时，你的决策住在一个对话里。跑四个时，**在一个聊天里做的决策，对所有其他聊天都是谣言。**agent 只能遵守它见过的决策，而普通配置里没有任何东西把决策从一个会话带进另一个。决策待在你做它的聊天里、Slack 帖子里、Linear 评论里——每个 agent 只看得到自己的工单。

我们后来精确测量了这一点：用一个悄悄违反「别处做的决策」的任务。没有该决策的 agent 每次都违反它。数字在下面的 TheAgentCompany 结果里。

## 没有上下文的交接

Agent C 完成了一次 schema 迁移并标记完成。Agent D 接手回填任务，读了工单，按工单描述的 schema 样子开始写代码。

工单过时了。迁移做了两个判断取舍，从未被写下来。Agent D 的回填损坏了几千行数据才有人发现——**它在按计划干活，不是按实际发生的干活。**

交接会安静地断裂。下一个 agent 拿到任务，却没有推进它所需的上下文，没有任何东西报警，直到生产环境报警。

决定交接成败的是两件事：**下一个 agent 收到什么**（真实代码与背后的决策，还是只有一张工单），以及**它何时收到**。我们自己的 agent runner 展示了时机的分量：runner 把完成的 commit 传给依赖它的步骤。在 60 次两个 agent 改同一个文件的交接里，它及时送达了 52 次。我们用 git 重放了失误的 8 次：最后才合并每对分支时，**7 对全部冲突**；而如果在第二个 agent 开始前就交出完成的 commit，**8 次里 6 次本可以干净套用**——其中 5 次，commit 在第二个 agent 开工时就已存在，只是没有任何东西把它递过去。

## 我试过的没用方案

给每个 agent 独立的 worktree。更清晰的会话命名。一份人人理应阅读的共享计划文档。

- **Worktree** 挡住了两个 agent 同时写同一个文件。它们没有让工作变得独立：agent 仍在同样的文件上构建——CooperBench 的任务就是证明。
- **会话命名**帮我在四十个会话里分辨彼此。它们没让 agent 知道彼此的存在。
- **共享文档**到午饭时间就过时了——因为更新它是我的活，而我在忙着当传声筒。

我反复回到这句话：**把 agent 隔开不等于协调它们。**隔离防止了一类问题，同时制造了另一类的温床。一旦 agent 看不见彼此，每个决策、假设和判断取舍都变成了局部知识。

## 底层的模式

每个 agent 为自己的任务优化。这是我们要求的，它们做得很好。**但没有人拥有共享的理解**：API 现在长什么样、哪些决策是现行的、什么真的落地了 versus 什么只是被报告落地了。

我开始把它想成一个缺失的层。不是更聪明的 agent，不是更好的 prompt，而是一份每个 agent 都读写的共享计划：声明归属、决策可见、交接自带上下文。

## 我们在建什么

在 Jindo AI 我们围绕这个想法造 Pawsly。它坐在「团队做决策的工具」与「写代码的 agent」之间，不替换任何一边，也不让任何单个 agent 更聪明——它确保每个 agent 从同样的决策、同样的计划、它依赖的最新代码出发。

一件工作经过五步：

1. **Collect（收集）。**Pawsly 接进讨论与决策发生的 Slack 帖、Linear 工单、GitHub PR——决策跟着工作走。
2. **Compare（比对）。**它把 agent 的报告对照达成的东西、标出缺口：报告完成却没有证据的工作，或与决策相矛盾的证据。
3. **Assign（分派）。**它为团队起草角色、里程碑与依赖。你批准计划，选择哪个 agent（Claude Code 或 Codex 等）接哪个角色。
4. **Coordinate（协调）。**agent 通过 MCP 与 Pawsly 对话。行动之前，agent 声明它打算做什么，Pawsly 对照团队决策检查：对齐，或附理由拦截。Pawsly 还会呈现其他 agent 的相关工作并标记重叠。依赖的里程碑收到它们需要的已接受 commit，并且等待真正的完成，而不是等某人的状态更新。
5. **Merge（合并）。**一个指定的整合者合并各角色分支；一个独立的验证器先对照里程碑检查合并结果，然后才轮到人类评审。

目标不是跑更多 agent，而是产出彼此咬合的工作——不让你当传声筒。

## 内部测试显示了什么

关于协调的说法很廉价，所以我们分三件事独立测：agent 能产出咬合的代码吗？它们会尊重一个从未被告知的决策吗？协调能阻止哪些已知的多 agent 失败模式？每项测试都是同一模型带与不带 Pawsly 对比。**我们自己跑的，把它们当内部对比，不是独立评估。**

- **CooperBench**——同一仓库上的两或四个 agent 会提交相同且通过的代码吗？设置：10 个核心任务 · claude-opus-5 · bare、基准自带 shared-Git 选项、Pawsly 三臂。评分：基准自带功能测试，字节级一致补丁。
- **TheAgentCompany（改造）**——agent 会尊重任务从未提及的决策吗？设置：36 个 GitLab issue、12 个受外部决策保护 · Codex CLI 0.145.0 · gpt-5.6-terra。评分：基准的对齐 oracle 与 GitLab 前后快照。
- **MAST（改造）**——14 种多 agent 失败模式里，协调能阻止哪些？设置：每种模式一个场景 · 每臂 3 次 · Claude Code。评分：对产物跑正则，无模型打分。

### 1. CooperBench：agent 们最后拿到的是同一份代码吗？

CooperBench 给同仓库的两或四个 agent 各一个功能，然后合并补丁、跑基准测试。三个设置：**bare**（agent 只能互发消息）、**Shared Git**（基准自带选项：agent 推送并互相合并）、**Pawsly**（加协调与一个指定整合者）。

一个任务足以说明差别。四个 agent 给 typst 代码库同一对函数各加一个选项。bare 的 agent 互发了 24 条消息却从不共享代码，各自提交了只有自己选项的补丁：四个不同的补丁。Shared Git 下，每个 agent 自己合并其他三个：三个最终一致，但一个在其他三个完成后又改了两行：两种补丁。Pawsly 下，一个 agent 担任整合者，合并全部四个并按哈希钉住结果：**四个提交了完全相同的字节：一种补丁。**

机制就在这个任务里：Shared Git 下，一致依赖于每个 agent 在同一时刻以同样方式合并；有了一个整合者，一致是内建的。双 agent 时任务代码一致率从 10 中的 7 升到 10；四 agent 时从 **10 中的 3 升到 9**。

正确性是另一回事。共享代码把通过率从 2/10 提到 6/10——而基准自带的 shared-Git 选项已经做到了 6/10。**Pawsly 通过的是同样六个任务。**一个 agent 独自建两个功能通过了五个。没有任何设置通过另外四个：三个是隐藏测试检查任务文本从未写明的细节，第四个是两个功能的测试互相矛盾。**协调让 agent 达成一致。它没有让它们变对。**

> **一次我们发布过的更正。**我们最初报四 agent shared Git 为 2/10：那个任务文件夹里还留着一次被中断的早期尝试的补丁，我们的计数把它们算进去了。CooperBench 只给每个 agent 的最终补丁打分，应为 3/10。上文是更正后的数字。

### 2. TheAgentCompany：agent 会尊重它从没听过的决策吗？

用 TheAgentCompany 的工具，我们建了一个 36 个开放 GitLab issue 的清理场景：任务要求关闭已完成或搁置的工作，24 个该关。另外 12 个受任务外决策保护——一个仍在 HR 与法务流程中的背调、一个受监管保留的数据集、一条支付合规线，还有九个。

上图的案例：任务说关闭所有带「shelved」标签的 issue；聊天里的决策说 #12 是现行的 PCI 要求必须保持开放。bare agent 把三个全关了。有 Pawsly 时，agent 每次关闭前跑对齐检查：#12 被拦下保持开放，#11 和 #10 对齐后被关。

全部 12 个案例：bare agent 尊重了 **0/12** 条既定决策，Pawsly 的 agent 尊重了 **12/12**。两者都完成了全部 12 个案例要求的清理——差别不在能力，bare agent 只是没见过那些决策。注意这测的是**送达，不是发现**：场景把决策递给了 Pawsly，它不能说明 Pawsly 是否会自己在 Slack 里找到它。

### 3. MAST：协调能消掉哪些失败模式？

MAST 是 Cemri 等人论文《Why Do Multi-Agent LLM Systems Fail?》里 14 种多 agent LLM 系统失败方式的分类。我们为每种失败模式写一个场景，每臂用 Claude Code agent 跑三次。

一个场景：程序员工单要求写 users 表 schema 并选列名；一个工单从未提及的规划决策要求标识列必须叫 `account_ref`。bare 程序员三次运行分别命名 `user_id`、`id`、`user_id`。有 Pawsly 时，程序员先读一份包含该决策的简报，三次全部命名 `account_ref`。

通过场景检查的运行从 **22/36 升到 35/36**。在「提供了决策且 bare 臂失败」的四种模式里，11 次失败降到零。七个模式是没有决策可送达的对照组，Pawsly 无从发力，其中多数在两臂都没失败过。模式 3.3 的失败度量的更多是检查本身：它要求测试代码出现在文件里，用散文描述测试的运行就不过。

> **一项披露。**我们在跑完后放宽了模式 2.4 的检查：它不再禁止已撤销密钥的名字——三次 Pawsly 运行都在注释里提到它以标记撤销。按最初写法，Pawsly 得 32/36、四种决策模式阻止 3 而非 4。

## 代价，和它买到什么

协调不免费。双 agent CooperBench 运行里，Pawsly 用了 951 步对 shared Git 的 630 步——约 **1.5 倍**的步骤和 1.5 倍的钱。按通过任务算更贵：**5.80 美元对 3.86 美元。**

多花的钱买到的是更少的错误结果。一个错误结果的代价高于产生它的那次运行：有人要发现它、撤销它、重做工作——这些都不出现在那次运行的账单上。当协调阻止的错误结果本会花掉比「多出的半次运行」更多的修复成本时，协调才回本。**我们还没测量那个修复成本，所以不主张净节省。**

## 这些结果不显示什么

- **样本小。**10 个 CooperBench 任务、每臂一次 TheAgentCompany、每模式三次 MAST、来自一个 demo 应用的 8 次失误交接。推不出任何总体性结论。
- **一致不等于正确。**四 agent CooperBench 运行从未被打分；双 agent 时 Pawsly 通过的与 shared Git 同为六个任务。
- **送达，不是发现。**TheAgentCompany 与 MAST 把决策递给 Pawsly——测的是它到没到 agent 手里，不是 Pawsly 会不会自己找。
- **交接数字是 git 重放。**它们说明代码能套用，不说明下一个 agent 会正确地在其上构建。
- **无速度或评审主张。**这一切不说明交付更快、成本更低、或人类评审可以取消。

这些是小的内部运行，不是生产可靠性测量。它们提示的是：协调层要紧，而且它是与 agent 智能分离的一个问题。

## 我剩下的问题

每个跟我聊的团队都有自己版本的这些失败：有的丢决策，有的丢合并，有的丢交接。

我们正邀请跑 Claude Code、Codex 或其他编码 agent 的设计伙伴在真实工作上测试 Pawsly。合适的话联系 founders@jindoai.net 或访问 jindoai.net。完整方法、逐例结果与每一次更正都在 jindoai.net/engineering。

我很好奇：你的 agent 在哪失去对齐？代码变更、共享决策，还是交接？

# 《Coding agents aren’t your teammates yet》的发芽报告

## 材料核心

并行编码 agent 的失败不在单个 agent 内部，而在 agent 之间：分支编码了互不兼容的假设、决策困在产生它的那个会话里、交接丢失判断取舍。作者用三个基准量化了一个协调层的收益与代价——一致率与决策遵守大幅上升、正确率原地不动、步骤成本 1.5 倍——并罕见地公布了更正、放宽检查的披露与完整的局限清单。

## 发芽 01：合并暴露问题，失败开始得更早

### 种子

两个 agent 对「它们各自最后一次看到的世界」都是正确的——合起来的构建第一次运行就失败。

### 故事

文章的三种失败各有精确的机制：Agent A 周二改名参数、Agent B 周一读过旧签名（代码漂移）；限流策略的转向到达一个会话死在那里（决策孤岛）；迁移的两个判断取舍没写进工单，回填损坏几千行（交接失忆）。git 重放补充了时机的分量：8 次失误交接里 6 次本可以靠「提前递交」避免——commit 已存在，只是没人递。

### Aha 瞬间

「一个聊天里做的决策，对所有其他聊天都是谣言」——这是多 agent 系统的核心脆弱性：共识不会从各自最优中涌现，必须有一个被所有方读写的共享层。排障时别只盯合并冲突本身，要往回找决策应该到达而未到达的时刻。

## 发芽 02：协调让 agent 一致，不让他们变对

### 种子

四 agent 一致率 3/10 升到 9/10，通过率停在 6/10——协调让 agent 达成一致，它没有让它们变对。

### 故事

CooperBench 的 typst 任务给出了机制的完美切片：bare 四补丁各异、shared Git 三同一异、Pawsly 靠指定整合者钉出字节级唯一的四个提交。但两个 agent 的通过任务数与基准自带的 shared-Git 完全相同，且没有任何设置通过剩下四个（隐藏测试检查任务文本未写明的细节、两个功能的测试互相矛盾）。TheAgentCompany 补上对照：bare 尊重 0/12 决策、Pawsly 12/12——差别在信息送达，不在能力。

### Aha 瞬间

「一致」和「正确」是两个正交的指标，协调层只买前者。这给多 agent 系统的预期管理划了线：别指望协调层提升单点智力或补全规格缺陷——它保证的是「大家按同一个版本的现实干活」，规格本身的坑一个不少。

## 发芽 03：把不利结果写进正文，是实验可信度的稀缺品质

### 种子

「包括那些不为我们脸上贴金的结果」——通过率 6→6 原地踏步、成本 1.5 倍、按通过任务算更贵（$5.80 vs $3.86）全部印在摘要里。

### 故事

文章的自我审计贯穿全文：更正了四 agent 基线数字（旧尝试的补丁被误计）、披露放宽了模式 2.4 的检查（否则 32/36）、列出不显示什么（样本小、一致非正确、送达非发现、git 重放非真实构建、无速度主张），甚至声明「未测量修复成本，所以不主张净节省」。

### Aha 瞬间

在 agent 能力营销泛滥的当下，可信度的信号不是结果多亮，而是不利结果的位置——它在脚注里还是摘要里。读任何基准对比时，先找三样东西：有没有更正记录、局限清单是否具体、成本是否与收益并列出现。
