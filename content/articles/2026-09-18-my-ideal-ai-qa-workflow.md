# 我理想中的 AI QA 工作流——不止于生成测试用例

> 原文：[My ideal AI QA Workflow — more than test case generation](https://medium.com/automated-testing/my-ideal-ai-qa-workflow-more-than-test-case-generation-f13b73d256d8)

---

## 演示到不了的地方

大多数 QA 领域的 AI 演示，都从一条需求开始、到一条生成的测试结束。有人敲下「写个测试」，代码刷满屏幕，有人念叨两句生产力，演示就收场了——那段代码从没经过真实仓库的考验。

缺的是生成代码周围的一切。一条自动化测试诞生之前，团队讨论过需求、评估过风险、评审过用例；诞生之后，代码还得编译、运行、通过评审。生成只是这条路上的一步，不是全程。

这正是我在软件开发生命周期里应用 AI 的位置：**一条从需求评审直通自动化合并请求的连贯工作流。**每个阶段，AI 拿到一份 SOP 和相关素材；它辅助的是既有的 QA 活动，而不是取代活动周围的过程。

## 我在用的工作流

主流程长这样：

```text
PM 写 Jira story 和产品需求
 ↓
团队对 story 做 grooming
 ↓
QA 用 AI 审查需求、找缺口
 ↓
开发构建功能
 ↓
AI 从 Jira story 和 PRD 起草测试用例
 ↓
QA 评审并修正草稿
 ↓
PM、开发、QA 一起评审测试用例
 ↓
AI 把批准的用例变成后端 API 自动化
 ↓
AI 编译并在本地运行相关测试
 ↓
AI 记录未解决项，commit、push、开合并请求
```

## 从测试用例生成之前就开始

AI 第一个有用的位置是需求分析。产品经理写完 Jira story 和配套需求、团队完成 grooming 之后，QA 让 AI 把这些材料连同相关现有产品行为一起审查。

这不是「总结一下工单」。有用的问题是 QA 让需求变得可测试时本来就会问的那些：

- 有没有规则含糊或自相矛盾？
- story 之间的需求有没有冲突？
- 提议的行为跟现有功能冲突吗？
- 哪些状态、权限、依赖被默认了却没写出来？

AI 可以交叉比对多份材料，把发现整理好供下一场讨论使用。**QA 依然负责判断某个发现是不是真实风险**——文档常常不完整，一个看似的缺口也许在 grooming 时已经敲定。产出是一组更好的问题，不是「AI 批准的需求」。在开发前抓到一处重要歧义，通常比事后生成五十条测试用例更有用、也更省。

## 生成「为评审而设计」的用例草稿

需求进入可测状态后，一份 SOP 接管测试用例生成。助手读 Jira story、验收标准和相关产品文档，然后按我们约定的 BDD 格式与命名规范准备原子化场景。

BDD 用 Given / When / Then 表达起始条件、动作和预期结果。它的价值在于纪律：把一个行为陈述到产品、开发、QA 能讨论同一件事的程度。

SOP 告诉助手怎么干这份活，而不是每次任其即兴发挥。它覆盖这些事项：

- 命名与 BDD 格式
- 正向、反向与边界场景
- 一条用例一个行为，映射到对应的验收标准
- 测试管理系统要求的格式
- 输出是「待评审」状态而非自动批准

输出只是初稿。我人工评审，因为模型会编造行为、误解领域语言，或者即便上下文充分也会漏掉重要用例。

QA 评审之后，用例还要和产品经理、开发一起讨论：产品确认意图和优先级，开发补充技术上下文，QA 把两者连到风险和可观察行为。这一步是团队在用例成为自动化基础之前，就「需求到底什么意思」达成一致。

## 把批准的用例变成「仓库感知」的自动化

批准的用例接着成为后端自动化的输入。光给编码 prompt 不够，因为助手必须搞清楚什么已经存在、该动哪一层、仓库期望测试怎么写。

我们的后端自动化框架已经提供了测试运行器、service client、模型、数据准备、helper 和报告。我不要 agent 重新发明这些——我要它理解现有什么可用，做出**最小的合适改动**。

几件事帮它稳定做到这一点：仓库指令说明编码规则和各类代码归属；SOP 与 skill 描述要做的决策及顺序；编译与本地执行校验结果；人工评审判断测试是否正确、值得保留。

这些知识我放在仓库里，而不是指望有人每次往对话里粘贴。随着工作流长大，我会把同一思路推得更远：**把指令放到离它治理的框架部分更近的地方。**成熟的布局可以是：

```text
repository/
├── AGENTS.md                        # 跨仓库生效的规则
├── .github/
│   ├── copilot-instructions.md      # 仓库级约定与工具路由
│   ├── prompts/
│   │   ├── generate-test-cases.md   # 常见任务的短入口
│   │   └── generate-api-test.md
│   └── skills/
│       └── generate-api-test/
│           └── SKILL.md             # 可执行的决策与工作流规则
├── sop/
│   ├── jira-test-cases.md           # 人类可读的测试设计流程
│   └── generate-api-test.md         # 人类可读的自动化流程
├── docs/
│   └── contributing/
│       ├── repository-map.md        # 各类代码归属
│       └── coding-conventions.md
└── tests/
    ├── AGENTS.md                    # 所有后端测试共享的规则
    ├── models/
    │   └── AGENTS.md                # 模型结构与序列化规则
    ├── services/
    │   └── AGENTS.md                # service client 职责与模式
    └── apiTests/
        └── AGENTS.md                # 测试结构、断言与数据准备
```

上面的名字做了泛化，各家编码 agent 的指令文件约定不同，此例用 AGENTS.md。根文件放全局规则；models、services、apiTests 下的文件各自解释对应包的职责与模式。

比如：模型指令描述序列化、命名、是否允许业务逻辑；service 指令解释端点、header、响应怎么处理；apiTest 指令定义注解、测试数据准备、断言风格，以及「一条测试只覆盖一个场景」的规则。**AI 拿到的是通用规则加上它正改动的文件相关的局部规则**，不必每个任务都加载整本仓库手册。

prompt 是入口，SOP 解释完整过程，skill 把它变成助手可执行的步骤；贡献者文档提供更外层的架构、示例与命令。

一个巨型 prompt 在包挪位置或编码规则变更时会变得难以维护。版本化文档更易于评审，而一个反复出现的 AI 错误，可以在指令里改一次、而不是在每一场未来的对话里纠正一遍。

## 让 AI 自己决定改动的规模

我们自动化 SOP 里最好用的部分之一：它不假设每条用例工作量相同。助手先判断自己面对的是哪种情形：

1. 给框架已覆盖的 API 补一条测试
2. 用现有 service 层覆盖一个新端点
3. 为完全没有框架支持的 API 新增自动化
4. 产品行为变了，更新现有测试

第一种情形可能只要加一个方法；第三种可能需要模型、service 操作、数据支持和一整个新测试类。不做这个判断，助手要么漏掉必要工作，要么给一个很小的测试修一个私人小框架。

它会去找最接近的能跑的示例，复用现有的模型、service、helper 和测试数据机制；代码放进正确的包，遵循现有注解与断言风格，一条测试一个场景；复杂度进共享 helper，而不是在测试方法里长出分支和循环。

BDD 用例也塑造代码：Given 变成准备（setup），When 定位动作，Then 描述断言什么。评审者可以把实现和商定的场景对照着看，而不是孤立地啃 Java。

信息缺失时，工作流要求 AI 留下显式 TODO 并上报——可能是一条缺失的测试引用、一个没写文档的响应、或者新 service 需要的设计输入。**看得见的缺口，比可信的编造更安全。**

实践中我觉得最有用的几项控制：

- 仓库指令 + 分层 AGENTS.md 约定行为
- SOP 规定决策顺序，skill 承载可执行步骤
- 编译与本地运行校验产物
- 缺失信息显式 TODO 并在 MR 里上报
- 人工评审保留对「是否正确、是否值得进套件」的终审

这就是我说「仓库感知」的意思：AI 不是在真空里写测试。它读现有框架、遵循本地规则、校验自己的工作、报告它搞不定的事。

## 让 AI 把工程闭环跑完

写完文件后，助手编译受影响的代码、在本地跑相关测试。编译抓住编造的方法、错误的类型、漏掉的 import；执行验证测试真的能用这套环境和框架。

本地全绿也**不能证明场景是对的**。QA 仍要对照商定的用例评审代码与结果，尤其是断言是否真的展示了预期行为。

助手报告每个改动文件、新增测试和未解决的 TODO，然后干例行的 Git 活：commit、push、开合并请求。评审者拿到的是正常的 diff、流水线和讨论串，而不是埋在聊天窗口里的代码。

合并请求依然是一场工程评审。评审者决定这条测试是否属于这个套件、是否证明了想证明的行为、是否长期可维护。

## 这个工作流里，什么仍然是人的

现代 AI 能起草场景、写断言、读代码、跑命令。更重要的人类贡献坐在这些任务之上：

- 决定哪些产品风险值得投入
- 把书面需求与业务、技术上下文对齐
- 识别一个貌似合理的答案何时证据不足
- 判断这条测试是否证明了有价值的东西
- 接受、拒绝或上报结果
- 对进入测试套件的东西负最终责任

正因如此，评审不止发生一次：QA 评审生成的用例，产品和开发一起确认，代码再走正常的合并请求评审。**每个阶段回答一个不同的问题。**

## 到目前为止的教训

我的主要教训很直白：**从真实的 QA 工作流出发，决定 AI 在哪里移除摩擦而不藏起决策。**给它正确的证据，教它仓库怎么运转，让不确定性可见，把既有的工程评审留在结果周围。

prompt 依然是个很好的起点。我只是不会让它独自扛起整个 SDLC。

我还在打磨这套工作流，也没给它挂一个转型百分比。AI 能从素材走到可评审的用例、从批准的用例走到符合仓库规范的后端测试；但对前置时间、评审工作量、自动化可靠性的影响，还需要测量。

今天，工作流仍在多个点上要人参与。我把这看作它当前的成熟度，不是最终形态。随着模型变强、仓库指令变厚，我预期常规测试用例会在少得多的干预下从需求走到能跑的代码——包括把对的代码放进对的层、并在本地完成验证。

质量指导也可以长进开发工作流本身：开发 agent 可以从 AGENTS.md 加载圈定范围的质量规则，实现 story 时考虑相关风险，开合并请求前备好合适的测试。信任必须靠持续的好结果挣来，但方向令人兴奋。**QA 思维可以成为软件被建造的方式的一部分，而不是开发完成后才追加的工序。**

# 《My ideal AI QA Workflow — more than test case generation》的发芽报告

## 材料核心

这篇文章给出 AI 进驻 QA 的完整姿势：不是「生成测试」这一个点，而是从需求评审到合并请求的整条流水线。每个阶段给 AI 一份 SOP 和素材，知识以分层 AGENTS.md 的形式住进仓库，信息缺失时显式留 TODO 上报，既有工程评审原样保留——AI 移除摩擦，但不藏起任何决策。

## 发芽 01：知识住进仓库，而不是聊天窗口

### 种子

仓库指令不是一本巨型手册，而是一棵分层的规则树：根目录 AGENTS.md 管全局，models、services、apiTests 各层的 AGENTS.md 只管自己的职责与模式。

### 故事

作者的布局里，AI 只加载它正改动文件相关的局部规则；规则变更在文档里改一次、版本化评审，而不是在每场对话里反复纠正。一个反复出现的 AI 错误，从「每场未来对话的隐患」变成「文档里的一次修订」。

### Aha 瞬间

这与「评审反馈应该改变下一次生成的环境」是同一条原理的两端：持久知识的正确住址是仓库而非对话。规则离它治理的代码越近，AI 的行为就越可预期——上下文工程的核心不是喂得更多，而是放得离问题更近。

## 发芽 02：看得见的缺口，好过可信的编造

### 种子

工作流明文规定：信息缺失时，AI 必须留下显式 TODO 并上报，而不是猜一个合理答案填上。

### 故事

文章列举了该上报的情形：缺失的测试引用、没写文档的响应、新 service 需要的设计输入。配套的判断是「本地全绿也不能证明场景正确」——执行通过只是工程信号，语义正确仍需人对照商定的用例。

### Aha 瞬间

这是 AI 系统设计的通用原则：把不确定性变成信号，而不是让它混进看起来完美的产出里。一个说「这里我没把握」的 agent，远比一个永远自信的 agent 可靠——因为前者把验证资源的分配权还给了人。

## 发芽 03：评审变密了，而不是变松了

### 种子

这条工作流里同一样东西被审了三遍：QA 审生成的用例，PM 和开发一起确认语义，代码再走一遍正常的合并请求评审——每个阶段回答一个不同的问题。

### 故事

作者明确「AI 能起草、能写断言、能跑命令」，但把六个更高层的人类职责列在它们之上：决定风险、对齐上下文、识别证据不足、判断测试价值、接受或上报、为套件负最终责任。重复出现的评审不是冗余，因为用例评审问「这是不是我们的意思」，代码评审问「这能不能长期维护」。

### Aha 瞬间

AI 时代的质量保障方向不是减少人的判断，而是把人的判断集中在只有人能答的问题上：意图、风险与责任。自动化移除的是摩擦，保留的是把关——分工越清楚，双方越强。
