# 生产环境中的 Agent 记忆：把 SimpleMem 部署进真实系统

> 原文：[Agentic Memory in Production](https://medium.com/@jjn62/productionizing-simplemem-0c20f79256e1)

---

*Agent 记忆让 AI 系统能记住过往经历，从而随时间学习。*

知识管理的困扰远在神经网络出现之前就缠着组织了。任何一起工作足够久的团队，多半都撞上过这些问题：

* 「谁在什么时候做了什么决定，为什么？」
* 「标准流程是什么，适用于哪些场景？」
* 「这个问题我们上回是怎么解决的？」

和人一样，AI 在拥有**有组织、相关且最新**的信息时表现最好。随着 AI agent 在专业团队中承接越来越多的工作，为 agent 建立维持长期组织上下文与任务记忆的机制，变得越来越重要。

## 进入 Agent 记忆

Agent 记忆是让 agent 保存并召回过往经历的系统。这些经历通常是人机对话，其中往往藏着有价值的个人知识、任务指令和用户偏好；它们被抽取出来、以文本块的形式保存在长期存储里。这些「记忆」随后会在相关的用户查询到来时被检索，让 agent 在理论上能随时间学习、产出更好的回答。

在此之前的替代方案都有代价。一是复用一个长期跑着的聊天窗口靠它保存长期上下文——但随着旧消息被压缩掉，细节终将丢失。二是在每个新会话加载一份写着关键事实的 CONTEXT.md——这确实实现了跨会话记忆，但需要频繁维护，于是又撞回人类团队面临的同一批知识管理问题。

本文讨论的是 **SimpleMemPlus**——对开源记忆框架 **SimpleMem** 的一次扩展重建。

## 它怎么工作

**SimpleMemPlus** 分三步走：抽取、检索、整合。

**第一步：摄取（ingestion）。**从聊天对话中抽取关键事实与偏好，通过一次 OpenAI Responses API 调用完成，输出带类型的记忆单元，分为四类：用户偏好（preference）、语义事实（semantic）、情节事件（episodic）、程序性观察（procedural）。值得注意的是，我们要求模型把记忆写成**无损转述（lossless restatement）**——每条记忆是一个自包含、独立的观察，不出现「他/她」或「昨天」这类上下文依赖的指代：

```
1. 完全覆盖：生成足够多的条目，确保对话中的所有信息都被捕获。
2. 强制消歧：禁止代词（他、她、它、他们、这个、那个）和相对时间
   表达（昨天、今天、上周、明天）。使用真实姓名和绝对引用。
3. 无损转述：每条 entry 必须恰好是一句完整、独立的句子，
   脱离周围对话也能成立。
4. 权重：为每条 entry 推断重要性（对未来召回的价值，0.0–1.0）
   和置信度（被明示的程度，0.0–1.0）。
```

置信度和重要性的判断标准有二：它被用户表达（或暗示）得多强烈；它对未来的交互有多大用处。比如「**我一直给家人买有机食品，因为我在乎他们的健康，也想减少环境影响**」在两个维度上都会远高于一句顺带的话「**我上周买了点有机燕麦奶**」——前者在未来请求中被检索出的概率也更高。

抽取之后，记忆内容由再一次 OpenAI 调用转换成向量嵌入，原文与向量一起存进 pgvector 数据库，供后续检索。我们的应用里，只在聊天**自动压缩时**才摄取新消息——这降低了生成冲突或重复记忆的概率。

**第二步：检索（retrieval）。**这部分基本沿用 SimpleMem Evolver 的实现：混合词法与向量搜索。这是整套系统的主角——通过只选择性地检索「与用户查询语义相似或共享关键词」的记忆，避免了把整库记录灌进 agent 的上下文窗口，在提升回答质量的同时降低延迟和输入 token 成本。查询「今天该买什么菜」只会召回「我一直给家人买有机食品……」，而不会召回「我的机油快没了」。

关键词 IDF 分数与余弦相似度分数分别排名、加权后，用下面的算法选出 top-k 记忆——**RRF（倒数排名融合）**：

```
def _rrf_contribution(weight, rank, rrf_k):
    if rank is None:
        return 0.0
    return weight / float(rrf_k + rank)

rrf_score = (
    _rrf_contribution(policy.rrf_keyword_weight,  keyword_ranks.get(id),  k)
  + _rrf_contribution(policy.rrf_metadata_weight, metadata_ranks.get(id), k)
  + _rrf_contribution(policy.rrf_embedding_weight, embedding_ranks.get(id), k)
)
```

RRF 比简单地把加权原始分相加更稳健：它保证某一类目的高分不会淹没其他类目的低分贡献。举例来说，一条在关键词和余弦两路都排第 3 的记忆，总分可能高于一条关键词第 1 但完全没有向量命中的记忆——根本原因是余弦相似度有界于 [0, 1] 而 IDF 无界，两者量纲不同，原始分数不可直接相加。

## 与 RAG 的区别：整合这一步

你可能会问：这和检索增强生成（RAG）有什么区别？区别就在最后的**整合（consolidation）**步骤。

用户的需要和偏好会随时间演变。假设用户现在说：「**我不再只买有机食品了——有些有机农场用的农药比非有机的还多。**」我们就需要把之前的记忆「我一直给家人买有机食品……」删除或标记为过期。

我新增了一个整合流程：先用初始余弦相似搜索找出候选记忆对，再用 LLM 对每一对做三分类判定——**矛盾（CONTRADICTION）**（如「永远别做 X」对「总是做 X」）、**重复（DUPLICATE）**（同一事实的不同措辞）、**独立（INDEPENDENT）**（两者可以同时为真）。对重复与冲突，按创建时间归档旧的、保留新的：

```
for pair, pv in verdicts:
    if pv.relationship == ConflictRelationship.INDEPENDENT:
        continue
    drop, keep = (a, b) if a.created_at <= b.created_at else (b, a)
    await self.store.supersede(drop.memory_id, keep.memory_id, now)
```

这个过程保证记忆池的内容保持新鲜，并且不会随时间无界增长。

## 生产环境需要什么

在生产环境中，聊天助手要以安全、健壮、可扩展的方式替用户检索记忆。SimpleMemPlus 做了三处改造。

**其一：从同步 SQLite 迁移到异步 pgvector。**在数千并发请求的生产系统里，多个 FastAPI 实例同时运行是常态。SimpleMem 原生的 SQLite 是基于文件、锁在单一主机上的数据库——多个任务无法在没有锁争用和数据损坏风险的情况下写入一个共享库。我们迁移到 PostgreSQL + pgvector 扩展（SQLAlchemy ORM），实现了多实例安全的并发读写。pgvector 还提供了完整的向量搜索能力——原版实现最多在内存里加载 500 条记忆、用 Python 顺序计算余弦相似度。PostgreSQL 还让我们能用上云厂商的附加能力（如 AWS RDS）：自动备份与访问控制，在数据库故障或误删表时支持时间点恢复。

**其二：按 userId 分区 + 层级命名空间。**每条记忆创建时都被赋予非空的 **user_id**；检索时只返回与可信调用者 user_id 匹配的记忆，读写被限定在用户自己的记忆范围内。

用户还常常在多个有共性的上下文里与 agent 交互。比如一个老师在学期里教多个班，而她的教学方法和教案大概率是相通的。原版 SimpleMem 允许创建时指定可选的 **scope_id**，检索时精确匹配。我把它扩展成 **namespace** 系统：记忆可以被赋予斜杠分隔的路径，如 `creative-writing/class-101` 或 `creative-writing/class-102`。命名空间按**前缀匹配**——查询 `creative-writing` 会同时召回上述两个命名空间、以及任何更深分支（如 `creative-writing/class-101/assignments`）的记忆。

这让 agent 能按查询选择合适的命名空间层级：「我 class 101 的哪个学生语法有困难」适合细粒度的 `creative-writing/class-101`；「到目前为止我教过哪些创意写作主题」适合一级命名空间 `creative-writing`。

**其三：OTel + Langfuse 可观测。**SimpleMemPlus 把所有摄取与检索事件记录为 OpenTelemetry traces，转发到 Langfuse v4 主机，开发者可以拿到完整遥测：延迟、token 成本和应用元数据。每次摄取打开一个根 trace、记录新增记忆数；摄取内的每次 LLM 调用则记录为嵌套的 generation span 及其 token 用量。这些 trace 还可以配置 live evaluator，对被摄取和被检索记忆的质量打分，输出系统性能指标。

## 结语

SimpleMem 名副其实——一个简单的、基于向量的记忆系统。它的 evolver 变体那套确定性、快速的混合检索器，使它非常适合延迟敏感的场景（比如 AI 助手）；不过与图式记忆系统相比，它缺少把相关记忆聚类并建立关联的正式机制。加上这里的改造，SimpleMemPlus 为用户提供自维护长期记忆，是一个健壮的入口。

好的知识管理依然是一件爬坡的苦活——至少，我们不用再替我们的 agent 做了。

# 《Agentic Memory in Production》的发芽报告

## 材料核心

这篇材料是一份把开源记忆系统 SimpleMem 改造上生产的完整工程实录。作者以组织知识管理的三问（谁做了什么决定、流程是什么、上次怎么解决的）开篇，指出 agent 记忆的两种朴素替代（长期聊天窗口、CONTEXT.md 文件）各自的失效方式，然后按三步展开 SimpleMemPlus 的设计：摄取时用 LLM 抽取四类记忆单元并强制「无损转述」（禁代词、禁相对时间，每条自足成句），同时推断重要性与置信度双分数；检索用关键词 IDF 与向量余弦的混合召回加 RRF 倒数排名融合排序；整合用 LLM 对候选记忆对做矛盾/重复/独立三分类、新记忆按创建时间「取代」旧记忆。生产化改造落在三处：SQLite 换异步 pgvector 支撑多实例并发、userId 分区加层级命名空间实现既隔离又可跨区检索、OTel+Langfuse 全链路遥测。结尾诚实地标出了边界：与图式记忆系统相比，它缺少聚类与关联机制。

## 发芽 01：记忆的第一品质不是聪明，是脱离语境后仍然成立

### 种子

材料里最容易被略过的设计约束是「无损转述」：禁止代词与相对时间表达，每条记忆必须是一句脱离对话也能成立的独立句子。「他昨天说搞定了」不是记忆，是还没失效的语境。

### 故事

这条约束对应着记忆系统里最隐蔽的失败模式：一条记忆在被写入的那一刻完全正确，却在被召回的另一刻失去所指——「他」变成了谁、「昨天」已经是哪天。抽取 prompt 甚至为此把「强制消歧」写成禁令，而不仅仅是偏好。

### Aha 瞬间

判断一条知识值不值得记住，先问它换一个时间、换一个读者还成不成立——记忆的可靠性在写入的那一秒就决定了，召回做得再好也救不回一句依赖语境的话。

## 发芽 02：量纲不同，就别把分数直接相加

### 种子

材料对 RRF 的辩护藏着一个通用的工程教训：余弦相似度有界于 [0, 1]，IDF 无界——两者量纲不同，直接加权相加会让某一类的数值尺度独裁整个排序。RRF 只用「排名」说话，任何一路的第一名贡献相同的分数。

### 故事

它的效果是反直觉的：一条关键词第 3、向量也第 3 的记忆，可以打败一条关键词第 1 但向量毫无命中的记忆——因为在两个独立证据源上都靠前的候选，比在单一证据源上登顶的候选更可信。

### Aha 瞬间

多信号融合的正确姿势不是调权重，是把不可通约的分数先折叠成可通约的排名——凡是遇到「几个 0 到 1 的分数和一个不封顶的分数怎么合」的问题，答案几乎总是先排名再融合。

## 发芽 03：取代而非删除——记忆系统的版本控制

### 种子

整合步骤的判例法设计：LLM 对记忆对做三分类（矛盾/重复/独立），只有前两者触发处理，且处理方式不是删除而是 `supersede`——新记忆记录自己取代了谁，旧的按创建时间归档。

### 故事

材料用偏好演变做例子：「我一直只买有机食品」被「我不再只买有机食品，因为有些有机农场用更多农药」取代——注意第二条不是简单否定，它带着改变的理由。这个流程同时解决了两个问题：记忆池保持新鲜，且不会无界增长。

### Aha 瞬间

好的记忆系统要像好的代码库一样有版本历史：被取代的记忆不是错误，是被更好的判断替换的判断——留着它，系统才能回答「我们曾经怎么想」，而不只是「我们现在怎么想」。
