# 在我们仍然不信任的数据上自动化决策

> 原文：[Automating Decisions on Data We Still Don't Trust](https://medium.com/towards-artificial-intelligence/automating-decisions-on-data-we-still-dont-trust-fcf8b06631e3) — Avinash Maddineni

---

多年来，当 AI 系统出错时，人有机会抓住它。模型产出一个数字，人看一眼，感觉不对就核查。这个人在环可以又慢又不一致——我们不停地抱怨这种摩擦。它不是正确性的保证，但它是一张安全网；而且我们对它的依赖，常常比架构图上承认的更多。

**Agentic 工作流刻意移动了那条审查边界。**卖点很诱人：不要只回答问题，去执行动作。不要告诉分析师这个账户看起来有风险——标记它。不要给出补货建议——下单。不要起草回复——发送。（本文的「agent」指能在授权范围内选择并调用工具改变外部状态的 AI 系统；并非每个 agent 都不经审批行事——令人担心的是：当执行不再等待独立检查时，会发生什么。）

我想请 AI 工程师审视的缺口是：**我们把自主权交给了依赖「从未为『行动』做过校验」的数据的系统。**同样的数据被用于报表时我们可能接受了——因为有人站在数据与决策之间，悄悄吸收了那些缺口。我以从业者的身份写这篇，出于对这一风险边界变化的担忧。我不是说每个生产数据集都不可靠，也不是说每个 agent 部署都剥除了人类监督。问题是：**支撑一个答案的证据，是否也足以授权一个动作。**

## 回答是宽容的，行动不是

错误的答案可以停留为一场对话。错误的行动改变状态。这就是那个转变的一句话版本，值得反复咀嚼。答案被依赖时也能造成伤害；区别不在「无害 vs 有害」，而在「错误是否必须先穿过另一个决策，才能变成一次已执行的变更」。

当助手给分析师一个错误的数字，分析师可以质疑、追问、上报——错误留在一个人类仍可介入的对话里。当一个拥有执行权的 agent 拿到同样的数字，它可以批准理赔、下达订单、路由工单、关闭案件。**除非工作流有显式的门禁，错误不再只是屏幕上的一句话——它是另一个系统里的状态变更，可能在任何人检查支撑证据之前就被记录为「已完成」。**

我们造过「产出输出供人审查」的 AI；我们也在造「产生后果、人可能事后才发现」的 AI。两类工作流共享建模难题，但**不共享同一个运营风险边界**。数据校验现在需要保护的是执行，而不只是提升一条展示建议的质量。一个好的「回答基准」，本身不能证明系统应该获得行动的许可。

## 出错时的样子

考虑一个假想的退款工作流（非真实事件）：一个 agent 有权在限额内批准常规退款。几个月来它表现良好——读到的数据与资格规则吻合，退款金额小。然后一次上游变更悄悄改变了一个状态码的语义，而没有更新下游契约。本应拒绝的交易现在符合批准规则。没有技术报错。管道是绿的。**这个 agent 以比人工审查所能跟上的速度，反复批准了它本应拒绝的退款。**

当终于有人注意到总量时，损害不再是一块可以在任何人行动前修正的错误仪表盘数字——而是一批已完成的退款：每一笔都与 agent 收到的记录一致，合在一起却难以回滚。**模型不需要产生幻觉，这个失败就会发生。**状态码的语义变了、校验没侦测到、工作流允许这些输入授权付款——这是系统性失败。一个有缺陷的模型、一次糟糕的工具调用、一个缺失的策略检查，各自都是通往同一结局的独立路线。

## 数据从来没有像 demo 里那么可信

企业数据工作里我一再撞见的事：**生产数据集依赖的假设，远强于任何写下来的东西。**新鲜度大致可以；一个 join 大致完整；某个字段的运营定义可能活在一位老员工脑子里，书面定义早就落后。仪表盘在那些弱点之下仍能显得有用——因为懂业务的人在行动前用判断力垫了一层。**这种安排并不构成「同一数据集适合授权自动交易」的证据。**

我亲身经历过。多年前我负责一条全公司都在看的指标（Net Booking Value）背后的管道。它从来不是一个数字：它从每条业务线（机票、租车、住宿、活动、忠诚度）汇上来，底下还压着一叠列：gross bookings、net bookings、cancellations。陷阱在最后一个。「取消」在那些业务线里不是同一件事：住宿按间夜取消，租车按普通退款取消，每条线有自己的逻辑。**列名完全相同**，于是仪表盘用一个取消公式套所有业务——某些线里同一笔取消被数了两次。schema 全程完美：每列都在、类型都对。Net Booking Value 被静默低估了约三周——直到数字不再符合懂业务的人预期看到的样子。**那道人的常识校验做了巨大而不可见的工作。它才是实际的质量层，而它从没被写下来任何地方。**

Agent 不应被假定继承了那些未成文的业务上下文。系统可能不知道某个供应商周日从不发货、某指标在季末会回落、某字段自一次迁移后有了两个含义。模型能对**给它的**上下文推理，但那不会补上缺失的上下文、也不会验证其真实性。如果那些约束对动作要紧，它们需要变成显式规则、可信的参照数据、或升级条件。否则，**agent 收到的记录就成了它行动于其中的世界——无论那条记录是否准确反映了业务。**

## 速度把小数据问题变成大问题

还有第二个效应，是让我睡不着的那个：**重复执行会在任何人抓到之前放大暴露。**人可能只碰到一次坏数据点；自动化工作流可以在任何人审查结果之前，把同一条缺陷规则复用在一整个队列上。关键量是：它行动多快、检测耗时多久、每次动作携带多大权限——而不是「午饭前出了多少次错」的普适数字。

一个过期价格、一个错标类别、一个上游变更后漂移的定义——在低量下是烦扰，在高量下是重复发生的决策错误。在 agent 的速度下，一条缺陷输入实际上可以变成**一条运营政策**，被施加到共享该依赖的每一个决策上。这种传播不是不可避免的：速率限制、异常检查、停止条件都能打断它。但只要那些控制不存在，工作流就没有理由在输入变怪时放慢——它可以对一致错误的一致证据持续一致地行动。

于是，同一个数据问题——过去的结果是「修正一份报告」——现在可以产出许多已完成错误动作。规模取决于吞吐、检测延迟、动作限额与恢复能力，而不是自动化本身。**这就是为什么动作量监控应当与管道健康监控并列。**技术上成功的请求不必然是有效的业务结果；从下游损害中发现两者的差别，是一种昂贵的学费。

> 一个有能力的模型，不能让一条不安全的数据路径变得可信。在 agent 行动之前，它脚下的证据必须挣得那份授权。

## 「但我们留着人在环，对吧？」

这是我听到团队最先搬出的安慰，而**一旦审批变成勾选框，它就比听起来弱得多。**一个部署可以保留人批准高风险动作，却仍让审查者没有时间、没有上下文去质疑建议。自动化偏置（automation bias）的研究记录了人——包括专家——如何服从于不完美的决策辅助；Parasuraman 与 Manzey 的综述把它归到注意力：一个看起来可靠的 agent 邀请过度依赖，即使在有经验的审查者身上。

一个审查步骤有效，仅当审查者拥有相关证据、足够的时间检查它、以及叫停动作的真实权威。这些条件会随 agent 接手更多工作而流失——尤其当界面强调「批准」而非「独立验证」。诚实的版本是：**人类监督是一种需要设计并测试的控制，不是在流程里加一个名字就自动生成的安全保证。**它可以长期保持价值。但如果底层数据不可信，要求一位审查者无限期地补偿它，不是可持续的架构。

## 在 agent 行动之前，信任实际需要什么

「干净数据」不是这里的门槛。干净通常意味着数据符合声明规则；而**可信（Trustworthy）——对一个即将行动的 agent——意味着证据适合这个决策、且工作流能负责任地处理不确定性。**我会在决策时点（而不是三周后的事故复盘中）先问四个实操问题。这是一份工程清单，不是完整的风险框架——隐私、安全、公平与模型行为仍需各自的评估。

**1. Provenance（出处）：这份数据从哪来，对这次行动来说够新吗？**如果 agent 使用一份文档或记录，识别其来源、版本、生效时间、以及任何取代它的更新。**保留「记录何时被取回」与「其底层事实何时生效」的区分**——一份刚取回的文档可能描述一条已过期的政策。为决策定义可接受的新鲜度，而不是把「一次成功读取」当作证据仍然有效的证明。

**2. Scope（范围）：这个 agent、代表这个用户，被允许访问这份数据、执行这个特定动作吗？**读权限与执行权限是两个不同的问题。在执行操作的系统里检查用户身份、工具权限、受影响资源、动作限额。**不要依赖模型对一条权限声明的解读。**自主权需要一个可强制执行的边界——包括权限缺失或含糊时的安全拒绝路径。

**3. Fitness（适配）：证据适合这个决策吗，相关假设变过吗？**在授权执行前检查必填字段、单位、join、允许值、业务定义与任务特定的一致性。分布监控可以帮助揭示变化，但它不能替代语义检查：**一个状态码可以在保留格式的同时改变含义。**定义系统必须弃权（abstain）或升级（escalate）的条件，而不是把不确定的证据变成一个自信的动作。

**4. Reversibility（可逆）：如果动作错了，你能恢复相关状态吗？能重建授权它的证据与政策吗？**审计轨迹不是撤销机制。一笔完成的退款可能需要补偿交易；一条已发送的消息无法变成未读。对无法干净逆转的动作，保留显式审批与更紧的限额，直到风险与恢复程序被验证。可逆性降低赌注——它不使每个动作都安全。

这些不是纯模型问题。**一个 prompt 可以要求出处，但它造不出缺失的来源历史；微调不能授予交易系统不提供的回滚能力。**它们是数据与系统的职责，与模型评估并列——恰恰是赶着发布炫酷 demo 时最容易被跳过的那部分看不见的工作。（NIST 的 Generative AI Profile 覆盖 AI 全生命周期的可信度，如果你想要更大的框架；上面四问是我在执行边界上的更窄切法，不是 NIST 的规定。)

## 没人想听的重构

诱惑是把能量倒进「让模型更强大」，同时把数据当作别人家的管道。**对接近真实执行的工作流，这个分配是反的。**demo 里最令人兴奋的部分与部署系统里最薄弱的部分，很少是同一个组件。

更好的模型修不好一个未成文的字段、一条过期的政策、一个能越权的工具；它也无法确立上游记录是否最新、交易是否被允许。**每一个正在拓宽 agent 权限的团队，都在同时下两注：它的推理、与它行动所依赖的证据。这两注应当可见、可测、有界——而不是藏在一个强有力的演示背后。**

## 我实际会怎么做

这不是一篇反对 agent 的文章。委托执行可以真正有价值。这是一篇主张「**故意地挣得自主权，而不是默认一个有说服力的答案蕴含一个安全的动作**」的文章。如果是我来搭一个能行动的 agent，以下是我会遵循的顺序（退款案例作为贯穿示例）。每个阶段都需要具名的负责人、定义好的失败响应、以及「控制在真实流量下有效」的证据：

**1. 把计划与执行分开，从可逆起步。**让模型组装候选动作及其支撑证据，但授权交给一个独立的门禁——不是模型自己的解释。在一切你无法干净撤销的东西（花钱、发送、删除、面向客户的变更）前面保持这道门，直到恢复程序被演练、限额被论证。**可逆的动作也需要上限**——暂时的伤害与清理仍然有成本。

**2. 把数据适配检查放进动作路径，而不只在摄入。**执行前校验新鲜度、出处、范围、以及这个特定决策依赖的语义假设。如果一个字段的含义未经验证、必需证据缺失、或定义已变更——门禁返回显式的 **do-not-execute** 并把案例路由给人审。把检查与状态变更耦合，使记录无法在校验与提交之间被替换；做不到就提交前立刻复查版本、拒绝不匹配。

**3. 让重试安全，记录每一个决策。**去重键防止一次重试发出第二笔退款。trace 应记录证据与政策的版本、授权结果、工具实际改变了什么——在真实保留规则下只记录重建所需的内容。**如果你的 trace 无法区分「提议的动作」与「已完成的动作」，你还没准备好拓宽权限。**

**4. 在拓宽权限之前，先测试失败路径。**故意喂给它：一份过期的政策、一个陌生的状态码、一个缺失的 join、一个被撤销的权限、一个重复请求、一条在校验之后被改动的记录。**成功的标准是工作流阻塞、升级或恢复——而不是它顺利跑完 happy path。**然后只拓宽「已被观察结果与恢复测试支持」的那些具体动作，并在每次上游 schema、政策或权限变更后重新评估。**昨天的证据，不为今天的权威辩护。**

## 结语

Agent 本身不是风险。**一个在未经验证的证据上自信且快速地行动、携带超出其安全措施所能辩护的权限的 agent，才是风险——而仅靠更聪明的模型无法消除它。**我们正在为我们可能仍不信任「用于行动」的数据自动化决策。要紧的工作不只是让 AI 更自主；**是让证据值得被行动、让权限显式化、让失败可控制。**在问「你的 agent 能否完成任务」之前，先问：**这条数据路径，是否已经挣得了让它行动的权利。**

（参考资料：Parasuraman & Manzey (2010) 关于自动化偏置与注意力；NIST AI 600-1 生成式 AI 风险管理框架概要。）

# 《Automating Decisions on Data We Still Don't Trust》的发芽报告

## 材料核心

Agentic 工作流把审查边界从「人看着数字」挪到「代码执行动作」，而支撑答案的证据从未为「行动」做过校验——一句话转折：**回答是宽容的（错误留在对话里），行动不是（错误直接变成另一个系统的状态变更）**。三个放大器：企业数据依赖未成文的业务常识（Net Booking Value 双计取消静默低估三周——人的常识是没写下来的实际质量层）、速度把缺陷输入放大成运营政策、勾选框审批被 automation bias 侵蚀。处方：决策时点四问（Provenance 出处与新鲜度/Scope 读权限≠执行权限/Fitness 语义适配与弃权条件/Reversibility 可逆性与审计≠撤销），落地四步（计划与执行分离+可逆起步、适配检查进动作路径、重试安全+区分提议与完成的 trace、扩权前先测失败路径——「昨天的证据不为今天的权威辩护」）。

## 发芽 01：「回答宽容，行动严厉」——风险边界的重新画线

### 种子

同样的错误数字，在分析师手里是「可以质疑的一场对话」，在带执行权的 agent 手里是「可能已被记为完成的退款」。区别不在错误的严重度，在错误与后果之间是否还隔着一个人工决策。

### 故事

作者假想的退款事故里最刺骨的细节是「管道是绿的」：上游悄悄改了状态码语义、校验没侦测、工作流授权了付款——没有幻觉参与，纯系统性失败。它揭示的是分类学的缺失：我们只有「回答质量」的度量（benchmark），没有「行动授权资格」的度量。数据校验的目标函数因此要重写：从「提升展示建议的质量」改为「保护执行的合法性与可逆性」。

### Aha 瞬间

**「支撑一个答案的证据是否足以授权一个动作」——这一问应该成为所有 agent 上线评审的第一题。**回答基准的分值与执行权限的授予，是两条必须分开审计的曲线。

## 发芽 02：未成文的常识是隐形的质量层——Net Booking Value 的三周

### 种子

全公司盯着的那条指标，被「取消在不同业务线含义不同但列名相同」静默低估三周——发现它的不是任何校验，而是懂业务的人觉得「数字不对劲」。那道人的常识校验做了巨大而不可见的工作，却从没被写下来。

### 故事

Agent 不会自动继承这些未成文上下文：某个供应商周日不发货、某指标季末回落、某字段迁移后有两个含义——模型能对给它的上下文推理，但「不会补上缺失的上下文，也不会验证其真实性」。所以这些约束要么变成显式规则、可信参照数据、升级条件，要么它们就不再存在——而 agent 收到的记录就是它行动的全部世界。

### Aha 瞬间

**每个组织都有一层「活在老员工脑子里的数据语义」，它曾是人肉质量层；agent 化之前必须把它显式化，否则自动化不是加速了正确决策，而是加速了那条隐性层的失效。**数据迁移清单里最贵的一项，从来不是字段，是这些没写下来的定义。

## 发芽 03：审批勾选框的失效——监督是要被测试的控制，不是名字

### 种子

「我们留着人在环」是团队最先搬出的安慰；automation bias 研究（Parasuraman & Manzey）指出：可靠的表象邀请过度依赖，包括在专家身上。审批变成勾选框的那一刻，监督就名存实亡。

### 故事

有效的审查需要三条件：相关证据、足够时间、叫停的真实权威——三者都会随 agent 接手更多工作而流失。落地四步把「监督」变成可测试的对象：计划与执行分离（独立门禁授权，不信模型的自我解释）、适配检查进动作路径（do-not-execute + 人审路由）、trace 区分「提议」与「完成」、扩权前故意喂失败路径（过期政策/陌生状态码/撤销权限/重复请求）——**成功标准是阻塞、升级或恢复，不是跑完 happy path。**以及一条时间纪律：昨天的证据不为今天的权威辩护。

### Aha 瞬间

**「人在环」不是部署状态，是一个必须设计、必须演练、会随负载流失的控制——它的质量要用「喂坏数据看会不会挡」来验收，而不是用「流程图上有个菱形」来宣告。**
