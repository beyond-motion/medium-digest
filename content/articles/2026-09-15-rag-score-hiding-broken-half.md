# 你的 RAG 分数正在掩盖坏掉的那一半

> 原文：[[deepeval/03] Your RAG Score Is Hiding Which Half Is Broken](https://medium.com/@tuhinsharma121/deepeval-03-your-rag-score-is-hiding-which-half-is-broken-208e40037669)

---

## 仪表盘全绿，代码在亏钱

虚构公司 Halcyon 是一家约 200 人的支付 API 厂商，客户是集成刷卡支付的开发者——通常赶着截止日期，通常在深夜。它的文档公开且按日期版本化。六个月前，文档团队在官网上线了一个文档助手：开发者输入问题，检索步骤找到几页文档，语言模型根据它们写出答案。开发者读答案、照着写代码。**Halcyon 没有人读这些答案。而这些代码在移动真金白银。**

今年三月，Halcyon 更换了 webhook 签名方案：旧方案在 `X-Halcyon-Signature` 头里放 HMAC-SHA1 摘要，新方案用带时间戳的 HMAC-SHA256。旧文档页仍然发布着——因为钉在旧 API 版本上的账户仍收到旧签名头，页面最后一句话就是这么说的。助手的仪表盘上只有一个质量数字：faithfulness（忠实度），自上线以来一直是绿的。上周，一位开发者问它「如何验证 webhook 签名」，照它说的实现了；周一她开了工单：所有事件验证失败。文档团队打开仪表盘——**还是绿的。**

## 一个数字说不出该修哪一半

RAG（检索增强生成）= 检索器在文本库中搜出与问题最像的片段 + 生成器（语言模型）根据片段写答案。两个组件，一个输出。**输出错误时，仪表盘上的那个数字说不出该修哪一个。**文档团队的绿灯是给生成器的分数；检索器根本没人在打分。

集成测试失败只能告诉你「管线坏了」；按环节的单元测试才能告诉你「哪个环节」。DeepEval 的 RAG 指南就建立在这个拆分上——但与真实单元测试有一处不同：**这里由一个裁判（judge）代替固定的期望值**。裁判是第二个语言模型，按固定评分表给输出打分并给出理由。

DeepEval 的五个 RAG 指标恰好骑在组件线的两侧：**三个读检索器返回了什么，两个读生成器写了什么。**每个指标读一个测试用例：问题、答案、检索器返回的块，以及一份手写的参考答案。参考答案住在 golden（每个问题无论跑多少次都保留的那条记录）里。需要参考答案的指标是 reference-based，只读「问题+答案+块」的是 referenceless——这个区分最后比「检索 vs 生成」的区分还要要紧。阈值是及格线：DeepEval 的分数一律越高越好，阈值是下限。

实验计划：把助手建成两节点图（retrieve 节点+generate 节点），让两半在代码和指标里都可见；用一个问题的全五指标打分并打开每一条裁决（裁判对每个块/每句给出的 yes/no）；**故意打坏检索器，看哪些分数动了**；然后引爆这个语料库埋着的两个陷阱，看哪个指标看见了哪个；最后把检索搬进真正的向量数据库——因为修复住在那里。（整条 notebook 从环境读 `GEMINI_API_KEY`，全程跑一遍花费略低于 2 美元，账单最后打印。）

## 两个陷阱：都是「文本对、语义错」的布局

语料里埋的两个陷阱对应 RAG 在真实文档库上最常见的两种死法：

**陷阱一：废弃页（deprecated-page）。**Webhook 签名问题只能从当前签名页正确回答，而旁边有一页读起来像正确答案的废弃页。切分之后，那页变成了两块：第一块是 53 个词的完美指令——header 名、算法、密钥、常数时间比较、拒绝规则，样样都对；**「这一切已过时」的那句话住在第二块里。**按生成器会读到的方式看，第一块里没有任何字说这页是死的。记录知道——元数据里 `status: deprecated`、`updated` 日期俱在。真实文档库里，版本时效恰恰就住在文本旁边的元数据里，而切块保留的是文本。**生成器读的是文本。**

**陷阱二：缺失的要求（missing-requirement）。**「如何创建 charge」在 charge 页有答案，但缺一条规则：每个动钱的请求都必须带 `Idempotency-Key` 头（客户端生成的唯一串，重试时返回原响应而不是再扣一笔）。这条规则住在 conventions 页——**问「怎么创建 charge」的人不会想到要点名这一页。**

十个开发者问题各配参考答案：八个普通（单页可答，做对照组）、两个带陷阱；另有 Q-10 需要变更日志与当前签名页两页合读。

## 故意打坏，看谁动了

作者还准备了「打坏」的方式：检索函数有个 `highest_first` 参数——设为 False，排序反向，返回的变成**最不像问题的三个块**。这精确复刻了一个真实世界的常见事故：**给「为相似度写的代码」传入了「距离」，而距离越小越好。**

（全流程跑完后的读数逻辑：对照组的五个指标应当全绿；陷阱一引爆时，检索侧的 Contextual Precision / Recall / Relevancy 应当报警——因为「正确的块没被检索到或被废弃块挤占」，而只读答案与块的 Faithfulness 完全可能继续绿着——**生成器忠实地总结了它拿到的错误文本，恰是「忠实地错着」**；这就是开头那个故事的机理：唯一能看见问题出在检索侧的指标，根本不在仪表盘上。）

## 修复住在向量数据库里

文末把检索从内联函数搬进真正的向量库（gemini-embedding-001，块上限 60 词、top_k=3），因为修复不住在演示脚本里。作者在本篇留下的方法论清单很干净：**把系统建成两节点图，让拆分在代码里可见；给每个问题配手写参考答案（golden）；陷阱题设计成「文本对、语义错」；故意打坏一半，看另一半的指标谁在动；然后才谈修。**

一句话版本：**faithfulness 全绿只能证明「生成器忠实于它拿到的上下文」；它对「上下文本身是错的」一字不提。想让 RAG 可诊断，先把检索侧的三个指标请上仪表盘。**

# 《[deepeval/03] Your RAG Score Is Hiding Which Half Is Broken》的发芽报告

## 材料核心

支付 API 厂商 Halcyon 的文档助手 faithfulness 自上线全绿，却让开发者照着过时的 HMAC-SHA1 签名文档写了代码、工单爆掉——因为仪表盘上唯一的分数是生成器指标，检索侧无人在评分。文章把 RAG 拆成两半来评：DeepEval 五指标中 3 个读检索返回（Contextual Precision/Recall/Relevancy）、2 个读生成文本（Answer Relevancy/Faithfulness），裁判按固定评分表代替单元测试的固定期望值；语料里埋了两个「文本对、语义错」的陷阱（53 词完美指令的废弃页切掉了「已过时」那句话；藏在另一页的 Idempotency-Key 必带规则），再用 `highest_first=False` 复刻「把距离当相似度」的真实事故，看哪些分数动了。

## 发芽 01：忠实于错误上下文的生成器，是最安静的失败

### 种子

故事里最冷的一笔：仪表盘绿灯与工单爆掉同时为真——faithfulness 衡量「答案是否忠实于检索到的上下文」，而那次失败里生成器完全做到了这一点：它忠实地总结了错误（过时）的文本。

### 故事

陷阱一的设计把这个盲区做成了标本：废弃页被切成两块后，53 词的完美指令块里没有任何字说页面已死——「这一切已过时」住在另一块里；版本时效只存在于元数据（status: deprecated、updated 日期），而切块保留的是文本、生成器读的是文本。于是每一步都「正常」：检索返回了语义最像的块，生成器忠实作答，指标全绿，代码上线，资金受损。

### Aha 瞬间

一个只测「链条最后一环是否诚实」的系统，对「喂给它的是什么」完全失明——评估的盲区从来不在被测的那一环，而在没被测的那一环。

## 发芽 02：集成测试说「坏了」，单元测试才说「哪里坏了」

### 种子

「集成测试失败只说管线坏了；按环节的单元测试才说哪个环节」——RAG 的一个总分是集成测试，骑在组件线两侧的五指标才是单元测试。

### 故事

文章的设计让拆分同时存在于代码与指标里：助手被建成 retrieve/generate 两节点图，三个指标读检索返回、两个读生成文本；打坏方式也复刻真实事故（为相似度写的代码收到了距离），于是「哪些分数动了、哪些纹丝不动」直接指认病灶——检索侧报警而生成侧全绿，答案就是「别改提示词，去修检索」。

### Aha 瞬间

可诊断性不是故障发生后的分析能力，而是系统建成时的结构选择——两节点图 + 按环节评分，等于提前把「哪里坏了」这道题的答案空间切成了可枚举的格子。

## 发芽 03：版本时效住在元数据里，死亡却写在另一块文本里

### 种子

废弃页陷阱的解剖：「53 词完美指令」与「这一切已过时」的句子被切块分进了两个世界；生成器读的是文本，而「这页是死的」只存在于元数据。

### 故事

这是 RAG 文档场景的结构性裂缝：切块（chunking）按语义完整性保留文字，版本状态按工程惯例存进 status/updated 字段——两个系统各说各话。当检索器按相似度选块时，「措辞最像答案的过时文本」与「真正的现行答案」得分相同，而唯一的辨析线索（元数据）根本不进入生成器的视野。

### Aha 瞬间

知识库的时效性不能只靠「某句话提到了日期」来传递——把状态与内容分开放置的工程惯例，在检索系统里必须重新接上，否则最危险的答案恰恰是写得最好的那版旧答案。
