# 超越 API 兼容性检查：Netflix 造了把「爆炸半径」量出来的工具

> 原文：[Beyond API Compatibility: Building a Tool to Measure the Blast Radius of Library Changes](https://medium.com/netflix-techblog/beyond-api-compatibility-building-a-tool-to-measure-the-blast-radius-of-library-changes-9474f2fd4f90)
> 作者：Roberto Perez Alcolea（Netflix Technology Blog · Java Platform Team）｜2026-10-23｜9 min read｜82 claps

---

## 问题：API diff 看得见，依赖者看不见

Netflix 的共享 Java 库支撑着一大片各自独立演进的仓库生态。一个库的改动从一个仓库出发，影响却可能波及许多其他仓库。库的生产者（producer）眼前摆着清晰的 API diff——他们看不到的，是**还有谁在依赖那些被改动的符号**。

这种可见性的需求，正随着编码智能体接管更多开发生命周期而变得更迫切：智能体能加速本地修改，但没有跨仓库上下文，它既判断不了下游风险，也帮不上消费方规划迁移。生产者评估一次改动所需的证据，同样能指导动手改代码的那个智能体。

一个常见场景是删除已废弃的 API。废弃入口扩大了生产者必须测试、文档化、支持的面，还会约束库的演进方向。假设替代方法已经发布了好几个版本，而旧方法又表达不了新行为所需的参数——库的测试全部通过，兼容性检查器标出这次删除。此时生产者依然回答不了决定下一步的四个问题：

- 还有消费方在调用这个方法吗？
- 消费方集中在一个版本上，还是散布在好几代版本？
- 有没有别的库实现或包装了这个 API，把影响放大？
- 直接协调就够了，还是需要一场正式的废弃加迁移运动？

仓库少的时候，挨个问一问、搜一搜就行。仓库一多，找到每个调用方及其所用库版本就难了——答案散落在各个消费方代码库和构建里。拿不到证据，生产者要么合并破坏性变更、通过消费方报错来发现影响，要么因为风险未知而把旧 API 永久供着。库需要演进，生产者需要帮他们「有意图地演进」的证据。

## Quasar：把「谁在用这个符号」变成可查询的事实

Netflix 为此造了 **Quasar**：跨仓库索引符号定义与引用，帮库的生产者回答两个问题——**库的公开 API 改了什么**，以及**哪些仓库正在使用被改动的那些符号**。前者识别潜在不兼容变更，后者估计「已观测到的影响半径」。两者合起来，把一句泛泛的兼容性警告变成合并或发布前就能行动的证据。

现有技术各自只看到问题的一角：二进制与源码兼容性工具能发现契约变更，却不知道谁在用；依赖图能看声明式的依赖范围，却证明不了代码真的调用了某个方法；文本搜索会漏掉重载、继承和调用背后的构件版本；消费方构建验证最可靠，但全量跑一遍太贵。

Quasar 选择站在 **SCIP**（一个开源的语义代码智能体交换格式）之上：各语言的索引器用稳定的符号标识符编码定义、引用与关系。每个接入的 CI 构建都会把 SCIP 索引提交给 Quasar 的摄取服务，API 定义与消费方引用以 Parquet 形式写入 Amazon S3，保留符号身份、依赖版本与源码位置。于是「一个仓库里的 API 变更」可以连到「另一个仓库里的精确调用」——哪怕这些仓库的索引是彼此独立完成的。查询侧用 Amazon Athena，结果通过 REST、GraphQL API 和 MCP 服务器暴露。

拿一个简化的 API 变更举例：接口方法 `getLegacyValue(Request)` 被替换成 `getValue(Request, Options)`。生产者侧工具提交旧方法描述符后，Quasar 构造其规范符号身份，用一条 Athena 查询在符号引用表里找出仍在调用被删方法的仓库，并顺带检查实现类及其调用方——确保每个受影响仓库只数一次。对这次变更，它会告诉生产者：哪些仓库还在用 `getLegacyValue`、用的什么版本、部分调用发生在哪里。

## 把分析搬到合并之前：PR 评审里的影响报告

版本对版本的比较在规划升级或写迁移指南时很有用，但反馈来得越早越好。Quasar 按提交存储 API 定义快照：给定 base 与 head 两个提交，它把符号分类为新增、删除或签名修改，删除与修改随即成为消费方影响分析的候选。

一次不兼容的变更并不自动等于一次高风险变更。Quasar 报告的是**已观测到的影响**，由生产者决定怎么办，它不强制执行发布策略。一份示例影响报告长这样：

```json
{
  "change": "REMOVED",
  "symbol": "Client#getLegacyValue(Request)",
  "affectedRepositories": 137,
  "versionDistribution": [
    { "version": "4.2.1", "repositories": 86 },
    { "version": "4.1.7", "repositories": 38 },
    { "version": "3.9.4", "repositories": 13 }
  ],
  "sampleConsumerLocations": [
    { "repository": "checkout-service",
      "filePath": "src/main/java/com/example/checkout/CheckoutClient.java",
      "lines": [84, 129] },
    { "repository": "client-wrapper",
      "filePath": "src/main/java/com/example/client/ClientAdapter.java",
      "lines": [57] }
  ],
  "libraryCriticality": { "tier": 1, "basis": "highest-tier downstream application" }
}
```

137 是符号级的数字：有 137 个已索引仓库引用了这个被删除的方法。版本分布揭示出主力群体已到 4.2.1，而 3.9.4 上还拖着一条长尾。文件路径与行号把影响范围变成工程师或编码智能体手里的具体工作清单。这些信号合在一起，改变生产者的计划：不再是「先合并、等报错」，而是保留并正式废弃旧方法、发布迁移路径、协调一次更大的迁移、再盯着长尾版本收尾。同一份 API diff 若配上微弱或陈旧的证据，正确动作则完全不同——先刷新索引再决策。价值不在于检测到删除本身，而在于**选择一个相称的下一步**。

## 证据质量：「没查到引用」不等于「可以安全删除」

Quasar 报告里最容易被误读的就是空结果。「未观测到引用」只说明在已索引范围内没找到——反射、配置、动态加载、陈旧分支、索引不完整，任何一种都能把消费方藏起来。所以结果必须同时说明：请求的提交是否已被索引、消费方索引有多新、证据是否被截断。

PR 评审要求 base 和 head 两个提交都有精确的索引快照，缺任何一个，Quasar 直接报告无法比较，而不会拿默认分支的快照凑数——免得一次「缺失的比较」看起来像一次干净的 API diff。

## SCIP 带来的多语言地基

共享的 SCIP 格式还让 Quasar 能索引多个语言生态。概念上，client-lib 把 `Client#getLegacyValue(Request)` 索引为定义，checkout-service 把对同一符号的调用索引为引用，Quasar 就能把库 API 跨仓库连到消费方。关系（relationships）在生成代码场景尤其有用：Quasar 可以把一个 Protobuf 定义沿着生成的 Java 成员追到使用它们的仓库，哪怕消费方代码从未点名那个 .proto 元素。

边界也要说清楚：SCIP 记录符号与引用，但判断一次变更是否「破坏性」需要该生态自己的兼容性规则。目前 Quasar 对 JVM 与 Protobuf API 做定义比较，并把 Protobuf 变更沿生成的 Java 代码追踪到受影响仓库；Go、Python、JavaScript/TypeScript、Rust 支持使用查询，但破坏性评估尚未覆盖。

## 把风险评估再往前挪：让智能体在写代码时就看到影响

如今 Quasar 在 PR 上呈现发现（观测到的消费方数量与置信度）。Netflix 想把这一步再往前挪：写库代码的智能体应当在自己改动公开符号时就意识到这件事，并在变更变成 PR 之前查询 Quasar。API 与 MCP 集成提供了访问通道，但**光有通道不等于有意识**——编码工作流还得识别出「这是在改公开 API」，智能体才知道何时查影响、何时叫来生产者。

提前介入不会取代 PR 分析：PR 评估仍要核对具体 diff、兜住编码阶段没识别出的变更；覆盖率、新鲜度、歧义、不支持的平台和截断信息，必须以机器可读的形式贯穿两道检查。文章里那句被反复强调的原则值得单独抄下来：**智能体不应该把「可用索引里没观测到使用」翻译成「可以安全删除」。**Netflix 的目标分工是：Quasar 供给语义证据，智能体削减迁移苦工，API 与发布决策的责任始终留在库的生产者手里。

## 四条实战教训

1. **兼容性与影响面分开看**。一个被删的方法即使没有任何调用者，也可能破坏 API 契约；受影响仓库及其版本清单才显示迁移工作量。两个信号都需要，才能选对发布路径。
2. **证据必须可检验**。仓库计数配上样例调用点和版本分布才有用；结果还要说明索引了哪些提交、消费方索引多新、证据是否截断——否则「没找到使用」会被误当成「没人受影响」的证明。
3. **跨语言把使用与兼容性分开**。SCIP 能在多个生态找到符号引用，但「是否破坏」需要该生态的兼容性规则或可信的生产者侧信号。
4. **趁选择还在手上时把证据送到生产者面前**。PR 阶段的发现能促使生产者保留 API、发布迁移路径或在合并前协调消费方；把同样的证据前移到编码工作流，还能在编辑发生时就塑形它。发布之后，这些证据仍能帮助定位待迁移的消费方。

Quasar 目前为跨仓库使用分析索引 JVM、Go、Python、JavaScript/TypeScript 与 Rust 代码。它内部服务于 Netflix，但**模式是可移植的**：语义化索引代码、保留 API 定义、在变更发生处比较、查询受影响的消费方、如实报告证据质量。库的生产者要的从来不只是兼容性判定——而是知道谁可能受影响，并在发布之前有足够的时间行动。

# Beyond API Compatibility: Building a Tool to Measure the Blast Radius of Library Changes（发芽报告）

## 材料核心

Netflix Java Platform Team 的 Quasar 用 SCIP 语义索引把「API 变更」与「消费方真实调用」连了起来：CI 构建持续提交符号级索引，PR 评审时用 Athena 查询出哪些仓库、哪些版本、哪些文件还在依赖被改动的符号，并在报告里附上证据质量（索引覆盖、新鲜度、截断）。它不替你做决定，只把「137 个仓库、版本长尾拖在 3.9.4、样例调用在第 84 行」这样的事实放在生产者面前——让破坏性变更的处理从「合并后等爆炸」变成「合并前选策略」。下一站是让编码智能体在改公开符号的当下就查询影响，而非等 PR 阶段才发现。

## 发芽 01：把「影响面」升级成一等公民数据

### 种子

工程协作里最贵的知识从来不是「这个函数怎么写」，而是「谁在依赖它」。依赖关系图人人都有，但它只回答声明式的「谁引入了包」，回答不了「谁真的调用了这个方法」。Quasar 的做法是把调用级的符号引用变成持续累积、可 SQL 查询的数据资产。

### 故事

想象一个平台组要下线一个老旧接口。没有 Quasar 时，流程是在群里的喊话、等几个季度、祈祷没人再用了。有了 Quasar，流程变成一次查询：137 个仓库、版本分布、示例调用点行号——迁移清单自动生成，还能按版本分布排出迁移的先后次序。删不删从「勇气问题」变成「排期问题」。

### Aha 瞬间

**「没查到引用」需要和「证据质量」一起读。**数据查询领域的人早就知道空结果有陷阱（索引覆盖不全、字段口径不对），但工程工具的输出常常不带这些元信息。Quasar 把「提交是否被索引、索引多新、是否截断」做进结果契约——这是把数据素养移植进研发工具链的范本，任何做「全局搜索/影响分析」类工具的人都该抄。

## 发芽 02：智能体时代的证据素养：别让「没找到」变成「安全」

### 种子

编码智能体最大的风险不是写错代码，而是**在错误的证据强度上做出正确的语法动作**。删掉一个没人调用的方法，代码审查全绿、测试全过——直到某个没被索引的消费方在生产环境炸掉。

### 故事

Netflix 把同一份证据设计成双通道：人在 PR 评审时看报告，智能体在编码时通过 MCP 查询。并且明确划了红线——智能体不得把「可用索引里没观测到使用」翻译成「可以安全删除」。这句话值得贴在每一个给智能体接内部工具的团队墙上：工具的输出是「在给定证据范围内的事实」，不是「世界的事实」。

### Aha 瞬间

**智能体工作流的真正接口不是 API，是证据契约。**给智能体接一个查询工具很容易，难的是让它理解结果的置信边界（覆盖率、新鲜度、截断）并据此调节行动。Quasar 的选择是把证据质量做成机器可读字段、贯穿 PR 与编码两道检查——这不只是工具设计，是在给智能体定义「什么算知道」。
