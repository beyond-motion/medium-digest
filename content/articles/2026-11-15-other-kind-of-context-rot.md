# 另一种上下文腐烂

> 原文：[The other kind of context rot](https://medium.com/data-science-collective/the-other-kind-of-context-rot-e4bd4c602062) — Barr Moses（Monte Carlo CEO）

---

每个跟大语言模型打过交道的开发者，都学会了害怕「上下文退化」。它的表现是：一个起初敏锐的 agent，随着对话变长逐渐丢失主线——忘记指令、执着于无关细节、最终开始整体幻觉。

业界已经给这种失败模式起了名字，很多实践者都知道：**context rot（上下文腐烂）**。腐烂之普遍，以至于这个领域的主要玩家都在深入研究并采取措施缓解它。比如 Anthropic 加了上下文编辑和记忆工具来帮 agent 管理长期上下文；开源搜索基础设施厂商 Chroma 发表研究显示，推理性能随上下文长度增加而系统性退化。一整个学科——context engineering（上下文工程）——已经兴起，专门修剪、压缩、优化每一次推理喂给 LLM 的 token。

这一切工作瞄准的都是一个真实且有充分记录的问题。**但它漏掉了一件事：它把上下文腐烂当成会话内的现象**——只发生在上下文窗口里、随 token 累积而发生的东西。

**还有另一种上下文腐烂，与窗口长度、token 上限、会话压缩都无关。**它阴险恰恰因为它不发生在窗口里，而发生在数据到达窗口之前很久的地方。

它还没有正式名字，我喜欢叫它 **source rot（源头腐烂）**：agent 检索的底层数据在源头就已经过时、schema 已经漂移、或质量以其他方式退化——这种现象。

窗口腐烂的 agent 输出变差，是因为它的内存满了；而源头腐烂的 agent 输出变差，是因为**它的内存里装满了被腐蚀的、过时的、互相矛盾的现实**。

两种都坏，但只有前者在获得关注。要真正大规模部署可信 AI，这一点需要改变。

## 两种失败模式：窗口腐烂 vs 源头腐烂

要修这个问题，团队得先分清两种 decay：**运行时的会话内 decay** 与 **持续的上游 decay**。各自有独特的成因、影响范围和修复机制。

窗口腐烂随新会话重置。源头腐烂持续存在，直到有人去修数据。

## 为什么上下文工程够不着源头腐烂

上下文工程是当下最热的话题之一，而且有充分理由：LLM 与 agent 需要健壮、结构化的信息喂进来才能表现得智能且准确。

但今天的上下文工程缺了一手，因为它**完全聚焦于优化什么进入模型、以什么结构进入**。它涵盖这些必要流程：压缩系统指令、抽取关键实体、去重聊天历史、为语义相关性过滤 RAG 检索块。

要理解影响 LLM 上下文的不同失败模式，借用开发者兼研究者 Drew Breunig 的分类很有用：

- **投毒（Poisoning）**：一个幻觉或错误进入上下文，被反复引用，错误复利。
- **分心（Distraction）**：上下文长得让模型依赖累积的历史，而不是用训练里学到的去推理。
- **困惑（Confusion）**：上下文里的多余内容被用来生成低质量回复。
- **冲突（Clash）**：上下文里的新信息或新工具与已有的打架，迫使模型选择信哪个。

借 Breunig 的词，**源头腐烂可以理解为发生在上游的上下文投毒与上下文冲突。**

不是一个幻觉进入一条孤立线程然后被重复——而是一条过时的数据管线，把错误输入注入每一个从该源构建的上下文窗口。**这是规模化的投毒。**

此外，源头的问题还会以更沉默、更不可见的方式镜像上下文冲突。向量库里的一份公司政策文档某天更新了，告诉 agent 一条新规则；而一条延迟的数据仓库表还反映着旧版本。这迫使模型在互相矛盾的真相之间任意选边——而且很可能不是一次，是 agent 反复运行的每一次。

**再多的 prompt 压缩、滑动窗口分块、语义重排都解不了这类问题。**当腐烂从那么上游开始，完美压缩的上下文会以绝对精度交付完美错误的答案。你很可能要到问题扩散到引发某些故障时才知道。

## 持久化问题：过期的长期记忆

当架构转向长期 agent 记忆，源头腐烂的问题会加深。

想想现在的生产级 agent 有多少动作：它们不只是查询静态文档——它们**写回**知识图谱、关系数据库、情景记忆存储，去记住客户偏好、用户状态、运营上下文，跨越数周或数月。

数据源的问题经由 agent 的动作传播出去之后，会反过来叠在自身之上——**agent 用更多（错误的）信息把循环再喂一遍。**

最近的研究表明，模型自己并不擅长抓住这个困境。比如 **STALE**，一个 2026 年 5 月发布的基准，专门测模型如何处理已被取代的信息：400 个专家核验的场景、1,200 道测试题、最长 150k token 的上下文。

在基准报告里，表现最好的模型在全部问题上的总准确率只有 **55%**。这涵盖三件事：注意到一个事实已过时、抵抗假设旧版本的问题、以及无人提示时应用新版本。**即便新信息就在上下文窗口里，模型也常常抓住旧版本不放。**

这对旨在保留长期记忆的 agentic 架构有直接含义。**如果企业 agent 的记忆存储缺少自动失效、新鲜度时间戳、数据生命周期管理，那么每一次下游的上下文组装都是一笔负债。**agent 失败时，原因不是上下文窗口太窄，而是企业架构把数据存储当作静态档案，而不是活的、会腐烂的系统。

## 真实的运营影响

在生产环境里，源头腐烂的表现是**静默退化**，而不是响亮的应用异常。几个例子：

- **两个源，两个答案。**2024 年，加拿大仲裁庭裁定 Air Canada 败诉——它的网站聊天机器人告诉一位客户，订票后可以申请丧亲折扣，而航空公司自己的政策页写着相反的内容。法庭认定航空公司为其网站上的一切负责——聊天机器人包括在内——并指出客户没有办法知道该信哪个源。**这就是野外的上下文冲突：当 agent 背后的源互相矛盾时，用户继承了矛盾。**
- **坏输入，安静的损害。**2022 年，Unity 披露：从一个大客户摄入的错误数据降低了其广告定向模型的准确性。模型继续在腐蚀的输入上运行，问题最终在业务结果上现形——**当年约 1.1 亿美元的营收损失。**
- **检索不检查来源。**Google 2024 年推出 AI Overviews 时，告诉一些用户往披萨酱里加胶水。追查发现答案来自 Reddit 上一个老笑话。模型把它检索到的东西流畅而自信地总结了。Google 后来表示系统难以区分真诚的建议与讽刺。

在我们自己 2026 年对 260 名生产级 agent 从业者的调查里，**64% 说上下文与数据质量是他们最大的可见性盲区，52% 说他们是通过客户或用户的投诉才发现生产问题的。**

正如这些例子所示，源头腐烂是非常真实的问题，而且常常要到终端用户撞上坏输出才暴露。

## 如何预防源头腐烂：四条架构解药

弥补这个缺口，需要把上下文当作一条端到端数据管线的末端交付机制。为了把 agent 与源头腐烂隔离，我建议工程团队实施四条架构护栏：

**1. 把新鲜度元数据直接注入上下文。**永远不要把检索到的数据当裸字符串喂给 LLM。始终让块和结构化记录伴随显式时间戳：

```
[DATA_SOURCE: warehouse.prod_finance.invoices]
[DATA_FRESHNESS_TIMESTAMP: 2026-11-11T13:00:00Z]
[DATA_STATUS: VALIDATED]
Account Balance: $142,500.00
```

并在系统 prompt 里指示 agent：如果检索到的时间戳超出工作流的新鲜度 SLA，就标记或拒绝计算。

**2. 在上游强制 schema 契约。**通过 text-to-SQL 或结构化工具查询数据库的自治 agent，对静默的列改名、类型变异、被删的表极其脆弱。对所有暴露给 agent 工具定义的分析表强制刚性的 schema 契约。**上游 schema 漂移时，管线应该 hold 住下游执行，而不是传递空 fallback。**

**3. 给 agent 记忆实现 TTL 与冲突失效。**情景记忆与长期记忆不应无限期存续。在记忆数据库里实现显式的 TTL 与冲突解决规则。当一条新的实体更新被记录时，过时的前驱记录必须被显式标记为 superseded，或从未来的检索轮里修剪掉。

**4. 监控喂给向量库与仓库的数据。**可观测性不能停在 token 计数与追踪延迟上。团队必须监控填充 embedding 与检索索引的那些源数据表的健康度、新鲜度、体量与分布。**上游管线停机时，监控系统必须在客户撞上幻觉漂移之前通知 agent 运营者。**

## 结论

上下文工程为 AI 生态做了一大好事：教会开发者尊重上下文窗口的极限。**但对 token 压缩的痴迷，可能让团队对喂进那些 token 的数据质量视而不见。**

你可以用数学级的精度优化块、修剪 prompt 历史、调校语义重排器。但如果进入窗口的数据在源头已经过时、不完整、被腐蚀，**你的 agent 会安静而自信地失败，每一次。**

可靠的 AI agent 不始于上下文窗口。**它们始于可靠的数据。**

# 《The other kind of context rot》的发芽报告

## 材料核心

业界盯住的 context rot（窗口腐烂）是会话内现象；作者提出 source rot（源头腐烂）——agent 检索的底层数据在源头就过时/schema 漂移/质量退化，与窗口长度无关。用 Breunig 四模式定位：source rot = 上游化的投毒（一条过时管线给每个从该源构建的窗口注入错误=规模化投毒）+ 上游化的冲突（向量库新政策 vs 延迟仓库旧表，模型被迫反复在矛盾真相间选边）。推论：「完美压缩的上下文会以绝对精度交付完美错误的答案」。持久化加深：agent 写回记忆库→错误循环自反喂；STALE 基准（2026-05，400 场景/1200 题/150k 上下文）最好模型仅 55%——新信息就在窗口里也抓着旧版不放。实战三案例：Air Canada 聊天机器人 vs 政策页（法庭判网站全责）、Unity 脏数据静默烧掉 1.1 亿美元、Google AI Overviews 把 Reddit 老笑话当披萨建议；2026 调查 260 从业者 64% 称上下文/数据质量是最大可见性盲区、52% 靠用户投诉才发现生产问题。四条架构解药：新鲜度元数据注入+SLA 拒算、上游 schema 契约（漂移时 hold 不传空 fallback）、记忆 TTL+冲突失效（superseded 标记）、监控源数据表健康度（停机告警先于客户撞幻觉）。

## 发芽 01：「完美压缩交付完美错误」——优化的局部性陷阱

### 种子

上下文工程的全部流程（压缩指令/抽取实体/去重历史/语义重排）聚焦「什么进入模型」；但当腐烂在源头，这些以数学精度执行的操作只会更高效地放大错误。

### 故事

这是一个经典的局部性陷阱：你在管线的末端做精细优化，而问题的位置在管线的前端。末端优化看不见前端腐烂，因为压缩器、重排器、去重器都只处理「到达它们的东西」——它们是盲传筒。更糟的是，优化程度与错误传播效率成正比：重排器越精确，腐烂数据被排得越靠前、被引用得越自信。「绝对精度交付完美错误」揭示了这条链的荒诞结构——每一段都做了正确的局部决策，全局输出却是系统性错误的。

### Aha 瞬间

**对 LLM 管线而言，「输入质量」与「输入呈现质量」是两条独立的质量轴——上下文工程只提升后者；当前者坏掉时，后者的每一次进步都在给错误提速。数据质量工作（ freshness/schema/lifecycle）无法被任何 token 层优化替代，因为它修的是另一个轴。**

## 发芽 02：写回循环——agent 把自己的错误变成自己的事实

### 种子

现代生产 agent 不只查询——它们写回知识图谱、关系库、情景记忆，把客户偏好与运营状态存下来跨周使用。数据源的问题经由 agent 动作传播后「反喂循环」：agent 用更多错误信息把循环再喂一遍。

### 故事

这是只读时代不存在的的新失败形状。只读 RAG 里，源头错误的影响=检索窗口内的污染；写回架构里，agent 成了源头的一部分——它检索到过时数据→基于它做出动作→把动作结果（带着污染的推理痕迹）写进记忆→下次检索时，记忆里的错误被当作「已经验证过的事实」读出。STALE 基准的 55% 说明模型自我纠错能力不足以打破这个环：即便正确信息在窗口里，模型也倾向沿用旧版。没有自动失效机制的长期记忆，等于给这个环上了永动机。

### Aha 瞬间

**写回型 agent 的记忆库不是「档案馆」而是「生态系统」——错误在里面有代谢率；没有 TTL 与 superseded 标记的记忆库，会让第一代错误获得与真实事实相同的检索地位，并随时间被反复确证为「经验」。**

## 发芽 03：可见性盲区的两个数字——64% 与 52%

### 种子

2026 年对 260 名生产级 agent 从业者的调查：64% 说上下文与数据质量是最大的可见性盲区；52% 说他们通过客户或用户投诉才发现生产问题。

### 故事

两个数字合起来刻画了源头腐烂的检测困境：它是静默退化（不抛异常、不报错、指标可能照常），唯一可靠的暴露途径是终端用户的坏体验——而等到用户投诉时，损害已经走完「过时数据→检索→自信回答→用户受害」全链。对比窗口腐烂至少有 token 计数与延迟这类可观测信号，源头腐烂需要的是数据层的观测（表的新鲜度/体量/分布/健康度）——这正是数据可观测性市场与 LLM 可观测性市场的接缝。

### Aha 瞬间

**当 52% 的团队靠用户投诉发现生产问题，说明监控买在了错误的层——token 与延迟观测的是「管道」，数据观测看的是「水质」；源头腐烂的告警必须在客户撞上幻觉漂移之前触发，这意味着可观测性的边界要从推理层上移到喂给推理的数据层。**
