# 我在自家笔记本上对比了三个流行 Python 数据库：这是我发现的东西

> 原文：[I Compared Three Popular Python Data Libraries on My Own Laptop](https://medium.com/@nguyenletuan220508/i-measured-the-energy-use-of-pandas-polars-and-dask-on-my-laptop-here-is-what-i-found-8661f22901a7) — Tuan Nguyen

---

注：本文的方法与实验设置改编自论文《Energy Consumption of Dataframe Libraries for End-to-Deep Learning Pipelines: A Comparative Analysis》（Punit Kumar、Asif Imran、Tevfik Kosar，arXiv:2511.08644），修改为在我的个人笔记本上运行。

**TL;DR**：我好奇一篇已发表论文报告的 DataFrame 库能耗排名，在我的笔记本上是否成立。围绕三个包做了六个实验、两个数据集，共测 **420 次**。我跑的每个基准里，**Dask 在 CPU 计算上的能耗都高于其他任何包。论文里报告的 Polars 的巨大能耗优势，在我的结果里没有出现。**

## 一、为什么选择复现这篇论文

我学机器学习与深度学习好几年了，下了数据集之后常用 Pandas 做探索性分析。我一直默认 Pandas 是处理数据集最快最省的 Python 库。

读到那篇论文时，我发现：**C2 上 Pandas 的 CPU 能耗约为 Polars 的 2.3 倍（3,328 J 对 1,437 J）；C6 上论文报告 CPU 能耗差 Pandas 约 3.6 倍、Dask 约 12.7 倍，GPU 差距约 2.4 倍与 15.0 倍。**

于是我有了一个问题：

**「同样的排名，在 16 GB 内存、2026 版本库的个人笔记本上还成立吗？」**

## 二、在中等配置笔记本上检验论文主张

上图对比我的笔记本与论文的工作站。下载 Insurance 与 MovieLens-1M 数据集跑完看规模时，我发现 Insurance 有 1,338 行（论文报 1,000 行）；MovieLens-1M 我数到 1,000,209 条评分（论文描述为约一百万）。

我的实验局限：

- 没测 COCO 上的 ResNet 与 Mask R-CNN 负载——我的笔记本只有 4 GB VRAM 和 16 GB RAM，跑不了可比的配置。
- 没测 DRAM 能耗——笔记本不暴露 DRAM 能耗计数器。我测的是 CPU package 能耗，所以我的焦耳值不应与论文的 CPU 测量直接对比。

## 三、方法论

论文没给模型超参和它的 CF/NCF 实现，所以我在测量之前先记录了自己的选择（协议见我 GitHub 仓库的 PROTOCOL.md §4）。

**跑之前**：先定义主张、假设与判定标准——这样拿到不理想的结果时，我不会事后改假设。CPU package 能耗用 Linux 的 perf stat 测；第二轮里 NVML 每 100 ms 采样 GPU 板功率，积分后减去 GPU 空闲基线。为估计仅属于目标任务的能耗，需要净 CPU package 能耗：测量脚本从 5 个独立的 30 秒空闲区间估计空闲功率，从实测 package 能耗中减去该基线得到净能耗：

净能耗(J) = 实测 package 能耗(J) − 空闲功率(W) × 运行时长(s)

**正式跑**：剔除 1 次预热、每配置记录 10 次实测。10 月 25 日 12 个配置收 120 次实测，11 月 16 日 30 个配置收 300 次成功实测。为限制背景干扰，每次用全新的 Python 进程、40 秒停顿；seed 42 控制运行顺序与 train/test 切分。

**跑之后**：每个配置用 10 次实测的中位数能耗与运行时长汇总，配 95% 置信区间；记录峰值进程内存，检查能耗波动与数据校验和满足协议要求。

## 四、搭建中遇到的四个问题

1. 机器不允许普通用户用 CPU 能耗计数器——用 `sudo perf stat` 测。
2. MovieLens 下载的 TLS 校验失败——curl 验不了 GroupLens 服务器证书；下载问题解决后用哈希校验了文件。
3. 10 月 19 日装 nvidia-driver-615（用户态库 615.71），内核还跑着 610.57.04 模块——nvidia-smi 报「Driver/library version mismatch」，它不会自动更新驱动。重启加载新内核模块后解决。
4. GPU 空闲测试需要更长的负载间隔——原来只停 3 秒，GPU 功率还高着、测试一直失败。改成 40 秒停顿解决。

## 五、结果

**发现 1：Dask 在全部六项主张里的 CPU package 能耗都最高。**

清清楚楚，六项全它最高。比如 C1，Dask 比 Pandas 高 55.7%——论文里这个差距只有 14.1%。

（图上的标签描述的是：按我在测量前设定的标准，我的结果与论文匹配的程度。）

**发现 2：Polars 的大幅能耗优势没有在 C2 或 C5 重现。**

在我的笔记本上，C2 的 Pandas 用了 **76.24 J、Polars 76.63 J**——置信区间重叠；论文报告的差距是约 2.3 倍。

C5 上，论文报告 TabNet CPU 能耗为 Polars < Dask < Pandas。我的笔记本上是 **Pandas < Polars < Dask**，95% bootstrap 区间不重叠。**两对成对关系方向反了，所以按我预定的标准 C5 不算重现。**

**发现 3：论文里 NCF GPU 能耗的差距大得多。**

论文最大的差距在 NCF GPU 能耗。我的笔记本上 Dask 的 GPU 中位数最高，**但三个 95% bootstrap 区间全部重叠——我没有发现清晰的 GPU 差异。**每个 DataFrame 库都在独立的运行里为同一个 NCF 实现准备数据。

CPU 上 Dask 明确比 Pandas 和 Polars 费电：Pandas（740.19 J）与 Polars（737.52 J）区间重叠，Dask（866.21 J）约为 Pandas 的 1.17 倍。论文的差距大得多。C6 CPU 算部分重现。

## 六、讨论：为什么我的数字与论文不同

可能的原因有几个：

1. **硬件差异**：我测的是笔记本 CPU package 能耗减空闲基线，论文求和的是工作站 CPU 核与 DRAM 能耗。
2. **库版本不同：我用的更新。**我用 Python 3.12 与较新的库；论文用 Python 3.8 与旧版本。作为对照，我在同一台笔记本上用旧的 Python 3.8 软件栈重跑了 Insurance+Random Forest：三个库的净 CPU package 能耗都比我当前栈低、95% 区间不重叠。但 Python 与多个依赖是一起变的，我无法把差异归因到任何单一版本。
3. **模型配置差异**：论文没给全部超参与 CF/NCF 实现细节，我记录了自己的选择。这些选择可能贡献了不同的能耗差距，但本实验无法分离其影响。

## 七、关键收获

跑完这个实验，我得到了几条实践教训：

1. **尽早健全性检查测量工具**：我用 sleep 测试与 2 倍循环测试验证 CPU 测量、检查 GPU 空闲行为、在冒烟测试里对比数据形状/列顺序/校验和，并把试点运行与正式数据分开。
2. **预先定义「假设」与「成功」标准**：这能保证你在拿到不理想的结果之后，不会回头改原始假设。
3. **比较置信区间，不只是点估计**：区间重叠并不能证明两个结果相同——但点估计接近而区间不重叠，也不能证明相同。
4. **当模型训练占管线的能耗大头时，数据框库之间的差异会变小。**我的 NCF GPU 结果没有显示出清晰的库差异。

# 《I Compared Three Popular Python Data Libraries》的发芽报告

## 材料核心

一名学习者对已发表能耗论文（arXiv:2511.08644：DataFrame 库端到端 DL 管线能耗对比）的个人笔记本复现：420 runs（6 实验/3 库/2 数据集）/12→30 配置/每配置 10 次实测/预注册判定标准。原论文声称：C2 Pandas 2.3x Polars、C6 CPU 差距 Pandas 3.6x/Dask 12.7x、GPU 2.4x/15.0x。复现结果：①Dask 六项 CPU 能耗全部最高（C1 比 Pandas 高 55.7% vs 论文 14.1%）；②Polars 大优势未重现（C2 76.24 vs 76.63 J 区间重叠；C5 排序两对关系反向）；③NCF GPU 三区间全重叠无清晰差异、CPU 上 Dask 1.17x 部分重现。差异归因三候选：硬件（笔记本 package 减基线 vs 工作站核+DRAM）、库版本（3.12 新 vs 3.8 旧，回滚对照验证方向但无法归因单版本）、模型配置（论文未给超参）。四个 setup 坑：sudo perf stat、TLS 验证、驱动内核版本错配、GPU 空闲间隔 3s→40s。四条方法论教训：尽早健全性检查测量工具（sleep/2x 循环/校验和/试点分离）、预定义假设与成功标准、比置信区间不只比点估计、训练占能耗大头时库差异变小。

## 发芽 01：复现研究是被低估的学习路径——「在自己机器上验证排行榜」

### 种子

作者的动机朴素到可爱：「我好奇论文报告的能耗排名，在我的笔记本上是否成立」——然后用 420 次实测、预注册标准、置信区间回答了这个问题，并诚实地报告「Polars 的优势没重现」。

### 故事

这篇的价值一半在结论一半在示范：它没有因为「我是学生/我的设备低端」而退回到引述论文结论，而是把论文的方法改编到自己的约束下（4GB VRAM 跑不了 ResNet 就明确排除并声明、没有 DRAM 计数器就换 CPU package 并声明不可直接对比）。最终得到的结论也比原论文更有分层价值：Dask CPU 高能耗是跨设备稳健的（六项全中），而 Polars 优势是设备/版本敏感的（未重现）——**「哪个库更省电」没有全局答案，只有「在什么硬件、什么版本、什么负载下」的条件答案。**

### Aha 瞬间

**排行榜类论文的正确打开方式不是引用排名而是复现排名——把别人的方法改编到自己约束下跑一遍，你得到的不是「论文对还是错」，而是「结论的适用边界在哪里」；这个边界信息比排名本身更有工程价值。**

## 发芽 02：预注册与置信区间——个人实验的方法论平权

### 种子

「跑之前先定义主张、假设与判定标准——这样拿到不理想的结果时，我不会事后改假设」；「比较置信区间，不只是点估计」。配合：每配置 10 次实测、全新进程、40 秒停顿、seed 42 控制顺序、试点与正式分离。

### 故事

这些通常是临床试验与 A/B 测试的纪律，出现在一个个人的库能耗对比里。它们在这里解决了三个个人实验最常见的自欺：①测出不理想结果后悄悄换指标（预注册堵死）；②用单次运行的点估计下结论（中位数+95% bootstrap 区间）；③把「点估计接近」读成「无差异」（C2 的 76.24 vs 76.63 J 区间重叠是正确的「无差异」表述，而 GPU 三区间重叠则正确地表述为「未发现清晰差异」而非「无差异」）。四个 setup 坑（sudo perf stat、TLS、驱动错配、GPU 空闲间隔 3s→40s）则是测量本身的可靠性审计——任何一条不处理，420 次运行的数据都是噪声。

### Aha 瞬间

**个人实验的方法论平权已经成立——预注册、区间比较、健全性检查这些「大科学」纪律的成本如今只是一个下午的配置；而它们换来的，是你的结论从「我机器上的一个数」升级为「在明确条件下可辩护的发现」。**

## 发芽 03：「库差异消失」的条件——能耗瓶颈在哪里，优化就在哪里失效

### 种子

发现 3 的推论（作者列为核心教训第 4 条）：「当模型训练占管线的能耗大头时，数据框库之间的差异会变小。我的 NCF GPU 结果没有显示出清晰的库差异。」原论文 12.7x/15.0x 的巨大差距全部出现在 CPU 数据准备侧，而 GPU 训练侧的差距在复现中消失。

### 故事

这给出了一个工程选型的通用判据：**比较工具的能耗（或性能）差异，先看它们作用于管线的哪一段、那一段占总预算的比例。**DataFrame 库优化的是数据准备段；当端到端管线的能耗被 GPU 训练段主导时，准备段的 3.6 倍差异对总能耗的贡献被稀释到不可测（区间重叠）。反过来说：库选型的大收益场景是「数据准备重、模型轻」的管线（特征工程/ETL 密集），而不是「数据小、模型重」的训练任务。这与 11-15 vLLM 译文的分析同构——优化要找瓶颈段，瓶颈不在的地方，工具差异只是噪声。

### Aha 瞬间

**工具对比结论必须附带「管线位置」的标签——「Dask 比 Polars 费电 12.7 倍」这个数字只在数据准备是瓶颈的管线上有意义；任何「X 比 Y 快/省 Z 倍」的断言，都默认了一个它常常忘记声明的负载分布假设。**
