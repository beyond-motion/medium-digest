# LLM 推理引擎是怎么工作的

> 原文：[How an LLM Inference Engine Works](https://medium.com/@0xA1M/how-an-llm-inference-engine-works-df2b9a921d12)

---

## 从「像魔法一样」到「到底发生了什么」

LLM 这几年走了多远？从数不清 strawberry 里有几个 r，到能写代码、能推理复杂问题，甚至开始尝试攻克有 90 年历史的数学难题——OpenAI 近期声称在 Navier–Stokes 问题上取得进展，就是这件事走到有多离谱的好例子。

你输入：「像我五岁一样给我解释 Kubernetes。」几秒后，回复就来了。

看起来像魔法。可惜世界不魔法——底下发生的事情多到离谱。你的请求要被分词（tokenize）、变成数字、穿过一个含数十亿参数的神经网络、变成一串预测出来的 token、再解码回文本、流式传回给你。

而这只是模型本身。模型背后还有 GPU 算力、矩阵乘法、注意力、内存管理、缓存、批处理、调度、网络，以及一堆我大概漏掉的东西。再想想：这些要同时对成千上万甚至上百万个请求做。

一瞬间，「就是生成点文本而已」听起来一点也不简单了。本文要搞清楚的，就是从你按下回车到模型吐出回复之间，到底发生了什么。

## 推理到底是个啥？

「推理（inference）」这个词到处都在用，但它到底是什么？最简单的层面：推理就是用训练好的模型产生输出。

训练阶段，模型烧掉天文数字的算力，根据训练数据调整参数。推理阶段，我们停止教它——不再更新权重，没有反向传播，没有「这是正确答案，再试一次」。我们给它输入，要它产出输出。对 LLM 来说，这个输出是一个 token 序列。

于是引出一个重要问题：token 到底是个什么东西？

## 模型根本看不到你的词

拿我们这个（自封的）精心雕琢的提示词来说：「像五岁小孩一样给我解释 Kubernetes。」

你可能以为模型收到的是整句字符串。不是。文本先要过一遍 tokenizer，被切成 token。token 不一定是完整的词——取决于具体 tokenizer，它可能代表整个词、词的一部分、标点、空白或其他文本片段。我们的例句大概会变成：

```text
["Explain", " Kubernetes", " to", " me", " like", " I", "'m", " five", "."]
```

别把这个具体切法当成标准答案——不同模型用不同 tokenizer。重要的是接下来：这些 token 被转成 token ID：

```text
[8493, 24127, 311, 757, 1093, 358, 2846, 1937, 13]
```

现在我们终于说起模型的「语言」了——好吧，是数字。模型说的是数字。

每个 token ID 用来在模型的嵌入表（embedding table）里查一个向量，这个向量就是该 token 的初始数值表示。但模型还得知道每个 token 在序列中的位置——现代 Transformer 用旋转位置编码（RoPE）这类位置机制来区分「The dog chased the cat.」和「The cat chased the dog.」：token 完全相同，位置不同。

到此为止，可以把它扔进所有人都在谈的那个庞然大物了：Transformer。

## Transformer 负责「思考」……某种意义上

模型的神经网络计算大部分发生在 Transformer 里。我们不打算花 40 页从第一性原理重建一个，重点是推理时运行 Transformer 会发生什么。

token 表示穿过一摞 Transformer 层。每层执行若干操作：矩阵乘法、注意力、归一化、激活函数、残差连接，可能还有我忘了的其他东西。一层的输出是下一层的输入，循环往复。大模型可以有几十甚至上百层、数十亿学到的参数，其中大量昂贵工作是 GPU 极其擅长并行执行的数值运算——这就是 LLM 推理偏爱 GPU 的原因。

但这一大堆计算到底产出什么？不是句子，不是答案。Transformer 产生的是**当前序列的一种表示**。在模型接近末端的地方，这个表示被投影到模型的词表（vocabulary）上，产生一组候选 token 的分数——通常叫 logits。概念上像这样：

```text
Kubernetes  3.1
is          2.2
basically   1.7
a           0.8
...
```

这些还不是概率，只是分数。我们可以把 logits 变换成概率，再用解码策略选出下一个 token。而这就把我们带到整个流程里最诡异的部分。

## 一次只吐一个 token

多数人的心理模型在这里出错。你问「像五岁小孩一样解释 Kubernetes」，模型并不是想：「好，这是我完整的答案，发回去吧。」它是逐个预测下一个 token：解码步骤把 logits 变成概率，用贪心解码或采样之类的策略选出一个 token——比如「Kubernetes」。这个 token 加入序列，模型预测下一个：可能「is」，然后「a」，然后「system」……直到「Kubernetes is a system for...」，直到触发停止条件——可能是序列结束 token、最大 token 数限制，或者客户端取消了。

所以生成回复不是一次巨型预测，而是**一个循环**。如果你在想：「等等，每生成一个 token 都要把这个巨型模型整个跑一遍？」

是的，每生成一个 token 模型都要做一次前向传播。但这不意味着把所有东西从零重算——那就蠢透了。

## Prefill、Decode 与 KV cache

先做个重要区分：生成第一个 token 和生成后面一千个，不是同一种工作负载。

请求刚到达时，模型要处理已有的 prompt，这个阶段叫 **prefill**：模型处理 prompt 的 token，算出后续生成时要复用的 key/value 张量，存进 KV cache。然后进入 **decode**：基础自回归情形下，一次生成一个新 token。关键区别是不再从零重算整个序列的 key/value 投影——每个新 token 可以复用之前步骤算好的 K/V。

这就轮到现代 LLM 推理最重要的思想之一登场：**KV cache**。

想象我们在造全世界最蠢的推理引擎：收到 prompt，分词，跑模型，得到「Kubernetes」；把这个 token 追加到序列末尾，把**整个模型**再跑一遍，得到「is」；再追加，再把整个模型跑一遍……如此循环。技术上可行，但冗余计算巨大——之前的 token 模型明明已经处理过了，凭什么让它重做一遍？

KV cache 的原理：自注意力中每个 token 会被投影成 query、key、value 三份。自回归解码时，旧 token 的 key 和 value 不需要每次重算——那就别扔，缓存起来。decode 一步的概略图景：

```text
Previous tokens
 │
 ↓
 KV cache ──────────┐
 │
New token ↓
 │ Attention
 ├──→ Q │
 └──→ K,V ──────────┘
```

下一步，模型计算新 token 自己的 Q/K/V，同时复用旧 token 的 K/V。模型每步仍在运行、仍要对之前的上下文做注意力，但巨量冗余工作被砍掉了——我们的推理引擎突然不那么脑残了。

不幸的是，我们顺手制造了另一个问题：内存。

### 顺带说两句推理延迟

这也给了我们两个谈推理性能的实用指标。**TTFT（Time To First Token，首 token 时间）**：从发出请求到收到第一个生成 token 要多久，主要受请求排队和 prefill 影响。**TPOT（Time Per Output Token，单 token 耗时）**：decode 阶段大约每个后续 token 要生成多久。粗略地画：

```text
Request
 │
 ├──→ TTFT ──→ First token
 │
 └──→ TPOT ──→ Token → Token → Token → ...
```

一个系统可以 TTFT 很低但 TPOT 慢，也可以反过来。一旦开始给推理系统做基准测试和优化，这两个指标就变得相当重要。

## GPU 的内存不是无底洞

KV cache 听起来很美：不再重算旧 token 的 K/V，留着就行。问题解决了？——except 现在你得留它们。而 GPU 内存从来不是以慷慨出名的。

别忘了，VRAM 本来就要放模型本身。一个 700 亿参数的模型按 16 位精度存储大约是：700 亿参数 × 2 字节 ≈ **140 GB**。这只是权重。没有 KV cache，没有临时 buffer，没有任何运行时分配。真实推理系统里，这些东西必须挤进同一池有限的 GPU 内存：

```text
GPU VRAM
├── Model weights
├── KV cache
├── Temporary tensors / activations
├── CUDA/runtime allocations
└── Other buffers
```

而且 KV cache 随序列变长而增长。现在想象不止一个请求，而是几百个——每个都有自己的序列状态和 KV cache 分配，每条序列长度还各不相同。

于是问题不再是「这块 GPU 能不能跑这个模型」，而变成「**内存耗尽之前，这块 GPU 上能同时保活多少请求？**」这是完全不同的问题。一个模型完全可以妥妥塞进 VRAM、而推理服务器照样烂得不行——因为剩不下足够内存去服务有用的并发量。内存管理一夜之间成了推理性能的一部分。

而这还没聊到多用户呢。

## 我们服务的可不是一个人

到现在为止我们都假装只有一个孤独的用户在跟模型说话——这是个相当不现实的推理服务器。现实中请求源源不断地到达。GPU 并不特别在乎这些请求来自 5 个人、30 个人还是 100 亿个人——在它眼里全是要相乘的张量。

那为什么不把几个请求一起处理？这就是**批处理（batching）**的基本思想：不是独立发射一堆小任务，而是把请求合并成更大的张量操作，给 GPU 更多可并行的活。GPU 一般都喜欢活多。

但有个坑：**LLM 请求是糟糕的批处理公民**。一个请求可能生成 10 个 token，另一个 500 个，有的立刻完成，有的等所有人都下班了还在生成。那一个请求完成了怎么办？干等整批跑完？那是对 GPU 相当愚蠢的使用方式。

于是**连续批处理（continuous batching）**登场。传统批处理把请求锁进固定批次，但 LLM 生成不配合：请求完成时间各异，固定批里总有先跑完的——批里出现空座。留着空座等整批结束？又蠢。

现代推理引擎的做法是持续更换正在处理的序列集：把生成看成一连串迭代，每次迭代由引擎决定哪些序列推进、提交对应工作给模型。序列完成，新序列顶上。批不再是固定的请求组，而是一个**不断变化、被引擎高效调度的序列集合**。

然后新的问题来了：谁决定哪些请求能用上 GPU？……总得有人决定。

## 调度器：推理引擎越长越像操作系统

请求不断到达。有的在等，有的正在解码，有的需要更多内存，有的已经等了很久；有的完成，有的被取消，有的带着超长上下文。而 GPU 的算力和内存都有限。总得有个东西协调这一切——**调度器（scheduler）**。

简化的请求生命周期：

```text
Incoming requests
 │
 ↓
Waiting queue
 │
 ↓
 Scheduler
 │
 ↓
Running sequences
 │
 ↓
 Model execution
 │
 ↓
 GPU
 │
 ├──→ more decoding
 │
 └──→ finished
```

调度器决定每次迭代处理什么工作、可用资源怎么用：哪些等待中的序列开跑、哪些运行中的继续、一次处理多少 token、新请求能否被接纳、KV cache 内存够不够、哪些请求优先。而且调度器不单干——它需要知道还剩多少内存、哪些序列在跑、哪些请求完成了、GPU 大概吃得下多少活。

到这一步，我们已经从「跑一个神经网络」走到了「**在昂贵硬件上管理一堆互相竞争的工作负载的同时，跑一个神经网络**」——后者才更接近推理引擎的真面目。

## 这堆 KV cache 到底往哪放？

知道 KV cache 吃内存了，但还有个烦人的问题：这块内存实际怎么管理？

简单设计：给每个请求划一块连续内存放它的 KV cache。看着挺合理——except 序列是动态增长的：这个请求可能生成 20 个 token，那个 2000 个，还有一个 20000 个。请求开始时你未必知道最终长度。那预先留一大块？浪费内存。随序列增长再扩？引入新的麻烦。还有**碎片化**：把 GPU 内存想成一排停车位，请求来了占位、完成离开、新请求再来，最后剩下一堆东一块西一块的空位——空闲总量够再停一辆，但不是一整块连续的。往 GPU 里挤几百条序列时，小块浪费会累积成大问题。

所以现代推理系统需要远比「每人发一大块连续内存」精细的 KV cache 管理。其中最有影响力的方案之一是 vLLM 提出的 **PagedAttention**：不要求一条序列的 KV cache 占据一整块连续区域，而是把缓存切成固定大小的块（block）：

```text
Sequence A:  [Block 4] [Block 19] [Block 7] [Block 31]
Sequence B:  [Block 2] [Block 8] [Block 15]
```

这些块在 KV cache 内存池里不必相邻。引擎记录哪些块属于哪条序列、实际住在哪里；序列需要更多空间就再分配块；序列结束，块归还池子复用。比不断扩张巨型连续分配优雅得多。当然，真实实现比这张示意图复杂得多。

但关键的领悟是：**KV cache 不是扔进 VRAM 就完事的某个张量。规模化之后，它是一个需要被高效分配、追踪、复用和释放的资源。**这跟「把模型加载进 VRAM 然后调 forward()」完全是两个问题。

## 一个请求的完整旅程

把推理引擎内部有趣的零件看得差不多了，还缺一块：一个真实请求是怎么流经整个系统的？一个简化的推理服务器：

```text
Client
 │
 ↓
HTTP / API server
 │
 ↓
Request handling
 │
 ↓
Tokenizer
 │
 ↓
Scheduler
 │
 ├──── waiting requests
 │
 └──── running sequences
 │
 ↓
 Model executor
 │
 ↓
 GPU
 │
 ↓
 Generated tokens
 │
 ↓
 Detokenizer
 │
 ↓
 Stream response
 │
 ↓
 Client
```

细节肯定还缺很多：请求校验、鉴权、流式协议、取消、超时、错误处理、多 worker、网络……但形状是有了。重点在于：**推理引擎不只是那个神经网络——它是围在神经网络周围、让我们能高效执行模型并服务真实请求的那一整套机器。**而一旦开始服务很多用户，连这都不够了，你还得考虑推理引擎周围的基础设施。

## 不再只是模型的事

如果你来自 AI 应用侧，很容易把 LLM 想成 prompt → 模型 → 响应。拉到足够高的层面看，没错。可一旦你在乎性能、成本、延迟和多用户服务，这层抽象就开始崩塌。你开始关心一连串问题：prompt 处理多快？每个 token 生成多快？能并发跑多少请求？GPU 用得高效吗？显存耗尽怎么办？KV cache 怎么高效管理？一个模型怎么摊到多张 GPU？流量尖峰时怎么稳住延迟？负载天差地别的请求怎么调度？请求怎么在 worker 之间路由？系统怎么水平扩展？结果怎么流回客户端？生成到一半怎么取消？整个系统怎么观测和调试？

到这一步，你做的已经不是机器学习了——**你做的是围绕机器学习的系统工程**。LLM 基础设施从这里开始成为一个独立的问题域。

## 接下来造什么？

我们在推理引擎内部转了一大圈，但说实话：我们并不需要从零造一个。已经有一批非常能干的推理引擎在替我们干 GPU 上执行模型的脏活，比如 vLLM、llama.cpp、sglang。

有趣的问题是：**把推理引擎当成一个更大系统里的普通组件，会发生什么？**因为在一块 GPU 上服务一个模型是一个问题；把同一个模型高效地服务成百上千用户，是完全不同的另一个。你得开始想：推理怎么摊到多卡？一块 GPU 不够怎么办？KV cache 怎么管到本地 GPU 之外？怎么复用缓存的上下文而不是重算？请求怎么路由？负载怎么跨实例调度？流量尖峰怎么办？怎么水平扩展？整条链路怎么观测调试？以及最终——怎么让这一切跨多台机器跑起来？

到那时，你就不只是在运行一个 LLM 了，你在构建 LLM 周围的基础设施——事情从这里开始真正有意思起来。

下一系列，我们会拿一个现成的推理引擎，开始搭建它周围的系统。从小处起步：一个模型，一张 GPU，一个推理服务器。然后逐一引入突破这个简单配置后出现的问题：更聪明的 KV cache 管理、分布式推理、请求路由、调度、多节点执行。不只是学会怎么跑一个 LLM，而是学会构建让别人也能可靠、高效、规模化地跑 LLM 的基础设施。

那，就是我们要造的东西。

# 《How an LLM Inference Engine Works》的发芽报告

## 材料核心

这篇文章把 LLM 推理从「输入 prompt、等输出」的黑盒拆开：模型逐 token 循环生成，prefill 与 decode 是两种工作负载，KV cache 用内存换掉巨量重复计算，连续批处理与调度器让一块 GPU 同时服务成百上千请求，PagedAttention 借操作系统分页思想管理缓存内存。全文的落点是：推理引擎不是神经网络本身，而是围绕神经网络的一整套系统工程——调度、内存、批处理、路由，像一台专门为张量设计的操作系统。

## 发芽 01：KV cache 是一笔「空间换时间」的交易，而账单在显存上

### 种子

不缓存旧 token 的 K/V，每生成一个字都要把之前所有 token 重算一遍——KV cache 砍掉了这笔冗余，但砍下来的计算变成了必须常驻显存的数据。

### 故事

文章里的账算得很直白：70B 参数模型按 16 位精度仅权重就约 140 GB，这还没算 KV cache、临时张量和运行时开销。于是问题从「这块卡能不能跑这个模型」悄悄换成了「内存耗尽前能同时保活多少请求」——一个模型可以稳稳塞进显存，推理服务器却因为剩不下内存而服务不了几个并发。

### Aha 瞬间

「能跑模型」和「能做服务」是两个问题。衡量一个推理系统的，不是模型装没装得下，而是同样一池显存里能挤进多少条活着的序列——容量规划的本质是内存管理，不是模型加载。

## 发芽 02：推理引擎正在重新发明操作系统

### 种子

请求要排队、资源要分配、进程要调度、内存要分页——这些操作系统课的关键词，全都出现在了 LLM 推理引擎里。

### 故事

文章后半段的展开几乎就是一部操作系统简史：调度器决定谁上 GPU、连续批处理让「批」变成动态集合、PagedAttention 把 KV cache 切成固定大小的块按需分配、序列结束块回收复用。vLLM 的 PagedAttention 直接借用了虚拟内存分页的思路来解决碎片化——三十年前为物理内存发明的技术，今天被搬去管显存里的张量。

### Aha 瞬间

LLM 服务化没有发明新问题，只是把老问题搬到了新硬件上：LLM 请求是「糟糕的批处理公民」（长短不一、完成时间各异），逼着引擎长出操作系统级别的调度与内存管理。懂系统的人在这里比懂模型的人更有优势。

## 发芽 03：延迟不是一个数字，是两个可以各自优化的量

### 种子

TTFT（首 token 时间）和 TPOT（每 token 耗时）把「这个模型快不快」拆成了两个独立指标：前者由排队和 prefill 决定，后者由 decode 决定。

### 故事

文章指出一个系统完全可以 TTFT 很低但 TPOT 慢，或者反过来。原因藏在结构里：首 token 之前要过排队和整个 prompt 的 prefill，之后每个 token 只需带着 KV cache 走 decode——两个阶段干的事不同，瓶颈自然不同。

### Aha 瞬间

优化前先问用户感知的是哪种等待：聊天产品里「第一个字出现得快」决定体感 responsiveness，长文本输出里「出字速度」决定总时长——两者的优化手段（排队策略、prefill 算力 vs decode 批处理、KV 效率）几乎不相交。把延迟拆成两个量，才知道该拧哪个旋钮。
