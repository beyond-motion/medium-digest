# 代码很便宜。运营它要花什么？

> 原文：[Code Is Cheap. What Will It Cost to Operate?](https://medium.com/@wolffrichardj/code-is-cheap-what-will-it-cost-to-operate-e21f60f2b5da)

---

## 从一个品牌需求说起

一个产品需要为不同客户呈现不同品牌。为每个客户建一个独立应用当然能解决看得见的问题，但也意味着每次都要多养一个应用。我推回去了，因为需求是「品牌可变」，我们需要先弄清为什么这一点要用「复制整个应用」来满足。

我比较了路由这种差异的几种方式，做了一个带中性 fallback 的小型路由验证。利益相关者认可了方向，尽管其余链路和路由仍待评审。我们得到的不是生产就绪的应用，而是一条可以继续测试的路径。

这个决策在我后来的 AI 工作里变得越来越相关：生成和改造代码的成本已经跌落。**当产出下一份副本几乎不费力气时，人们很容易把这种期待带进后续的工作**——那份副本接入另一个团队的数据、系统和流程之后，我们实际同意运营的是什么？

生成代码能让一个想法迅速变成可用的演示，这本身是极有价值的用法，我自己也用。但生成的原型会让剩下的工作看起来像几个小尾巴：接上数据、给另一个团队开权限、加一个依赖、再部署一个实例。跑得快的时候，支持和总拥有成本就成了「以后再说」的事。而被推迟的这部分里，**连接组织本身就是我们在创建的系统的一部分**——即便代码本身花的时间很少，仍然要有人设计这些连接、维持它们工作、并理解它们变化时会发生什么。

## 下一份副本继承义务

我在客户部署里遇到过这种情况：给客户一个专用应用实例是合理的选择——它在客户环境周围画出清晰边界，给团队一个管理其需求的地方。考量在于：随着客户和环境增多，这个选择如何向前演化。

想想一个实例变成几个之后会发生什么。源代码也许完全相同，但**每一个安全更新仍然要抵达交付管线里所有受影响的实例**——生产、开发、测试和其他环境。当实例之间的配置和更新方式缺乏共享控制时，这会变得耗时又沉重。配置要在该一致的地方保持一致，同时有意的差异保持可见。得有人知道哪个版本在跑、哪些环境恢复成功、哪个客户不再需要他的副本。

持续集成与部署自动化能协调其中大部分——前提是我们定义了它们需要处理的差异，并且有可观测性来跨环境验证结果。有些团队会选 monorepo，但 monorepo 本身不会自动产出单一的发布和支持流程。那些运营路径仍然需要被设计并长期维护。

那如果客户量还不大、专用部署的开销是客户养不起的呢？共享的区域化设计也许是合理选项——但工作只是换了地方：要管理的独立环境少了，我们仍然要在共享系统里解决租户路由、容量均衡、数据隔离和区域恢复这些企业级问题。共享也有成本，所以只有当合并后的设计匹配预期需求时，共享才划算。

对这个取舍，我的起点是理解**每种设计让我们承诺维护什么**。专用部署也许值得付钱，某些共享基础设施也许值得建。要判断这笔交易，需要弄清哪些客户差异必须独立环境、哪些能在同一系统内支撑。某种意义上我们在看「水晶球」——权衡那些需求出现的概率与后果，选择成本与价值的更优平衡。我们应该说清这个选择背后的假设，以及什么信号会让我们重新审视它。

## 复用什么才可行

这就是为什么品牌案例从「客户差异住在哪里」开始：给它们在一个应用里一个明确定义的位置，我们就能在承担多应用成本之前先评估这种差异。

同样的推理适用于另一个团队想复用一个 AI 方案。一个能跑的 agent 可能依赖指令、工具、检索源、权限和审批流程。把它递出去之前，我想弄清这些依赖里哪些绑在原始环境上、哪些到了下一个团队那里必须变。

比如，复制来的 prompt 可能仍然产出看似合理的答案，同时依赖着一个已不再成立的假设。它的工具可能遇到不同的数据形状或访问边界，让下一个团队不断「追包」来让集成工作。每个依赖都解决一个问题，但也增加一件「在它变化时需要理解和维护」的东西。

**把这些差异命名出来，才谈得上决定复用该怎么做**：哪些可以走配置，哪些需要独立的集成或部署。初次改造也许很快，但还要考虑那些差异多大概率变化、由谁维护。一条有用的捷径，就是在这里变成长期承诺——为下一个任务付出的成本超过它省下的。

这不意味着每个实验都需要通用平台。有边界的原型正因为「让我们先学习再决定大投入」而有价值。随着使用扩大，我们才需要重审那些关于环境差异与工作量的假设。

## 一个请求可以藏起一份工作负载

就算部署与集成控制住了，工作负载还会以从界面上难以看见的方式增长。把一个 agent 复用于更大的任务，可能不改变用户请求的样子，却改变了它背后系统的负荷。

想象业务用户让 agent 通过 Model Context Protocol（MCP）暴露的工具更新记录。同步设计下，agent harness 可能并行发起大量工具调用并等待结果，这些工具直达底层业务系统。记录数增长时，用户体验到的仍是「一个请求」，而接收系统处理的是大得多的工作量。MCP 并不规定这种执行模型——重点是有两种管理方式需要对照。

这里我会问：**谁对打到接收系统上的工作负载负责**——包括一次能跑多少的上限，以及部分失败时发生什么。

验证与重试能帮工作可靠完成，但它们需要协调。当好几层各自独立重试，一次失败的动作制造的工作可能远超发起用户的预期。重放一个改状态的操作还有别的问题：如果系统认不出操作已完成，重试就是二次写入。request ID 帮助追踪；防止重复写入则需要接收系统能识别重复操作，或者超时导致完成状态不明时，有一个持久的对账流程。

对更大的工作负载，agent 可以提交一个批量任务、拿到 job ID，由队列和工作池管理执行、重试与进度。这把工作挪出了交互，但也引入容量规划、监控、以及处理无法完成的任务的方法。如果量还小或不确定，更简单的控制也许够用——约定好一个点，增长或失败行为到了那里就重新考虑设计。

无论选哪条路，**都得有人拥有执行策略**，并与接收系统的团队就并发与重试上限达成一致。装好这些控制会引出下一个问题：一旦别人开始依赖结果，谁来支持它？

## 谁来支持共享的结果？

分享一个 agent 或技能，开始时只是递过去一条有用的捷径。一旦另一个团队把它织进自己的工作，他们就开始依赖它的行为和它使用的系统。支持预期必须显式化：它可以用谁的数据、哪些决策需要人工复核、一次失败的运行谁处理、当假设变化时谁能把它下线？

这些责任被留给「以后」时，未解决的会以调查、对账、支持或下线的形式到达——而且**可能落在与获得最初生产率收益不同的那个团队头上**。我把这种被推迟的责任叫**判断债（judgment debt）**：人们已经开始依赖这个结果，而我们还没确定谁拥有它、谁评审它。

加自动评审会有帮助，尽管第二个 agent 可能和第一个缺同一份业务上下文。我们仍然需要一个能判断「技术上有效的改动是否服务于本意」的人。我们也需要知道谁能接受或回滚工作、评审漏了怎么办。我想趁方案还容易改的时候把责任谈定——因为它们是运营成本的一部分。

## 给完成的结果定价

把运营与评审工作算进来之后，每次模型调用的成本只是更大比较中的一个输入。我想知道的是：**到达一个可接受的结果要花多少钱**——包括第一次没到达时所需的额外努力。

对这个工具调用场景，「完成」可以定义为：目标记录已更新、变更通过要求的检查、异常已浮出、操作者能看到结果。产出一份计划或发起调用不算满足定义。

定义立住之后，就可以在一个时间段内归账：模型与工具调用、检索、重试、计算、失败的尝试，加上花在评审、对账和支持上的人类时间。备选方案需要按同样的任务组合和同样的验收标准来算。共享成本需要一致的处理，把小时换算成钱需要显式的定价假设。

用「可归因成本 ÷ 满足标准的结果数」得到**每次被接受结果的成本**。同时仍要报告失败率与延迟；否则一个系统可以显得很经济——靠的是丢掉难做的活，或把结果交付得太晚而失去用处。

这把架构选择接回了我们想要的收益：一个更贵的组件如果削减了足够多的重复工作或评审，就是正当的；要求的质量守得住时，更便宜的组件就够。需求还是估计值时，实际用量给了我们修正判断的依据。

## 在下一个团队拿副本之前

我们不需要在尝试想法之前备好一切答案。但在下一个团队拿走副本、开始依赖它之前，我会把这四个问题带上桌：

1. **谁受益，谁支持？**把支持集成的团队算进来，而不只是用工具的人。
2. **下一个团队、下十个客户那里，什么会变？**在把第一次成功当作可复用的证据之前，先检查数据、权限、量和失败行为的差异。
3. **这份副本创造了什么责任？**说出它增加的发布、依赖、支持与退役工作。
4. **谁能改、能回滚、能停掉它？**让「决定」在事故强迫之前成为可能。

套回品牌案例，这些问题把我们带回路由与 fallback 行为；套回工具调用场景，它们把我们带向工作负载上限、调用与重试的追踪、可见的失败路径。无论哪种，下一步都应该反映我们已经确认了什么、还有什么待测。

我们仍可能选一份专用副本——也许带共享基础设施——或一个更有限的 prototype。要紧的是：我们把能获得的价值，与接下的运营责任，放在同一杆秤上称过。

代码生成让我们能试更多想法。在把下一个想法变成别人依赖的东西之前，我想知道：**让它持续工作，需要什么。**

# 《Code Is Cheap. What Will It Cost to Operate?》的发芽报告

## 材料核心

生成代码趋近零成本后，真正的成本转移到了运营：每一份副本都继承安全更新、配置一致性、支持与退役的义务；AI agent 的复用隐藏着 prompt 假设与工具依赖；MCP 工具调用可以在用户无感时放大数据系统的负载；而被推迟的支持责任是「判断债」——人们开始依赖结果时，没人拥有它。文章的解法是给完成的定价（每次被接受结果的成本）和四个上手前必问。

## 发芽 01：判断债——被推迟的责任会换一个债主上门

### 种子

支持责任被留给「以后」时，未解决的会以调查、对账、支持或下线的形式到达——而且可能落在与获得最初收益不同的那个团队头上。

### 故事

文章的机制很锋利：分享一个 agent 开始只是递捷径，另一个团队把它织进工作后就开始依赖它的行为；此时「谁的 数据能用、哪些决策要人审、失败谁处理、假设变了谁能下线」如果没谈定，成本就以事故的形式到期。作者命名为判断债（judgment debt）——人们依赖结果，而所有权与评审权悬空。

### Aha 瞬间

这与技术债同构但更隐蔽：技术债记在代码里，判断债记在组织关系里——它偿还的货币是「谁该背锅」的争吵。趁方案还容易改的时候谈定四个 W（谁受益谁支持、什么会变、创造什么责任、谁能停掉它），是把债的利息锁死在最低点的唯一窗口。

## 发芽 02：用户看见一个请求，系统承受一份工作负载

### 种子

记录数增长时，用户体验到的仍是「一个请求」，而接收系统处理的是大得多的工作量——MCP 并行工具调用把放大的负荷藏在了界面之下。

### 故事

文章给出两种管理方式的对照：同步设计里 agent harness 并行发起大量工具调用等结果；批量设计里提交一个 job、由队列与工作池管理执行重试。前者需要有人对并发与重试上限负责、防重复写入（request ID + 幂等或对账），后者引入容量规划与监控。「多层级独立重试」是放大器：一次失败的动作能制造远超预期的混乱。

### Aha 瞬间

AI 系统的负载设计要回答「接口之下的放大系数」：用户意图的粒度和系统执行的粒度可以差几个数量级。任何把 agent 接到有状态系统上的集成，都需要显式的执行策略拥有者、并发上限协议和失败语义——否则用户体验的「一个请求」就是系统账单上的「一百次操作」。

## 发芽 03：给完成的定价，而不是给调用的定价

### 种子

每次模型调用的成本只是输入之一——真正要算的是「到达一个可接受的结果要花多少钱」，包括第一次没到达时的全部努力。

### 故事

文章的验收定义值得抄：「完成 = 目标记录已更新 + 通过要求的检查 + 异常已浮出 + 操作者能看到结果」——产出计划或发起调用不算。在这个定义下归账：调用、检索、重试、计算、失败尝试，加上评审对账支持的人类时间；同时必须并列报告失败率与延迟，否则系统可以靠丢掉难活显得经济。

### Aha 瞬间

「每次被接受结果的成本」把 AI 的成本核算从投入侧翻到了产出侧，与昨天常见的「每次调用 X 美分」形成对照：便宜的调用配上三次重试和人工对账，可能比昂贵的单次成功更贵。成本表必须和失败率、延迟印在同一页上——只印一页的 ROI 都是广告。
