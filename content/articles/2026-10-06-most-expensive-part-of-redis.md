# 没人提醒过后端工程师：Redis 最贵的部分不是内存

> 原文：[Nobody Warns Backend Engineers About the Most Expensive Part of Redis. It Isn't Memory.](https://medium.com/engineering-playbook/nobody-warns-backend-engineers-about-the-most-expensive-part-of-redis-it-isnt-memory-33747d030a79)

---

*Redis 让我们的系统几乎立刻变快了。它也给了我们第二份需要维护的「现实」。*

第一次在一个慢后端前面加上 Redis，效果近乎不讲理：一条 180 毫秒的数据库查询变成个位数毫秒的缓存查找，PostgreSQL 的负载应声下降，那个被所有人抱怨的端点忽然又健康了。

这种体验让 Redis 非常容易爱上。

账单晚一点才到——而我说的通常不是内存那张。

贵的部分，从应用必须回答一个难受得多的问题开始：**此时此刻，我该相信哪一份数据？**

## 第一版美好而简单

设想一个返回商品信息的端点：每分钟被请求数千次，但数据很少变。每次都读 PostgreSQL 显得浪费，于是我们把结果在 Redis 里缓存十分钟。

读路径变得很直白：先查 Redis，命中就返回；没命中就查 PostgreSQL 并回填缓存。

性能立刻改善。

然后有人更新了商品。

现在我们有几个选择：更新时顺手删掉缓存键；PostgreSQL 成功后再更新 Redis；缩短 TTL、容忍过期数据；或者引入某种事件驱动的失效机制。

**每一种都能工作。每一种也都为系统制造了一条新的出错路径。**

假设 PostgreSQL 提交成功、而删除 Redis 键失败了——数据库里是新值，用户读到的还是旧值。假设我们先更新 Redis、而数据库事务随后失败——同样的问题换了个方向。

原来的性能问题很容易测量。我们引入的一致性问题，可能难发现得多。

## 然后 Redis 挂了

真正改变我缓存观的是这个场景。

一种常见设计说：Redis 不可用时，应用直接回落数据库。听起来很有韧性——Redis 只是优化，PostgreSQL 才是真相源。

这个假设完全合理，直到你算一算 Redis 到底在替 PostgreSQL 挡住什么。

想象一个端点：每秒 8000 次请求，缓存命中率 95%。PostgreSQL 平时只承接其中大约 400 次读。

Redis 消失了。

应用骄傲地执行它的回退逻辑，PostgreSQL 迎来的是接近 8000。

**你的优雅降级路径，刚刚把数据库流量放大约二十倍。**

Redis 不需要损坏任何数据、不需要任何错误行为。它只需要不可用得足够久，久到它提供的保护消失。

## 缓存未命中可以表现得像流量倍增器

同一问题还有个不需要 Redis 彻底故障的版本。

一个热门键过期了。在第一个请求完成重建缓存值之前，几百个请求已经涌到。每一个都看到 miss，每一个都去执行那条你当初引入 Redis 就是为了避免的昂贵数据库操作。

缓存最终会被填回来，事故可能只持续一小会儿。

PostgreSQL 依然承受了一次突发的劳动高峰。

这就是 request coalescing（请求合并）、分布式锁、stale-while-revalidate、TTL 抖动这些技术开始变得相关的地方。具体选哪个取决于负载，但重要的是理解问题为什么存在：**缓存改变了数据库所看到的流量形状。这是架构后果，不只是性能优化。**

## Redis 很简单，直到它变得重要

我至今在用 Redis，也仍然认为它是后端工程师手里最有用的工具之一。错误在于把它当作一层免费的速度，插在数据库前面而不改变系统本身。

一旦你的数据库容量是按 95% 命中率规划的，Redis 在任何运维意义上都不再是「可选项」。

一旦业务正确性依赖缓存失效发生在正确的时刻，缓存就已经是你一致性模型的一部分。

一旦鉴权、会话、限流、分布式锁或幂等键住进了里面，一次故障的含义就不再是「请求会稍微慢一点」。

**架构已经悄悄依赖上了 Redis——哪怕最初的架构图上，它还标注为 cache。**

## 我现在加缓存前只问一个问题

我想知道：**缓存为空的时候，这个系统长什么样？**

这个问题会逼着我们去计算数据库容量、理解 miss 路径、思考键同时过期的场景、决定能容忍多少过期数据，以及判断 Redis 不可用时应用是否真的应该无限制地回退。

有时候，答案仍然让 Redis 成为显而易见的选择。

区别在于，我们清楚自己买的是什么。

Redis 能省掉海量的数据库工作、大幅改善延迟。危险的部分在于，让这份成功遮住一件事：系统的其余部分，已经多么依赖「缓存永远按预期运转」。

**这份依赖，通常比内存贵。**

# 《Nobody Warns Backend Engineers About the Most Expensive Part of Redis. It Isn't Memory.》的发芽报告

## 材料核心

这篇材料把缓存从「性能优化」重新归类为「架构决策」。作者用三段递进的实测教训展开：引入 Redis 后真正的成本从应用必须回答「此刻该相信哪一份数据」开始——更新数据库与删缓存的顺序、TTL 与事件失效，每种组合都能工作也都新增一条出错路径；当 Redis 不可用、应用按设计回落数据库时，8000 QPS、95% 命中率的系统会让只承接 400 QPS 读的 PostgreSQL 瞬间接住近 8000——优雅降级路径成了二十倍流量放大器；热键过期造成的缓存击穿是同一问题的常态版。结论落在一个提问习惯上：加缓存之前，先回答「缓存为空时系统长什么样」——容量、miss 路径、同时过期、可容忍的陈旧度、无限制回退是否合理。缓存改变的不是延迟数字，是数据库看到的流量形状。

## 发芽 01：优化层的失效模式，是被优化层的容量规划

### 种子

材料里最锋利的数字对比：95% 命中率让 PostgreSQL 平时只承接近 400 QPS 中的 400 次——数据库的容量规划从此建立在「缓存永远在场」的前提上。Redis 挂掉时不需要做错任何事，「只需不可用得足够久」。

### 故事

所谓「优雅降级」在这个前提下反转成攻击路径：回退逻辑本身完全正确，每一步都符合「Redis 是优化、数据库是真相源」的教科书假设——组合起来却是二十倍的瞬时流量。缓存没有制造新故障，它只是让系统把原有的余量花掉了。

### Aha 瞬间

每引入一个优化层，就要重算一次被优化层在「优化层缺席」时的容量——性能数字是成对出现的：缓存命中时的延迟，和缓存失效瞬间的数据库负载，是同一个设计的两面。

## 发芽 02：一致性问题难测量，恰恰因为它不出现在监控里

### 种子

材料的对照：原来的性能问题容易测量（180 毫秒变个位数，人人看得见），引入的一致性问题难察觉——数据库新值与用户读到的旧值并存，没有任何请求报错。

### 故事

四种失效策略（更新时删键、库成后再更缓存、缩短 TTL、事件驱动失效）每一种都能工作、每一种都新增一条出错路径：先更库后删键可能删失败，先更缓存可能库回滚。这些事故的共同点是静默——数据不一致不会抛异常，只会被某个用户在某个时刻发现。

### Aha 瞬间

判断一项优化的真实成本，别只看它改善的指标能不能测量，要看它引入的故障能不能被发现——最贵的失败模式是那种「不报错、只是慢慢变得不真实」的失败。

## 发芽 03：「它还标注为 cache」——架构图与现实的时差

### 种子

材料的三连句是全文的重锤：容量按命中率规划后它不再是可选项；正确性依赖失效时机后它成了一致性模型的一部分；鉴权、会话、限流、锁、幂等键住进去之后，故障的含义彻底改变——而架构图上它还写着 cache。

### 故事

作者的应对是一个提问习惯：「缓存为空的时候，这个系统长什么样？」这个问题强制展开五件事：容量、miss 路径、同时过期、陈旧度容忍、回退是否该有界。答案有时仍是「该上缓存」——但那是一个知情的决定，不是习惯性的加速动作。

### Aha 瞬间

系统对某组件的依赖，不取决于它在图上标注的角色，取决于「它消失时什么会塌」——定期把每个组件按「拿走它会怎样」重新问一遍，是架构图追上现实的最便宜方式。
