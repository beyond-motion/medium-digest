# 在你信任一个因果推断库之前，先检查它的证据

> 原文：[Before You Trust a Causal Inference Library, Check Its Evidence](https://medium.com/@charles.hinshaw/before-you-trust-a-causal-inference-library-check-its-evidence-b724d5f1eb01) — Charles Hinshaw

---

假设我们要选一个 Python 库来估计「某项治疗是否改善康复」。它的文档列出了我们需要的方法，它的示例返回了一个效应估计值。在把那个结果写进研究报告之前，我们想知道：**支撑这个软件计算的证据是什么？**

有几件事要查：这个实现处理我们这类研究吗？它与独立已知的答案一致吗？它依赖公开方法的哪些假设？如果它报告置信区间，什么证据支撑那个区间的统计行为？

[Antecedent](https://github.com/iridae-dev/antecedent) 是一个有 Python 和 Rust 接口的开源因果推断库。它在**声明的关于研究的假设下**估计干预的后果，并且为自身实现记录证据：每个方法支持哪些分析、数值检查、指向科学方法的链接、以及不确定性程序的测量。本文讲怎么读这些记录、各自能确立什么——先看一个库接受的小计算和一个它拒绝的相关请求，再看这些边界背后的检查。

## 支持属于特定的分析

一个方法名覆盖许多可能的请求：我们要的是平均处理效应，还是某个人在另一种处理下结局的预测？因果图是我们自己给的，还是从观测学出来的？每种组合都需要与之相配的实现和证据。

Antecedent 用**支持矩阵（support matrix）**列出这些组合：项目支持的分析配置及其引用证据的记录。一个被支持的组合叫 _licensed_——这里这个词指「有记录的科学与实现支持」，与项目的开源许可证无关。

矩阵区分三类：被支持的组合；与声明的问题或图类型不兼容的请求；以及**被拒绝的有意义请求**。缺支持时，拒绝是默认。例如：一个估计器的存在，并不能确立它能为「从同一批观测学出来的图」提供贝叶斯不确定性。

我们用反事实分析做小例子：在结构模型的条件下，估计同一单元在替代干预下的结局。第一个调用提供一个 DAG（有向无环图，箭头方向固定、无环）；第二个提供一个允许「处理与结局存在未观测共同原因」的混合图。观测数据由「处理效应为 2」的规则生成，比较处理水平 0 与 1：

```python
import numpy as np
import antecedent as ant

rng = np.random.default_rng(1)
treatment = rng.normal(size=200)
data = {
    "t": treatment,
    "y": 2 * treatment + rng.normal(size=200),
}
query = ant.Counterfactual("t", "y")

result = ant.analyze(
    data, graph=[("t", "y")], query=query,
    bootstrap=0, refute=False,
)
print("Mean individual contrast:", result.mean_ite)

latent_graph = ant.Admg.from_edges(
    ["t", "y"], [("t", "y")], bidirected=[("t", "y")]
)
try:
    ant.analyze(
        data, graph=latent_graph, query=query,
        bootstrap=0, refute=False,
    )
except ant.CausalError as error:
    print(type(error).__name__, error)
```

第一个计算在拟合的结构模型下返回接近 2 的平均对比。注意：仅有全定向的 DAG 并不能识别每个单元的反事实——拟合的方程与对未观测扰动的假设做了额外的工作。第二个调用**在拟合之前就被拒绝**：这个反事实分析要求一个全定向的静态 DAG。「反事实代码存在」并没有把同样的分析开放给允许隐藏混杂的图。

这个拒绝标出的是一个实现边界。它不证明所有含隐藏共同原因的反事实问题都不可能——Antecedent 的其他分析以不同的证据与假设处理特定的反事实识别与迁移问题。**能力声明必须点名实际执行过的那个分析。**

## Parity 记录实际检查了什么

下一个问题是数值计算是否与参考答案一致。Antecedent 把这类比较称为 **parity 检查**。要紧的是：两个程序返回同一个数字，可能因为都对、可能因为共享同一个错误、也可能因为其中一个在复现自己早期版本保存的结果。我们需要知道读到的是哪一种比较。

Antecedent 的 parity 记录区分比较的来源，而不是把它们统一塞进一个「已验证」标签。标签告诉我们一致性是怎么检查的；它们**不能排除共享错误**：

- **回归钉（regression pin）**：与保存的早期结果比较——它是变化检测器。
- **内部交叉检查**：两个 Antecedent 计算互相比较。
- **已知真值测试**：解析解、穷举枚举、或其他独立构造。
- **外部 oracle**：来自另一个项目指定版本的参考答案——这才算独立数值比较。

这些检查都可以用，前提是保持含义清楚。粒度同样要紧：独立检查过的估计器加独立检查过的识别器，是**组件证据**——不等于有人把完整分析（含路由、预处理、推断、报告）对照过独立的端到端答案。parity schema 要求证据标签与可核查的引用：对每个支持的组合，引用的测试必须真的执行「问题×图×推断×验证」的那个组合。**测试文件的存在，不能为它从未运行过的案例建立支持。**

## Provenance 把方法连到科学基础

追溯一个方法的出处时，论文引用是起点——但它很少说出实现里的每一个选择。一个实用估计器可能用了某个特定求解器、引入数值近似、只支持部分输入、或省略了公开保证所要求的某道程序。这些选择应该与方法名放在一起。

Antecedent 的 provenance 记录把方法连到源文献、实现路径、证据、假设与偏离。Schema 检查让记录可检查、强制必需的引用。但它们**不能确立每篇论文都被正确解读**——实质性的人读审查仍然必要。

这把审查切成了可管理的工作：可以自动化检查「记录存在、指向真实的实现位置、含必需字段」；但科学论证与实现是否配得上声明的范围，仍然需要人来评。这里记录的局限应当影响下游的支持与校准声明——**一条假设独立观测的定理，不能悄悄为把重复测量当独立单元的路线背书。**

## 校准跟随实现

一个不确定性程序是对统计行为的声明：例如 95% 置信区间程序，目标是在其假设下、重复采样中 95% 的区间包含真值。要测某个设定下的覆盖率，就反复生成已知答案的数据、数区间包含真值的频率。Antecedent 把这类性能评估记为 **calibration**。

测量是有限的：样本量、数据生成条件、名义水平、重复次数、Monte Carlo 误差都影响结果。**一个设定下的好表现，不确立普遍覆盖。**

Antecedent 记录测量条件以及每条校准记录依赖的代码组件。**Attestation（证明）检查这些组件自测量以来是否变化**。被允许的重放必须复现存储的结果，并满足一个显式验证过的豁免。这给维护者一个具体答案：旧测量还能不能支撑新代码。运行时通过 `result.calibration` 暴露这个区分——结果可能存在，而校准不可用或范围未评估。在为本文测试的例子中，就出现了「计算跑出了结果、但该执行不带当前覆盖声明」的情况。如果你在准备采购或审计报告，这两个发现都应记录在案。

## 自动化门把证据拴在代码上

项目用名为 **gates** 的自动化检查对这些记录强制要求。从 Antecedent 源码 checkout 的顶层目录（先按开发文档配置）可以运行：

```bash
python scripts/gate_support_matrix.py
python scripts/gate_parity_schema.py
python scripts/gate_provenance_schema.py
bash scripts/gate_calibration_attestation.sh
```

各有分工：矩阵检查审查支持声明与证据引用；parity 检查约束证据标签的含义与覆盖范围；provenance 检查验证必需记录与路径；校准 attestation 检查既有测量是否仍然「拴」在它们声称支撑的代码上。这些检查还参与 CI（自动测试提议的变更）与发布评审。校准模拟单独测量；attestation 门把记录对照当前实现——**相关代码漂移了，门就要求重新测量或经过验证的重放，这些记录才能继续支撑发布流程。**

同理，一个执行失败的测试应当阻塞依赖它的工作流：声明救不了破碎的实现；反过来，通过 schema 检查不代表所有数值测试都过了——**每个检查只确立论证中属于它的那一部分。**

## 声明保持条件性

普通软件检查在这里同样是必需的：内存安全、确定性恒等、有效序列化、正确的数值执行。科学软件还需要一层证据：把那些性质连接到用户看到的科学陈述上。

评估一个提议的分析时，可以沿着记录走：它的支持组合、引用的执行测试、源方法与实现偏离、以及当前的校准记录。这给出一条实用的审查路径，并让证据缺失更容易被发现。

这条工程路线有一个坚硬的边界：**软件无法从一条支持记录里判定「医院的处理分配真的无混杂」或「某项商业干预没有溢出效应」。这些前提仍然需要科学判断和关于世界的证据。**

第一次评估的具体做法：选你实际打算用的那个分析，沿它的支持条目走到引用的测试、方法参考与校准状态；记下这些检查确立了什么、什么仍是科学假设。当日后的库或依赖更新改变了相关实现，那份记录就是你要复查的具体对象。

# 《Before You Trust a Causal Inference Library, Check Its Evidence》的发芽报告

## 材料核心

以「选一个因果推断库用于研究报告」为场景，通过开源库 Antecedent 展示科学软件的证据体系应长什么样：支持矩阵（方法名×问题×图类型的组合逐项 licensed，缺支持默认拒绝——混合图反事实被拒就是实现边界的诚实标示）；parity 四级标签（回归钉/内部交叉/已知真值/外部 oracle——区分变化检测器与独立数值比较，且测试文件存在≠为其没跑过的案例背书）；provenance 记录（方法连文献/实现偏离/假设，schema 可查但论文解读仍需人审）；校准 + attestation（覆盖率测量绑定代码组件，代码漂移即要求重测）；自动化 gates 与 CI 把证据拴在代码上。硬边界：软件无法判定「处理分配真的无混杂」——那永远是科学判断。

## 发芽 01：「拒绝」是功能——把不支持做成显式边界

### 种子

大多数库的能力声明是「有什么」；Antecedent 的支持矩阵还声明「拒绝什么」：混合图（允许隐藏混杂）上的反事实分析在拟合之前就被拒绝，尽管反事实代码确实存在。

### 故事

拒绝不是因为反事实不可能——其他分析以不同证据处理特定识别问题——而是这个组合的科学与实现证据不存在。这把「静默给出不可信结果」变成了「显式报错+指向边界」。对使用者，能力声明的最小单元从「方法名」细化到「问题×图×推断×验证的具体组合」。

### Aha 瞬间

**成熟工具与玩具的分界线，常常不在支持了多少功能，而在拒绝得多诚实。**评估任何工具，先找它的「不支持清单」；没有拒绝机制的「全都能做」，才是最大的危险信号。

## 发芽 02：「两个程序答案一致」的三种解释——一致性证据的分级学

### 种子

parity 一致的数字有三种来历：都对、共享错误、自我复现（一个程序重现自己早期版本保存的结果）。Antecedent 用四级标签区分：回归钉（变化检测器）/内部交叉/已知真值/外部 oracle（唯一真独立）。

### 故事

这套分级戳破了最常见的偷懒论证：「我们跑过另一个库，结果一样」——如果不指明对方版本与实现独立性，它可能只是共享了同一个错误的实现思路，甚至只是都抄了同一篇论文的同一处近似。粒度也要紧：估计器和识别器各自独立验证过，不等于完整分析链（路由+预处理+推断+报告）对照过端到端答案。

### Aha 瞬间

**一致性本身不是证据，比较的「独立性等级」才是。**引用任何「与参考一致」的说辞时，先问三件事：参考从哪来、谁更独立、查的是组件还是全链路。

## 发芽 03：attestation——让证据有保质期机制的工程化

### 种子

校准记录（覆盖率测量）天然会过期：它绑定的是「测量当时的代码组件」。Antecedent 的 attestation 检查组件是否漂移，漂移即要求重测或显式验证的重放；运行时通过 `result.calibration` 让「区间存在」与「区间带着当前覆盖声明」成为两个可区分的状态。

### 故事

这解决了科学软件最隐蔽的腐烂方式：代码演进了、旧论文的测量还挂着、用户以为 95% 区间仍是 95%。procurement/审计场景的诚实写法是把两个发现都记下来——「计算执行了」+「该执行不带当前覆盖声明」。gates 与 CI 让这套纪律自动化：每个检查只确立论证的一部分，schema 通过不等于数值通过。

### Aha 瞬间

**证据不是资产，是负债——需要像代码一样做版本管理与变更检测。**「这个结论依据哪次测量、那次测量对应的代码还在吗」应当成为一切科学/审计类系统的标配问题。
