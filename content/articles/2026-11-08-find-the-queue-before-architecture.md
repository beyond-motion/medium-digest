# 应用性能：先找到队列，再谈改架构

> 原文：[Application Performance: Find the Queue Before You Change the Architecture](https://medium.com/@tanvin-ahmed-touhid/application-performance-find-the-queue-before-you-change-the-architecture-56989932764d) — Tanvin Ahmed
> ——延迟、吞吐、瓶颈与增长后端优化实用指南：从尾延迟到 CPU 成本

---

作为一个软件工程师，我喜欢模块化单体的开发速度与简洁。但当应用快速增长、大量用户在短期内涌入时会发生什么？

我的第一反应**不是**换架构。架构转型要时间。在迈那一步之前，我想先理解现有应用的行为：请求在哪里等待、哪些东西可以不改架构就优化。

我用来组织这些问题的框架：**定义性能 → 测量它 → 定位瓶颈 → 优化瓶颈处的工作。**

## 什么是应用性能？

应用性能描述应用运行得好不好——响应性、稳定性、可扩展性、资源利用率、用户体验。对后端，我把它定义得更具体：**给定负载、给定硬件下，系统多快、多响应？**

负载包括后端数据与请求量；硬件包括种类与容量。**固定负载与硬件，才有了比较服务器性能的基准。**没有那个上下文，「应用很快」不是一个特别有用的测量。

## 我怎么发现性能问题

在读仪表盘之前，先理解系统：内存管理、应用所在的操作系统、线程、网络及相关概念。然后把监控指标、用户反馈、主动检查与视觉指标放在一起看。

**监控指标**找这些信号：响应时间上升（页面变慢、输入处理延迟、无响应）；错误率升高（频繁崩溃、事务失败）；资源利用率变化（CPU 尖峰、极端内存占用、高网络带宽）；日志证据（错误、警告、性能相关事件）。

**用户反馈**：关于慢、迟滞、无响应的抱怨是有价值的证据；性能类支持工单上升强化调查必要。

**主动检查**：负载测试（模拟高流量看系统受压行为）；性能剖析（找哪些代码执行最久、耗多少资源）；基准对比（与既定基准或历史水平比较找回归）。

**视觉指标**：加载动画或进度条异常耗时；卡顿的界面——跳动的动画、无响应的输入、延迟的视觉更新。

记住：**性能问题常以指标组合的形式出现。**一次慢的页面加载未必警报；持续的延迟、资源尖峰、重复的用户投诉才值得调查。

## 每个性能问题都是某处正在排队的队列

这是我的笔记的中心思想：**当工作在系统某处等待，我要找到那个等待点。**

从四个区域开始：网络、数据库、操作系统、应用代码。

**1. 网络**：延迟上升（ping 变长、传下载变慢、超时频发）；丢包（重传请求与更长等待）；收发缓冲区满（网卡或 OS 的队列被填满，阻碍高效传输）。

**2. 数据库**：慢查询（长执行时间拖慢页面与用户动作）；连接池耗尽（连接全忙，新请求必须等）；磁盘 I/O 瓶颈（数据库读写的队列拖慢操作与响应）。

**3. 操作系统**：高 CPU 利用（进程占大头，其他任务分不到处理能力）；内存过度使用（换页到磁盘、处理变慢）；进程等待时间长（等 CPU/内存/I/O，延迟增加、吞吐下降）。

**4. 应用代码**：低效算法（计算昂贵）；冗余计算（重复同样的计算浪费工作）；死锁（线程互相等待，资源饥饿甚至级联问题）。

**我的队列检查清单**：

- 队列容量有限；超限制造积压与延迟。
- 找保持满载或快速增长旳队列。
- 把队列长度与 CPU、内存、网络利用率放在一起分析。
- 监控趋势与基线，检测对正常行为的偏离。

这个视角帮我早发现问题、诊断根因、选有针对性的修复而不是瞎猜。

## 队列积压的三个根因

**低效缓慢的处理。**负责任务的代码耗时过长——先查代码库里的低效实现；如果代码高效而外部依赖响应慢，调查那个服务、考虑替代。

**串行资源访问。**工作必须逐个访问资源：并发需求超过数据库承载时数据库访问排队（缓存可帮）；共享文件迫使线程排队等待串行访问；顺序应用逻辑——尤其一连串网络调用——也会拖慢请求。

**资源容量受限。**存储约束与资源不足限制系统承载的流量：内存太少逼换页；网络带宽有限制造传输队列、拖慢上传下载。

设计新系统时，我尽量避免意外队列；在现有系统里，我找它们正在哪里堆积。**这不意味着所有队列都不好**——消息代理与消息队列是故意排队的：跨服务器分发请求、均衡负载、让不重要的工作延后运行。

## 三条性能原则

**效率**：降低单个请求的响应时间——高效的资源利用（内存/网络/磁盘 I/O/CPU）、高效的逻辑（算法与查询）、高效的数据存储（数据结构与 schema）、缓存（避免重复工作或取同样的数据）。

**并发**：降低并发请求下的响应时间——需要合适的硬件与能利用它的软件（多核只在软件用得上时有用）；还有不阻塞请求的排队与一致性（保持并发设计逻辑一致）。

**容量**：加硬件改善——CPU 处理更多信息、内存让更多信息随取随用、磁盘存更多、网络撑更快。

## 系统性能目标：延迟与吞吐

两个核心目标：**最小化请求-响应延迟，最大化吞吐。**

延迟用时间单位测量，包含等待/空闲时间与处理时间。吞吐是请求处理的速率，取决于延迟与可用容量。它们相关但回答不同的问题：**一个请求要多久？系统一段时间能处理多少？**

## 我盯的四个测量指标

**延迟**：毫秒计，反映系统响应多快、直接影响用户体验。方向是更低。

**吞吐**：单位时间的请求数（RPS/RPM），反映请求处理能力。我希望系统的处理能力**超过**进入的请求速率——才能避免积压、在峰值下保持响应。

**错误率**：出错请求的百分比，反映可靠性、正确性、功能是否如期。目标是零错误。

**资源饱和度**：CPU、内存、网络有多忙的百分比。峰期高使用率正常；**应用本该空闲时的高使用率值得调查。**过饱和制造瓶颈、可能提示需要更多硬件。目标是高效利用：既不浪费资源、也没有过度利用造成的瓶颈。

## 尾延迟：平均值不够

尾延迟描述最慢的请求有多慢。不要只看平均响应时间——看百分位 P95、P99、P99.9。

想象 100 个用户请求一个 API：95 个在 100ms 内完成；4 个花 200ms；**1 个花 2 秒**。平均可能看起来可接受，而那个 2 秒请求暴露了尾部的糟糕体验。**分布式系统里，一个慢服务可以拖慢整个请求——哪怕大多数服务都很快。**

常用指标：P50（中位数）、P95（约 5% 更慢）、P99（约 1% 更慢）、P99.9（约 0.1% 更慢）。

在 Express 服务器里测延迟，用这个中间件：

```javascript
app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on("finish", () => {
    const end = process.hrtime.bigint();
    const latency = Number(end - start) / 1_000_000;
    console.log(req.method + " " + req.url + " - " + latency.toFixed(2) + "ms");
  });
  next();
});
```

生产系统我不会从日志手算 P99——用 Prometheus + Grafana、OpenTelemetry 或 Datadog 这类监控工具。

## 降尾延迟：找到慢路径

Node.js 常见原因与对策：慢数据库查询（加合适的索引、优化查询）；慢外部 API（谨慎用超时、缓存、重试）；过多同步工作（别阻塞事件循环）；重复的数据库/API 调用（用 Redis 等缓存）；大响应（分页与压缩）；数据库连接问题（连接池）；CPU 重活（移到 worker 线程或后台任务）。

看这个例子：

```
P50 = 80ms
P95 = 150ms
P99 = 2000ms
```

平均看着不错，但约 1% 的请求卡在 2 秒尾部。追查慢路径发现一个 MongoDB 查询：

```
API → Node.js → MongoDB → slow query
                         ↑
                     2 seconds
```

加上合适的 Mongo 索引后：

```
P50 = 70ms
P95 = 120ms
P99 = 180ms
```

我的实操循环很简单：**测 P95/P99 → 找慢请求的瓶颈 → 优化它 → 再测。**

## 把指标放进上下文

我为系统、用户与负载定义现实的目标；持续监控以在用户感知之前发现趋势与新问题。优化应当降低延迟、提升吞吐、减少错误、高效用资源——**这些指标相互作用：改善一个会影响另一个，所以需要整体视角而不是单一夺冠数字。**

## 串行请求延迟从网络开始

我的笔记区分公共互联网与私有内网（内网更快更可靠）、对比 TCP 与 UDP（TCP 关联连接建立与可靠性，UDP 关联低开销与速度；下文的安全层是 TLS，不是 TCP 本身）。

对这里覆盖的基于 TCP 的 HTTP 通信，**连接建立是延迟预算的一部分。**

**TCP 三次握手**：客户端发 SYN → 服务器回 SYN-ACK → 客户端发 ACK，握手完成、通信开始。建立连接的时间计入连接延迟。

**TLS 握手**在 TCP 之上加安全层——建立安全连接需要额外操作，产生额外通信开销与延迟。

**网络延迟的三个组成部分**：数据传输延迟（数据跨链路移动需要时间）；TCP 连接延迟（建新连接耗时）；SSL/TLS 连接开销（安全会话建立加活；复用会话信息可降低后续连接的开销）。

**降低连接建立成本**：连接池（数据库与应用服务器之间——复用既有连接，不为每个请求新建）；持久连接（客户端与 API 网关之间——HTTP/1.1 持久连接允许复用而非重复握手）；SSL 会话缓存（复用会话信息降低安全握手开销）。

**降低数据传输成本**：会话/数据缓存（在客户端或中间层如 API 网关缓存高频数据，避免反复回源与往返）；静态内容缓存（logo、脚本、图片通过 CDN 靠近用户）；数据格式与压缩（选高效格式与压缩减小载荷——笔记里以 JSON vs XML 为例）；二进制传输 gRPC（传大数据集时考虑二进制协议，减少文本处理与序列化开销）。

还有：组合资源减少 HTTP 请求数、优化 DNS 解析、策略性放置 CDN 缓存；持续监控网络延迟、吞吐、丢包，找出下一个优化点。

## 内存访问延迟

底层内存读写速度约束直接访问的延迟。应用层面，笔记聚焦内存怎么被用：有限的堆内存（到顶会崩）；大堆占用；GC 算法（回收行为是延迟图景的一部分）；有限的数据库缓冲内存。

**最小化内存相关延迟**：避免内存膨胀（减少应用任意时刻持有的数据量）；在支持处用弱/软引用（让 GC 回收合资格数据而非无谓保留）；考虑多个更小的进程（聚焦的进程降低单个内存足迹）；选择并调优垃圾回收（合适的回收行为、高效回收、低停顿）；批量处理数据（改善内存效率、降低切换开销、改善 cache line 内的数据局部性）；避免反复创建销毁主进程（保活可减少分配释放开销）；合理规范化数据库数据（避免冗余存储与不必要传输）；可行处用内存计算替代磁盘访问（免得反复从慢存储取）；不留不必要的数据（易推导的信息现算，内存留给必要数据）。

## 磁盘访问延迟

磁盘 I/O 慢，而且出现在几个要害处：web 内容文件、日志——尤其数据库访问。

**最小化磁盘访问延迟**：顺序与批量 I/O（分组操作、尽量顺序访问而非散乱随机读写）；异步日志（用 worker 线程，日志不阻塞主线程的关键工作）；web 内容缓存（图片/脚本/样式表经 CDN 靠近用户，减少回源磁盘访问）；反向代理与负载均衡（跨服务器分摊流量降低单机磁盘负载；反代还能缓存内容）；动静分离（频繁变化的动态数据如 JSON 与静态二进制资产如图片视频音频分开托管）；page cache 与零拷贝（OS 的页缓存把高频数据留在内存、减少重复磁盘读）；查询优化（只取应用需要的数据）；数据缓存（高频数据库结果缓在应用里）；schema 优化（高效的数据布局与合适的索引减少磁盘寻道、改善查询执行）；存储硬件（更高 IOPS 的盘、合适的 RAID 配置做访问并行、SSD 替代 HDD）。

## CPU 延迟

两个 CPU 相关的关注点：低效算法（可直接在代码里解决）与上下文切换（系统保存进程/线程状态以便之后恢复、再恢复另一个已存状态来执行）。

**最小化 CPU 延迟**的清单：高效算法；高效数据库查询；批量或异步 I/O；合适处的单线程模型；线程池大小；虚拟环境中的多进程。**这些是要对照负载评估的区域，不是盲目套用的改动。**

笔记里那张对比图把 CPU 缓存、主内存、磁盘访问、网络操作放到同一把尺上——**一个有用的提醒：操作触碰的资源，可能与操作本身同样重要。**

（并发请求处理需要 OS 与多线程知识，笔记里是独立深挖，此处从略。容量=性能图景的硬件侧：加 CPU/内存/磁盘/网络资源改善性能——它与效率、并发并列，而不是替代对它们的理解。缓存贯穿了这些优化技巧，但笔记里的专门章节标着「以后」——更深的讨论留待以后。）

## 改架构之前，先找瓶颈

当增长中的应用变慢，我要**先拿证据，再做架构重写。**

从延迟、吞吐、错误、资源饱和开始。越过平均看 P95 与 P99。然后追着「正在等待的工作」穿过网络、数据库、操作系统与应用代码。

从那里，决策变得具体：改善单请求的效率、评估并发执行、或增加容量。

**找到队列。理解它为什么在涨。优化瓶颈。再测一次。**

# 《Find the Queue Before You Change the Architecture》的发芽报告

## 材料核心

面对「应用变慢」的第一反应不该是换架构——先按「定义（固定负载与硬件的响应性）→测量（延迟/吞吐/错误率/饱和度四指标）→定位（四大区域找队列）→优化」框架走。中心命题：**每个性能问题都是某处正在排队的队列**——网络（缓冲区满/丢包重传）、数据库（慢查询/连接池耗尽/磁盘 I/O）、OS（CPU 争抢/换页/进程等待）、代码（低效算法/冗余计算/死锁）各找各的队列。队列积压三根因：处理慢、串行访问、容量不足；且队列不全是坏的（消息队列是故意的）。实战核心是尾延迟：平均不够要看 P95/P99（100 请求里 1 个 2 秒的例子），加一个 Mongo 索引 P99 2000ms→180ms；再往上按网络（TCP/TLS 握手成本→连接池/持久连接/会话缓存）、内存（GC/批量/弱引用）、磁盘（异步日志/动静分离/零拷贝）、CPU（算法/上下文切换）逐层削减。结束语即方法论：「找到队列，理解它为什么涨，优化瓶颈，再测。」

## 发芽 01：「队列视角」——把模糊的「慢」翻译成可定位的等待点

### 种子

「应用很慢」是一个不可操作的陈述；「某个队列正在变长」是可操作的——队列有位置、有长度、有进出速率、有容量上限。

### 故事

框架的威力在于把四大区域（网络/数据库/OS/代码）各自翻译成「队列会出现在哪」：网络是网卡与 OS 缓冲区、数据库是连接池与磁盘 I/O、OS 是 CPU 调度与换页、代码是锁与串行逻辑。检查清单（找满载或快涨的队列、队列长度与三资源利用率合读、盯趋势对基线的偏离）给出了从「现象」到「等待点」的完整搜索路径。同时保留了必要的平衡：消息队列是故意排队的——**区分「意外等待」与「设计内缓冲」是队列视角的进阶课**。

### Aha 瞬间

**性能诊断的通用第一问不是「哪里慢」而是「什么在等什么」——找到那个等待点，修复选项通常自己浮现。**「改架构」在这个框架里是最后一位的选项，而非第一位。

## 发芽 02：P99 的一课——平均值会合谋掩盖尾部

### 种子

100 个请求：95 个 100ms、4 个 200ms、1 个 2000ms——平均看起来可接受，而那一个 2 秒请求就是用户体验的最差值。加一个 Mongo 索引：P99 2000ms→180ms。

### 故事

为什么尾部要紧：分布式系统里一次前端请求可能扇出几十次后端调用——单服务 P99=2% 的慢概率经过多次扇出叠加，「至少一个子调用落在尾部」的**概率**就不再小；用户体验由最差路径决定。实操循环「测 P95/P99→找慢请求瓶颈→优化→再测」把性能工作变成可迭代闭环，而不是一次性的大重写。作者同时给出生产化的边界：不要从日志手算百分位，用 Prometheus/OpenTelemetry/Datadog。

### Aha 瞬间

**平均值描述系统，百分位描述用户——每一个被平均抹平的 2 秒请求，都对应着一个真实的人在等待。**性能优化的第一刀永远砍向 P99 的那个慢路径，而不是给平均数再涂一层漆。

## 发芽 03：延迟预算的分层账本——从握手到 cache line

### 种子

网络延迟三成分（数据传输/TCP 连接/TLS 开销）、内存的 GC 停顿、磁盘的随机 I/O、CPU 的上下文切换——笔记那张「CPU 缓存、主内存、磁盘、网络同尺对比图」是全篇的隐藏骨架。

### 故事

分层账本的用法：每一层有自己的廉价优化清单——网络层是连接池/持久连接/会话缓存/CDN/压缩/gRPC；内存层是批量处理/弱引用/GC 调优/主进程保活；磁盘层是异步日志/动静分离/零拷贝/索引 schema；CPU 层是算法与线程池大小。共同原则是「让数据离计算更近、让等待不阻塞关键路径」。作者诚实标注了边界：并发深挖与缓存专题标「以后」——**框架的完备性与个人的推进节奏可以分开。**

### Aha 瞬间

**「操作触碰的资源，可能与操作本身同样重要」——同一个函数从网络取数与从内存取数，成本差出几个数量级。**优化清单的正确读法不是逐条执行，而是先问「这个请求的钱花在哪一层」，再翻那一层的账本。
