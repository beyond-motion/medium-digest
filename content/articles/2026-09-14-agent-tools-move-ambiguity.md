# Agent 工具不会消除模糊性，只会把它搬进产品

> 原文：[Agent Tools Don't Remove Ambiguity. They Move It Into the Product.](https://medium.com/@zyane/agent-tools-dont-remove-ambiguity-they-move-it-into-the-product-906d0ffd9284)

---

## agent 在从界面上逆向工程产品的意义

一个浏览器 agent 必须猜测一个网站意味着什么。不是完全瞎猜：它可以检查文本、DOM 结构、无障碍标签、表单状态、禁用的控件、导航、截图，以及上一步操作之后变化了什么。信号足够时，它能从一个面向人类的界面上重建出可用的动作模型。

这已经很有用——细看之下也有点怪：**产品本来就知道自己每个动作的含义，而 agent 在从「展示层」反向工程这层含义。**

面向 agent 的结构化工具改变其中一环：不再让 agent 从一串控件推断「这代表执行某个操作」，网站直接声明这个操作——一个名字、一段描述、结构化的输入、一条执行路径，也许还有行为提示。

agent 少了交互层面的猜测。**网站多了一份责任。模糊性没有消失——它搬进了产品契约。**

## 第二个界面仍然是界面

拿一件平常事：把商品加入购物车。人类路径是：商品页 → 选规格 → 选数量 → 加入购物车 → 查看购物车 → 去结算。人从整个界面上读取含义——按钮文字重要，位置、前序步骤、后续出现的东西、以及人对购物这件事的既有知识同样重要；只看页面的 agent 必须重建全部这些上下文。

结构化工具可以把能力压缩得更显式：

```
add_to_cart
inputs:
  product_id
  variant_id
  quantity
```

这对机器推理更好：动作有了稳定的身份、必需的输入形状可见、agent 不必再发现「哪些控件合起来构成这个操作」。

但这个紧凑版本同时暴露了界面原本撒落在页面各处的问题：**这件商品会开启订阅吗？这个账号能买十件吗？选中的规格还有货吗？当前会话允许购买吗？如果另一个工具叫 finalize_cart，它展示最终订单，还是直接扣款？**

这些不是 agent 的问题，是产品语义。网站一旦直接声明能力，就直接拥有了这份声明。正确的模型不是「agent 绕过 UI」，而是**一个产品、两个界面**：交互层可以不同，含义不能。

## 结构不是真相

当前的 WebMCP 草案把这个设计问题具体化了。先看状态：WebMCP 目前是 Web 机器学习社区组的一份草案社区组报告（Draft Community Group Report），不是 W3C 标准、不在标准轨道上。

在这个边界内，草案让 Web 应用可以暴露基于 JavaScript 的工具：显式的名字、自然语言描述、结构化输入 schema、执行回调、可选注解、以及围绕工具暴露位置的控制。这把真实信息从「推断」搬进了「声明的结构」。

**但它不能把声明变成证明。**一个叫 publish_article 的工具仍然可以有误导性的描述；JSON Schema 仍可以索要超出动作所需的信息；只读提示仍可能与实现相矛盾；执行回调仍可能走上与可见 UI 不同的代码路径。这正是「结构化」一词制造虚假安慰的地方：结构给了 agent 一个可清晰推理的对象，却不保证被描述的东西安全、被授权、完整、甚至准确。**声明是契约的一部分，实现仍然必须让声明保持为真。**

## 认证不是授权

agent 工具在已登录的浏览器会话里运行时，变得更有分量。便利显而易见：网站已经知道哪个用户登录了，工具可以直接复用这个状态，不必再造一套账号系统。但认证回答的问题比人们以为的窄：它告诉产品「这是谁的会话」，**不回答「agent 现在是否可以执行该会话内可用的每一个动作」。**

人可以登录着发布系统，仍然期望上线前有确认；登录着电商产品，仍然期望扣款前有另一次决定；登录着管理后台，仍然期望权限变更或数据删除前重新认证或单独审批。**如果面向机器的工具把「用户已认证」悄悄变成「agent 可以行使会话内的一切权限」，界面就压缩掉了一个治理步骤。**有些摩擦是意外的交互成本，有些摩擦是政策。好的 agent 界面应该去掉前者，而不是顺手删掉后者。

## 两条路径需要一条策略边界

最重要的架构问题不是「工具回调会不会执行」，而是：**工具路径是否与人类路径服从同一套规则。**

假设可见的产品阻止超额退款、要求删除账户前重新认证、没有审批状态不许发布、大额购买要二次确认——现在假设 agent 工具调用的是一个跳过其中某项检查的便捷端点。网站没有造出一个更干净的界面，它造出了一个**策略分裂**。

更安全的形态很无聊（这通常是好迹象）：

```
human UI ─────────┐
                  ├─→ shared domain action
agent tool ───────┘        ↓
                   authorization
                    validation
                 side-effect policy
                 resulting state
```

两个交互层调用同一个受治理的动作边界——业务规则不必在两个前端重复，产品也获得了一个测试真正要紧之事的位置：不是「这个工具能执行吗」，而是「**这个动作无论从哪个界面调用，是否服从同一份契约？**」

## 失败需要领域含义

浏览器自动化常常通过后果发现失败：输入框变红、toast 弹出、模态框不关、按钮保持禁用、页面去了意想不到的地方。结构化工具可以做得更好——失败可以被显式返回。但如果 agent 不知道下一步该做什么，`success: false` 只比红色按钮好一点点。

有用的失败语义要在 agent 能行动的层级上描述领域问题：无效输入；状态过期；缺少授权；并发的冲突变更；需要用户确认；限流；资源已不存在；部分完成；不允许的不可逆步骤；上游依赖故障。（这些是产品级含义的示例，不是「WebMCP 已标准化统一错误分类法」的声明。）

区分之所以要紧，是因为机器界面的职责是帮 agent 决定：改输入？刷新状态？问用户？换动作？稍后重试？还是停下。**技术失败是可观察的；领域失败才是 agent 能行动的版本。**

## 「完成」需要证据

结果这一侧同样容易欠设计。只读动作返回所请求的信息也许就够了；**变更类动作不同**。如果 agent 更新了文档、改了权限、创建了订单、发布了内容，回调正常返回并不能确立「预期的状态转换真的发生了」。

依产品不同，有用的结果可能包括：受影响对象的稳定标识符；结果状态；修订号或版本号；变更是待定还是最终；剩余的审批步骤；（在要紧的地方）时间戳；一个可检视的去处；以及——如果存在——撤销或恢复的引用。

确切的回执模型是产品决定；WebMCP 目前不提供完整的标准化证据体系，也不应该被描述成有。但设计要求无论如何存在：agent 可以直接调工具，**仍然需要人可以检视的证据。**这对「后果严重」的动作最重要——在那里，「回调结束了」与「用户想要的事现在是事实了」不是同一句话；把两者当成一句话，「完成」就成了一种哲学。

## 人类界面仍然有工作

面向机器的能力面不会让可见的网站过时。人类界面承载着不属于每个工具描述的上下文：让人比较选项、看到警告、检视状态、注意后果、确认决策；它还为产品提供了「agent 行动之后把人送回哪里」的地方——最干净的机器结果通常配着一个人类可检视的后果：更新后的文档、最终订单、权限页、发布记录、改过的设置。

所以两个界面互相成就而非竞争：**agent 得到精确的动作面，人得到清晰的状态面，一个含义垫在两者之下。**

## WebMCP 是更大产品问题的一个例子

OpenAI 目前把 WebMCP 作为实验性实现路径：其 WebMCP Challenge 围绕「网站为 agent 定义结构化工具、而不是逼 agent 从 UI 猜每个动作」展开；ChatGPT 桌面应用的站点工具帮助文档描述了一个具体版本——在支持的网页上，内置浏览器可以发现站点提供的工具（可用性取决于账号、模型、站点与当前产品支持）。

这是有用的实现证据，不是通用浏览器采纳、标准落定或完整 agent-web 安全模型的证据。无所谓——因为产品问题比这份草案更大：**任何让网站向 agent 直接声明可调用能力的机制，都会产生同一族义务**——语义身份、窄参数、权限、副作用、校验、失败、证据、作用域与生命周期。

agent 可以不再猜动作。**产品仍然必须说话算话。**

# 《Agent Tools Don't Remove Ambiguity. They Move It Into the Product.》的发芽报告

## 材料核心

浏览器 agent 在从展示层逆向工程产品语义，而结构化 agent 工具（以 WebMCP 草案为例）让网站直接声明操作——agent 少了猜测，网站多了责任；模糊性没有消失，而是从交互界面搬进了产品契约。四组具体义务随之显形：结构不是真相（publish_article 的描述仍可撒谎，声明与实现可以分叉）；认证不是授权（「谁的会话」不等于「能执行会话内一切动作」）；两条路径需要一条策略边界（agent 工具跳过人类路径的检查=策略分裂，正确形态是两个界面调用同一个受治理的动作边界）；失败需要领域含义、「完成」需要人可检视的证据。

## 发芽 01：省略掉的摩擦里，有些是政策

### 种子

「有些摩擦是意外的交互成本，有些摩擦是政策。好的 agent 界面应该去掉前者，而不是顺手删掉后者。」——为机器优化体验时，最危险的是把治理步骤当成体验缺陷。

### 故事

文章的例证全是「多一步」的形状：上线前的确认、扣款前的决定、删除前的重新认证、大额的二次确认。人路径里它们以页面的形态存在；一旦工具把能力压缩成 add_to_cart 三个参数，这些散落在页面各处的检查如果不被显式收编进共享动作边界，就随着页面的旁路一起消失了。

### Aha 瞬间

给机器修路之前要先盘点路上的每道闸机——哪些是路障（拆掉是优化），哪些是关卡（绕过是事故）；区分的标准不是「烦不烦」，而是它守护的是体验还是契约。

## 发芽 02：结构化提升的是可读性，不是诚实性

### 种子

「『结构化』制造虚假安慰：结构给了 agent 一个可清晰推理的对象，却不保证被描述的东西安全、被授权、完整、甚至准确。」——声明是契约的一部分，实现必须让声明保持为真。

### 故事

四个具体的分叉点：误导性的工具描述、索要过度的 schema、与实现矛盾的只读注解、走上不同代码路径的执行回调。结构化把「从页面猜」换成了「读声明」，但没有换掉「声明可能不真」这个古老问题——它只是把验证责任从 agent 的推断能力移到了产品的工程纪律。

### Aha 瞬间

可读的谎言比不可读的真相更危险——结构化接口给了 agent（和信任 agent 的人）一种「已经理解了」的确定感，而验证声明与实现的一致性这件脏活，一步都没少。

## 发芽 03：回调结束不等于事情完成——「done」的证据学

### 种子

「对后果严重的动作，『回调结束了』与『用户想要的事现在是事实了』不是同一句话；把两者当成一句话，『完成』就成了一种哲学。」

### 故事

文章给变更类动作开出的回执清单是具体的：稳定标识符、结果状态、版本号、待定还是最终、剩余审批步骤、时间戳、可检视的去处、撤销引用——并且特别强调「agent 可以直接调工具，仍然需要人可以检视的证据」。失败一侧同理：`success: false` 只比红色按钮好一点，除非失败语义告诉 agent 该改输入、刷状态、问用户还是停下。

### Aha 瞬间

异步系统的「完成」不是时刻而是证据链——machine-facing 界面的成熟度，恰恰体现在它愿不愿意为每个变更附上一张人类能看懂的回执。
