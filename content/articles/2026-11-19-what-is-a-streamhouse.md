# 什么是 Streamhouse（流仓）？

> 原文：[What Is a Streamhouse?](https://medium.com/@seanfalconer/what-is-a-streamhouse-667eef91b8d5) — Sean Falconer

---

streamhouse 定义公开的时候，我听到的第一反应是「这不就是流处理换了个名字？」第二个是「我的 lakehouse 为什么做不到？」我在 Confluent 工作——定义背后的五家公司之一——而且我是塑造这套话语的人之一，所以你应该默认我有利益相关。这是你在阅读时保持怀疑的好理由，我会尽力证明我说的每句话。

**streamhouse 是一种围绕「业务每一次变更的日志」构建的架构**，外加把这些变更在到达时就地转化为当前状态的处理与表存储。怀疑者部分正确——几乎没有任何单个组件是新的。新的是把它们当作**一个有共享定义的架构**来对待：Aiven、Confluent、Redpanda、StreamNative 和 Ververica 在九月联合发布了它。五家公司在同一个词上达成一致，说明不了这个词有没有用——尤其五家全来自流与数据基础设施侧、没有一家来自 lakehouse 阵营。所以本文剩下的部分试着把它挣回来。

但这不等于换皮重发。lakehouse 同样是从既有零件组装的，**正是这个名字让人们把它们当一个系统对待**。现在这个组合值得同样对待的原因，是**读数据的人变了**。

一个人一天查几次 BI 面板，数据停在 8:00 无所谓；两个系统打架，他能发现、能自己裁决。**一个 agent 每次运行都在做决策**——批准一笔退款、改道一件货、回答一个客户——当订单系统说包裹已发货而仓库系统说没发，它会默默选一个、不告诉任何人。乘上每天数千次决策，一套对面板够用的数据栈，开始**在规模上产出错误行动**。所以当你的 agent 在做决定时，你的数据到底在对它说什么？

## streamhouse 是什么

定义描述的架构能「持续地捕获、传输、转换、治理并服务业务的当前状态，让生产应用与 agent 能对它采取行动」。

你的银行账户是个好的想象方式。你账户的记录是存款、取款与手续费的**账本**，手机上的余额是把它们按序应用后的结果。手机、ATM、柜员显示同一个余额，因为它们都从同一本账本构建；收费到账时你收到的短信，就是「对变更实时采取行动」。数字看起来不对时，银行从账本重建余额——而账本没法从余额重建。**streamhouse 的运转方式相同：变更日志是账本，表是余额。**

银行里的一笔交易经过类似的步骤：被记录、进账本、应用进余额、对照规则检查、展示给你。在 streamhouse 里，这些步骤就是定义里的五个动词。

- **Capture（捕获）**：连接器从数据产生的系统里读出变更——数据库、SaaS 应用、设备。用 CDC（变更数据捕获）逐条读每个 insert、update、delete，而不是按计划拷整张表。
- **Transport（传输）**：每条变更追加进一本持久、有序的日志。生产者写一次，任意数量的消费者按自己的节奏读，历史随时可重放。
- **Transform（转换）**：流处理器在变更流动时清洗、连接、富化，把原始事件变成业务认识的实体——一个客户、一张订单、一件货。它随每条变更到达就更新结果，不从零重算。
- **Govern（治理）**：schema、数据质量规则、血缘、访问策略定义一次、在生产时强制——每个消费者自动继承。
- **Serve（服务）**：结果以每种消费者需要的形态保存。同一份变更可以同时是可重放的日志、对象存储里的开放表（Iceberg/Delta Lake）供分析、以及供应用与 agent 快速查找的索引。

合起来它们是一个系统：每个应用、agent、分析系统读的都是**同一批变更构建出的状态**。快速判别法：一条变更能否在不为每个下游单建管线的情况下，同时到达一个应用、一张分析表、一个 agent，且事后可重放？如果每个消费者都得有自己的拷贝任务，那更像「lakehouse 加了点流处理」。

## 这个想法从哪来

2010 年代初，想要又新鲜又正确的结果通常意味着 **Lambda 架构**：同一套逻辑跑两遍——一遍批、一遍流——查询时合并答案。2014 年 Jay Kreps 论证「跑两套系统并调试它们的运维负担会非常高」，提出把一切记进日志、在上面跑单一流作业、要重算就把日志重放进作业的新副本。他建议叫它 **Kappa 架构**——「虽然这个想法可能简单到不配用希腊字母。」

Kappa 去掉了重复代码，但撞上另一组问题：**日志擅长重放，不擅长回答问题。**重算意味着重放整条流；Kafka topic 里的中间结果可消费但不可查询，团队把数据拷进别的系统去分析——管线又回来了。

lakehouse 从另一个方向来。它在便宜的对象存储上加了一层表，让分析开放且便宜——但它是围绕批设计的。流式灌进去多数只是摄入，真正的处理发生在别处。

Ververica 的论证：streamhouse 把两者合起来——kappa 的流优先设计+lakehouse 的可查表，正如 lakehouse 当年合流了数据湖与数仓。Yelp 2015 年建的管线用 Kafka 同时当传输与永久存储、数据要过四五个 topic、同一份数据存多处；他们的替代方案在 S3 上跑 Flink+Paimon，**分析延迟从 18 小时降到分钟级、存储成本降 80% 以上**。（注意分寸：Yelp 自己的要求是分钟不是秒，这些收益主要来自退役自研管线和把存储从 Kafka 搬去 S3——它支持的是这个模式，不是速度本身的论点。）

## 为什么 lakehouse 不能直接这么干

明显的反驳：lakehouse 越来越快，把它做快不就行了？先看 streamhouse 设计要求什么——**三条性质，每条都来自 agent 的需要而查 BI 的人从来没有的需要**，而 lakehouse 为分析而生，在这三条上各差一种。

**永远当前（Always current）。**agent 每次运行就决策一次，数据要多新鲜取决于决策：商品推荐也许能容忍一小时旧的数据，但**对着十分钟前变了状态的订单批一笔退款不能。**lakehouse 围绕批组织：数据先进 raw 层、下一层清洗、第三层成型，每步按计划跑——agent 读顶层，看到的是上一轮的画面。缩短计划有帮助，但每层仍在等下一层，中间任何 job 挂了，下游全部静默变陈旧，没人通知你。lakehouse 厂商看到了这一点，流入开放表的能力持续改进（Tableflow 把 Kafka topic 变成 Iceberg/Delta 表；Kinesis streaming tables 直灌 S3 上的 Iceberg）——这能缩短滞后，但不能消灭它。有些团队更进一步让 agent 直接查开放表：省一跳，但数据的fresh程度只取决于最后一次写入。而且**缩短滞后会移动球门柱**：做过开放表同步的人都见过十五分钟「感觉很快」直到不再快——然后五分钟、一分钟、十秒。每次改进都抬高 agent 被期望处理的场景，没有哪个固定数字是终点。

**关键任务级（Mission critical）。**一旦应用或 agent 在做业务依赖的决策，喂它的数据就在关键路径上。它迟到或不可用，结账停摆、订单不动——它必须按生产系统的标准被对待：日志跨故障域复制、处理从故障中恢复不丢不重、升级不停机。**lakehouse 通常按分析系统运维**——夜里停机维护、大家等着。多数 lakehouse 的可用性目标是分析级的：对内部分析合理，对客户触摸的东西糟糕。

**去中心化（Decentralized）。**agent 需要跨全业务行动，而它要的数据活在许多系统、许多主人手里，新系统出现的速度比任何整合都快。lakehouse 靠引力工作：数据必须先进来才能用——每个新源意味着一条要建要养、且源还在变的管线。streamhouse 把变更送到需要的地方、就地构建每个消费者需要的状态，**什么都不用先汇聚。**

这不是说拆掉 lakehouse。报表、历史分析、模型训练照旧——那里一小时一天旧的数据无妨。而且上游有 streamhouse 它反而更好：数据到达时已验证、已去重、以分钟而不是小时。

## 变更是原语

数仓与 lakehouse 都围绕**表**构建。表是某时刻「什么是真的」的快照，保鲜靠加载更多数据或重算。两者都在加增量特性（change feed、增量维护视图），但设计的中心仍是表。**而业务产生的是变更**——一张订单、一笔结算、一次包裹扫描、一个座位被占——表是我们事后从它们构建出来的东西。数据库内部一直如此：write-ahead log 加派生自它的表。streamhouse 把这个思想跨系统应用。

回到银行的例子：月度对账单是账本的快照，适合回看；手机上的余额始终当前，因为每笔交易都更新它。streamhouse 里，表从变更日志构建、随每条到达而更新——**表永远是「到目前为止的变更应用结果」**。订单 1043 在 8:12 发货：lakehouse 表要等 9:00 的 batch commit 才显示，streamhouse 表毫秒到秒级就显示；日志与索引同理。分析引擎读的开放表副本通常落后几分钟——仍远好于 batch commit。

把变更当单位，给你两样快照难以给的东西：**每个消费者收敛到同一个状态**（同一个 key、同样的变更、同样的顺序——不是同时更新，但终点一致）；以及**出错或演进时可以重放日志**，而不必回到源系统从头再来。

（Decentralized 需要澄清：日志是唯一有序的「发生了什么」记录，每个需要数据的系统从它构建自己的副本、按自己的用途塑形——副本可以住不同云、服务不同目的、却仍然一致，因为它们构建自同一批变更。日志本身跨区域跨云复制，但它仍是人人依赖的共享基础设施——所以「去中心化」描述的是数据的落点与使用者，不是日志本身。）

## Agent 需要长大

按需答疑的 agent 靠别人投喂就能活。**运行业务的一部分、并最终自主行动的 agent，不行。**要被信任，它需要两样有经验同事都有的东西：**知道此刻什么是真的**；**不经询问就知道什么变了。**

第一，当前且一致的图景。一个系统说包裹发了、另一个说没发——agent 无从判断哪个可信。streamhouse 不替你裁决哪个系统对，但它**按序捕获两个系统的变更、让你把规则定义一次**（比如谁赢），于是每个消费者拿到同一个答案。

第二，主动感知变更。自主行动的 agent 必须在订单取消、传感器漂移、客户变卦时**不等被问就**知道。简单答案是让 agent 直查源系统——单系统可行且永远当前；但跨多个系统、要看变更随时间的演变、或与许多其他 agent 共享这些系统时就难了。没有「有东西变了」的信号，唯一选项是轮询——问每个系统有没有新东西，多数时候答案是「没有」。把它乘上许多 agent 与许多系统，就是一套源系统从未按其设计的负载；而且 agent 仍只在询问的频率上得知变更。

**在 streamhouse 里，变更本身就是信号。**它发生即发布，关心它的 agent 立刻听到——而且当前状态已经在手。

信任还依赖回看的能力。表快照能显示某表在某时刻持有什么；变更日志还能显示**事情发生的顺序**。当一个 agent 做了糟糕的决定，你可以重放到它行动前的那一刻、看到它当时看到了什么。**能否回答这个问题，是团队敢把更多责任交给 agent 的大部分前提。**

（streamhouse 持续守着的四个保证：变更处处以同序应用；故障后没有变更丢失或被重复计入；每份副本落后日志的延迟小而可测；历史可重放以重建或回填。）

## 所以这只是一股流吗？

流处理是一种技术。streamhouse 是你把它与处理、表存储和治理合起来、并以「当前状态可被生产应用与 agent 行动」为目标时的产物。单个零件都不新——新的是这组零件、这个名字、和让它们必须一起工作的那个新读者。你的数据栈为面板服务的年代结束了；当读者变成每天做数千次决策的 agent，**「数据是什么时候刷新的」这个问题，就变成了「我的 agent 此刻相信的现实是谁构建的」。**

# 《What Is a Streamhouse?》的发芽报告

## 材料核心

五家流厂商（Aiven/Confluent/Redpanda/StreamNative/Ververica，作者来自 Confluent、利益明示）9 月联合发布的 streamhouse 定义：围绕「业务每一次变更的日志」+处理+表存储，把变更在到达时就地转化为当前状态，供生产应用与 agent 行动。推动力是读者变了：人一天几个决策（8:00 刷新无妨、分歧人工裁决）vs agent 每次运行即决策且在矛盾源间默默选边。银行账本比喻：变更日志=账本（可重建余额、反之不行），表=余额。五动词：Capture（CDC 逐条）/Transport（持久有序日志可重放）/Transform（增量更新不重算）/Govern（一次定义生产时强制）/Serve（同一变更三形态：日志/开放表/索引）。判别法：一条变更能否无独立管线同时到达应用+分析表+agent 且可重放。源流：Lambda（双跑合并）→Kappa（Kreps 2014，去重码但日志善重放不善答题）→lakehouse（开放便宜但围绕批）→streamhouse（kappa 流优先+lakehouse 可查表）；Yelp 案例（Flink+Paimon on S3：18 小时→分钟、存储 -80%，作者注明分寸：支持模式非速度）。三性质（agent 需要而 BI 人不需要）：永远当前（批层层等待+静默陈旧+球门柱上移）/关键任务级（生产标准 vs 分析级可用性）/去中心化（lakehouse 靠引力汇聚 vs 变更就地构建）。变更即原语：WAL+派生表跨系统化、订单 1043 三种形态的时延对比、消费者收敛+重放。Agents need to grow up：两样同事有的东西（当前一致图景+主动感知变更）——轮询的负载与滞后 vs 变更即信号；回看重放「它当时看到了什么」是授权的前提。四保证：同序/不丢不重/可测滞后/可重放。

## 发芽 01：「读者变了」——数据架构的需求侧革命

### 种子

「一个人一天查几次 BI 面板，数据停在 8:00 无所谓；一个 agent 每次运行都在做决策……乘上每天数千次决策，一套对面板够用的数据栈，开始在规模上产出错误行动。」

### 故事

streamhouse 的论证骨架不是技术优越性而是需求侧变化：人查数据是间歇性的（容忍滞后、能人工裁决矛盾），agent 查数据是每次行动必查（滞后即错误、矛盾即随机选边且无人知晓）。这把「要不要上流式」从性能问题重写成了正确性问题——面板时代的最大损失是「看到旧数据」，agent 时代的最大损失是「基于矛盾现实行动且规模放大」。作者甚至不要求你相信定义——他给的判别法（一条变更能否无独立管线同时到达应用+表+agent 且可重放）让架构选择可以被逐案检验。

### Aha 瞬间

**数据架构的演进从来不是由写入侧驱动的，是由「谁在读」驱动的——报表读者容忍 T+1，应用读者要求秒级，agent 读者要求「永远当前且矛盾可裁决」；streamhouse 的出现时刻，就是 agent 从数据消费者变成决策者的时刻。**

## 发芽 02：账本与余额——「变更即原语」的一致性来源

### 种子

银行比喻：账本（存/取/费的完整记录）可以重建余额，余额没法重建账本；ATM、手机、柜员显示同一余额，因为它们都从同一本账本构建。数仓与 lakehouse 围绕表（快照）设计，而业务产生的原生形态是变更——表是事后构建物；数据库内部一直如此（WAL+派生表），streamhouse 把这个思想跨系统应用。

### 故事

「变更作原语」给出一对从快照难以获得的东西：收敛性（同一 key 同序应用同变更——不同时但同终点，天然解决「两个系统打架」）与可重放性（出错/schema 演进时重放日志而非回源重来）。Yelp 案例里被作者小心标注的细节（收益主要来自退役自研管线与存储迁移，而非速度本身）同样是方法论的一部分：区分「模式有效」与「具体指标惊人」，前者才可迁移。对比 Kappa 的失败教训（日志善重放不善答题、中间结果不可查询导致拷贝回归），streamhouse 的增量是 Serve 动词——同一变更同时以日志/开放表/索引三形态存在，让「重放」与「查询」不再是二选一。

### Aha 瞬间

**「表快照」与「变更账本」的关系就是「余额」与「账本」的关系——快照适合回看、账本适合重建；当系统的读者从「想看现在」变成「需要知道为什么现在是现在」（agent 问责），只有账本形态能提供答案。**

## 发芽 03：轮询与信号——agent 的感知基础设施

### 种子

自主 agent 需要两样有经验同事才有的东西：知道此刻什么是真的；不经询问就知道什么变了。没有变更信号就只能轮询——多数调用返回「没变化」，多 agent×多系统构成源系统从未被设计承受的负载，且 agent 仍只在询问频率上得知变更。streamhouse 里「变更本身就是信号：发生即发布，关心的 agent 立刻听到，当前状态已经在手。」信任还依赖重放「agent 行动前那一刻看到了什么」的能力。

### 故事

轮询模式的成本是三层叠加的：源系统负载（从未按轮询设计的 API 被打爆）、感知滞后（变更只在询问时被发现）、以及隐性的不一致（每个 agent 轮询的时刻不同，同一时刻各自持有不同的现实图景）。变更信号模式把这三层一次性解决——发布/订阅的语义恰好是「感知」的正确抽象。而「重放 agent 行动前的那一刻」则把问责变成了可执行的操作：不是「我们检查了日志」（人类口径），而是「我们恢复了 agent 的全部输入并复现了它的信念状态」（机器口径）。四保证（同序/不丢不重/可测滞后/可重放）实际是 agent 授权清单的 infra 侧条款。

### Aha 瞬间

**让 agent 承担业务决策的前提不是更强的模型，是感知基础设施——「知道此刻什么是真的」需要一致的状态服务，「知道什么变了」需要变更流，「事后可问责」需要可重放；这三样是给 agent 的「听觉与记忆」，缺任何一样，模型的聪明都只是在更大的无知上押注。**
