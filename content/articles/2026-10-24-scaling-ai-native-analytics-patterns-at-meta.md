# 在 Meta 规模化「AI 原生分析」：模式库 + 确定性查询生成器

> 原文：[Scaling AI-Native Analytics Patterns at Meta](https://medium.com/@AnalyticsAtMeta/scaling-ai-native-analytics-patterns-at-meta-b29162cb46bf)
> 作者：Benjamin Wan Rothschild（Analytics at Meta）｜2026-10-20｜7 min read

---

在 Meta，分析团队发现了一个朴素的事实：绝大多数产品分析问题，都是少数几个模式的变奏——用户有多活跃？留存怎么样？在哪里流失？什么在驱动大盘？可即便如此，各团队仍在反复重造同一批度量原语：指标、留存计算、实验表、增长核算、漏斗。产品发布与度量组合不断膨胀，数据仓库里堆积起大量近似重复的管道，不一致性的产生速度超过了团队把数据变成洞察的速度。

他们的解法分两步：把高频度量原语固化成**参数化的管道模式**，并保证每个产出物都附带一份**智能体可读的数据模型**。这不只是统一了全公司的指标口径——参数化模式创造了一个统一接口，让人类与智能体以对等身份协作：智能体可以借助 skills 可靠地「编写」每一种模式，再通过确定性的查询生成 API 消费结果。Meta 由此消除了 LLM 直写 SQL 时常见的非确定性与幻觉，让智能体得以精确地横跨整个分析栈。把智能体当作数据资产的一等生产者与消费者，还带来了一个能力飞轮：自动建看板、深度分析配方、准确的指标问答智能体。

## 大多数分析都是少数模式的混搭

活跃度、回访、流失点、大盘归因——Meta 对最常用的度量原语做了编目，归纳出**七个核心模式**（作者强调你的目录可能不同，但大概率同样精简）。标准化、可预测的原语之所以重要，在于它提供了一个稳定接口：AI 智能体可以放心地用它生产和消费洞察。

但文章同样坦承标准化的边界：它适用于**重复出现、高信任要求**的度量，不适用于灵活的、探索性的、一次性的分析——把早期探索硬塞进僵硬的 schema 会扼杀发现与创新的灵活性。维护受治理的库与资产目录，还需要一支稳定团队的持续投入。只有在「广泛的复用足以抵消维护成本」时，标准化一个模式才划算。

## 我们造了什么：Analytics Libraries

**模式重复出现，就定义一次。** Analytics Libraries 的思路是：每个规范模式都提供可复用、参数化、受治理的实现。你不再手写留存或漏斗的定制 SQL，而是声明需求——活动事件、时间窗口、关键维度——由库生成底层 SQL 和管道。因为这些声明是结构化输入，AI 智能体可以轻松生成它们；而模式逻辑藏在参数化库里，SQL 字符串与管道任务类型这类关键逻辑是**确定性生成**的（Meta 用的是数据管道里的 Python 库），从根本上不可能被幻觉。

「指标物化」（Metric Materialization）是典型示范。过去指标散落在各处口径不一的裸 SQL 片段里，现在它们活在统一逻辑生成的受治理制品中。由于规格是声明式、强类型的，而非自由发挥的 SQL，智能体编写管道的准确率与人类持平，能把一句模糊的需求变成生产级管道。**仅指标物化库目前就支撑着超过 3,250 条生产管道；整个 Analytics Libraries 目录驱动的管道超过 9,000 条。**

## 为什么标准化划算

一次编码、处处复用，回报体现在四点：**默认正确**（易错的细节只解决和评审一次，处处继承，正确性不再需要每个分析师或智能体重新学习）；**速度**（用智能体编写参数化管道已缩短到几分钟的配置）；**可发现性与治理**（标准化产出注册在数据库中、自带描述，人和智能体都能找到、敢信任，不再重复造轮子）；**复利式复用**（每条建于共享原语之上的新管道，都让新功能推及全部管道变得更容易）。

分析工作有一笔隐形税：重复劳动。标准化是停缴这笔税的方式，也是把工作交给智能体消费的前提。把智能体扔进一堆定制的、没有文档的管道，它更可能淹没在无关上下文里、算出一个错误的数字；把它指向一份干净的受治理产出表目录——每张表自带自描述 schema 和注册的语义模型——它表现得像个领域专家。

## AI 原生地基：三个模型层

有了标准化地基，Meta 为智能体建了三层能力：管道生成 skills、面向数据模型的确定性 SQL 生成、以及解释层的分析配方。端到端工作流由此串起。

### Produce：让任何人都能建管道的 skills

第一层是自然语言 skills 作为入口。任何人说「我想按国家拆分统计这个注册事件的留存」，智能体就把请求映射到正确的库，生成管道。开工前它还会查模型数据库里是否已有类似度量，决定复用还是新建。管道生成复用了为 DEmate（Meta 此前自研的 LLM 数据工程工具）开发的自动代码生成与验证循环，确保产出在部署前符合 Meta 的数据工程标准。除物化表外，每条管道还输出一份 YAML 格式的数据模型——维度、指标、数据源的强类型表示，供后续查询生成使用。

### Query Model：智能体当工具调用的确定性查询生成器

分析 AI 最难的问题是**信任**：LLM 会兴高采烈写出「看起来对、返回错」的 SQL。Meta 的对策是让 SQL 生成尽可能确定化——他们造了一个确定性查询生成器，暴露为命令行工具。实践发现：**智能体学会用一个简单 API 来生成 SQL，远比直接生成 SQL 表现好**。智能体调用这个 CLI 而不是手写 SQL；模型负责模糊的那部分（理解问题、选对输入），确定性工具负责把输入变成正确的 SQL。生成器做两件事：数据源选择与查询生成。Meta 内部常有多个表都能算出同一指标（如 cube 表 vs 事实表），生成器内置了按表保留策略、分区行数、存储层优先排序数据源的逻辑。

### Analyze Model：「发生了什么」之后的分析配方

分析配方把资深分析师的调查程序编码下来——「什么在驱动留存下滑？」「这个指标为什么涨？」——配方带着确定性查询生成器走完流程，LLM 负责分析总结结果。目前配方擅长回答指标变动、漏斗流失归因、在新产品的用户人口统计维度里寻找 PMF 这类问题。Meta 的经验是：**编码了程序的配方，比让智能体自由发挥可靠得多。**

### Consume Model：自己长出来的看板

最后是消费层。因为每个库都有标准 YAML 输出与确定性查询生成器，看板这类消费体验可以轻松驱动——指标调查、增长、留存、漏斗分析都有现成模板，看板几乎是自己组装自己的。

## 接下来呢？

Meta 的 AI 原生分析栈仍在早期：扩展库支持更多模式、自动生成更丰富的语义模型、产出更多分析配方。目标说来简单、做到很难：Meta 的任何人都应该能描述自己想度量什么，然后得到一个正确的、受治理的答案——无论是问同事还是问智能体。

对任何分析组织，教训都一样：**找到你的模式，尽早标准化，好好写文档。** 现在肯做这些不光鲜的标准化工作的团队，就是将来智能体真正能干活的团队。你无法自动化一团混乱。一小撮定义清晰的模式，编码一次，就是几乎可以构建一切的地基——包括那些开始替我们干活的智能体。

# 《Scaling AI-Native Analytics Patterns at Meta》的发芽报告

## 材料核心

Meta 分析团队发现产品分析存在幂律：少数度量模式覆盖绝大多数真实需求，于是把这批原语固化成参数化、受治理的 Analytics Libraries（仅指标物化库就支撑 3,250+ 生产管道，全目录 9,000+），并让每个产出物自带智能体可读的 YAML 数据模型。在此基础上，智能体获得了三层对等能力：自然语言 skills 建管道、调用确定性 CLI 生成 SQL（模型管模糊理解、工具管精确翻译）、以及编码了资深分析师程序的分析配方。核心洞察是：智能体的上限不由模型决定，而由数据资产的整洁程度决定——标准化是智能体化（agentization）的前置工程。

## 发芽 01：让智能体不写 SQL，反而更聪明

### 种子

Meta 发现 LLM 直写 SQL 会「看起来对、返回错」，于是不提升提示词，而是造了一个确定性查询生成器暴露成 CLI，让智能体调用工具而非手写 SQL。

### 故事

文章描述的分工很精确：模型负责它擅长的模糊部分——理解问题、选择输入；确定性工具负责它擅长的精确部分——把输入翻译成正确 SQL。这个结构和站内 context engineering 一文的「把不可靠环节从模型手里拿走」完全同构：与其训练模型不出错，不如让出错变得结构上不可能。

### Aha 瞬间

「智能体学会用一个简单 API 来生成 SQL，远比直接生成 SQL 表现好」——工具化不是能力的妥协，而是能力的放大器。提示工程的终点，往往是把提示工程本身消灭掉。

## 发芽 02：标准化是自动化的入场券，不是敌人

### 种子

文章坦承标准化的边界：它只适用于重复出现、高信任的度量；把早期探索硬塞进僵硬 schema 会扼杀发现。

### 故事

Meta 没有把「标准」与「探索」对立起来，而是给了判定准则——只有当广泛复用足以抵消维护成本时才固化模式。这意味着组织的分析资产天然分成两层：受治理的复用层与自由探索层，智能体主要吃前者。

### Aha 瞬间

「你无法自动化一团混乱。」这句收尾把 AI 落地的因果链倒转了：企业 AI 项目的瓶颈常常不在模型选型，而在有多少资产配得上被自动化。先整理，再智能。

## 发芽 03：数据模型是给智能体的「用户界面」

### 种子

每条管道除物化表外，还输出一份 YAML 格式的强类型数据模型（维度/指标/数据源），专门供查询生成消费。

### 故事

过去数据建模服务的是人——BI 工具、报表读者。Meta 的 YAML 模型则把 schema 当作智能体的交互界面：模型可读、可注册、可发现，智能体「表现得像个领域专家」的前提，是它面对的是自描述的资产目录而非裸管道。

### Aha 瞬间

当智能体成为数据资产的一等消费者，「文档质量」就从美德变成了接口契约——写给智能体读的文档，比写给人读的文档更要求严谨，因为它没有直觉可以兜底。
