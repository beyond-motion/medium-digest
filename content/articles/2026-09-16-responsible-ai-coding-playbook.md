# 负责任 AI 编码实操手册

> 原文：[The Responsible AI Coding Playbook](https://medium.com/@aaleenmirza110/the-responsible-ai-coding-playbook-bfb34bac2d32)

---

## 不谈哲学，只谈周二下午

上一篇（系列第一篇）讲心态：为什么人们对 AI 犹豫，以及为什么「负责任的 vibe coding」优于盲目信任与盲目排斥——那篇刻意非技术，讲的是怎么想。

这一篇讲怎么干活。

因为事情是这样的：「评审逻辑，别只看语法」是好建议，**也是你前三次听到时毫无用处的建议——因为没人告诉你怎么做。**你到底该找什么？你往 Cursor 里实际输入什么才能让它思考规模问题？CLAUDE.md 里该放什么？

所以这次没有哲学。只有配置、prompt、清单，和一个带真实 React + FastAPI 代码的仓库（github.com/Aaleen110/ai-coding-toolkit），让你看见而不是想象。

## 一、停止重复自己——给 AI 常驻上下文

作者对 AI 工具用法做的最大升级，不是一条更好的 prompt，而是**把规则从 prompt 里整个搬出去**。

Claude Code 与 Cursor 都支持，概念上一致：**Claude Code 每次会话开始时读取 CLAUDE.md**——项目约定、不可协商项、没问过就不该碰的东西。官方文档的长话短说：保持具体，因为模糊的指令被执行得忽左忽右，具体的不会。**Cursor 用 `.cursor/rules/*.mdc`**——markdown 规则可以按文件模式（globs）限定作用范围，或 `alwaysApply` 全局生效。Cursor 也会读项目根的 AGENTS.md，与 Claude Code 读 CLAUDE.md 同理：不同工具、同一份不可协商项，一起提交进仓库，谁都不会漂移过时。

示例仓库的根目录有 CLAUDE.md / AGENTS.md，`.cursor/rules/` 下三个规则文件：一个通用；一个限定 `frontend/**`（React 约定）；一个限定 `backend/**`（FastAPI 约定）。

这些东西一旦存在，你就不用在每个 prompt 里打「记得用 Pydantic schema，别用裸 dict」——**它本来就是真的。**这就是「碰巧有时写得还行的 AI」与「真正被 onboard 进你代码库的 AI」的区别。

## 二、像写工单一样写 prompt，不是许愿

对比这两条：

> 「加一个更新用户邮箱的端点。」

> 「加一个 PATCH /users/{id}/email 端点。保存前验证格式与唯一性。用户不存在返回 404，邮箱被占用返回 409。遵循 users.py 里的既有模式。为以下情况加测试：成功、重复、用户缺失。」

第二条多花大约 30 秒。它同时消掉了模型本来会做的几乎每一个错误假设——**而大多数「AI 写了有 bug 的代码」的故事，源头正是错误假设。**

两个杠杆远高于成本的 prompt 追加（仓库 `docs/prompting-guide.md`）：

- **可扩展性 pass**：「初稿之后，告诉我这个表有一千万行时会坏什么。」**在它写代码之前**问——你常常直接得到更好的初稿，因为它知道这个问题要来。
- **安全 pass**：「一个恶意用户能往这里发的最坏东西是什么，代码处理了吗？」问起来便宜，抓到缺失的鉴权检查与未验证输入的频率超乎想象。

还有一个容易被跳过的，因为感觉在拖慢你：**凡是涉及多个文件的任务，先让它规划**——「先别写代码，列出你会碰哪些文件、为什么，然后等我。」读 10 秒钟的计划，好过花 10 分钟去拆解一个在第二个文件就跑偏的 200 行 diff。

## 三、评审 AI 代码是另一份工作，不是评审 PR

同事的 pull request 即使错了，也反映理解。AI 的输出可以**流畅且自信地错**——它优化的是「看起来可信」，不是「正确」。所以要用不同的方式评审。特别盯四类：

- **静默回退**——`except: pass`、空 catch、用一个默认值悄悄掩盖真实失败；
- **假测试**——断言 `true === true`，或者把本该测试的那个东西 mock 掉；
- **发明的 API**——你实际用的那个库版本上根本不存在的方法；
- **硬编码值**——本该是常量或配置的地方，抄自模型推理时所依据的那个示例。

完整清单在 `docs/code-review-checklist.md`。作者原话：「我真心希望你偷走的是这个文件，而不是我的 prompting 技巧——粗心使用 AI 造成的真实伤害，大部分发生在这里。」

再从那个文件里偷一样：**用不同的模型来评审，而不只是你自己。**Claude 评审 Cursor 写的东西（或反过来）不共享第一个模型的盲点，也对它刚采用的方案没有情感依附。它不能替代你自己读 diff——它是第二道、带着不同偏置的关卡，而且加进习惯的成本很低。

## 四、把测试写进 prompt

先要测试用例，再要实现：「在你写这个端点之前，列出你会为它写的测试用例。」你通常会在它还只是一行修复时就抓住缺失的边角情况，而不是等它变成一张 bug 报告。

然后，不可协商地：**每次改动之后跑真实的完整测试套件，不只是改动文件附近的那几个。**AI 编辑有个习惯：悄悄弄坏两个文件之外它从没看过的地方。

示例仓库 `backend/tests/test_users.py` 展示了作者给每个端点用的模式：happy path / 坏输入 / not found / conflict。那个 PATCH email 端点又加了两个容易忘的：完全没有身份时 401；「登录了，但这不是你的记录」403。**authenticated 与 authorized 的这个区别，正是 AI 写的鉴权代码悄悄不足的地方**——所以它配得上一个独立测试，而不是被折进笼统的「处理错误」。

## 五、知道什么不该交出去

有些代码值得你自己写得慢一点，而不是逐行评审 AI 的尝试：**auth/session 逻辑、支付处理、任何碰生产数据迁移的东西、任何涉密码学的东西。**在这些地方用 AI 解释方案、评审你的代码——而不是让它写初稿。`docs/security-checklist.md` 有更完整的清单。

## 六、让它展示工作

一个安静地比上面任何一条都更省时间的习惯：**让 AI 记录它自己的改动。**任何非平凡的改动之后，要求一份简短的 change log——碰了哪些文件、为什么、它假设了什么、该复查什么——存到 `docs/changelogs/`（模板在 `docs/ai-change-log-template.md`）。

成本几秒钟。回报发生在两周后某处坏了、你需要知道一段逻辑为何存在的时候——那时「AI 写的」不是一个任何人都能用的答案。附带的好处：当 AI 能回忆起某次改动的原因时，它调试得也更好。

## 七、前端和后端需要各自的规则

通用的「写好代码」类指令迁移性很差。React 需要的与 FastAPI/Node 需要的是真不一样的东西，所以要分成两本手册：

- **React**——props 带类型（不许 any）；取数走 hooks 不写内联 fetch；显式的 loading/error 状态；列表用真 key；测试与组件同置。
- **FastAPI**——路由保持薄；业务逻辑放 service 层；每个响应都有 Pydantic `response_model`；用依赖注入替代重复样板。

在仓库里它们住在 `.claude/skills/` 与 `.cursor/skills/`——两个工具都会在克隆仓库的那一刻自动加载项目技能，不需要手工引用。它们还被蒸馏进 `.cursor/rules` 的常开限定版。**同一份事实源，三处呈现**——你或队友拿起哪个工具都一样。

## Cursor 还是 Claude——都用

总被问到这个问题，诚实的答案是：它们擅长重叠但略有不同的事。**Cursor** 的内联编辑与 tab 补全，在快、看得见 diff 的编辑器内改动上难以击败。**Claude Code** 用于任何需要先规划、跨多个文件、或需要在动手前把「为什么」想清楚的任务。两个都不替代你自己评审输出——这一步无论选谁都不会被自动化。

## 加分项：也别让 AI 写你的 commit message

自己写 commit message，是代码上线前的最后一道检查点。它是那个迫使你真正看 diff、并用自己的话写下「改了什么、为什么」的时刻。跳过它，你就跳过了把「AI 写了这个」变成「我评审过了、我负责这个」的唯一一步。经验之谈：这是个不起眼的小习惯，干的活比看上去多。

## 去把仓库克隆下来吧

这些没有一样是复杂的。大体上就是：**有目的地、用文字、保持具体——而不是指望模型读心。**仓库里所有东西已经接在一起，克隆、跑测试、把不适合你技术栈的部分拆掉。

抄之前的诚实提示：示例应用本身（内存数据、没有真数据库）是教学样例，不是生产起步模板；上面那条鉴权条件只是其中一个实例。**规则、技能与清单尽管整份拿走；把应用当成「遵守它们」长什么样的一份已解示例**，而不是拿去部署的东西。

如果第一篇是「信任 AI，但保持掌控」，这一篇就是「保持掌控」在某个周二下午的实际样子。

# 《The Responsible AI Coding Playbook》的发芽报告

## 材料核心

这篇实操手册把「负责任的 vibe coding」落到七件具体事上：规则搬出 prompt 进常驻文件（CLAUDE.md/AGENTS.md/.cursor/rules，按目录限定作用域）；prompt 写成工单（端点、校验、状态码、测试点一次说清）；加「扩展性 pass」与「安全 pass」两道追问、跨文件任务先要计划；评审 AI 代码专盯静默回退/假测试/发明 API/硬编码四类，并用异构模型做第二道不同偏置的评审；实现前先要测试清单、每次改动跑全量套件、单独测 authenticated 与 authorized 的分野；auth/支付/迁移/密码学不交初稿；让 AI 写 change log 自留档案；自己写 commit message 作为最后的「我评审过」仪式。

## 发芽 01：规则的位置决定它是否生效

### 种子

最大的升级不是更好的 prompt，而是把规则从 prompt 里整个搬出去——「它本来就是真的」与「每个 prompt 里再叮嘱一遍」是两种不同的现实状态。

### 故事

文章给出三层落点：仓库根的 CLAUDE.md/AGENTS.md 承载不可协商项；.cursor/rules 的限定版按 frontend/**、backend/** 分治（React 与 FastAPI 需要的确实不同）；.claude/skills/ 与 .cursor/skills/ 克隆即自动加载——同一份事实源三处呈现，谁都不会漂移过时。

### Aha 瞬间

指令的可靠性是位置的函数：活在对话里的规则会随对话蒸发，活在仓库里的规则随代码 checkout——把纪律从「提醒」升格为「环境」，一致性才不依赖记性。

## 发芽 02：错误假设是 bug 的上游，prompt 是上上游

### 种子

「大多数『AI 写了有 bug 的代码』的故事，源头正是错误假设」——工单式 prompt 多花的 30 秒，消掉的是模型本来会做的每一个擅自决定。

### 故事

手册把这道防线布在三个时间点：写之前要计划（「列出你会碰哪些文件然后等我」，10 秒读计划好过 10 分钟拆 diff）；初稿前预告追问（「告诉我这个表有一千万行会坏什么」——因为它知道问题要来，初稿就更好）；实现前先要测试清单（边角情况还是一行修复时就被抓住）。三件事共享同一逻辑：把「事后发现」前移为「事前约束」。

### Aha 瞬间

与 AI 协作的杠杆点不在改产出，而在改提问——错误在它发生前一个环节被命名，修复成本就下降一个数量级。

## 发芽 03：自己写 commit message，是所有权的最后一道闸

### 种子

「自己写 commit message，是把『AI 写了这个』变成『我评审过了、我负责这个』的唯一一步」——跳过它，前面所有的评审都可能只是名义上的。

### 故事

这条加分项排在全部技术建议之后，却是整篇手册的落点：写 message 的动作迫使你真正读完 diff、用自己的话复述「改了什么、为什么」——它无法被委托，因为它的产出物（你的复述）本身就是理解的证明。与之配套的是「让 AI 写 change log」：机器留档案负责可回溯，人写 message 负责可问责。

### Aha 瞬间

自动化时代的所有权不是一种状态，而是一组必须亲手完成的动作——能被委托的都可以自动化，而「我看过、我懂、我认」这个动作一旦外包，系统里就再没有人在法律与事实意义上拥有这段代码。
