# 写了 60 年代码的老程序员：别读 AI Agent 的代码

> 原文：[A 60-Year Coder’s Rule: Don’t Read AI Agent Code](https://medium.com/@ai-engineering-trend/a-60-year-coders-rule-don-t-read-ai-agent-code-f9ce98563626)

---

## Uncle Bob 的争议主张

Uncle Bob Martin 写代码已经快 60 年了。最近他分享了一个颇具争议但锋利的观点，讲怎么跟 AI 编码 agent 协作——在开发者社区掀起不小的波浪。他的原话：

> 我不读任何 AI agent 写的代码。这是我发现唯一能真正利用它们生产力的方式。
>
> 相反，我把 agent 关进极端的约束里：单元测试、Gherkin 场景、正式 QA 流程、质量指标、变异测试、测试覆盖率目标，等等。最终我能信任它们生成的代码，因为它必须通过这里的每一道关卡。

核心思想？**别再逐行读 AI 生成的代码，改用一面测试墙来保证质量。**开发者 0xAA 把这套哲学做成了开源工具 old-coder，它已经开始改变工程团队与 AI agent 的协作方式。

一条命令安装：

```bash
npx skills add https://github.com/amazingang/old-coder
```

它可以与 Claude Code、Codex CLI、Cursor、Aider 或你已有的任何自定义 agent 工作流无缝配合。就是纯 markdown，不需要什么花哨依赖。

## 工作流比听上去完整

old-coder 不只是「跑测试、吐报告」。它把一个完整的测试驱动开发（TDD）循环直接嵌进你的 agent 工作流：

```text
SPEC → RED → GREEN → REFACTOR → GAUNTLET → EVIDENCE
```

作为人类工程师，你只需要审两样东西：

- **SPEC（编码之前）**：agent 先生成一份清晰的测试计划，带具体行为示例和所需工具。你要做的只是批准它。
- **EVIDENCE（编码之后）**：一份完全可复现的报告，记录代码如何通过了每一道检查，全部来自一次干净的运行。你可以用一条命令重新验证整个过程。

中间的一切？agent 自己搞定：写测试、看着它们失败、写代码让它们通过、重构，然后跑完全套质量关卡。

## GAUNTLET（难关）里到底有什么

这不是某个含糊的「10+ 项检查」清单。它有 **8 道核心关卡**，每一道都为回答一个具体的关键问题：

| 检查 | 它验证什么 |
| — — | — — |
| 全测试套件运行 | 有没有东西被弄坏？ |
| 类型检查 + Lint + 复杂度分析 | 有没有明显 bug？代码是不是没法读的意大利面？ |
| 变更行覆盖率 | 新代码的每一行都被测试执行过吗？ |
| 变异测试 | 故意往代码里注入 bug，现有测试能抓住它们吗？ |
| 属性测试（Property-Based Testing） | 面对成百上千个随机输入变体，规则还成立吗？ |
| 真实环境执行 | 代码真的能在测试框架之外跑起来吗？ |
| 供应链与密钥扫描 | agent 有没有偷偷塞进恶意依赖或泄露 API key？ |
| 测试套件健康度 | 测试本身稳定吗？换个执行顺序还能通过吗？ |

在这些核心检查之上，还有按项目风险等级定制的可选领域检查——规则是**投入随风险放大**：修个 typo 只跑少数基础检查；但如果代码涉及支付、认证、用户数据或并发流程，每道检查都全速运行——agent 甚至得用恶意攻击输入来测试自己的代码。

## 怎么防止 agent 在检查上作弊？

既然检查是 agent 自己跑的，规则就被有意定得死板，防止自欺：

- 永不为了让测试通过而削弱测试
- 永不报告一个没有实际运行过的检查
- 任何未经验证的代码标记为 unverified——永不伪造通过
- 如果 spec 没经人批准，报告必须明确说明并降低置信分

项目对自身局限也很坦白：**这道难关只能证明代码符合已批准的 spec，不能证明 spec 覆盖了产品需要的每个边界情况。**这正是为什么 spec 的人工评审仍然必不可少。

## 一个能跑的 demo 已经内置

仓库自带一个限流器（rate limiter）的完整 demo。结果本身会说话：17 个测试、100% 分支覆盖率、8/8 注入 bug 全部被抓。工作流甚至抓到了一个逃过初始输入校验的真实细微 bug：一个会导致生产环境异常行为的 NaN 时间窗。

你可以自己复现完整的 demo 报告：

```bash
cd demo-rate-limiter
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt -e .
./tools/gauntlet.sh
```

## 回到 Uncle Bob 的原始讨论

有人问他：在 AI agent 的时代，代码质量还重要吗？他的回答：**比以往任何时候都重要。**混乱、无结构的代码会让 agent 的速度急剧下降。他亲眼见过 AI agent 在烂泥潭一样的代码库里原地打转，他自己不得不下场清理。这就是为什么对函数大小、圈复杂度和测试覆盖率执行严格约束如此重要——它让 agent 保持流畅、多产。

另一个常见问题：谁来监督约束本身？Uncle Bob 的回答很简单：你来。你是工程师，最终责任在你。你监督 AI agent 的方式，就跟监督一个初级工程师一样：在高层保持参与，但不需要读他们写的每一行代码。

如果你一直在纠结要不要逐行读 AI agent 写的代码，试试这个思路：**别读了，让代码先闯一遍难关。**

# 《A 60-Year Coder’s Rule: Don’t Read AI Agent Code》的发芽报告

## 材料核心

Uncle Bob 的主张把「信任 AI 代码」问题整个搬了家：不靠人眼逐行审读，靠极端约束——SPEC 评审、TDD 循环、8 道质量关卡、防作弊铁律。开源工具 old-coder 把它落成 SPEC → RED → GREEN → REFACTOR → GAUNTLET → EVIDENCE 的流水线，人只审两端的规格与证据，中间全自动。

## 发芽 01：评审的对象从代码换成了证据链

### 种子

人只看两样东西：编码前的 SPEC，编码后的 EVIDENCE——一份一条命令就能重新复现的验证报告。

### 故事

文章的工作流里，中间的写测试、看失败、写实现、重构、闯关卡全部由 agent 自主完成；人类评审从「读代码找问题」变成「批准计划 + 核验证据」。demo 里那份 17 测试、100% 分支覆盖、8/8 注入 bug 被抓的报告，就是信任的载体。

### Aha 瞬间

这跟学术界的机制同构：你不需要重做实验来信任一篇论文，你需要的是可复现的方法与数据。当 AI 产出快过人能读的速度，信任的单元就从「作品」换成「验证过程的记录」——谁掌握证据链，谁掌握质量。

## 发芽 02：变异测试——给测试本身做的压力测试

### 种子

8 道关卡里最锋利的一道问的不是「代码对不对」，而是「你的测试抓得住 bug 吗」：故意往代码注入 bug，看测试能不能全部抓住。

### 故事

文章的 demo 直接给了量化答案：8/8 注入 bug 被现有测试捕获。配上变更行覆盖率（新代码每行都被执行过）与测试套件健康度（换序执行仍通过），测试墙自己也被审了三层。

### Aha 瞬间

高覆盖率不等于测试有效——覆盖率只说明代码被「碰到」过，变异测试才说明测试有「杀伤力」。在用 AI 批量生成代码和测试的时代，后者的权重应该远高于前者： agent 完全可以写一堆永远绿着的无效测试，只有注入 bug 才能拆穿。

## 发芽 03：乱代码现在连 AI 都跑不动了

### 种子

Uncle Bob 的观察：混乱无结构的代码库会让 agent 原地空转，烂到需要人先下场清理，AI 才能干活。

### 故事

他把这个现象直接转译成了约束的必要性：函数大小、圈复杂度、测试覆盖率这些老派纪律，新理由是「让 agent 保持流畅多产」。修 typo 只跑几道检查，碰支付认证并发就全速闯关加恶意输入测试——投入随风险放大。

### Aha 瞬间

代码质量完成了一次身份转换：从「工程师的美德」变成「AI 生产力的基础设施」。拒绝重构烂代码的团队，过去是让新人痛苦，现在是直接掐断自己 agent 的产能——技术债第一次有了即时的、可感知的生产力账单。
