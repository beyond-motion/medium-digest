# 代码只是评审的一半

> 原文：[The Code Is Only Half the Review](https://medium.com/@aludanyi/the-code-is-only-half-the-review-88b7cd61eab6)

---

## 评审不是验货

代码评审常被描述成一种检查（inspection）：有人来看代码，试图找出缺陷。这种描述吸引人，因为它容易理解也容易度量。但它大概是有效评审中最无趣的部分。如果缺陷总是等到代码进入评审才被发现，组织其实已经学到了一件不愉快的事：**它的开发流程放任这些缺陷活到了一轮工作的终点**。检查也许能抓住它们，但抓住不等于弄明白它们为什么会出现。

LLM 的到来让软件工程里一个老真相变得更难忽视：代码只是一个大得多的过程的可见结果——背后是关于系统的假设、约束、决策和理论。因此有效的代码评审首要的不是缺陷检查，而是一个机会：去发现代码为什么长成这样、它暴露了架构的什么、团队误解了什么或留下了什么没说破的。

## 代码是心智过程的可见结果

面对人类作者，这些知识中有不少可以通过对话找回。你可以问：「你为什么这么写？」答案可能揭示一个假设、一个误解、一个设计约束、一个权衡，或者只是作者忘了的东西。这场对话有价值，因为代码只是一个大得多的心智过程的可见结果——我们不只是在检查结果，而是在尝试重建它背后的推理，好增进对系统的理解。

这在人类软件工程里本就如此。程序员不是凭空写出代码的，他们头脑里有一套关于系统的理论。Peter Naur「编程即理论构建」的思想在这里很有用：维护一个程序，就是维护对「程序意味着什么、为什么这样组织、各部分如何拼合」的理解。源代码是这套理论的表达，但**不等于**理论本身。

LLM 把这个问题推到了一个特别显眼的位置，因为它的输入和输出之间可以隔着巨大的距离。给它一份规范、一个仓库、几份架构文档和一组示例，它可能产出一个像样的实现——甚至可能是对的。但「正确」不能告诉我们：它到底是理解了架构，还是撞见了一个不变量、模仿了某个偶然的惯例、复制了局部模式，或者补偿了一个没人明说过的不成文约束。这个区分对学习来说至关重要。

## 有用的单元是「交互」，不是代码

于是有了第一条原则：**AI 辅助开发过程中有用的单元，不是生成的代码，而是产生它的那次交互。**

代码是输出。prompt、相关的仓库状态、架构约束、规范、示例、测试、决策、工具结果、此前的修正与反馈——这些构成了产出该输出的条件。条件一旦消失，团队手里只剩结果，却丢了理解它所需的大部分证据。

## 一个不必要的抽象，五种病根

想象 LLM 在某段代码里引入了一个抽象。评审时团队发现这个抽象并不必要，还把设计搞复杂了。传统评审会把它删掉；面向学习的评审会追问第二个问题：**LLM 为什么认为这个抽象是合适的？**

也许仓库里已经有二十个类似的抽象；也许规范里的措辞强烈暗示了它的存在；也许某个现有接口让它显得必要；也许模型凭空推断出一条没人想要的需求；也许架构文档和实际代码互相矛盾。每种解释指向一种不同的改进。

重要的发现可能跟被评审的那几行代码毫无关系。如果模型因为架构在仓库里表达得糟糕而反复犯同一个错，修生成的代码几乎无关痛痒——组织该改进的是架构的表达方式。因为规范含糊就改规范；因为测试奖励了错误行为就改测试；相关信息都给到了还犯错，才轮到改进 prompt 或交互方式；而如果人类反复接受同样的坏设计，问题也许出在团队自己对系统的理论里。

## LLM 是假设的来源，不是更快的打字员

这给了我们一个更有用的 AI 团队模型：LLM 不该被简单当成打字更快的员工。它是关于系统的**另一个假设来源**——生成的代码是一个假设，对规范的解读是另一个，它提出的架构、抽象的选择、测试策略、对依赖的识别都是假设。团队拿这些假设跟自己的理解、跟运行中系统的行为对照。

AI 的「为什么」因此有价值，但要小心「为什么」指什么。我们不需要一个无法验证的、关于模型内部推理的故事；我们需要的是一份**可审计的记录**——哪些输入和中间决策实质性地影响了输出。

比如，不要只存一句「实现对账逻辑」。开发记录可以更接近这样：「使用现有的 TransactionMatcher 抽象实现对账，因为仓库里已有它的三个消费方、规范要求按外部交易 ID 匹配、而且测试暗示外部 ID 可能重复。我考虑过引入新的对账抽象但放弃了，因为现有抽象已经拥有相关的不变量。」

现在评审有东西可抓了。团队可以检验这些前提是真是假：前提是假的，评审发现了一个误解；前提是真的但实现错了，团队发现了一个设计问题；推理是健全的，实现就变得更好理解、更好维护。

## 反馈要改变下一次的环境

同样的机制可以反向运转。人类评审者说：「我们不要这个抽象。对账属于事务边界，因为不变量是事务局部的。」这条反馈不该只改这一个补丁——它应该成为后续 AI 交互可用的信息。否则组织就是在反复教同一课、反复付同一笔学费。

这正是 AI 辅助开发可能真正不同于「给团队加一个 AI 程序员」的地方：**评审应该修改产生下一份 AI 代码的环境。**反馈循环变成：上下文 → 假设 → 实现 → 执行 → 评审 → 学习 → 改进的上下文 → 下一个假设。

关键词是上下文。如果评审产出的知识没有随后到达生成下一个实现的人或系统手里，那几乎等于没有组织学习——团队修正了代码，却没有修正产生代码的过程。

这也解释了为什么把和 LLM 的每段对话都倒进数据库解决不了问题。信息多不等于上下文好。面对几千页历史对话的 LLM，可能还不如拿到一个维护良好的架构模型、一小组显式决策、相关约束、已知不变量和近期反馈的 LLM。**目标不是保存一切，而是保存那些改变了团队系统理论的东西。**一次开发可以记录：相关规范、架构约束、假设、考虑过的替代方案、重要的仓库证据、用作反馈的测试、评审中的重大修正、以及应当影响未来工作的决策。格式不重要，原则才重要：信息要人能读懂、AI 能用上。

## 评审变成科学实验

这能让代码评审有趣得多。开场白不再是「这是 diff，找问题」，而是：AI 产出这段代码时，它相信系统是什么样的？这些信念里哪些和我们一致？哪些相左？哪些假设此前从未被写下来？运行中的系统告诉我们什么？我们该改代码、测试、架构、规范，还是共享知识？

这更接近科学式的学习，而非检查。代码成了对系统理论做的一次实验：测试提供反馈，评审暴露分歧，得到的知识修改理论，于是也修改下一次实验。

## 一个双向的学习循环，和一张未成文架构的地图

这里有一个重要的不对称：即使 LLM 什么都没学到，人类也能从 LLM 身上学到东西——发现模型对某条需求的解读不同、推断出一个我们从没注意到的架构模式、暴露文档与实现之间的不一致。但更大的机会是双向循环：人了解系统，人了解 AI 的局限与倾向，而 AI 为未来的工作获得更好的上下文。

最后这部分别跟「LLM 会从单次评审中永久学习」混淆——模型底层参数可能一个都没变。能变的是模型周围的上下文与环境：仓库指令、架构知识、示例、测试、检索到的决策、工具配置。实践中，这就足以让下一次交互表现得像整个系统学过了。

还有一层更深的推论。如果 LLM 反复生成「局部合理、全局不一致」的代码，未必说明它编程差——可能说明**架构主要存在于资深工程师的脑子里**。干了五年的老工程师立刻知道某个类不该被某个子系统调用、某个看似多余的数据库调用其实在保护一个不变量、某段丑代码存在是因为一个谁也不信任的外部系统。这些都不写在语法里。AI 之所以暴露这个知识空洞，是因为它会心安理得地在它能访问到的信息上干活。

于是我们得到一个可能很强力的架构诊断工具：**凡是 AI 反复需要人来解释、而系统本身无法充分传达的地方，我们就可能发现了一处未成文的架构。**恰当的回应未必是再写一份文档——有时答案是更好的命名、更清晰的边界、可执行的测试、更简单的架构、更强的不变量，或者代码里更好的表达。文档只是传递理论的方式之一。

## 一个可以被证伪的命题

这套理论给了我们可检验的预言。如果它是对的：把 AI 代码评审主要当缺陷检测的团队，改进主要体现在修好一个个单独的输出；而保存并复用评审中重要上下文与学习的团队，改善会出现在缺陷率之外——重复错误率、评审延迟、架构一致性、以及后续 AI 工作所需的人工解释量。

更具体地：如果某一类错误在之前的评审里明确纠正过、之后还是反复出现，那学习循环就在某处断了。也许反馈没被记录，也许记录了但检索不到，也许上下文在但没起作用，也许人类的结论本身就是错的。这些全都是可检验的可能。

最强形式的假设不是「给 AI 更多上下文它就写出更好的代码」——那太含糊，没用。它是这样：**当开发与评审产出的信息，系统性地改变了后续开发决策所依据的上下文时，一个软件团队才会变得更强。**

LLM 让这条原则异常可见，因为它的上下文可检查、可重建、可有意修改。但原则同样适用于人。好的评审改变开发者知道什么，好的架构改变开发者需要知道什么，好的测试改变团队能发现什么，好的流程改变哪些信息能活到下一次迭代。

也许这正是「检查」与「评审」的区分如此重要的原因。检查问的是：这一个输出可以接受吗？评审问的是：**这个输出居然存在，这件事能教给我们什么？**

面对人类作者，我们可以直接问作者；面对 LLM，我们需要保存足够的交互记录来重建相关假设与决策。但目标相同：不只是让这段代码更好，而是让团队对系统的理论更好。

一旦做到这一点，一场代码评审最有价值的产出可能根本不是修正后的代码——而是人和 AI 在写下下一行代码之前，所知道的东西发生了变化。

# 《The Code Is Only Half the Review》的发芽报告

## 材料核心

这篇文章把代码评审从「缺陷检查」重新定义为「理论学习」：代码只是心智过程（或模型交互）的可见结果，有用的评审单位是产生代码的那次交互——prompt、约束、规范、反馈这些条件。AI 辅助开发的反馈循环要求评审产出的知识流回下一次生成所依据的上下文；而 LLM 反复需要人工解释的地方，恰恰标出了组织里未成文的架构。

## 发芽 01：AI 是组织隐性知识的 X 光机

### 种子

LLM 只会老老实实地使用它能访问到的信息——它不会脑补老工程师脑子里那五年的经验。

### 故事

文章指出，某类不能这样调用、某个看似多余的调用其实在保护不变量、某段丑代码是为了迁就一个不可信的外部系统——这些判断只存在于资深工程师的头脑里，从不出现在语法中。人类工程师靠口口相传绕过这些坑，LLM 则一头撞上去，把「局部合理、全局不一致」的代码摆上评审桌。

### Aha 瞬间

AI 反复需要人来解释的地方，就是未成文架构的精确坐标——这是免费的架构审计。而修补方式可以不是写文档：更好的命名、更硬的边界、可执行的测试，都是把隐性理论「写进系统本身」的手段。AI 犯的错，其实是在给组织的知识债拍 X 光片。

## 发芽 02：别保存一切，保存改变了理论的东西

### 种子

上下文的质量不等于信息的数量——几千页对话记录可能不如一页维护良好的决策清单。

### 故事

文章给出的对照很尖锐：喂给模型全量历史对话，可能比不上给它「架构模型 + 一小组显式决策 + 相关约束 + 已知不变量 + 近期反馈」。判据落在「它是否改变了团队对系统的理解」上：评审里那句「对账属于事务边界，因为不变量是事务局部的」，值得记下来；而促成它的中间二十轮调试对话，不必。

### Aha 瞬间

这不仅适用于 AI 上下文管理，也适用于人的知识管理：记录的取舍标准不是「以后可能有用」，而是「它是否修正了我们对系统的理论」。按这个标准过滤，知识库才不会膨胀成没人检索得动的对话坟场。

## 发芽 03：把每次评审当一场实验来设计

### 种子

LLM 的每个输出都是关于系统的一个假设——评审的任务是检验假设，而不是给成品打分。

### 故事

文章给出的评审开场白完全不同于「这是 diff，找问题」：AI 产出这段代码时相信系统是什么？哪些信念与我们一致、哪些相左、哪些假设从未被写下？检验前提的真假可以直接分类发现：前提为假是误解，前提为真而实现错是设计问题，推理健全则是可维护的好代码。

### Aha 瞬间

「发现误解」比「发现缺陷」值钱——缺陷只属于这一个补丁，误解属于整个生成它的流程。把评审从验收环节改造成实验环节，团队的每一次生成都在为系统理论积累证据，下一次生成自然站在更好的起点上。
