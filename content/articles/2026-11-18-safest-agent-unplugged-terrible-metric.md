# 最安全的 Agent 是拔掉电源的那个。而那是个糟糕的产品指标。

> 原文：[The Safest Agent Is Unplugged. That Is a Terrible Product Metric.](https://medium.com/@SebastianMateusP/the-safest-agent-is-unplugged-that-is-a-terrible-product-metric-b9b44e31dd8b) — Sebastian Mateus

---

## 一个零危险、零产出的 agent

测量有用工作与对抗性结果，要放在一起测。

**我发明了一个零危险工具调用的 agent。它同时也零有用产出。**

它从不发邮件（没有钓鱼风险），从不写文件（没有数据外泄风险），从不调用任何工具（没有注入风险），甚至从不联网检索（没有供应链风险）。按「危险事件计数」这个最常见的 agent 安全指标，它是满分。按任何一个客户真正付钱想要的指标，它是零分——一台昂贵、安静、什么都不做的摆设。

## 为什么单边安全指标必然奖励不作为

这就是把安全当独立优化目标时会发生的事：**指标会奖励拔掉插头。**你约束得越狠，危险调用越少，有用工作也越少——而仪表盘上只有前者的曲线在下降。

## 有用工作与对抗性结果：同一个度量

正确的做法不是给安全降权，而是**让有用工作与对抗性结果出现在同一个度量里**。一个 agent 应该在「完成了多少真实任务」与「制造了多少危险事件」的联合分布上被评估：前者是分子，后者不是可以独立最小化的分母——两者共享同一个行动预算，每一步工具调用既可能产出也可能闯祸。任何只考核其中一项的团队，最后得到的都是另一项的反面。

实际的评估问题因此变成一对而不是一个：

- 这周它完成了多少真实工作？（任务完成率、被用户接受的比例、下游被引用的次数）
- 这周它造成了多少需要人来收拾的局面？（被拒绝的工具调用、回滚、误报升级）

两个数字各自单独看都可以被游戏化：只报第一列，你会得到一个把危险操作伪装成成功任务的黑洞 agent；只报第二列，你会得到刚才那个拔了插头的圣人。**并排、同预算、同一时间窗，才是完整的一张安全-产出报表。**

一个从不闯祸也从不干活的 agent，和干了活也闯了祸但净产出为正的 agent，必须能被这两个数字分开。前者是安全的幻觉，后者才是可以托付工作的同事——而把它们混淆的报表，会同时冤枉好人和奖励懒汉。**安全的进步应该是「同样多的有用工作、更少的对抗性结果」，而不是「更少的对抗性结果」本身。**

下次有人给你看一条只往下走的安全曲线，先问一句：**同期的有用工作曲线在哪？**两条曲线的比值（单位产出的风险密度）才是安全工程的真实成效——密度下降说明防护在进步，两条一起下降说明你只是在退场。

（这是本篇的全部论点。它的反面——「更聪明的 agent」如何证明自己真的更聪明——是姊妹篇《Recursive Self-Improvement Needs a Better Experiment》的主题。）

# 《The Safest Agent Is Unplugged》的发芽报告

## 材料核心

作者以一个思想实验拆穿单边安全指标：「零危险工具调用」的 agent 同时「零有用产出」——不发邮件（无钓鱼）、不写文件（无外泄）、不调工具（无注入），危险事件计数满分、客户价值零分。论点：把安全当独立优化目标，指标会奖励拔掉插头的 agent（约束越狠危险越少、有用工作也越少，仪表盘只见前者下降）。处方：有用工作与对抗性结果必须在同一度量里——两者共享同一个行动预算，每步工具调用既可能产出也可能闯祸；实际评估问题是一对：本周完成多少真实工作（任务完成率/用户接受率/下游引用）+造成多少需要人收拾的局面（被拒调用/回滚/误报升级）。安全的正确定义是「同样多的有用工作、更少的对抗性结果」。结尾指向姊妹篇《Recursive Self-Improvement Needs a Better Experiment》。

## 发芽 01：Goodhart 的 agent 版——为什么「危险计数」必然被玩坏

### 种子

「把安全当独立优化目标时会发生的事：指标会奖励拔掉插头。」危险事件计数满分的 agent 是一个被 Goodhart 定律完美击中的产品。

### 故事

这个结构与知名的指标退化同构：任何「越低越好」的单一风险计数，在优化压力下都会收敛到「什么都不做」的平凡解——因为它没有与收益项耦合。拔线 agent 的思想实验之所以锋利，在于它不依赖任何技术细节：约束的每一个来源（工具白名单收窄、审批门槛提高、行动预算压缩）都会同时压低两个量，而只报告一个量就等于只展示了约束的一半。真实世界里的对应物是「为了合规把 agent 限制到只能查文档」的部署——安全曲线漂亮，产品已经死了。

### Aha 瞬间

**任何只报告「坏事变少」而不报告「好事是否还在」的 agent 安全指标，都在结构上奖励不作为——安全不是可以单独最大化的维度，它是产出的约束条件，必须与产出在同一张报表上。**

## 发芽 02：「同一行动预算」——安全与产出是守恒的，不是对立的

### 种子

「两者共享同一个行动预算，每一步工具调用既可能产出也可能闯祸」——安全与产出不是天平的两端，而是同一条行动流的两面。

### 故事

这个框架比「权衡（trade-off）」更精确：权衡暗示你可以在保产出的同时少冒险，但每一步行动的风险与收益是同一枚硬币——不行动就同时归零。真正的优化对象是行动的**质量分布**：把高收益低风险的行动比例做大，把高风险低收益的部分（误操作、幻觉调用、越权访问）挤出去。这也给出了评估的具体形态：作者列的两列数字（完成/闯祸）在同一个行动预算下读数，比值的变化才是安全工作的真实成效——「同样的活、更少的祸」是唯一有意义的进步方向。

### Aha 瞬间

**agent 安全的正确度量不是风险的绝对值，而是「单位有用工作的风险密度」——拔掉插头能让分子分母同时归零，但只有密度下降才说明安全工程真的在进步。**

## 发芽 03：两列数字的治理学——谁在为「需要人收拾的局面」付费

### 种子

评估问题是一对：本周完成了多少真实工作（任务完成率/用户接受率/下游引用）；造成了多少需要人收拾的局面（被拒调用/回滚/误报升级）。

### 故事

第二列的分类学（被拒调用/回滚/误报升级）其实是把隐性成本显性化的清单：每一次 agent 闯祸的成本都由人类承担（审阅者的时间、回滚的操作、误报的升级疲劳），而这些成本在传统报表里分散在「支持工时」「运维工时」里，从不与 agent 的产出并排。把两列并排，等于把 agent 的净贡献做成了可审计的科目。姊妹篇的方向（递归自我改进需要对照实验）则把同一逻辑推到元层面：连「改进 agent 的过程」也要用同样的两列思维审计。

### Aha 瞬间

**agent 治理的核心账本是「净贡献 = 有用工作 − 人类收拾成本」——第二列从来不是零，问题只是它被记在别人的科目里；把两列并到一张仪表盘，agent 才从「神奇的生产力」变成一个可以被正常管理的员工。**
